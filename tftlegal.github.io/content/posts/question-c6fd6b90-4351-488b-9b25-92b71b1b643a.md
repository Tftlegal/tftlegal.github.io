# Ниже полный гайд по запуску LLM на GTX 1050 (2GB) в Kubernetes: От MTP до оптимизации ресурсов

Запуск современных нейросетей на видеокартах начального уровня (NVIDIA GTX 1050 с 2GB VRAM) — это экстремальная инженерная задача. 
Стандартные движки вроде **vLLM** или **TGI** здесь не запустятся, так как требуют минимум 4–8 ГБ памяти только для инициализации PagedAttention и KV-кэша.

В данном руководстве мы разберем, как запустить **llama.cpp** (через Ollama или напрямую) с поддержкой CUDA, квантованием и стратегией гибридного оффлоадинга.

## 1. Анализ ограничений и стратегия «выживания»

Прежде чем писать манифесты, необходимо принять архитектурные решения для работы в рамках 2 ГБ VRAM:

*   **Модель:** Используйте сверхлегкие модели — `Qwen2-0.5B` или `TinyLlama-1.1B`.
*   **Формат:** Только **GGUF**. Он позволяет гибко распределять слои между видеокартой и оперативной памятью.
*   **Квантование:** Используйте `Q4_K_M` или `Q3_K_L`. Это критически важно для удержания весов в пределах лимита.
*   **Контекст:** Жестко ограничьте контекстное окно (`-c 512`). KV-кэш — главный «пожиратель» памяти при генерации.
*   **MTP (Multi-Token Prediction):** Если ваша цель — именно архитектурное использование MTP, убедитесь, что используемые веса (например, семейства DeepSeek) поддерживают этот метод на уровне бинарного файла `llama.cpp`.

## 2. Подготовка инфраструктуры (Worker Node)

Чтобы Kubernetes мог «видеть» GPU, необходимо подготовить хостовую машину. Вариант установки для Ubuntu 24.

### Установка драйверов и Toolkit на Ubuntu 24 (Это не провеялось)
1. **Драйверы NVIDIA:** Установите версию 550+ (совместимая с CUDA 12.x).
2. **NVIDIA Container Toolkit:**
   ```bash
   curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
   sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
   sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

   sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
   sudo systemctl restart containerd # или docker    
   ```

### Установка Toolkit на Debian 12 (Рекомендуется)

Чтобы Kubernetes мог «видеть» GPU, необходимо подготовить хостовую машину. Вариант установки для Debian 12.

Ошибка возникает потому, что APT не может найти публичный ключ `DDCAE044F796ECB0` для репозитория NVIDIA. Нужно импортировать ключ в файл, указанный в `signed-by`, и затем обновить кэш.

## Решение

Выполните следующие команды на `worker001`:

```bash
# 1. Убедитесь, что директория существует
sudo mkdir -p /usr/share/keyrings

# 2. Скачайте публичный ключ NVIDIA в нужный файл
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

# 3. Добавьте репозитарий NVIDIA (Add the NVIDIA Container Toolkit Repository)
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

# 3. Обновите кэш APT
sudo apt-get update

# 4. Посомотреть какие версии пакета можно установить:
sudo apt-cache policy nvidia-container-toolkit
```

# 5. Важно чтобы версиия toolkit соответствовала версии драйвера который планируется ставить (С последней версией 615 на старом железе можно хапнуть проблем) по этому можно создать политику на даунгрейд ПО

Для ветки драйвера 550 (CUDA 12.4) оптимальной и стабильной версией является 1.14.6-1 (или любая старшая минорная версия линейки 1.14.x / 1.15.x)
```
cat <<EOF | sudo tee /etc/apt/preferences.d/toolkit-fix-version-for-nvidia-550
Package: nvidia-container-toolkit
Pin: version 1.14.6-1   
Pin-Priority: 1001

# Блокировать устаревшие версии 1.12 и ниже для всех пакетов
Package: *
Pin: version 1.12*
Pin-Priority: -1
EOF
```

Для новейшей ветки драйвера 590 (CUDA 13.1 / 13.2) требуется актуальный инструментарий. Официальная документация NVIDIA в связке с драйверами 590 рекомендует использовать версию не ниже 1.13.5, однако для полноценной поддержки всех функций современной экосистемы отлично подходит стабильная версия 1.17.3-1 или 1.18.2-1
```
cat <<EOF | sudo tee /etc/apt/preferences.d/toolkit-fix-version-for-nvidia-590
Package: nvidia-container-toolkit
Pin: version 1.18.2-1   
Pin-Priority: 1001

# Блокировать старые версии ветки 1.14 и ниже для всех пакетов
Package: *
Pin: version 1.14*
Pin-Priority: -1
EOF
```

C 535 драйвером устанавливается эта версия toolkit - вот пример файла с политикой для нее
```
cat <<EOF | sudo tee /etc/apt/preferences.d/toolkit-fix-version-for-nvidia-535
Package: nvidia-container-toolkit
Pin: version 1.20.0-1
Pin-Priority: 1001

# Блокировать версии 1.1x и для всех пакетов
Package: *
Pin: version 1.1*
Pin-Priority: -1
EOF
```

### Установка драйвера на Debian 12 

Но одним тулкитом сыт не будешь - у NVIDIA проприетарные драйвера чтобы они появились можно  запоганить себе /etc/apt/sources.list

Для Debian 12 полностью замените содержимое файла (проще всего перезаписать его целиком):
```bash
sudo tee /etc/apt/sources.list > /dev/null <<'EOF'
# Debian 12 (Bookworm) — основные репозитории
deb http://deb.debian.org/debian/ bookworm main contrib non-free non-free-firmware
deb-src http://deb.debian.org/debian/ bookworm main contrib non-free non-free-firmware

# Обновления безопасности
deb http://security.debian.org/debian-security bookworm-security main contrib non-free non-free-firmware
deb-src http://security.debian.org/debian-security bookworm-security main contrib non-free non-free-firmware

# Обновления до point release
deb http://deb.debian.org/debian/ bookworm-updates main contrib non-free non-free-firmware
deb-src http://deb.debian.org/debian/ bookworm-updates main contrib non-free non-free-firmware
EOF
```

Проверьте, что файл существует и не пуст:

```bash
ls -l /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
gpg --show-keys /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
```

Если ключ есть, но APT всё равно ругается, можно явно указать ключ при обновлении (временное решение):

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
sudo apt-get --allow-insecure-repositories update
sudo apt-get install -y nvidia-container-toolkit
```

Но предпочтительно первый вариант с корректным ключом в `signed-by`.

## 1. EFI‑ключи и UEFI 2023 (предупреждение)

Сообщение говорит, что у EFI‑диска ВМ нет опции `ms-cert=2023k`, и, возможно, не записаны новые UEFI‑ключи Microsoft 2023 года. Старые UEFI 2011 ключи истекают в июне 2026, после этого Secure Boot‑обновления для Windows и многих дистрибутивов могут перестать работать. 

### Как исправить

Если ВМ выключена:

```bash
qm enroll-efi-keys <VMID>
```

В вашем случае:

```bash
qm enroll-efi-keys 151
```

Это запишет обновлённые ключи Microsoft в EFI‑переменные ВМ. 

Если ВМ запущена — сначала выключите её:

```bash
qm stop 151
qm enroll-efi-keys 151
qm start 151
```

Для Windows с BitLocker: перед перезагрузкой после enrolment рекомендуется внутри гостевой ОС выполнить:

```powershell
manage-bde -protectors -disable C:
```

(и для других зашифрованных томов), чтобы не запросило recovery‑ключ при следующем старте. 

## 2. Ошибка сброса PCI‑устройства (`reset: Inappropriate ioctl for device`)

Сообщение:

```text
error writing '1' to '/sys/bus/pci/devices/0000:03:00.0/reset': Inappropriate ioctl for device
failed to reset PCI device '0000:03:00.0', but trying to continue as not all devices need a reset
```

означает, что Proxmox попытался сделать сброс GPU (PCI 0000:03:00.0) через стандартный механизм, но устройство не поддерживает этот тип сброса. Это часто бывает с GPU NVIDIA. 

Обычно это **не критично**, если:

- ВМ запускается и GPU виден внутри гостя (`nvidia-smi` работает).
- Нет проблем с повторным запуском/остановкой ВМ.

Если в дальнейшем будут проблемы (ВМ не стартует после остановки, GPU «залипает» на хосте), можно включить более надёжный сброс через `vfio-pci`.


### Базовая настройка VFIO для GPU (если ещё не сделана)

На хосте Proxmox:

1. Включить VFIO‑модули в загрузку:

```bash
echo "vfio" | sudo tee -a /etc/modules
echo "vfio_pci" | sudo tee -a /etc/modules
```

2. Указать устройство для VFIO (по ID вендора/устройства). Узнайте ID:

```bash
lspci -nn | grep -i nvidia
# например: 03:00.0 VGA compatible controller [0300]: NVIDIA Corporation ... [10de:1b80]
```

Допустим, ID `10de:1b80`. Тогда:

```bash
echo "options vfio-pci ids=10de:1b80" | sudo tee /etc/modprobe.d/vfio.conf
```

Если у GPU есть и audio‑функция (например, `0000:03:00.1`), добавьте и её ID.

3. Обновить initramfs и перезагрузить хост:

```bash
update-initramfs -u -k all
sudo reboot
```

После этого Proxmox будет привязывать устройство к `vfio-pci`, и сброс обычно работает надёжнее. 


3. Если ВМ стартует и GPU работает — предупреждение про `reset` можно пока игнорировать. Если позже будут проблемы с GPU после остановки/перезапуска ВМ — настройте VFIO, как описано выше.

Если хотите, пришлите вывод:

```bash

qm config 151
```

# Варианты решения

### Вариант A: Отключить Secure Boot в BIOS/UEFI (самый простой, но это не путь самурая)

Если это допустимо в вашей среде:

1. Перезагрузите сервер.
2. В BIOS/UEFI отключите **Secure Boot**.
3. Загрузитесь и проверьте:

   ```bash
   cat /sys/kernel/security/lockdown
   modprobe nvidia
   nvidia-smi
   ```
После отключения Secure Boot модуль должен загружаться без подписи. 


### Вариант B: Подписать модуль NVIDIA своим ключом и добавить его в MOK (Рекомендуется)

Если Secure Boot должен остаться включён:

1. Создать ключи MOK:

   ```bash
   sudo mkdir -p /root/MOK
   cd /root/MOK
   sudo openssl req -new -x509 -newkey rsa:2048 -keyout MOK.key -out MOK.crt -days 3650 -nodes -subj "/CN=My NVIDIA MOK/"
   ```

2. Конвертировать в DER:

   ```bash
   sudo openssl x509 -outform DER -in MOK.crt -out MOK.der
   ```

3. Зарегистрировать ключ:

   ```bash
   sudo mokutil --import MOK.der
   ```

## DEBUG (повезло если непригодится)

Типичные проблемы:

- В логах ошибки типа `error starting NVML: could not load NVML library` — значит, внутри пода нет доступа к драйверу/библиотекам.
- Падает с `Failed to discover GPU devices` — часто из‑за отсутствия `nvidia-container-toolkit` или неправильного runtime.

Главная проблема здесь — не `shpchp`, а **не загрузившийся NVIDIA-драйвер**. Из-за этого последовательно падают:

```text
systemctl status systemd-modules-load.service
systemctl status nvidia-cdi-refresh.service
systemctl status nvidia-persistenced.service
```

## Что означает каждая строка

### `shpchp ... error -16`

Код `-16` — это `-EBUSY`: ресурс уже занят или PCI hotplug уже зарегистрирован другим обработчиком.

```text
shpchp 0000:05:01.0: pci_hp_register failed with error -16
```

Обычно это второстепенное сообщение о конфликте между старыми механизмами `shpchp` и `pciehp`, особенно в виртуальной машине или при особенностях BIOS/PCIe. Похожие сообщения встречаются в QEMU-гостях и не обязательно означают неисправность GPU или диска. [gitlab](https://gitlab.com/qemu-project/qemu/-/issues/2212)

Проверить, что реально загружено:

```bash
lsmod | grep -E 'shpchp|pciehp'
```

Если hotplug PCIe вам не нужен, это сообщение обычно можно оставить без внимания. Не стоит сразу добавлять `acpi=off`: это может отключить важные ACPI-функции.

### `recovering journal`

```text
/dev/mapper/worker001-vg-root: recovering journal
/dev/mapper/worker001-vg-root: clean
```

Это означает, что файловая система восстанавливала журнал после некорректного выключения или сброса питания. Восстановление завершилось успешно:

```text
clean
```

Само по себе это не ошибка. Но если сообщение появляется после каждой перезагрузки, нужно искать причину внезапного выключения:

```bash
journalctl -b -1 -p warning..alert
last -x | head -20
```

### `snd_hda_intel ... no codecs found`

```text
snd_hda_intel 0000:00:1b.0: no codecs found!
```
Это обычно означает, что HDA-аудиоустройство присутствует на PCI-шине, но к нему не подключен аудиокодек. Для серверной машины без аудио — практически неважно.

Проверить устройство:

```bash
lspci -nnk -s 00:1b.0
```
Если звук не нужен, эту строку можно игнорировать.

## Критические ошибки NVIDIA

### `systemd-modules-load.service`

```text
[FAILED] Failed to start systemd-modules-load.service
```

Это общий сервис загрузки модулей ядра. Важно получить его реальную причину:

```bash
systemctl status systemd-modules-load.service --no-pager -l
journalctl -b -u systemd-modules-load.service --no-pager
```

Частые причины:

- модуль NVIDIA не собран под текущий kernel;
- DKMS-модуль собран для старого ядра;
- в `/etc/modules` или `/etc/modules-load.d/` указан несуществующий модуль;
- после обновления ядра не установлен пакет `linux-headers`;
- Secure Boot блокирует неподписанный модуль;
- stale-конфигурация от старой версии драйвера.

Проверьте:

```bash
uname -r
cat /etc/modules
grep -RIn . /etc/modules-load.d/
lsmod | grep nvidia
modinfo nvidia
```

Если `modinfo nvidia` сообщает:

```text
Module nvidia not found
```

или ошибку версии, драйвер не установлен для текущего ядра.

### `nvidia-persistenced`

```text
[FAILED] Failed to start nvidia-persistenced.service
```

Это, скорее всего, **следствие**, а не первопричина. Демон NVIDIA не может нормально стартовать, если ядро не загрузило модуль `nvidia`.

Проверьте:

```bash
systemctl status nvidia-persistenced.service --no-pager -l
journalctl -b -u nvidia-persistenced.service --no-pager
nvidia-smi
```

Ключевой тест:

```bash
nvidia-smi
```

Если получите:

```text
NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver
```

то сначала нужно чинить kernel module/driver, а не `nvidia-persistenced`.

### `nvidia-cdi-refresh`

```text
[FAILED] Failed to start nvidia-cdi-refresh.service
```

Этот сервис генерирует CDI-описание NVIDIA, обычно:

```text
/var/run/cdi/nvidia.yaml
```

Оно нужно container runtime для передачи GPU в Docker/Kubernetes. NVIDIA рекомендует смотреть журнал этого сервиса и после исправления драйвера перезапустить генерацию CDI. [docs.nvidia](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/cdi-support.html)

Проверьте:

```bash
systemctl status nvidia-cdi-refresh.service --no-pager -l
journalctl -b -u nvidia-cdi-refresh.service --no-pager
ls -l /var/run/cdi/nvidia.yaml /run/cdi/nvidia.yaml 2>/dev/null
```

После того как `nvidia-smi` заработает:

```bash
sudo systemctl restart nvidia-cdi-refresh.service
sudo systemctl status nvidia-cdi-refresh.service --no-pager -l
```

В некоторых версиях `nvidia-container-toolkit` сервис может запускаться до готовности драйвера; тогда повторный запуск после загрузки модулей решает проблему. [forums.developer.nvidia](https://forums.developer.nvidia.com/t/jetson-r39-2-package-ships-stale-nvidia-cdi-refresh-service/377209)

## 6. Что чаще всего ломает регистрацию GPU

На Debian/Proxmox с ручным DKMS/Secure Boot типичные причины:

- Device plugin запускается, но внутри контейнера нет доступа к `/dev/nvidia*` или NVML из‑за того, что `nvidia-container-toolkit` не настроен для containerd.
- RuntimeClass `nvidia` отсутствует или не связан с правильным handler.
- Device plugin запущен только на master‑ноде, а GPU на `worker001`.

Сначала проверьте логи device plugin и наличие RuntimeClass:

```bash
kubectl get runtimeclass
kubectl logs -n kube-system -l app=nvidia-device-plugin --tail=200
```

Хорошо, `nvidia-container-runtime` уже настроен в containerd (секция `nvidia` с `BinaryName: /usr/bin/nvidia-container-runtime`). Дальше нужно проверить RuntimeClass и логи device plugin.

## 1. Проверить RuntimeClass

```bash
kubectl get runtimeclass
```

Если `nvidia` нет — создайте:

```bash
kubectl apply -f - <<EOF
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: nvidia
handler: nvidia
EOF
```

## 2. Посмотреть логи device plugin

```bash
kubectl get pods -n kube-system -l app=nvidia-device-plugin -o wide
kubectl logs -n kube-system -l app=nvidia-device-plugin --tail=200
```

Типичные варианты:

- Если в логах видите что‑то вроде:

  ```text

  Starting NVML-based Device Plugin
  NVML Initialized
  Found X NVIDIA devices
  ```

- Если ошибка типа:

  ```text
  error starting NVML: could not load NVML library
  ```

  или

  ```text
  Failed to discover GPU devices
  ```

  — значит, внутри пода нет доступа к драйверу/библиотекам, чаще всего из‑за того, что под запускается без `runtimeClassName: nvidia`.

## 3. Проверить, что device plugin использует `runtimeClassName: nvidia`

```bash
kubectl get pod -n kube-system -l app=nvidia-device-plugin -o yaml | grep -A5 runtimeClassName
```

Если поля нет или оно пустое — пересоздайте релиз с явным указанием runtime:

```bash

```

(в новых версиях чарта это значение подхватывается автоматически, если есть RuntimeClass `nvidia`).

## 4. Проверить, что под device plugin работает на `worker001`

```bash
kubectl get pods -n kube-system -l app=nvidia-device-plugin -o wide
```

Убедитесь, что под запущен на `worker001` (где физически стоит GPU). Если он только на master — GPU не будет виден.

Можно форсировать запуск на всех подходящих нодах через daemonset (чарт по умолчанию так и делает), но убедитесь, что нет `nodeSelector` / `tolerations`, которые исключают `worker001`.

Посмотрите:

```bash

kubectl describe node worker001 | grep -i taint
```

Если на `worker001` есть тейнты (например, `node-role.kubernetes.io/control-plane` или кастомные), возможно, нужно добавить tolerations в чарт.

## 5. Быстрый тест вручную на `worker001`

На самом `worker001` попробуйте запустить контейнер с GPU через `crictl`/`containerd`:

```bash
cat > /tmp/gpu-test.yaml <<EOF
metadata:
  name: gpu-test
  namespace: default
image:
  image: docker.io/nvidia/cuda:12.2.0-base-ubuntu22.04
command: ["nvidia-smi"]
linux:
  security_context:
    privileged: false

  limits:
    nvidia.com/gpu: "1"
EOF

sudo crictl runp /tmp/gpu-test.yaml
```

Если получите ошибку, что ресурс `nvidia.com/gpu` неизвестен на уровне CRI, значит, kubelet ещё не видит GPU.

Чаще всего проблема именно в том, что device plugin не использует `runtimeClassName: nvidia` или не запущен на нужной ноде.

Пришлите вывод:

```bash
kubectl get runtimeclass
kubectl get pods -n kube-system -l app=nvidia-device-plugin -o wide
kubectl logs -n kube-system -l app=nvidia-device-plugin --tail=200
kubectl describe node worker001 | grep -A10 Capacity
```

Проблема ясна: scheduler пишет `2 Insufficient nvidia.com/gpu` — на двух нодах (видимо, `worker001` и `worker002`) ресурс `nvidia.com/gpu` не зарегистрирован, а на третьей ноде (master) есть тейнт `disk-pressure`, который под не толерирует.

Значит, device plugin не зарегистрировал GPU ни на одной ноде. Нужно смотреть, почему он не видит GPU.

## 1. Проверить статус и логи device plugin


Обратите внимание на строки вида:

- `NVML Initialized` / `Found X NVIDIA devices`
- или ошибки: `error starting NVML`, `Failed to discover GPU devices`, `could not load NVML library`.

## 2. Проверить, что под device plugin работает на `worker001`

В выводе `kubectl get pods -n kube-system -l app=nvidia-device-plugin -o wide` посмотрите колонку `NODE`. Под должен быть на `worker001` (где физически GPU). Если его там нет — значит, daemonset не запускается на этой ноде (возможно, из‑за тейнтов или nodeSelector).

Проверьте тейнты на `worker001`:

Если есть тейнты (например, `node-role.kubernetes.io/control-plane` или кастомные), их нужно либо убрать, либо добавить tolerations в чарт device plugin.


## 4. Пересоздать device plugin с явным runtimeClassName

Если чарт не подхватил runtime автоматически, пересоздайте с явным указанием (однако пере этим прерьте доступность image который используется чартом - см. ниже):

Но это не решит основную проблему — GPU должны быть зарегистрированы на `worker001` через device plugin.

## 2. Подготовка Kubernetes 


2.1  **NVIDIA Device Plugin:** Установите через Helm для автоматической регистрации ресурсов:
   ```bash
   helm repo add nvdp https://nvidia.github.io/k8s-device-plugin
   helm install nvdp nvdp/nvidia-device-plugin   --namespace kube-system   --create-namespace   --set runtimeClassName=nvidia   --set gfd.enabled=false   --set mps.enabled=false   --set affinity=null \
   --set image.repository=harbor.sytes.ru:443/harbor/cnrancher/mirrored-nvidia-k8s-device-plugin   --set image.tag=v0.13.0
   ```
*Проверка:* `kubectl get nodes -o custom-columns=NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu` (должно быть `1`).
```
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.allocatable.nvidia\.com/gpu}{"\n"}{end}'
```

Проблема ясна: daemonset `nvdp-nvidia-device-plugin` имеет `DESIRED = 0` — значит, чарт установился, но не нашёл подходящих нод для запуска. 
У MPS‑контроллера есть `NODE SELECTOR: nvidia.com/mps.capable=true`, а у основного device plugin — `<none>`, но всё равно 0 подов.

Скорее всего, чарт по умолчанию не создаёт поды, потому что:

- либо не включён `gfd` (GPU Feature Discovery) и нет лейбла `nvidia.com/gpu.present=true`,
- либо в values по умолчанию стоит какое‑то условие, которое не выполняется на ваших нодах.

Самый простой способ — явно включить создание daemonset и отключить лишние проверки(Не рекомендуется!)

## 1. Пересоздать релиз с явными values

```bash
helm uninstall nvdp -n kube-system

helm install nvdp nvdp/nvidia-device-plugin \
  --namespace kube-system \
  --create-namespace \
  --set runtimeClassName=nvidia \
  --set gfd.enabled=false \
  --set mps.enabled=false \
  --set nodeSelector=null \
  --set tolerations=null
```

Если ваш чарт требует другой синтаксис для сброса `nodeSelector`, можно так:

```bash
helm install nvdp nvdp/nvidia-device-plugin \
  --namespace kube-system \
  --create-namespace \
  --set runtimeClassName=nvidia \
  --set gfd.enabled=false \
  --set mps.enabled=false \
  --set nodeSelector."kubernetes\.io/os"=linux
```

(чтобы daemonset запускался на всех Linux‑нодах, как calico/kube-proxy).

## 2. Проверить, что поды появились

```bash
kubectl get daemonset -n kube-system nvdp-nvidia-device-plugin -o wide
kubectl get pods -n kube-system -l app.kubernetes.io/instance=nvdp,app.kubernetes.io/name=nvidia-device-plugin  -o wide
kubectl logs -n kube-system -l app.kubernetes.io/instance=nvdp,app.kubernetes.io/name=nvidia-device-plugin  --tail=300
```

Ожидаемый результат: `DESIRED = 3` (или 2, если не хотите на master), поды запущены на всех нодах (включая `worker001`).

## 3. Если поды всё равно не создаются

Посмотрите полный spec daemonset:

```bash
kubectl get daemonset -n kube-system nvdp-nvidia-device-plugin -o yaml
```

Обратите внимание на секции `spec.template.spec.nodeSelector` и `spec.template.spec.tolerations`. Если там есть условия, которые не выполняются на ваших нодах, их нужно убрать через values чарта.

Можно также явно указать, на каких нодах запускать:

```bash
helm uninstall nvdp -n kube-system

helm install nvdp nvdp/nvidia-device-plugin \
  --namespace kube-system \
  --create-namespace \
  --set runtimeClassName=nvidia \
  --set gfd.enabled=false \
  --set mps.enabled=false \
  --set nodeSelector."kubernetes\.io/os"=linux \
  --set affinity=null
```

## 4. После запуска device plugin

Когда поды будут в `Running` на `worker001`:

```bash
kubectl get nodes -o custom-columns=NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu
```

Должно появиться `1` (или больше) на `worker001`.

```bash
kubectl get daemonset -n kube-system nvdp-nvidia-device-plugin -o yaml | grep -A10 nodeSelector
kubectl get pods -n kube-system -l app=nvidia-device-plugin -o wide
```

Проблема найдена: в spec daemonset есть `nodeAffinity` с требованием:

```yaml
- key: feature.node.kubernetes.io/pci-10de.present
  operator: In
  values: ["true"]
- key: feature.node.kubernetes.io/cpu-model.vendor_id
  operator: In
  values: ["NVIDIA"]
- key: nvidia.com/gpu.present
  operator: In
  values: ["true"]
```

Это лейблы от **GPU Feature Discovery (GFD)**. У вас `gfd.enabled=false`, но чарт всё равно оставил affinity, и поскольку ни на одной ноде нет лейблов `nvidia.com/gpu.present=true` 
и `feature.node.kubernetes.io/*`, daemonset не создаёт поды (`DESIRED = 0`). 

## Решение: отключить affinity или включить GFD

### Вариант 1: Отключить node affinity (быстрее)

Нужно явно убрать affinity в values чарта. В текущей версии чарта это делается так:

```bash
helm uninstall nvdp -n kube-system

helm install nvdp nvdp/nvidia-device-plugin \
  --namespace kube-system \
  --create-namespace \
  --set runtimeClassName=nvidia \
  --set gfd.enabled=false \
  --set mps.enabled=false \
  --set affinity=null
```

Если `--set affinity=null` не сработает, создайте values‑файл:

```bash
cat > /tmp/nvdp-values.yaml <<EOF
gfd:
  enabled: false
mps:
  enabled: false
runtimeClassName: nvidia
affinity: {}
EOF

helm uninstall nvdp -n kube-system 2>/dev/null || true
helm install nvdp nvdp/nvidia-device-plugin \
  -f /tmp/nvdp-values.yaml \
  --namespace kube-system \
  --create-namespace
```

После этого:

```bash
kubectl get daemonset -n kube-system nvdp-nvidia-device-plugin -o wide
kubectl get pods -n kube-system  -o wide
```

Ожидайте `DESIRED = 3` (или 2, если не хотите на master) и поды на всех нодах.



### Вариант 2: Включить GFD, чтобы появились нужные лейблы

Если хотите «правильно» по документации NVIDIA:

```bash
helm uninstall nvdp -n kube-system 2>/dev/null || true

helm install nvdp nvdp/nvidia-device-plugin \
  --namespace kube-system \
  --create-namespace \
  --set runtimeClassName=nvidia \
  --set gfd.enabled=true \
  --set mps.enabled=false
```

GFD запустится, обнаружит GPU на `worker001` и проставит лейблы вида `nvidia.com/gpu.present=true`, `feature.node.kubernetes.io/pci-10de.present=true`. После этого daemonset device plugin увидит подходящие ноды и запустится. 

Минус: GFD тоже требует доступа к GPU и может не заработать, если device plugin ещё не настроен полностью. Поэтому для начала лучше Вариант 1 (отключить affinity).

Когда поды device plugin будут в `Running`:

```bash
kubectl logs -n kube-system -l app=nvidia-device-plugin --tail=100
```

На `worker001` должно появиться `1` (или больше) в колонке GPU.

## 5. Траблшутинг и критические рекомендации

1.  **Ошибка Out of Memory (OOM) при запуске:**
    *   *Проблема:* Модель или KV-кэш превышают 2 ГБ VRAM.
    *   *Решение:* Уменьшите флаг `-ngl` (количество слоев на GPU). Если поставить `-ngl 0`, модель будет работать полностью на CPU (медленнее, но стабильно). Уменьшите контекст до `-c 256`.
2.  **Проблема с правами доступа (Permission Denied):**
    *   *Проблема:* Контейнер не может писать в монтируемую папку моделей.
    *   *Решение:* Используйте `securityContext` в манифесте для установки `fsGroup` или проверьте права на PVC.
3.  **MTP и Ollama:**
    *   *Проблема:* Ollama — это высокоуровневая обертка. Она может не поддерживать специфические флаги MTP "из коробки".
    *   *Решение:* Для полного контроля над архитектурой MTP используйте прямой бинарный файл `llama-server` (как в примере Dockerfile) вместо Ollama.
4.  **Дробление GPU (Fractional GPU):**
    *   *Проблема:* Стандартный плагин выделяет GPU целиком (`1`).
    *   *Решение:* Если нужно запустить несколько инстансов на одной GTX 1050, используйте **NVIDIA Time-Slicing** в конфигурации Device Plugin.

## 1. Введение: почему vLLM не подходит, и что мы будем делать

На карте с 2 ГБ памяти невозможно запустить даже 7B-модель в половинной точности. **vLLM** требует минимум 4–8 ГБ для PagedAttention и KV-кэша. Поэтому наше решение — **llama.cpp** с поддержкой CUDA, который позволяет:

- загружать модель в формате **GGUF** с 4-битным квантованием (вес модели — ~600–800 МБ);
- контролировать, сколько слоёв отдать на GPU (`-ngl`), а остальные оставить на CPU;
- ограничивать размер контекстного окна (`-c`), чтобы экономить VRAM под KV-кэш;
- предоставлять API, совместимый с OpenAI (через встроенный `llama-server`).

## 5. Развёртывание в Kubernetes

### 5.1. Подготовка хранилища для модели

Модель необходимо поместить в постоянное хранилище. Рассмотрим два варианта:

- **PVC (PersistentVolumeClaim)** — предпочтительнее для production.

**Пример PVC:**
```yaml
apiVersion: v1

metadata:
  name: models-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```
Затем в Deployment смонтируйте этот PVC в `/app/models`.

**Альтернатива hostPath (если модель уже лежит на хосте):**
```yaml
volumes:
- name: model-storage
  hostPath:
    path: /mnt/models   # путь к папке с .gguf файлом на узле
    type: Directory
```

### 5.2. Deployment

Ключевые моменты манифеста:
- Обязательно укажите **лимит памяти** не менее 8 ГБ — этого достаточно для оффлоадинга (CPU RAM), чтобы K8s не убивал под по OOM.
- Настройте **Shared Memory (`/dev/shm`)** через `emptyDir` с `medium: Memory`, это критично для работы CUDA внутри контейнера.
- Добавьте **livenessProbe** и **readinessProbe** для контроля состояния.

**deployment.yaml:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-gtx1050
  labels:
    app: llm
spec:
  replicas: 1
  selector:
    matchLabels:
      app: llm
  template:
    metadata:
      labels:
        app: llm
    spec:
      containers:
      - name: llama-server
        image: your-registry/llama-cuda:latest
        resources:
          limits:
            nvidia.com/gpu: 1          # полная карта
            memory: "8Gi"              # общая RAM для CPU-оффлоадинга
            cpu: "4"
          requests:
            nvidia.com/gpu: 1
            memory: "4Gi"
            cpu: "2"
        env:
        - name: NVIDIA_VISIBLE_DEVICES
          value: "0"                   # запасной параметр для совместимости
        args:
        - "-m"
        - "/app/models/tinyllama-1.1b-q4_k_m.gguf"   # путь к модели
        - "--host"
        - "0.0.0.0"
        - "--port"
        - "8080"
        - "-ngl"
        - "20"                        # количество слоёв на GPU (подбирайте!)
        - "-c"
        - "512"                       # размер контекста
        - "--ctx-size"
        - "512"
        - "-fa"                       # Flash Attention (если собрано)
        # можно добавить -b 512 -ub 512 для batch-оптимизации
        ports:
        - containerPort: 8080
        livenessProbe:
          tcpSocket:
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          tcpSocket:
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
        volumeMounts:
        - name: model-storage
          mountPath: /app/models
        - name: shm
          mountPath: /dev/shm
      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: models-pvc
      - name: shm
        emptyDir:
          medium: Memory
          sizeLimit: "2Gi"            # выделяем 2 ГБ под /dev/shm
```

**Примечания по параметрам:**
- `-ngl 20` — число слоёв, загружаемых в GPU. Для TinyLlama (22 слоя) это почти все; при OOM уменьшайте до 15, 10.
- `-c 512` — жёсткое ограничение контекста. Снижайте до 256 при нехватке памяти.
- `-fa` — включает Flash Attention (если бинарник собран с поддержкой). Для GTX 1050 поддержка может отсутствовать — тогда уберите флаг.

## 7. Оптимизация и решение типичных проблем

### 7.1. Ошибка Out of Memory (OOM) во время инференса

**Признаки:** под перезапускается, в логах `CUDA_ERROR_OUT_OF_MEMORY` или `bad_alloc`.

**Действия:**
- Уменьшите `-ngl` (например, с 20 до 12, 8). Чем меньше слоёв на GPU, тем больше вычислений на CPU, но VRAM освобождается.
- Уменьшите размер контекста (`-c 256`). Это немедленно сокращает KV-кэш.
- Попробуйте более агрессивное квантование модели (Q3_K_L вместо Q4_K_M).

### 7.2. Контейнер падает сразу после запуска

- Проверьте права доступа: в контейнере выполните `ls -l /dev/nvidia*` — должны быть устройства.
- Убедитесь, что `nvidia-container-toolkit` корректно настроен и перезапущен рантайм.
- Проверьте, что в манифесте указан `nvidia.com/gpu: 1` и узел действительно имеет ресурс.

### 7.3. Медленная генерация

- Снизьте `-ngl` до минимума (например, 5) — это заставит модель работать в основном на CPU, что может быть медленнее, но стабильнее.
- Убедитесь, что в поде достаточно CPU (запросите 4 ядра) и RAM (> 8 ГБ).
- Используйте batch-обработку (параметры `-b 512 -ub 512`) для ускорения инференса.

### 7.4. Ограничение Shared Memory

Если вы не выделили `/dev/shm`, llama.cpp может упасть с ошибкой при работе с большими тензорами. Мы уже добавили том `shm` с `medium: Memory` и `sizeLimit: 2Gi` — этого достаточно.

## 9. Заключение и критические замечания

- **vLLM не запустить** на 2 ГБ VRAM — мы сделали правильный выбор в пользу llama.cpp.
- **Multi-Token Prediction (MTP)** — это архитектурная фича, требующая специальных весов и кода. В данном гайде мы используем стандартный авторегрессионный инференс. Если вам нужна именно MTP, ищите модели, обученные с этой техникой (например, DeepSeek-V3) и соответствующие форки llama.cpp.
- **Дробление GPU** (`nvidia.com/gpu: 0.25`) не поддерживается стандартным Device Plugin — только целые карты. Для долей используйте NVIDIA MPS или Time-Slicing (выходят за рамки статьи).
- **Лимит памяти** в K8s должен быть достаточно высоким (≥ 8 ГБ), иначе под будет убит по OOM, даже если фактически RAM используется меньше — это связано с работой CUDA и оффлоадингом.
- **Безопасность**: для production используйте PVC и избегайте hostPath; добавьте политики PodSecurity.

Следуя этому руководству, вы получите работающий инференс-сервер на самом скромном GPU и сможете интегрировать его в свои пайплайны.
