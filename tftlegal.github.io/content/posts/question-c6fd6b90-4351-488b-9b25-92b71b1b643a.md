# Полный гайд по запуску LLM на GTX 1050 (2GB) в Kubernetes: От MTP до оптимизации ресурсов

Запуск современных нейросетей на видеокартах начального уровня (NVIDIA GTX 1050 с 2GB VRAM) — это экстремальная инженерная задача. Стандартные движки вроде **vLLM** или **TGI** здесь не запустятся, так как требуют минимум 4–8 ГБ памяти только для инициализации PagedAttention и KV-кэша.

В данном руководстве мы разберем, как запустить **llama.cpp** (через Ollama или напрямую) с поддержкой CUDA, квантованием и стратегией гибридного оффлоадинга.

---

## 1. Анализ ограничений и стратегия «выживания»

Прежде чем писать манифесты, необходимо принять архитектурные решения для работы в рамках 2 ГБ VRAM:

*   **Модель:** Используйте сверхлегкие модели — `Qwen2-0.5B` или `TinyLlama-1.1B`.
*   **Формат:** Только **GGUF**. Он позволяет гибко распределять слои между видеокартой и оперативной памятью.
*   **Квантование:** Используйте `Q4_K_M` или `Q3_K_L`. Это критически важно для удержания весов в пределах лимита.
*   **Контекст:** Жестко ограничьте контекстное окно (`-c 512`). KV-кэш — главный «пожиратель» памяти при генерации.
*   **MTP (Multi-Token Prediction):** Если ваша цель — именно архитектурное использование MTP, убедитесь, что используемые веса (например, семейства DeepSeek) поддерживают этот метод на уровне бинарного файла `llama.cpp`.

## 2. Подготовка инфраструктуры (Worker Node)

Чтобы Kubernetes мог «видеть» GPU, необходимо подготовить хостовую машину.

### Установка драйверов и Toolkit
1. **Драйверы NVIDIA:** Установите версию 525+ (совместимая с CUDA 12.x).
2. **NVIDIA Container Toolkit:**
   ```bash
   curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
     sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
     sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
   sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
   sudo systemctl restart docker # или containerd
   ```
3. **NVIDIA Device Plugin:** Установите через Helm для автоматической регистрации ресурсов:
   ```bash
   helm repo add nvdp https://nvidia.github.io/k8s-device-plugin
   helm install nvdp nvdp/nvidia-device-plugin --namespace kube-system --create-namespace
   ```
   *Проверка:* `kubectl get nodes -o custom-columns=NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu` (должно быть `1`).

## 3. Создание Docker-образа (Multi-stage)

Используем многоэтапную сборку, чтобы уменьшить размер образа и оптимизировать бинарный файл под CUDA.

**Dockerfile:**
```dockerfile
# Stage 1: Build
FROM nvidia/cuda:12.1.1-devel-ubuntu22.04 AS builder
RUN apt-get update && apt-get install -y git build-essential cmake libcurl4-openssl-dev
RUN git clone https://github.com/ggerganov/llama.cpp && \
    cd llama.cpp && mkdir build && cd build && \
    cmake .. -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release && \
    cmake --build . --config Release --parallel $(nproc)

# Stage 2: Runtime
FROM nvidia/cuda:12.1.1-runtime-ubuntu22.04
RUN apt-get update && apt-get install -y libcurl4 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=builder /llama.cpp/build/bin/llama-server /app/llama-server
# Модели лучше монтировать через PVC, но для теста можно скопировать
COPY ./models /app/models
EXPOSE 8080
ENTRYPOINT ["/app/llama-server"]
```

## 4. Развертывание в Kubernetes

Ключевой момент здесь — **Shared Memory** и **Resource Limits**. Kubernetes может убить под по OOM, если не учесть, что лимит памяти — это сумма RAM + VRAM.

**Deployment.yaml:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-gtx1050
spec:
  replicas: 1
  selector:
    matchLabels:
      app: llm-service
  template:
    metadata:
      labels:
        app: llm-service
    spec:
      containers:
      - name: llm-container
        image: your-registry/llm-gpu-image:latest
        resources:
          limits:
            nvidia.com/gpu: 1
            memory: "8Gi"       # Увеличьте лимит RAM для стабильного оффлоадинга
            cpu: "4"
          requests:
            nvidia.com/gpu: 1
            memory: "4Gi"
            cpu: "2"
        env:
        - name: NVIDIA_VISIBLE_DEVICES
          value: "0"
        args:
        - "--host"
        - "0.0.0.0"
        - "--port"
        - "8080"
        - "-m"
        - "/app/models/qwen2-0.5b-q4_k_m.gguf"
        - "-ngl"
        - "15"         # Кол-во слоев на GPU. Уменьшайте, если есть OOM!
        - "-c"
        - "512"         # Ограничение контекста (критично для 2GB!)
        - "-fa"         # Flash Attention
        volumeMounts:
        - name: shm
          mountPath: /dev/shm
        - name: models
          mountPath: /app/models
      volumes:
      - name: shm
        emptyDir:
          medium: Memory
          sizeLimit: "2Gi"
      - name: models
        persistentVolumeClaim:
          claimName: ollama-pvc
```

## 5. Траблшутинг и критические рекомендации

1.  **Ошибка Out of Memory (OOM) при запуске:**
    *   *Проблема:* Модель или KV-кэш превышают 2 ГБ VRAM.
    *   *Решение:* Уменьшите флаг `-ngl` (количество слоев на GPU). Если поставить `-ngl 0`, модель будет работать полностью на CPU (медленнее, но стабильно). Уменьшите контекст до `-c 256`.
2.  **Проблема с правами доступа (Permission Denied):**
    *   *Проблема:* Контейнер не может писать в монтируемую папку моделей.
    *   *Решение:* Используйте `securityContext` в манифесте для установки `fsGroup` или проверьте права на PVC.
3.  **MTP и Ollama:**
    *   *Проблема:* Ollama — это высокоуровневая обертка. Она может не поддерживать специфические флаги MTP "из коробки".
    *   *Решение:* Для полного контроля над архитектурой MTP используйте прямой бинарный файл `llama-server` (как в примере Dockerfile) вместо Ollama.
4.  **Дробление GPU (Fractional GPU):**
    *   *Проблема:* Стандартный плагин выделяет GPU целиком (`1`).
    *   *Решение:* Если нужно запустить несколько инстансов на одной GTX 1050, используйте **NVIDIA Time-Slicing** в конфигурации Device Plugin.

# Полный гайд по запуску LLM на GTX 1050 (2 ГБ VRAM) в Kubernetes

**Аннотация:** В этой статье мы развернём легковесную языковую модель на видеокарте NVIDIA GTX 1050 с 2 ГБ видеопамяти внутри кластера Kubernetes. Из-за жёстких ограничений по VRAM стандартные движки (vLLM, TGI) непригодны — мы используем **llama.cpp** с квантованием GGUF и гибридным оффлоадингом (GPU + CPU). В результате вы получите рабочий OpenAI-совместимый API, способный обрабатывать запросы в реальных условиях.

## 1. Введение: почему vLLM не подходит, и что мы будем делать

На карте с 2 ГБ памяти невозможно запустить даже 7B-модель в половинной точности. **vLLM** требует минимум 4–8 ГБ для PagedAttention и KV-кэша. Поэтому наше решение — **llama.cpp** с поддержкой CUDA, который позволяет:

- загружать модель в формате **GGUF** с 4-битным квантованием (вес модели — ~600–800 МБ);
- контролировать, сколько слоёв отдать на GPU (`-ngl`), а остальные оставить на CPU;
- ограничивать размер контекстного окна (`-c`), чтобы экономить VRAM под KV-кэш;
- предоставлять API, совместимый с OpenAI (через встроенный `llama-server`).

---

## 2. Подготовка узла (Worker Node) для работы с GPU

Перед развёртыванием нужно настроить хост-машину: установить драйверы NVIDIA, контейнерный рантайм и Device Plugin для Kubernetes.

### 2.1. Драйверы NVIDIA

Для GTX 1050 (архитектура Pascal) рекомендуются драйверы версии **≥ 470** (мы используем 535+ для совместимости с CUDA 12).

```bash
# Ubuntu / Debian
sudo apt update
sudo apt install -y nvidia-driver-535
# Перезагрузка обязательна
sudo reboot
```

Проверка: `nvidia-smi` должна показывать карту с 2 ГБ памяти.

### 2.2. NVIDIA Container Toolkit

Этот инструмент позволяет контейнерам обращаться к GPU.

```bash
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
  sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg

curl -fsSL https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
  sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
  sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt update
sudo apt install -y nvidia-container-toolkit
```

#### Настройка рантайма (для containerd или Docker)

Если вы используете **containerd** (стандарт в Kubernetes), отредактируйте `/etc/containerd/config.toml`, чтобы рантайм по умолчанию использовал NVIDIA:

```toml
[plugins."io.containerd.grpc.v1.cri".containerd]
  default_runtime_name = "nvidia"
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia]
    runtime_type = "io.containerd.runc.v2"
    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia.options]
      BinaryName = "/usr/bin/nvidia-container-runtime"
```

После изменений перезапустите службу:
```bash
sudo systemctl restart containerd
```

Для Docker аналогичная настройка выполняется через `/etc/docker/daemon.json`.

### 2.3. NVIDIA Device Plugin для Kubernetes

Плагин регистрирует GPU как ресурс `nvidia.com/gpu` в кластере.

**Установка через Helm (рекомендуется):**
```bash
helm repo add nvdp https://nvidia.github.io/k8s-device-plugin
helm repo update
helm install nvdp nvdp/nvidia-device-plugin --namespace kube-system --create-namespace
```

**Альтернатива — прямой манифест:**
```bash

```

**Проверка:** выполните `kubectl describe node <имя-узла>` и найдите в разделе `Allocatable` строку `nvidia.com/gpu: 1`. Если ресурс отсутствует — проверьте логи плагина.

| **Qwen2-0.5B**        | ~350 МБ         | Лучший выбор для скорости и качества |
| **TinyLlama-1.1B**    | ~650 МБ         | Чуть умнее, но медленнее         |
| **Phi-2 (2.7B)**      | ~1.5 ГБ         | Не помещается целиком — только оффлоадинг |

**Формат:** только **GGUF**. Уровень квантования выбирайте:
- `Q4_K_M` — оптимальный баланс.
- `Q3_K_L` — если с Q4_K_M возникает OOM (Out Of Memory).

Скачайте модель с Hugging Face (например, от `bartowski` или `MaziyarPanahi`) и поместите в каталог, доступный для Kubernetes (позже мы смонтируем его через PVC или hostPath).

## 4. Сборка Docker-образа с llama.cpp

Мы используем **многоэтапную сборку**, чтобы уменьшить размер финального образа и гарантировать наличие всех CUDA-зависимостей.

### Dockerfile

```dockerfile
# Этап 1: сборка бинарника
FROM nvidia/cuda:12.1.1-devel-ubuntu22.04 AS builder

RUN apt-get update && apt-get install -y \
    git build-essential cmake libcurl4-openssl-dev && \
    rm -rf /var/lib/apt/lists/*

RUN git clone --depth 1 https://github.com/ggerganov/llama.cpp && \
    cd llama.cpp && mkdir build && cd build && \
    cmake .. -DGGML_CUDA=ON -DCMAKE_BUILD_TYPE=Release && \
    cmake --build . --config Release --parallel $(nproc)

# Этап 2: финальный образ
FROM nvidia/cuda:12.1.1-runtime-ubuntu22.04

RUN apt-get update && apt-get install -y libcurl4 && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY --from=builder /llama.cpp/build/bin/llama-server /app/llama-server

# Копируем модель (можно сделать через volume, чтобы не раздувать образ)
# COPY ./models /app/models

EXPOSE 8080

# Запускаем сервер с параметрами по умолчанию (они будут переопределены в K8s)
ENTRYPOINT ["/app/llama-server"]
```

**Сборка и загрузка в реестр:**
```bash
docker build -t your-registry/llama-cuda:latest .
docker push your-registry/llama-cuda:latest
```

## 5. Развёртывание в Kubernetes

### 5.1. Подготовка хранилища для модели

Модель необходимо поместить в постоянное хранилище. Рассмотрим два варианта:

- **PVC (PersistentVolumeClaim)** — предпочтительнее для production.
- **hostPath** — для быстрого тестирования (но может вызвать проблемы с правами доступа).

**Пример PVC:**
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: models-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 5Gi
```
Затем в Deployment смонтируйте этот PVC в `/app/models`.

**Альтернатива hostPath (если модель уже лежит на хосте):**
```yaml
volumes:
- name: model-storage
  hostPath:
    path: /mnt/models   # путь к папке с .gguf файлом на узле
    type: Directory
```

### 5.2. Deployment

Ключевые моменты манифеста:
- Обязательно укажите **лимит памяти** не менее 8 ГБ — этого достаточно для оффлоадинга (CPU RAM), чтобы K8s не убивал под по OOM.
- Настройте **Shared Memory (`/dev/shm`)** через `emptyDir` с `medium: Memory`, это критично для работы CUDA внутри контейнера.
- Добавьте **livenessProbe** и **readinessProbe** для контроля состояния.

**deployment.yaml:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-gtx1050
  labels:
    app: llm
spec:
  replicas: 1
  selector:
    matchLabels:
      app: llm
  template:
    metadata:
      labels:
        app: llm
    spec:
      containers:
      - name: llama-server
        image: your-registry/llama-cuda:latest
        resources:
          limits:
            nvidia.com/gpu: 1          # полная карта
            memory: "8Gi"              # общая RAM для CPU-оффлоадинга
            cpu: "4"
          requests:
            nvidia.com/gpu: 1
            memory: "4Gi"
            cpu: "2"
        env:
        - name: NVIDIA_VISIBLE_DEVICES
          value: "0"                   # запасной параметр для совместимости
        args:
        - "-m"
        - "/app/models/tinyllama-1.1b-q4_k_m.gguf"   # путь к модели
        - "--host"
        - "0.0.0.0"
        - "--port"
        - "8080"
        - "-ngl"
        - "20"                        # количество слоёв на GPU (подбирайте!)
        - "-c"
        - "512"                       # размер контекста
        - "--ctx-size"
        - "512"
        - "-fa"                       # Flash Attention (если собрано)
        # можно добавить -b 512 -ub 512 для batch-оптимизации
        ports:
        - containerPort: 8080
        livenessProbe:
          tcpSocket:
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          tcpSocket:
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
        volumeMounts:
        - name: model-storage
          mountPath: /app/models
        - name: shm
          mountPath: /dev/shm
      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: models-pvc
      - name: shm
        emptyDir:
          medium: Memory
          sizeLimit: "2Gi"            # выделяем 2 ГБ под /dev/shm
```

**Примечания по параметрам:**
- `-ngl 20` — число слоёв, загружаемых в GPU. Для TinyLlama (22 слоя) это почти все; при OOM уменьшайте до 15, 10.
- `-c 512` — жёсткое ограничение контекста. Снижайте до 256 при нехватке памяти.
- `-fa` — включает Flash Attention (если бинарник собран с поддержкой). Для GTX 1050 поддержка может отсутствовать — тогда уберите флаг.

### 5.3. Service

Открываем доступ к API через ClusterIP или LoadBalancer:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: llm-api
spec:
  selector:
    app: llm
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
  type: ClusterIP   # или LoadBalancer для внешнего доступа
```

## 7. Оптимизация и решение типичных проблем

### 7.1. Ошибка Out of Memory (OOM) во время инференса

**Признаки:** под перезапускается, в логах `CUDA_ERROR_OUT_OF_MEMORY` или `bad_alloc`.

**Действия:**
- Уменьшите `-ngl` (например, с 20 до 12, 8). Чем меньше слоёв на GPU, тем больше вычислений на CPU, но VRAM освобождается.
- Уменьшите размер контекста (`-c 256`). Это немедленно сокращает KV-кэш.
- Попробуйте более агрессивное квантование модели (Q3_K_L вместо Q4_K_M).

### 7.2. Контейнер падает сразу после запуска

- Проверьте права доступа: в контейнере выполните `ls -l /dev/nvidia*` — должны быть устройства.
- Убедитесь, что `nvidia-container-toolkit` корректно настроен и перезапущен рантайм.
- Проверьте, что в манифесте указан `nvidia.com/gpu: 1` и узел действительно имеет ресурс.

### 7.3. Медленная генерация

- Снизьте `-ngl` до минимума (например, 5) — это заставит модель работать в основном на CPU, что может быть медленнее, но стабильнее.
- Убедитесь, что в поде достаточно CPU (запросите 4 ядра) и RAM (> 8 ГБ).
- Используйте batch-обработку (параметры `-b 512 -ub 512`) для ускорения инференса.

### 7.4. Ограничение Shared Memory

Если вы не выделили `/dev/shm`, llama.cpp может упасть с ошибкой при работе с большими тензорами. Мы уже добавили том `shm` с `medium: Memory` и `sizeLimit: 2Gi` — этого достаточно.

## 9. Заключение и критические замечания

- **vLLM не запустить** на 2 ГБ VRAM — мы сделали правильный выбор в пользу llama.cpp.
- **Multi-Token Prediction (MTP)** — это архитектурная фича, требующая специальных весов и кода. В данном гайде мы используем стандартный авторегрессионный инференс. Если вам нужна именно MTP, ищите модели, обученные с этой техникой (например, DeepSeek-V3) и соответствующие форки llama.cpp.
- **Дробление GPU** (`nvidia.com/gpu: 0.25`) не поддерживается стандартным Device Plugin — только целые карты. Для долей используйте NVIDIA MPS или Time-Slicing (выходят за рамки статьи).
- **Лимит памяти** в K8s должен быть достаточно высоким (≥ 8 ГБ), иначе под будет убит по OOM, даже если фактически RAM используется меньше — это связано с работой CUDA и оффлоадингом.
- **Безопасность**: для production используйте PVC и избегайте hostPath; добавьте политики PodSecurity.

Следуя этому руководству, вы получите работающий инференс-сервер на самом скромном GPU и сможете интегрировать его в свои пайплайны.
