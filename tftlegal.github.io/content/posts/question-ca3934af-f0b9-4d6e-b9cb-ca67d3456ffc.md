# Организация сетевой связности в Kubernetes с CNI Calico: BGP, VXLAN и IP-in-IP

## Введение

Calico — один из самых популярных CNI-плагинов для Kubernetes, предлагающий гибкие механизмы организации сетевого взаимодействия. В зависимости от инфраструктуры и требований можно использовать разные подходы: маршрутизацию через BGP, оверлейные сети на базе VXLAN или IP-in-IP туннели. В статье рассмотрены практические сценарии: выход трафика в интернет, связь между кластерами в разных ЦОД, настройка пограничного маршрутизатора, а также передача трафика между подсетями внутри кластера.

---

## 1. Передача трафика в интернет из кластера Calico

Существует два принципиальных подхода к организации исходящего трафика из подов в интернет.

### 1.1. NAT на узлах кластера (natOutgoing)

Самый простой способ — включить исходящий NAT на пуле IP-адресов Calico. В этом случае трафик от подов с приватными IP-адресами будет проходить через SNAT: source IP пода заменяется на IP-адрес узла, на котором запущен под. Ответный трафик автоматически денATируется обратно.

Пример IPPool с включённым NAT:

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 192.168.0.0/16
  natOutgoing: true
```

Применить можно через `calicoctl apply -f ippool.yaml`. Если необходимо исключить определённые диапазоны из NAT (например, внутренние сети 10.0.0.0/8), создаётся дополнительный IPPool с флагом `disabled: true`.

### 1.2. NAT на внешней инфраструктуре (при BGP-пиринге)

Если Calico настроен на пиринг с физической сетевой инфраструктурой через BGP, рекомендуется отключить `natOutgoing` и передать функцию NAT пограничному маршрутизатору. В этом случае подам можно назначить публичные IP-адреса, и они будут маршрутизироваться напрямую:

1. Настроить BGP-пиринг Calico с физической инфраструктурой.
2. Создать IPPool с публичными IP-адресами и `natOutgoing: false`.
3. Убедиться, что сетевое оборудование не выполняет дополнительный NAT для трафика подов.

## 2. BGP для связи между кластерами в разных ЦОД

BGP является предпочтительным механизмом для организации связности между кластерами Kubernetes, расположенными в разных центрах обработки данных. Calico использует BGP для анонсирования маршрутов к pod CIDR и service CIDR, что позволяет отказаться от оверлейных туннелей и обеспечить нативную L3-маршрутизацию.

### 2.1. Архитектура

Каждый узел кластера запускает BGP-спикер (BIRD), который анонсирует маршруты к подсетям подов, размещённым на этом узле. Для межкластерной связи необходимо обеспечить обмен маршрутами между BGP-спикерами разных кластеров — либо напрямую, либо через маршрутизаторы ЦОД.

Ключевое требование: оба кластера должны использовать **non-overlay BGP networking** и **eBGP** для пиринга как с Top-of-Rack маршрутизатором, так и между кластерами.

### 2.2. Настройка BGPConfiguration

Глобальная конфигурация BGP задаётся через ресурс `BGPConfiguration`. Для небольших кластеров (до ~100 узлов) можно оставить full-mesh топологию, для крупных — использовать route reflectors:

```yaml
apiVersion: projectcalico.org/v3
kind: BGPConfiguration
metadata:
  name: default
spec:
  logSeverityScreen: Info
  nodeToNodeMeshEnabled: true
  asNumber: 64512
```

### 2.3. Настройка BGPPeer для внешнего маршрутизатора

Для пиринга с маршрутизатором, обеспечивающим связь между ЦОД, создаётся ресурс `BGPPeer`:

```yaml
apiVersion: projectcalico.org/v3
kind: BGPPeer
metadata:
  name: dc-interconnect-router
spec:
  peerIP: 192.168.1.1
  asNumber: 64513
```

Если необходимо ограничить пиринг конкретным узлом:

```yaml
apiVersion: projectcalico.org/v3
kind: BGPPeer
metadata:
  name: node1-external-router
spec:
  node: k8s-node-01
  peerIP: 192.168.1.1
  asNumber: 64513
```

После применения конфигурации статус BGP-сессии проверяется командой `calicoctl node status` — состояние должно быть `Established`.

### 2.4. Использование Route Reflectors для масштабирования

В крупных кластерах full-mesh BGP становится неэффективным. В этом случае выделяются узлы-route reflectors:

```yaml
apiVersion: projectcalico.org/v3
kind: BGPPeer
metadata:
  name: peer-with-route-reflectors
spec:
  nodeSelector: all()
  peerSelector: route-reflector == 'true'
```

Узлам-рефлекторам присваивается метка `route-reflector=true`, и они должны быть помечены как unschedulable. Для высокой доступности рекомендуется развернуть минимум два route reflector'а.

## 3. Настройка пограничного маршрутизатора

Пограничный маршрутизатор (border router) выполняет ключевую роль: он принимает BGP-анонсы от узлов Calico и обеспечивает маршрутизацию трафика между кластерами и внешними сетями.

### 3.1. Пример настройки на Cisco

```cisco
router bgp 65001
 bgp router-id 10.2.0.3
 address-family ipv4 unicast
  maximum-paths 4
  maximum-paths ibgp 16
  neighbor 10.13.0.0/24 remote-as 64512
  neighbor 10.13.0.0/24 activate
  neighbor 10.13.0.0/24 soft-reconfiguration inbound
```

Маршрутизатор должен быть настроен на приём маршрутов к pod CIDR и service CIDR от каждого узла Calico. В больших инсталляциях может потребоваться настройка `disable-peer-as-check` и `as-override`.

### 3.2. Пример настройки на Juniper

```juniper
protocols {
    bgp {
        group calico-nodes {
            type external;
            peer-as 64512;
            neighbor 192.168.1.10;
            neighbor 192.168.1.11;
            export advertise-calico-routes;
        }
    }
}
```

### 3.3. Ключевые моменты

- **AS-номера**: каждый кластер (или группа кластеров) должен иметь уникальный AS-номер для eBGP-пиринга.
- **Фильтрация маршрутов**: необходимо настроить политики, запрещающие анонс приватных маршрутов во внешние сети.
- **MTU**: при использовании оверлеев необходимо согласовать MTU на всех участниках маршрутизации.
- **Next-hop**: для eBGP-сессий обычно требуется настройка `next-hop-self` на маршрутизаторе, чтобы трафик между кластерами шёл через него.

## 4. VXLAN для передачи трафика между подсетями внутри кластера

VXLAN — это протокол инкапсуляции, который упаковывает кадры Ethernet в UDP-пакеты (порт 4789). В Calico VXLAN используется для создания оверлейной сети, когда узлы кластера находятся в разных подсетях и BGP-пиринг с физической сетью невозможен или нецелесообразен.

### 4.1. Настройка IPPool с VXLAN

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 10.244.0.0/16
  vxlanMode: Always
  ipipMode: Never
  natOutgoing: true
```

Применить: `calicoctl apply -f ippool-vxlan.yaml`.

Режим `vxlanMode: Always` означает, что весь трафик между подами на разных узлах инкапсулируется в VXLAN. Для оптимизации можно использовать `vxlanMode: CrossSubnet` — в этом случае инкапсуляция применяется только для трафика, пересекающего границы подсетей.

### 4.2. Проверка состояния

```bash
# Проверить создание VXLAN-интерфейса
ip link show vxlan.calico

# Просмотреть таблицу VTEP
bridge fdb show dev vxlan.calico

# Проверить статистику
ip -s link show vxlan.calico
```

### 4.3. Тестирование связности

```bash
# Разместить поды на узлах из разных подсетей
kubectl run pod1 --image=busybox --overrides='{"spec":{"nodeName":"node-subnet-a"}}' -- sleep 3600
kubectl run pod2 --image=busybox --overrides='{"spec":{"nodeName":"node-subnet-b"}}' -- sleep 3600

# Проверить связность
POD2_IP=$(kubectl get pod pod2 -o jsonpath='{.status.podIP}')
kubectl exec pod1 -- ping -c 3 ${POD2_IP}

# Убедиться в наличии VXLAN-инкапсуляции
tcpdump -i eth0 -n 'udp port 4789' -c 10
```

### 4.4. Ограничения VXLAN

- **MTU**: необходимо уменьшить MTU на 50 байт относительно MTU физического интерфейса (VXLAN-заголовок: 50 байт).
- **Производительность**: инкапсуляция/декапсуляция потребляет CPU.
- **NAT-траверсал**: VXLAN лучше проходит через NAT-устройства, так как использует UDP.

## 5. IP-in-IP туннели для связи между узлами внутри кластера

IP-in-IP (IPIP) — более лёгкий протокол инкапсуляции по сравнению с VXLAN. Он добавляет всего 20 байт служебной информации (дополнительный IP-заголовок) и использует протокол номер 4. Calico создаёт виртуальный интерфейс `tunl0` на каждом узле.

### 5.1. Настройка IPPool с IP-in-IP

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 10.244.0.0/16
  ipipMode: CrossSubnet
  natOutgoing: true
```

Применить: `calicoctl apply -f ippool-ipip.yaml`.

Режим `CrossSubnet` означает, что инкапсуляция применяется только при пересечении границ подсетей. Для трафика между узлами в одной подсети используется нативная маршрутизация, что снижает накладные расходы.

### 5.2. Проверка туннеля

```bash
# Проверить создание туннельного интерфейса
ip link show tunl0
ip addr show tunl0

# Проверить статистику туннеля
ip -s link show tunl0
```

### 5.3. Тестирование связности между узлами

```bash
# Разместить поды на разных узлах
kubectl run pod-a --image=busybox --overrides='{"spec":{"nodeName":"node-a"}}' -- sleep 3600
kubectl run pod-b --image=busybox --overrides='{"spec":{"nodeName":"node-b"}}' -- sleep 3600

POD_B_IP=$(kubectl get pod pod-b -o jsonpath='{.status.podIP}')
kubectl exec pod-a -- ping -c 3 ${POD_B_IP}

# Убедиться в наличии IP-in-IP пакетов
tcpdump -i eth0 -n 'proto 4' -c 10
```

### 5.4. Сравнение IP-in-IP и VXLAN

| Характеристика | IP-in-IP | VXLAN |
|---|---|---|
| Накладные расходы | ~20 байт | ~50 байт |
| Протокол | IP protocol 4 | UDP port 4789 |
| Прохождение NAT | Может блокироваться | Лучше проходит |
| Поддержка IPv6 | Нет (только IPv4) | Да |
| Производительность | Выше | Ниже |

IP-in-IP предпочтителен, когда важна производительность и сетевое оборудование поддерживает протокол 4. VXLAN — когда требуется прохождение через NAT или поддержка IPv6.

## Заключение

Calico предоставляет три взаимодополняющих механизма для организации сетевой связности:

1. **BGP** — обеспечивает нативную L3-маршрутизацию без оверлеев, идеален для связи между кластерами в разных ЦОД и выхода в интернет через внешний NAT.
2. **VXLAN** — оверлейная сеть на базе UDP, подходит для облачных сред и сред без поддержки BGP.
3. **IP-in-IP** — лёгкий оверлей с минимальными накладными расходами для связи между узлами внутри кластера.

Выбор конкретного механизма зависит от инфраструктуры: в контролируемых ЦОД с поддержкой BGP предпочтительнее нативная маршрутизация; в облачных средах или при отсутствии контроля над сетью — оверлейные решения. На практике часто используется комбинированный подход: BGP для внешней связности и IP-in-IP или VXLAN для внутренней маршрутизации между узлами.
