# Динамический инвентарь в Ansible через API GitLab

Ansible традиционно использует статические файлы инвентаря (например, `hosts.ini`) для описания управляемых хостов. Однако в современных динамических средах, где инфраструктура постоянно меняется, ручное обновление таких файлов становится неэффективным.

Решение — **динамический инвентарь**. Ansible может получать список хостов из внешних источников: облачных провайдеров, систем CMDB или, как в нашем случае, из GitLab.

Эта статья — практическое руководство по настройке динамического инвентаря для GitLab с использованием официального плагина `community.general.gitlab_runners`.

---

## 1. Что такое динамический инвентарь и зачем он нужен

**Динамический инвентарь** — это механизм, который позволяет Ansible получать актуальный список хостов и их параметры непосредственно во время выполнения плейбука, обращаясь к внешнему API.

**Преимущества**:
- **Актуальность** — хосты всегда соответствуют текущему состоянию инфраструктуры.
- **Масштабируемость** — не нужно вручную добавлять новые раннеры.
- **Группировка** — хосты можно автоматически распределять по группам на основе их атрибутов (например, `active`, `shared`, `specific`).

В контексте GitLab динамический инвентарь особенно полезен для управления **GitLab Runners** — агентов, выполняющих CI/CD-задачи. Вы можете:
- автоматически получать список всех зарегистрированных раннеров;
- фильтровать их по статусу (`active`, `paused`, `online`);
- группировать по типу (`shared` или `specific`);
- использовать эти данные в плейбуках для массовой настройки или мониторинга.

## 2. Установка и требования

Плагин `community.general.gitlab_runners` входит в коллекцию `community.general`. Он **не входит** в базовый пакет `ansible-core`, поэтому его нужно установить отдельно.

### 2.1 Установка коллекции

```bash
ansible-galaxy collection install community.general
```

После установки проверьте, что плагин доступен:

```bash
ansible-doc -t inventory -l | grep gitlab
```

Вы должны увидеть строку с `community.general.gitlab_runners`.

### 2.2 Требования к окружению

На **контрольной ноде** (где вы запускаете Ansible) должна быть установлена Python-библиотека `python-gitlab` версии **> 1.8.0**.

Установка:

```bash
pip install "python-gitlab>=1.8.0"
```

## 3. Базовый файл инвентаря

Плагин использует YAML-конфигурационный файл с расширением `.yml` или `.yaml`. По умолчанию он ожидает имя `gitlab_runners.yml`, но вы можете назвать его как угодно.

Создайте файл, например `inventory/gitlab.yml`, со следующим содержимым:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'GITLAB_TOKEN') }}"
```

**Пояснение:**
- `plugin` — обязательно указывает, какой плагин использовать.
- `server_url` — URL вашего GitLab-инстанса (с протоколом).
- `api_token` — Personal Access Token (PAT) для аутентификации в API. В примере мы используем lookup для чтения из переменной окружения `GITLAB_TOKEN`. Это безопаснее, чем хранить токен в файле.

### 3.1 Альтернативные способы передачи токена

Помимо явного указания в файле, токен можно передать через:

- **Переменную окружения** `GITLAB_API_TOKEN`
- **Алиас** `private_token` или `access_token`

Если вы используете переменную окружения, файл инвентаря можно упростить:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
# api_token не указываем — будет взят из GITLAB_API_TOKEN
```

## 4. Проверка работы инвентаря

Перед использованием в плейбуках полезно проверить, что плагин корректно получает данные.

### 4.1 Просмотр списка хостов

```bash
ansible-inventory -i inventory/gitlab.yml --list
```

Вывод будет содержать JSON со всеми раннерами, их атрибутами и автоматически сгенерированными группами.

### 4.2 Просмотр хостов в удобном формате

```bash
ansible-inventory -i inventory/gitlab.yml --graph
```

Пример вывода:

```
@all:
  |--@ungrouped:
  |--@gitlab_runners:
  |  |--runner-abc123
  |  |--runner-def456
  |--@gitlab_runners_active:
  |  |--runner-abc123
  |--@gitlab_runners_shared:
  |  |--runner-def456
```

## 5. Расширенная настройка: фильтрация и группировка

Плагин предоставляет гибкие возможности для фильтрации и группировки раннеров.

### 5.1 Фильтрация раннеров

Параметр `filter` позволяет отобрать только нужные раннеры по их статусу или типу:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'GITLAB_TOKEN') }}"
filter: active   # только активные раннеры
```

Доступные значения:
- `active` — только активные
- `paused` — только приостановленные
- `online` — только онлайн
- `specific` — только привязанные к конкретным проектам
- `shared` — только общие для всего инстанса

### 5.2 Группировка по атрибутам

Параметр `keyed_groups` позволяет автоматически создавать группы на основе значений атрибутов раннеров:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'GITLAB_TOKEN') }}"
keyed_groups:
  - key: active
    prefix: runner_status
  - key: runner_type
    prefix: runner_type
```

В этом примере:
- Раннеры будут добавлены в группы `runner_status_active` или `runner_status_paused` в зависимости от значения поля `active`.
- Также появятся группы `runner_type_shared` или `runner_type_specific`.

### 5.3 Создание пользовательских групп

Параметр `groups` позволяет добавлять хосты в группы на основе Jinja2-условий:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'GITLAB_TOKEN') }}"
groups:
  production: "runner_type == 'specific' and active == true"
  staging: "runner_type == 'shared' and active == true"
  offline: "active == false"
```

## 6. Использование в плейбуках

После настройки инвентаря вы можете использовать его как обычный файл инвентаря.

**Пример плейбука** `playbook.yml`:

```yaml
---
- name: "Check status of GitLab Runners"
  hosts: all
  gather_facts: false

  tasks:
    - name: "Display runner info"
      debug:
        msg: "Runner {{ inventory_hostname }} is {{ 'active' if active else 'inactive' }}"
```

**Запуск:**

```bash
ansible-playbook -i inventory/gitlab.yml playbook.yml
```

### 6.1 Работа с группами

Вы можете адресовать задачи конкретным группам:

```bash
# Только активные раннеры
ansible-playbook -i inventory/gitlab.yml playbook.yml --limit gitlab_runners_active

# Только общие раннеры
ansible-playbook -i inventory/gitlab.yml playbook.yml --limit gitlab_runners_shared
```

## 7. Безопасность: работа с токенами

Personal Access Token (PAT) — это чувствительные данные. Вот несколько способов безопасно работать с ними в Ansible.

### 7.1 Переменные окружения

Самый простой и распространённый способ:

```bash
export GITLAB_TOKEN="your_personal_access_token_here"
ansible-playbook -i inventory/gitlab.yml playbook.yml
```

### 7.2 Ansible Vault

Зашифруйте токен с помощью Ansible Vault и храните его в защищённом файле:

```bash
# Создаём зашифрованный файл с переменной
ansible-vault create group_vars/all/vault.yml
```

Содержимое `vault.yml`:

```yaml
gitlab_token: "your_personal_access_token_here"
```

В файле инвентаря:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ gitlab_token }}"
```

Запуск:

```bash
ansible-playbook -i inventory/gitlab.yml playbook.yml --ask-vault-pass
```

### 7.3 Использование в CI/CD (GitLab CI)

Если вы запускаете Ansible внутри самого GitLab CI, токен можно получить из предопределённой переменной `CI_JOB_TOKEN`:

```yaml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'CI_JOB_TOKEN') }}"
```

## 8. Полный пример конфигурации

Ниже приведён полноценный файл инвентаря с фильтрацией, группировкой и использованием переменной окружения:

```yaml
# inventory/gitlab.yml
---
plugin: community.general.gitlab_runners
server_url: https://gitlab.com
api_token: "{{ lookup('env', 'GITLAB_TOKEN') }}"

# Фильтруем только активные раннеры
filter: active

# Создаём группы по статусу и типу
keyed_groups:
  - key: active
    prefix: runner_status
  - key: runner_type
    prefix: runner_type

# Пользовательские группы по условиям
groups:
  production: "runner_type == 'specific'"
  shared_pool: "runner_type == 'shared'"
  needs_update: "runner_type == 'specific' and active == true"
```

## 9. Возможные проблемы и их решение

### 9.1 Плагин не найден

**Ошибка:** `Unable to find plugin community.general.gitlab_runners`

**Решение:** Убедитесь, что коллекция установлена:

```bash
ansible-galaxy collection list | grep community.general
```

Если коллекция отсутствует, установите её:

```bash
ansible-galaxy collection install community.general
```

### 9.2 Ошибка аутентификации

**Ошибка:** `401 Unauthorized` или `403 Forbidden`

**Решение:**
- Проверьте, что токен действителен и имеет права на чтение раннеров.
- Убедитесь, что токен передан корректно (через переменную окружения или явно в файле).
- Для самоподписанных сертификатов может потребоваться отключить проверку SSL (не рекомендуется для production):

```yaml
validate_certs: false
```

### 9.3 Отсутствует python-gitlab

**Ошибка:** `ModuleNotFoundError: No module named 'gitlab'`

**Решение:**

```bash
pip install "python-gitlab>=1.8.0"
```

### 9.4 Пустой список хостов

Если `--list` показывает пустой результат:

- Проверьте, что в вашем GitLab-инстансе есть зарегистрированные раннеры.
- Убедитесь, что токен имеет доступ к API раннеров (обычно требуется роль `admin` или `owner`).
- Проверьте параметр `filter` — возможно, он слишком строгий.

## 10. Альтернативные подходы

Помимо плагина `community.general.gitlab_runners`, существуют и другие способы интеграции Ansible с GitLab:

- **Кастомный скрипт инвентаря** — можно написать свой скрипт на Python или Bash, который обращается к GitLab API и выводит JSON в нужном формате. Такой скрипт должен поддерживать флаги `--list` и `--host <hostname>`.
- **Модуль `community.general.gitlab_runner`** — позволяет не только читать, но и создавать, изменять и удалять раннеры.
- **Ручное обновление статического инвентаря** — подходит только для очень маленьких и стабильных окружений.

Однако плагин `community.general.gitlab_runners` — это наиболее простой, поддерживаемый и документированный способ.
