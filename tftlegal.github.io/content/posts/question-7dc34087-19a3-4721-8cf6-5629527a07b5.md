## Часть 1. CAP Теорема: Фундаментальное ограничение распределенных систем

### 1.1. Введение

При работе с реальными распределенными системами мы сталкиваемся с различными ошибками: потеря данных, проблемы с соединением, отказ сервера и т.д. Следовательно, мы стараемся сделать нашу систему максимально устойчивой и надежной. Но здесь возникает вопрос: *возможно ли создать "идеальную" распределенную систему?*

**CAP теорема дает нам ответ: НЕТ.**

### 1.2. Три основных свойства

Согласно CAP теореме, распределенные системы имеют 3 основных состояния:

**C (Consistency) – Консистентность (Согласованность)**

Все узлы системы работают с одинаковым набором данных. Это означает, что пользователь системы может читать или записывать на любой узел и получит одни и те же данные. Если запись попала на один узел, все остальные узлы должны "увидеть" это изменение.

**A (Availability) – Доступность**

Любой запрос на рабочий узел будет обработан. Это означает, что даже в случае отказа одного или более узлов система должна продолжать обрабатывать запросы.

**P (Partition tolerance) – Устойчивость к разделению (сетевым сбоям)**

В данном случае мы говорим о ситуации, когда рабочие узлы системы не могут общаться между собой из-за проблем с соединением. Устойчивая к разделению система должна продолжать работу даже в этом случае.

### 1.3. Суть теоремы

Теорема гласит:

> **В любой реализации распределённых вычислений возможно обеспечить не более двух из трёх следующих свойств**

Проще говоря, мы можем создать систему, которая будет **AP**, **CP** или **CA**:

| Комбинация | Описание | Примеры |
|------------|----------|---------|
| **AP** (Доступность + Устойчивость) | Жертвуем консистентностью ради доступности | Cassandra, DynamoDB, Redis |
| **CP** (Консистентность + Устойчивость) | Жертвуем доступностью ради консистентности | MongoDB (по умолчанию), HBase, ZooKeeper |
| **CA** (Консистентность + Доступность) | Жертвуем устойчивостью к разделению | Традиционные реляционные БД (PostgreSQL, MySQL в одной ноде) |

**Важно понимать:** Выбор CA означает, что система не может работать при сетевом разделении — она либо откажет, либо потеряет одно из свойств. Именно поэтому в распределенных системах CA-системы практически не встречаются.

### 1.4. Наглядный пример

Представьте два узла (А и Б), между которыми пропала связь. Клиент отправляет запрос на запись на узел А:

- Если мы **обновляем данные на узле А, но не можем синхронизировать с узлом Б** → данные становятся неконсистентными (жертвуем **C**)
- Если мы **блокируем узел А до восстановления связи** → система становится недоступной (жертвуем **A**)

## Часть 2. PACELC Теорема: Расширение CAP для реального мира

### 2.1. Почему CAP недостаточно?

CAP теорема помогает нам понять, какие свойства могут быть в системе, когда она разделена по сети (партиционирование). Но что, если система **не разделена**? Именно на этот вопрос отвечает теорема PACELC.

### 2.2. Суть PACELC

**PACELC** является расширением теоремы CAP. Она утверждает:

> **If partitioned (P), then Availability and Consistency (AC); else (E), Latency and Consistency (LC)**

Расшифровка:

- **P** (Partition) — при сетевом разделении
- **A** (Availability) или **C** (Consistency) — выбор между доступностью и консистентностью
- **E** (Else) — в штатном режиме (без разделений)
- **L** (Latency) или **C** (Consistency) — выбор между задержкой и консистентностью

### 2.3. Классификация систем по PACELC

| Система | P + A | P + C | E + L | E + C |
|---------|-------|-------|-------|-------|
| **Cassandra** | ✅ | | ✅ | |
| **DynamoDB** | | ✅ | ✅ | ✅ |
| **MongoDB** | ✅ | | | ✅ |
| **PostgreSQL** | | ✅ | | ✅ |
| **Bigtable** | | ✅ | | ✅ |
| **Cosmos DB** | | ✅ | ✅ | |

*Источник: таблица из конспекта*

### 2.4. Практическое значение PACELC

PACELC помогает объяснить, почему разные системы выбирают разные компромиссы. Например:

- **Cassandra** выбирает **AP + EL**: при разделении жертвует консистентностью ради доступности, а в штатном режиме жертвует консистентностью ради низкой задержки. Именно поэтому Cassandra часто используется в системах, где важна скорость, а не строгая согласованность.

- **PostgreSQL** в кластерной конфигурации выбирает **CP + EC**: при разделении жертвует доступностью ради консистентности, а в штатном режиме предпочитает консистентность, даже если это увеличивает задержку.

## Часть 3. Балансировка нагрузки (Load Balancing)

### 3.1. Что такое балансировка нагрузки?

**Балансировщик нагрузки (Load Balancer, БН)** — это критически важный компонент при построении распределённых систем. Его задача — распределение нагрузки между серверами одного кластера, что помогает:

- Уменьшить время ответа на запрос
- Повысить надежность и доступность системы в целом

Если определённый сервер недоступен, БН перенаправит запросы на другие доступные серверы.

### 3.2. Расположение балансировщика

Обычно БН располагается между клиентом и кластером серверов. Но также он может располагаться:

- Между кластером и базой данных
- Между пользователем и веб-сервером
- Между веб-сервером и внутренними сервисами (серверы кэширования, внутренние приложения)

### 3.3. Алгоритмы балансировки

Для выбора сервера из списка доступных БН использует один из следующих алгоритмов:

#### Round Robin (Циклический обход)

Обход всех доступных серверов кластера по очереди. Обычно используется, когда все серверы имеют одинаковые вычислительные мощности.

```go
// Round Robin балансировщик на Go
package main

import (
    "sync"
    "sync/atomic"
)

type RoundRobinBalancer struct {
    servers []string
    counter atomic.Uint64
    mu      sync.RWMutex
}

func NewRoundRobinBalancer(servers []string) *RoundRobinBalancer {
    return &RoundRobinBalancer{
        servers: servers,
    }
}

func (b *RoundRobinBalancer) NextServer() string {
    b.mu.RLock()
    defer b.mu.RUnlock()
    
    if len(b.servers) == 0 {
        return ""
    }
    
    idx := b.counter.Add(1) % uint64(len(b.servers))
    return b.servers[idx]
}

func (b *RoundRobinBalancer) AddServer(server string) {
    b.mu.Lock()
    defer b.mu.Unlock()
    b.servers = append(b.servers, server)
}
```

#### Weighted Round Robin (Взвешенный циклический обход)

Каждому серверу присваивается "вес" — целое число, обозначающее "мощность" сервера. Сервера с большим весом получают больше запросов.

```go
type Server struct {
    Address string
    Weight  int
}

type WeightedRoundRobinBalancer struct {
    servers    []Server
    current    int
    totalWeight int
    mu         sync.Mutex
}

func (b *WeightedRoundRobinBalancer) NextServer() string {
    b.mu.Lock()
    defer b.mu.Unlock()
    
    if len(b.servers) == 0 {
        return ""
    }
    
    // Алгоритм взвешенного циклического обхода
    for {
        b.current = (b.current + 1) % len(b.servers)
        if b.servers[b.current].Weight > 0 {
            return b.servers[b.current].Address
        }
    }
}
```

#### Least Connections (Наименьшее количество соединений)

Запросы направляются на сервер с наименьшим количеством активных соединений. Это особенно полезно при переменной нагрузке или разной производительности серверов.

```go
type ServerWithConnections struct {
    Address    string
    Connections int32
}

type LeastConnectionsBalancer struct {
    servers []*ServerWithConnections
    mu      sync.RWMutex
}

func (b *LeastConnectionsBalancer) NextServer() string {
    b.mu.RLock()
    defer b.mu.RUnlock()
    
    if len(b.servers) == 0 {
        return ""
    }
    
    var minServer *ServerWithConnections
    minConn := int32(^uint32(0) >> 1) // MaxInt32
    
    for _, s := range b.servers {
        if s.Connections < minConn {
            minConn = s.Connections
            minServer = s
        }
    }
    
    atomic.AddInt32(&minServer.Connections, 1)
    return minServer.Address
}

func (b *LeastConnectionsBalancer) Release(addr string) {
    b.mu.RLock()
    defer b.mu.RUnlock()
    
    for _, s := range b.servers {
        if s.Address == addr {
            atomic.AddInt32(&s.Connections, -1)
            return
        }
    }
}
```

#### Другие алгоритмы

- **IP Hash** — вычисление хэш-кода IP адреса клиента для определения сервера (обеспечивает "липкость" сессии)
- **Least Bandwidth** — запросы направляются на сервер с наименьшим трафиком
- **Least Response Time** — запросы направляются на сервер с наименьшим средним временем ответа

### 3.5. Преимущества балансировки нагрузки

1. **Повышение надежности системы** — даже полный выход из строя одного сервера не приведет к отказу всей системы
2. **Уменьшение времени ответа** — при загруженности одного сервера, запрос перенаправляется на другой
3. **Аналитика** — современные БН могут анализировать текущую нагрузку и давать рекомендации по масштабированию

## Часть 4. Кэширование (Caching)

### 4.1. Что такое кэш?

**Кэш** — это кратковременная память, которая имеет меньшие объемы, чем долгосрочная, но более высокую скорость доступа. Данный механизм базируется на предположении, что данные, запрошенные однажды, будут запрошены еще раз.

Кэши используются на различных уровнях:
- Веб-браузер
- Операционная система
- Железо (CPU cache)
- Веб-приложение

### 4.2. Типы кэшей в распределенных системах

#### Кэш приложения (Application Cache)

При получении запроса данных, сервер сначала пробует найти их в локальном кэше. Если данных нет, они запрашиваются из основного хранилища и записываются в кэш.

**Проблема:** При горизонтальном масштабировании каждый инстанс приложения работает со своим собственным кэшем. Балансировщик может перенаправить запрос на другой инстанс, в котором нет этих данных.

#### Распределенный кэш (Distributed Cache)

Состоит из нескольких узлов, каждый из которых хранит определенную часть данных. Если запрошенных данных нет на текущем узле — они запрашиваются на другом. Основное преимущество — легкость горизонтального масштабирования.

**Пример реализации распределенного кэша на Go:**

```go
// Простая реализация распределенного кэша с consistent hashing
package main

import (
    "hash/crc32"
    "sort"
    "sync"
)

type ConsistentHash struct {
    nodes       []uint32
    nodeMap     map[uint32]string
    virtualNodes int
    mu          sync.RWMutex
}

func NewConsistentHash(virtualNodes int) *ConsistentHash {
    return &ConsistentHash{
        nodes:        make([]uint32, 0),
        nodeMap:      make(map[uint32]string),
        virtualNodes: virtualNodes,
    }
}

func (ch *ConsistentHash) AddNode(node string) {
    ch.mu.Lock()
    defer ch.mu.Unlock()
    
    for i := 0; i < ch.virtualNodes; i++ {
        hash := crc32.ChecksumIEEE([]byte(node + string(i)))
        ch.nodes = append(ch.nodes, hash)
        ch.nodeMap[hash] = node
    }
    sort.Slice(ch.nodes, func(i, j int) bool {
        return ch.nodes[i] < ch.nodes[j]
    })
}

func (ch *ConsistentHash) GetNode(key string) string {
    ch.mu.RLock()
    defer ch.mu.RUnlock()
    
    if len(ch.nodes) == 0 {
        return ""
    }
    
    hash := crc32.ChecksumIEEE([]byte(key))
    idx := sort.Search(len(ch.nodes), func(i int) bool {
        return ch.nodes[i] >= hash
    })
    
    if idx == len(ch.nodes) {
        idx = 0
    }
    
    return ch.nodeMap[ch.nodes[idx]]
}

// Использование распределенного кэша
type DistributedCache struct {
    hashRing *ConsistentHash
    stores   map[string]*sync.Map // имитация узлов кэша
}

func (dc *DistributedCache) Get(key string) (interface{}, bool) {
    node := dc.hashRing.GetNode(key)
    if node == "" {
        return nil, false
    }
    store, ok := dc.stores[node]
    if !ok {
        return nil, false
    }
    val, ok := store.Load(key)
    return val, ok
}

func (dc *DistributedCache) Set(key string, value interface{}) {
    node := dc.hashRing.GetNode(key)
    if node == "" {
        return
    }
    store, ok := dc.stores[node]
    if !ok {
        return
    }
    store.Store(key, value)
}
```

#### Глобальный кэш (Global Cache)

Состоит из одного узла, на который идут все запросы. Есть два подвида:

1. **Кэш сам отвечает за получение отсутствующих данных** из основного источника (применяется чаще)
2. **Приложение получает данные из основного источника**, если их нет в глобальном кэше

### 4.3. Стратегии инвалидации кэша

Существует две основные проблемы программирования: именование переменных и инвалидация кэша. Рассмотрим основные подходы:

#### Сквозное кэширование (Cache-Through)

Данные записываются в кэш и основное хранилище одновременно.
- **Преимущества:** быстрое получение, безопасность, полная согласованность
- **Недостатки:** высокая нагрузка на кэш

#### Обходное кэширование (Cache-Aside)

Данные записываются в основное хранилище "в обход" кэша и записываются в кэш только при получении запроса на эти данные.
- **Преимущества:** более низкая нагрузка на кэш
- **Недостатки:** более высокая задержка при получении новых данных

```go
// Cache-Aside паттерн на Go с PostgreSQL
type CacheAside struct {
    cache *DistributedCache
    db    *sql.DB
}

func (ca *CacheAside) GetUser(ctx context.Context, id string) (*User, error) {
    // 1. Проверяем кэш
    if val, ok := ca.cache.Get(id); ok {
        if user, ok := val.(*User); ok {
            return user, nil
        }
    }
    
    // 2. Данных нет в кэше — запрашиваем из БД
    var user User
    err := ca.db.QueryRowContext(ctx,
        "SELECT id, name, email FROM users WHERE id = $1", id,
    ).Scan(&user.ID, &user.Name, &user.Email)
    if err != nil {
        return nil, err
    }
    
    // 3. Записываем в кэш
    ca.cache.Set(id, &user)
    return &user, nil
}

func (ca *CacheAside) UpdateUser(ctx context.Context, user *User) error {
    // 1. Обновляем в БД
    _, err := ca.db.ExecContext(ctx,
        "UPDATE users SET name = $1, email = $2 WHERE id = $3",
        user.Name, user.Email, user.ID,
    )
    if err != nil {
        return err
    }
    
    // 2. Инвалидируем кэш (или обновляем)
    ca.cache.Set(user.ID, user)
    return nil
}
```

#### Отложенное кэширование (Write-Behind)

Данные записываются только в кэш, а запись в основное хранилище происходит через определенные интервалы.
- **Преимущества:** высокая скорость записи
- **Недостатки:** риск потери данных при аварийном завершении

### 4.4. Стратегии вытеснения кэша (Eviction Policies)

Так как объем кэша ограничен, необходимо убирать данные из кэша:

| Стратегия | Описание |
|-----------|----------|
| **LRU** (Least Recently Used) | Удаляется элемент, не использованный дольше всего |
| **MRU** (Most Recently Used) | Удаляется элемент, использованный наиболее недавно |
| **FIFO** (First In First Out) | Удаляется элемент, записанный раньше всех |
| **LIFO** (Last In First Out) | Удаляется элемент, записанный позже всех |
| **RR** (Random Replacement) | Удаляется случайный элемент |

**Реализация LRU кэша на Go:**

```go
package main

import (
    "container/list"
    "sync"
)

type LRUCache struct {
    capacity int
    cache    map[string]*list.Element
    list     *list.List
    mu       sync.RWMutex
}

type entry struct {
    key   string
    value interface{}
}

func NewLRUCache(capacity int) *LRUCache {
    return &LRUCache{
        capacity: capacity,
        cache:    make(map[string]*list.Element),
        list:     list.New(),
    }
}

func (c *LRUCache) Get(key string) (interface{}, bool) {
    c.mu.Lock()
    defer c.mu.Unlock()
    
    if elem, ok := c.cache[key]; ok {
        c.list.MoveToFront(elem)
        return elem.Value.(*entry).value, true
    }
    return nil, false
}

func (c *LRUCache) Set(key string, value interface{}) {
    c.mu.Lock()
    defer c.mu.Unlock()
    
    if elem, ok := c.cache[key]; ok {
        c.list.MoveToFront(elem)
        elem.Value.(*entry).value = value
        return
    }
    
    if c.list.Len() >= c.capacity {
        // Удаляем самый старый элемент
        oldest := c.list.Back()
        if oldest != nil {
            c.list.Remove(oldest)
            delete(c.cache, oldest.Value.(*entry).key)
        }
    }
    
    // Добавляем новый элемент
    elem := c.list.PushFront(&entry{key: key, value: value})
    c.cache[key] = elem
}
```

## Часть 5. Партиционирование данных (Data Partitioning / Sharding)

### 5.1. Что такое партиционирование?

После определенного объема данных становится технически и экономически целесообразнее масштабировать хранилище **горизонтально**, добавляя новые сервера. **Партиционирование** (или **шардирование**) — это механизм разделения больших массивов данных на меньшие части, распределенные по нескольким серверам.

> **Важно:** Партиционирование и репликация — это ортогональные оси. Партиционирование масштабирует запись/хранение/пропускную способность за пределы одного узла, а репликация обеспечивает выживаемость при отказе узла.

### 5.2. Виды партиционирования

#### Вертикальное партиционирование

Данные разбиваются по доменам: таблицы, относящиеся к определенному домену, находятся на выделенных серверах.

**Пример:** Для сайта медицинских услуг данные о врачах и лекарствах хранятся на одном сервере, а данные о пациентах и болезнях — на другом.

**Проблема:** Мы можем столкнуться с ситуацией, когда потребуется дополнительное партиционирование (например, 500 миллионов исследований не поместятся на одном сервере).

#### Горизонтальное партиционирование (Шардирование)

Распределение записей одного типа по разным таблицам/серверам. Например, исследования из США хранятся в одной таблице, из Китая — в другой.

**Основная сложность:** Корректный выбор критерия для распределения данных. Неправильный выбор приводит к дисбалансу.

#### Партиционирование на основе поискового сервиса

Предполагает наличие отдельного сервиса вне БД, который знает подход к распределению данных и сам определяет, в какую партицию записывать новые данные.

### 5.3. Стратегии партиционирования

#### Хэш-партиционирование

Вычисляется хэш-код ключа, и сервер определяется по формуле: `partition = hash(key) % N`.

**Проблема:** При добавлении новых серверов меняется вычисление позиции, и требуется перераспределение данных (rebalancing).

```go
// Хэш-партиционирование на Go
type HashPartitioner struct {
    numPartitions int
}

func (p *HashPartitioner) GetPartition(key string) int {
    hash := crc32.ChecksumIEEE([]byte(key))
    return int(hash) % p.numPartitions
}

// Пример использования с PostgreSQL
func (p *HashPartitioner) GetUser(ctx context.Context, db *sql.DB, id string) (*User, error) {
    partition := p.GetPartition(id)
    // Запрос к соответствующей партиции
    // В PostgreSQL можно использовать партиционирование по хэшу:
    // CREATE TABLE users PARTITION BY HASH (id);
    // CREATE TABLE users_0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
    // ...
    return nil, nil
}
```

#### Партиционирование по диапазону (Range Partitioning)

Данные делятся на диапазоны значений. Например, пользователи с ID от 1 до 10000 — в партиции 1, от 10001 до 20000 — в партиции 2.

```sql
-- PostgreSQL: партиционирование по диапазону
CREATE TABLE orders (
    id SERIAL,
    order_date DATE,
    customer_id INT,
    amount DECIMAL
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');
    
CREATE TABLE orders_2024_q2 PARTITION OF orders
    FOR VALUES FROM ('2024-04-01') TO ('2024-07-01');
```

#### Консистентное хэширование (Consistent Hashing)

Используется в распределенных системах для минимизации перераспределения данных при добавлении/удалении узлов.

```go
// Реализация консистентного хэширования (упрощенная)
type ConsistentHashPartitioner struct {
    ring   *ConsistentHash // см. реализацию выше
}

func (p *ConsistentHashPartitioner) GetNode(key string) string {
    return p.ring.GetNode(key)
}
```

### 5.4. Ключевые проблемы партиционирования

#### Перераспределение (Rebalancing)

При изменении подхода к партиционированию (слишком частые обращения, переполнение партиции) приходится создавать новые партиции и перераспределять данные, что почти всегда приводит к недоступности на определенное время.

#### Денормализация

При JOIN-запросах между партициями производительность сильно страдает. Часто приходится денормализовать БД, перенося логику констрейнтов на уровень приложения.

```go
// Пример денормализации: хранение связанных данных в одном документе
type OrderWithCustomer struct {
    OrderID    string
    OrderDate  time.Time
    CustomerID string
    Customer   Customer // Денормализованные данные клиента
    Items      []OrderItem
}
```

## Часть 6. SQL vs NoSQL: Выбор хранилища данных

### 6.1. Введение

При работе над дизайном распределенных систем часто встает необходимость выбора основного хранилища данных. Хотя реляционные БД являются наиболее зрелой технологией, иногда выбор NoSQL крайне целесообразен.

> **Важно:** "SQL vs NoSQL" — это ложная дихотомия, которая схлопывает две независимые оси в одну. Реальный выбор зависит от характеристик нагрузки, формы запросов и требований к консистентности.

### 6.2. SQL (Реляционные БД)

**Особенности:**
- Данные хранятся в таблицах с четкой структурой
- Для добавления нового свойства необходимо менять схему
- Используется структурированный язык запросов SQL
- Поддерживают ACID-транзакции
- Чаще всего вертикальное масштабирование

**Примеры:** PostgreSQL, MySQL, MariaDB, Oracle, MS SQL Server

### 6.3. NoSQL БД

**Основные виды:**

| Тип | Описание | Примеры |
|-----|----------|---------|
| **Документоориентированные** | Документы в коллекциях, разная структура | MongoDB, OrientDB |
| **Графовые** | Данные связаны графом (узлы + связи) | Neo4J, IndraDB |
| **Ключ-значение** | Пары "ключ-значение", как хэш-таблица | Redis, Cassandra |
| **Колоночные** | Данные хранятся по колонкам | Cassandra, HBase |

### 6.4. Сравнительный анализ

| Характеристика | SQL | NoSQL |
|----------------|-----|-------|
| **Тип хранения** | Таблицы, четкая структура | Документы, графы, ключ-значение |
| **Запросы** | Структурированный SQL | Неструктурированный UnQL |
| **Надежность** | Поддержка ACID | ACID не поддерживается (кроме некоторых) |
| **Масштабируемость** | Вертикальное (дорого) | Горизонтальное (быстро и дешево) |

### 6.5. Сильные стороны

**SQL:**
- Данные структурированы и редко меняются
- Поддерживается консистентность данных
- Поддерживается транзакционность (ACID)

**NoSQL:**
- Динамическая структура данных
- Высокая производительность (чтение/запись)
- Легко масштабируется горизонтально
- Экономия (особенно в облаках)

### 6.6. Пример работы с PostgreSQL на Go

```go
package main

import (
    "context"
    "database/sql"
    "log"
    "time"

    _ "github.com/lib/pq"
)

type User struct {
    ID        string    `json:"id"`
    Name      string    `json:"name"`
    Email     string    `json:"email"`
    CreatedAt time.Time `json:"created_at"`
}

type UserRepository struct {
    db *sql.DB
}

func NewUserRepository(connStr string) (*UserRepository, error) {
    db, err := sql.Open("postgres", connStr)
    if err != nil {
        return nil, err
    }
    
    // Настройка пула соединений
    db.SetMaxOpenConns(25)
    db.SetMaxIdleConns(25)
    db.SetConnMaxLifetime(5 * time.Minute)
    
    return &UserRepository{db: db}, nil
}

func (r *UserRepository) CreateUser(ctx context.Context, user *User) error {
    query := `
        INSERT INTO users (id, name, email, created_at)
        VALUES ($1, $2, $3, $4)
    `
    _, err := r.db.ExecContext(ctx, query,
        user.ID, user.Name, user.Email, user.CreatedAt,
    )
    return err
}

func (r *UserRepository) GetUserByID(ctx context.Context, id string) (*User, error) {
    query := `SELECT id, name, email, created_at FROM users WHERE id = $1`
    
    var user User
    err := r.db.QueryRowContext(ctx, query, id).Scan(
        &user.ID, &user.Name, &user.Email, &user.CreatedAt,
    )
    if err != nil {
        return nil, err
    }
    return &user, nil
}

// Транзакционный пример
func (r *UserRepository) TransferFunds(ctx context.Context, fromID, toID string, amount float64) error {
    tx, err := r.db.BeginTx(ctx, nil)
    if err != nil {
        return err
    }
    defer tx.Rollback()
    
    // Списываем
    _, err = tx.ExecContext(ctx,
        "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
        amount, fromID,
    )
    if err != nil {
        return err
    }
    
    // Зачисляем
    _, err = tx.ExecContext(ctx,
        "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
        amount, toID,
    )
    if err != nil {
        return err
    }
    
    return tx.Commit()
}
```

## Часть 7. Индексы в базах данных

### 7.1. Что такое индексы?

При увеличении объема хранимых данных мы сталкиваемся с долгой обработкой запросов. **Индексы** помогают увеличить скорость поиска данных в таблицах по определенным параметрам.

> **Важно:** Индексы увеличивают скорость чтения, но уменьшают скорость вставки, обновления и удаления.

### 7.2. Как работают индексы

Индекс — это отдельная структура данных, содержащая ключ поиска и указатель на место в памяти, где хранится запись.

**Пример:** Таблица `events` с колонками `event_type`, `description`, `triggered_by`. При индексе по комбинации `event_type + triggered_by` создается структура:

```
(event_type + triggered_by) → указатель на запись
```

Порядок элементов важен: `petya@mail.com + ERROR` ≠ `ERROR + petya@mail.com`

### 7.3. Типы индексов в PostgreSQL

PostgreSQL поддерживает несколько типов индексов:

#### B-tree (по умолчанию)

Самый универсальный индекс. Поддерживает операции равенства, диапазоны, сортировку и JOIN'ы.

```sql
-- Создание B-tree индекса (по умолчанию)
CREATE INDEX idx_users_email ON users (email);

-- Составной индекс
CREATE INDEX idx_events_type_triggered ON events (event_type, triggered_by);

-- Уникальный индекс
CREATE UNIQUE INDEX idx_users_email_unique ON users (email);
```

**Сложность:** O(log n) для поиска, вставки, удаления.

#### Hash индекс

Оптимизирован для быстрого поиска по точному равенству.

```sql
-- Создание hash индекса
CREATE INDEX idx_users_id_hash ON users USING HASH (id);
```

**Сложность:** O(1) для поиска по равенству.

#### GiST, GIN, BRIN

- **GiST** — для пространственных данных, range-типов
- **GIN** — для полнотекстового поиска, массивов, JSONB
- **BRIN** — для очень больших таблиц с коррелированными данными

```sql
-- GIN индекс для JSONB
CREATE INDEX idx_orders_metadata ON orders USING GIN (metadata);

-- GIN индекс для полнотекстового поиска
CREATE INDEX idx_documents_content ON documents USING GIN (to_tsvector('russian', content));
```

### 7.4. Пример работы с индексами на Go

```go
package main

import (
    "context"
    "database/sql"
    "fmt"
    "time"
)

type Event struct {
    ID          int64
    EventType   string
    Description string
    TriggeredBy string
    CreatedAt   time.Time
}

type EventRepository struct {
    db *sql.DB
}

// Поиск с использованием индекса
func (r *EventRepository) GetEventsByTypeAndTrigger(ctx context.Context, eventType, triggeredBy string) ([]Event, error) {
    // Использует индекс idx_events_type_triggered
    query := `
        SELECT id, event_type, description, triggered_by, created_at
        FROM events
        WHERE event_type = $1 AND triggered_by = $2
        ORDER BY created_at DESC
        LIMIT 100
    `
    
    rows, err := r.db.QueryContext(ctx, query, eventType, triggeredBy)
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    
    var events []Event
    for rows.Next() {
        var e Event
        err := rows.Scan(&e.ID, &e.EventType, &e.Description, &e.TriggeredBy, &e.CreatedAt)
        if err != nil {
            return nil, err
        }
        events = append(events, e)
    }
    return events, nil
}

// Поиск с использованием частичного индекса (условный индекс)
func (r *EventRepository) GetRecentErrors(ctx context.Context) ([]Event, error) {
    // Частичный индекс: CREATE INDEX idx_events_recent_errors ON events (created_at) 
    // WHERE event_type = 'ERROR' AND created_at > NOW() - INTERVAL '7 days'
    query := `
        SELECT id, event_type, description, triggered_by, created_at
        FROM events
        WHERE event_type = 'ERROR' AND created_at > NOW() - INTERVAL '7 days'
        ORDER BY created_at DESC
    `
    rows, err := r.db.QueryContext(ctx, query)
    if err != nil {
        return nil, err
    }
    defer rows.Close()
    
    var events []Event
    for rows.Next() {
        var e Event
        err := rows.Scan(&e.ID, &e.EventType, &e.Description, &e.TriggeredBy, &e.CreatedAt)
        if err != nil {
            return nil, err
        }
        events = append(events, e)
    }
    return events, nil
}

// Анализ плана запроса для проверки использования индекса
func (r *EventRepository) ExplainQuery(ctx context.Context, query string, args ...interface{}) (string, error) {
    explainQuery := fmt.Sprintf("EXPLAIN ANALYZE %s", query)
    var plan string
    err := r.db.QueryRowContext(ctx, explainQuery, args...).Scan(&plan)
    return plan, err
}
```

### 7.5. Когда использовать индексы

**Индексы полезны, когда:**
- Таблица часто читается и редко обновляется
- Поиск идет по часто используемым колонкам
- Данные имеют высокую селективность (много уникальных значений)

**Индексы вредны, когда:**
- Таблица часто обновляется (INSERT, UPDATE, DELETE)
- Данные имеют низкую селективность (например, булевы поля)
- Индекс создан на колонке, которая редко используется в WHERE

## Часть 8. Итоговые рекомендации по системному дизайну

### 8.1. Ключевые принципы

1. **Понимайте ограничения CAP и PACELC** — ни одна система не может быть идеальной во всем. Выбирайте компромиссы осознанно.

2. **Проектируйте для отказоустойчивости** — используйте балансировку нагрузки, репликацию и Health Checks.

3. **Кэшируйте стратегически** — выбирайте правильную стратегию инвалидации и вытеснения для вашего сценария.

4. **Партиционируйте данные с умом** — учитывайте паттерны доступа и возможность перераспределения.

5. **Выбирайте БД под задачу** — SQL для транзакционных данных, NoSQL для гибких схем и высокой нагрузки.

6. **Индексируйте осознанно** — каждый индекс ускоряет чтение, но замедляет запись.

### 8.2. Чек-лист для проектирования

- [ ] Определены требования к консистентности (CAP/PACELC выбор)
- [ ] Выбран подходящий алгоритм балансировки
- [ ] Реализованы Health Checks
- [ ] Выбрана стратегия кэширования
- [ ] Определена стратегия партиционирования
- [ ] Выбран тип БД (SQL/NoSQL) под нагрузку
- [ ] Созданы индексы для критичных запросов
- [ ] Настроен мониторинг всех компонентов

Системный дизайн — это искусство поиска компромиссов. CAP и PACELC теоремы дают нам фундаментальное понимание ограничений распределенных систем. Балансировка нагрузки, кэширование, партиционирование и правильный выбор хранилища данных — это инструменты, которые позволяют нам строить масштабируемые и отказоустойчивые системы.
Помните: **нет универсального решения**. Каждая система уникальна, и правильный выбор зависит от конкретных требований, бюджета и команды. Используйте знания из этой статьи как отправную точку, но всегда адаптируйте решения под свой контекст.

Ниже представлена финальная версия статьи. Я добавил блоки про технический долг, операционную сложность и итеративность, чтобы сделать текст максимально исчерпывающим.
В современной инженерии программного обеспечения не существует «правильных» решений в абсолютном смысле слова. Существуют лишь решения, которые являются наиболее подходящими для конкретных условий, ограничений и целей. Именно это делает системный дизайн не столько наукой о поиске идеальной архитектуры, сколько дисциплиной управления ограничениями и осознанного принятия издержек.

### 1. Определение ключевых понятий

**Системный дизайн (System Design)** — это процесс определения архитектуры, компонентов, интерфейсов и взаимодействий данных для создания сложной системы. Это проектирование «каркаса», который обеспечивает баланс между функциональностью и нефункциональными требованиями (надежность, масштабируемость, производительность).

**Компромиссы (Trade-offs)** — это фундаментальная ситуация, при которой улучшение одного параметра системы неизбежно ведет к ухудшению другого. В инженерии невозможно получить «всё и сразу». Каждый выбор — будь то протокол передачи данных, модель хранения или паттерн взаимодействия — влечет за собой скрытые издержки. Системный дизайн — это осознанный выбор того, какими издержками мы готовы пожертвовать ради достижения приоритетных целей.

### 2. Анализ фундаментальных дилемм

Классическим примером системного дизайна как игры компромиссов служит **CAP-теорема**. Она утверждает, что в распределенной системе невозможно одновременно обеспечить три свойства:
*   **Consistency (Согласованность):** Все узлы видят одни и те же данные одновременно.
*   **Availability (Доступность):** Каждый запрос к работающему узлу получает ответ.
*   **Partition Tolerance (Устойчивость к разделению):** Система продолжает работать при разрыве связи между узлами.

Поскольку в распределенных сетях сетевые сбои неизбежны (P — обязательное условие), инженеры вынуждены выбирать между **CP** (строгая согласованность при возможной потере доступности) и **AP** (доступность при возможности получения устаревших данных). Теорема **PACELC** расширяет этот взгляд, указывая, что даже при отсутствии сбоев мы постоянно балансируем между **Latency (Задержкой)** и **Consistency (Согласованностью)**.

### 3. Идентификация факторов влияния

При проектировании системы инженер должен балансировать между следующими переменными:

*   **Масштабируемость (Scalability):** Горизонтальное масштабирование позволяет системе расти, но вносит сложности в согласованность данных и требует механизмов координации (например, распределенные блокировки), что увеличивает задержки.
*   **Задержка (Latency) vs Пропускная способность (Throughput):** Оптимизация под мгновенный отклик одного запроса часто требует упрощения логики или использования кэширования, что может снизить общую пропускную способность системы при массовых операциях.
*   **Стоимость (Cost):** Решение может быть технически совершенным, но экономически нежизнеспособным. Избыточное резервирование или использование сверхдорогих облачных сервисов должны быть оправданы бизнес-ценностью.
*   **Сложность поддержки (Maintainability & Operability):** Микросервисная архитектура дает гибкость, но увеличивает сложность мониторинга, деплоя и отладки. Важно помнить: *сложность системы должна быть пропорциональна сложности задачи, которую она решает.*
*   **Надежность (Reliability) и Отказоустойчивость (Fault Tolerance):** Внедрение механизмов репликации и чекпоинтов защищает от сбоев, но увеличивает время отклика и усложняет код приложения.

### 4. Роль бизнес-контекста

Техническое решение никогда не существует в вакууме; оно всегда обслуживает бизнес-цели. Именно контекст определяет, какой компромисс является «правильным».

*   **Пример банковской системы:** Критически важна **Consistency**. Если пользователь снимает деньги, баланс должен обновиться мгновенно. Мы готовы пожертвовать доступностью (система может временно «замереть» при сбое) и скоростью ради исключения двойного списания.
*   **Пример социальной сети (Лайки/Просмотры):** Приоритет — **Availability** и **Latency**. Если пользователь увидит количество лайков с задержкой в 2 секунды, это не критично. Мы жертвуем строгой согласованностью ради мгновенного отклика и высокой доступности.

### 5. Методология принятия решений и управление долгом

Профессиональный подход к системному дизайну строится на методологии **«наилучшего из доступных вариантов»**:

1.  **Определение ограничений:** Выявление жестких требований (RPS, Latency, бюджет, сроки).
2.  **Генерация альтернатив:** Разработка минимум 2–3 различных архитектурных подходов.
3.  **Анализ последствий (Trade-off Analysis):** Составление матрицы плюсов и минусов. Важно оценивать не только текущие преимущества, но и **Технический долг**: «Какую сложность мы создаем на будущее, выбирая этот путь сейчас?».
4.  **Оценка рисков:** Определение сценариев отказа и их последствий для бизнеса.
5.  **Выбор и обоснование:** Выбор варианта, который максимально соответствует приоритетам бизнеса при минимально приемлемых издержках.
6.  **Наблюдаемость (Observability):** Внедрение инструментов мониторинга для проверки того, оправдал ли выбранный компромисс ожидания в реальных условиях.

### 6. Примеры из практики: SQL vs NoSQL

Выбор базы данных — это не выбор «лучшей» технологии, а выбор подходящего набора компромиссов:

*   **Реляционные БД (SQL, например, PostgreSQL):**
    *   *Компромисс:* Обеспечивают ACID-транзакции и сложные связи, но сложнее масштабируются горизонтально (требуется шардинг).
    *   *Когда выбирать:* Финансовые операции, системы учета, где целостность данных превыше всего.
*   **Нереляционные БД (NoSQL, например, Cassandra, MongoDB):**
    *   *Компромисс:* Легко масштабируются и обеспечивают высокую доступность, но часто жертвуют строгой согласованностью (Eventual Consistency) и сложными запросами (Joins).
    *   *Когда выбирать:* Аналитика больших данных, системы чатов, кэширование, где скорость записи и объем данных растут экспоненциально.

### 7. Вывод

Системный дизайн — это не поиск «идеальной» архитектуры, потому что идеала не существует. Любое архитектурное решение — это балансировка на канате между противоречивыми требованиями: скоростью, надежностью, стоимостью и сложностью.

Мастерство системного дизайна заключается в способности **осознанно выбирать, чем мы готовы пожертвовать**. Профессионал не говорит: «Это лучшее решение». Он говорит: «Это решение лучшее для наших текущих целей, потому что оно обеспечивает необходимую доступность при допустимом уровне задержки, и мы понимаем риски, связанные с отказом от строгой согласованности в данном конкретном сценарии».

**Системный дизайн — это искусство управления последствиями выбора.**
