# Проектирование БД SQL/NoSQL и Event-Driven Architecture

## Определение требований и констраинтов

### Ключевые требования:
- **Масштабируемость**: БД должна поддерживать высокий объем трафика и масштабироваться легко.
- **Разделение R/W**: Распределение данных между чтением и записью должно быть эффективным.
- **RPO (время восстановления)**: Время восстановления должно быть минимально, не превышая 1 день.
- **P99 латентность**: 99% запросов должны быть обработаны в миллисекунде или меньше.
- **3-летний TCO (Total Cost of Ownership)**: Бюджет на 3 года должен быть минимизирован.

### Выбор базы данных:
- **SQL (PostgreSQL)**: Используется для операций с ACID-свойствами, гибкости с использованием JSONB для сложных структур данных.
- **NoSQL (Apache Cassandra)**: Рекомендуется для высоких трафиков из-за его устойчивости к высокой транзакционной нагрузке и использованию LSM-Tree.

## Реализация индексов

### PostgreSQL:
- **Композитные индексы**: Позволяют ускорить выполнение запросов с условиями на несколько столбцов.
- **Покрывающие индексы**: Помогают избежать дополнительных поисков в записях, ускоряя выполнение запросов.
- **BRIN-индексы**: Эффективны для индексирования больших таблиц с выраженной локальностью данных.

### NoSQL (Cassandra):
- **Высококардинальные ключи разбиения**: Уменьшение hot spots и более эффективное распределение данных по нодам.

## Реализация архитектуры событий

### Паттерн Event-Driven Architecture:
- **Transactional Outbox**: Обеспечивает атомарность записи в базу данных и отправку событий в Kafka.
- **Debezium**: Позволяет преобразовывать изменения в базе данных в события для Kafka, обеспечивая согласованность данных.

### Идемпотентность потребителей событий:
- Используются маркеры или идентификаторы, чтобы гарантировать, что одно событие не обрабатывается дважды.

## Реализация CQRS

### Разделение запросов на чтение от операций на запись:
- **Materialized Views**: Создаются в Redis для ускорения чтения данных.
- **Redis**: Используется для кэширования часто используемых данных, инвалидируется по событиям из Transactional Outbox.

## Связка со всеми требованиями

### Удовлетворение требований:
- **PostgreSQL + Kafka + Redis** должны удовлетворять все 5 ключевых требований, включая масштабируемость, скорость восстановления, латентность и TCO.
- Если это верно, продолжение работы с этим решением.

## Установка безопасности

- **Подготовленные выражения**: Используются для предотвращения SQL инъекций.
- **Row- Level Security**: Ограничивает доступ к данным на уровне строки.
- **TLS**: Обеспечивает защиту данных в обмене.
- **Регулярная эволюция схемы**: Предотвращает возникновение новых арматурных болезней.

## Избегание антипаттернов

- **Дублированные записи без атомарности**: Используются Atomic Operations для гарантирования последовательности.
- **Низкокардинальные ключи разбиения**: Приводят к hot spots, избегаем с помощью высококардинальных ключей.
- **Сообщения для синхронного RPC**: Используются для асинхронных операций.
- **Неустойчивые потребители событий**: Обеспечиваем их стабильность с помощью Idempotent Consumers.

## Тестирование и мониторинг

### "Boring Test":
- Выполнение теста на одном решении PostgreSQL + Kafka + Redis, проверяя, что оно удовлетворяет все 5 ключевых требований.
- Если да, переходим к продакшну, иначе добавляем сложность и оптимизации по мере необходимости.
