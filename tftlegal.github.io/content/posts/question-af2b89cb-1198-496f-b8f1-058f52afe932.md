### Экспертный разбор (Критика):

**Сильные стороны:**
1.  **Правильный выбор стека:** Использование `TanStack Query` для работы с внешним API (Jira) — это стандарт индустрии. `Zustand` оправдан для высокопроизводительных UI-компонентов (Gantt).
2.  **Архитектурный паттерн:** Идея с **Adapter Pattern** для Jira — критически важная. Это спасает проект от превращения в «спагетти-код», где логика API перемешана с UI.
3.  **Модель данных:** Выделение сущности `Dependency` — верное решение для полноценной диаграммы Ганта (без связей это просто список задач с датами).

**Слабые стороны и ошибки (что нужно исправить немедленно):**
1.  **Проблема "Source of Truth" (Источник истины):** В черновике не прописано, как разрешаются конфликты. Если пользователь изменил статус в Jira, а одновременно в приложении — кто победит? Нужна стратегия *Conflict Resolution*.
2.  **Отсутствие Rate Limiting:** Jira API имеет жесткие лимиты на количество запросов. Если на доске 100 задач и мы будем делать 100 запросов при загрузке — приложение "умрет". Нужна стратегия *Batch Fetching* или агрессивное кэширование.
3.  **Безопасность (Auth):** Упоминание "кастомного OAuth2" — это риск. Для корпоративного софта лучше использовать стандартные библиотеки (например, `Passport.js` или готовые решения для Azure AD/Okta), так как Jira часто сидит за корпоративными SSO.
4.  **Производительность Gantt:** `Frappe Gantt` может тормозить на больших проектах (50+ задач). Для "корпоративного" уровня лучше сразу закладывать поддержку виртуализации списка или Canvas-рендеринга.

# Шаг 1: Технический стек и архитектура системы

Цель данного этапа — создание масштабируемого фундамента, который обеспечит бесшовную интеграцию с Jira, высокую скорость работы с динамическими данными и гибкую кастомизацию интерфейса.

## 1.1. Технологический стек (Technology Stack)

### Frontend (User Experience & Visualization)
*   **Framework:** `React.js` (TypeScript — обязателен для корпоративного уровня).
*   **State Management:** `Zustand`. Выбран из-за легкости управления состоянием "Drag-and-Drop" досок и возможности быстрого доступа к глобальным настройкам проектов.
*   **Data Fetching & Sync:** `TanStack Query` (React Query). Обеспечит автоматическое кэширование ответов Jira API, обработку состояний `loading/error` и механизм `Optimistic Updates` (обновление UI до получения ответа от сервера).
*   **Styling:** `Tailwind CSS` + `Shadcn UI`. Позволяет быстро собирать сложные интерфейсы с высокой степенью кастомизации.
*   **Visualization:** `dnd-kit` (для Drag-and-Drop задач) + кастомный компонент на `SVG` для диаграммы Ганта (для обеспечения высокой производительности при большом количестве связей).

### Backend (Orchestration & Integration)
*   **Runtime:** `Node.js` с фреймворком `NestJS`. Обеспечивает модульность и Dependency Injection.
*   **Database:** `PostgreSQL`. Для хранения структуры проектов, метаданных и связей.
*   **ORM:** `Prisma`. Для строгой типизации схем БД.
*   **Real-time:** `Socket.io`. Для мгновенной передачи обновлений из Jira (через Webhooks) на фронтенд.
*   **Caching:** `Redis`. Для хранения сессий и кэширования часто запрашиваемых данных из Jira API (снижение нагрузки на лимиты Jira).

## 1.2. Проектирование схемы данных (Data Modeling)

Система строится на принципе **"Shadowing"**: мы создаем локальные "тени" объектов Jira, чтобы обеспечить мгновенный отклик интерфейса.

### Сущность `Project` (Контейнер)
*   `id`: UUID
*   `title`: String
*   `jira_project_key`: String (опционально, для связи с проектом в Jira)
*   `layout_config`: JSONB (хранит настройки: порядок колонок, скрытые поля, цветовые схемы).
*   `pinned_status`: Boolean (для отображения на главном экране).

### Сущность `Task` (Атомарная единица)
*   `id`: UUID
*   `project_id`: UUID (FK)
*   `title`: String
*   `status`: Enum (To Do, In Progress, Review, Done)
*   `start_date`: DateTime
*   `end_date`: DateTime
*   **`external_id`**: String (ID задачи в Jira)
*   **`source_type`**: Enum (LOCAL, JIRA) — *определяет, где первичный источник данных.*
*   **`sync_state`**: Enum (SYNCED, DIRTY, ERROR) — *флаг для отслеживания конфликтов.*
*   `priority`: Enum (Low, Medium, High, Critical)

### Сущность `Dependency` (Связи Ганта)
*   `id`: UUID
*   `predecessor_id`: UUID (FK к Task)
*   `successor_id`: UUID (FK к Task)
*   `lag_time`: Integer (задержка в днях/часах)
*   `type`: Enum (FS, SS, FF, SF)

## 1.3. Ключевые архитектурные решения (Critical Points)

### 1. Jira Adapter Layer (Абстракция)
Мы внедряем паттерн **Adapter**. Фронтенд никогда не знает, как устроено API Jira.
*   *Backend Service:* `JiraService` -> `JiraAdapter` -> `JiraAPI`.
*   Это позволяет менять логику маппинга полей (например, если в одной Jira поле называется "Due Date", а в другой "Deadline") в одном месте.

### 2. Стратегия синхронизации и конфликтов
Чтобы избежать потери данных при одновременном редактировании:
*   **Optimistic UI:** При изменении задачи в приложении, UI обновляется мгновенно, а запрос в Jira уходит в фоне.
*   **Conflict Resolution:** Если при ответе от Jira приходит ошибка (например, задача уже изменена кем-то другим), система помечает задачу как `DIRTY` и выводит уведомление пользователю с предложением "Перезаписать" или "Обновить из Jira".

### 3. Batching & Throttling
Для работы с диаграммой Ганта:
*   Вместо запроса каждой задачи отдельно, система использует **Batch Fetching** (запрос списка задач по проекту одним запросом).
*   Используется **Debouncing** на изменение дат в диаграмме Ганта, чтобы не спамить запросами к Jira при каждом движении ползунка.

## 1.4. Поток данных (Data Flow)

1.  **Инициализация:** Пользователь заходит в проект. `TanStack Query` запрашивает данные из нашей БД.
2.  **Синхронизация:** Бэкенд проверяет `sync_state`. Если есть задачи в статусе `DIRTY`, он пытается отправить их в Jira.
3.  **Интеграция:** Пользователь вводит ключ задачи Jira. Бэкенд через `JiraAdapter` забирает данные, создает запись в `Task` с флагом `source_type: JIRA` и сохраняет в БД.
4.  **Визуализация:** Данные попадают в `Zustand` стор. Компонент диаграммы Ганта пересчитывает связи через `Dependency` и отрисовывает SVG-линии.
5.  **Обновление:** Приходит Webhook от Jira (статус задачи изменен коллегой). Бэкенд обновляет БД и через `Socket.io` шлет сигнал фронтенду. `TanStack Query` инвалидирует кэш, и доска обновляется автоматически.
