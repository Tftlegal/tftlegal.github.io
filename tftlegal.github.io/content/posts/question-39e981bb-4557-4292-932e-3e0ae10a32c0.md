### 🚩 Критические замечания (Что нужно исправить немедленно):

1.  **Проблема MTP и Ollama:** Ollama — это высокоуровневая обертка. Она отлично работает с обычными моделями, но **не имеет прямой поддержки специфических конфигураций MTP** (как в DeepSeek-V3/V2) «из коробки» через стандартные команды. Если модель требует специфических весов для MTP-головок, Ollama может их просто проигнорировать или выдать ошибку парсинга GGUF.
    *   *Решение:* Нужно явно указать использование `llama.cpp` через кастомный конфиг или использовать напрямую бинарный файл `llama.cpp` в контейнере для полного контроля над параметрами.
2.  **Лимиты ресурсов (Resources Limits):** В манифесте указан `memory: "4Gi"`. В Kubernetes лимит памяти для контейнера — это **общая память (RAM + VRAM)**. Если вы укажете лимит меньше, чем потребляет модель + системные процессы, K8s убьет под по OOM (Out Of Memory). Для 2ГБ видеокарты и оффлоадинга в RAM, лимит должен быть существенно выше (минимум 8-16 ГБ), чтобы избежать киллинга процесса.
3.  **HostPath и права доступа:** Использование `hostPath` для `/mnt/data/ollama` часто вызывает проблемы с правами доступа (Permission Denied) внутри контейнера, так как пользователь внутри Ollama может не иметь прав на запись/чтение в корень хоста.
4.  **Отсутствие инициализации:** В манифесте нет механизма автоматической загрузки модели. Пользователю придется делать `exec`, что не является "профессиональным" подходом для K8s. Нужно использовать `initContainers` или скрипт запуска.

# Полный гайд по развертыванию LLM с поддержкой Multi-Token Prediction (MTP) на GTX 1050 (2GB) в Kubernetes

Данное руководство описывает экстремальный сценарий развертывания: запуск современных архитектур на оборудовании, которое формально не соответствует минимальным требованиям индустрии.

### 1. Стратегия выживания на 2 ГБ VRAM

При работе с MTP на GTX 1050 мы сталкиваемся с "бутылочным горлышком" памяти. MTP требует хранения весов для предсказания нескольких токенов вперед, что увеличивает объем занимаемой памяти.

**Технологический стек:**
*   **Модель:** `TinyLlama-1.1B` или `Qwen2-0.5B` (высокая эффективность на малых весах).
*   **Квантование:** **GGUF (Q4_K_M или Q3_K_L)**. Это позволяет упаковать модель в ~600-800 МБ.
*   **Движок:** `llama.cpp` (через Ollama или прямой бинарник). Он поддерживает **GPU Offloading**, что критично: мы загружаем только часть слоев в VRAM, остальное — в системную RAM.
*   **Оптимизация MTP:** Ограничение контекстного окна до 512 токенов для минимизации размера KV-кэша.

### 3. Конфигурация и Оптимизация инференса

Для работы с MTP на слабом железе стандартный запуск Ollama может быть нестабилен. Мы будем использовать параметры, жестко ограничивающие потребление памяти.

**Ключевые параметры для `llama.cpp` (через Ollama переменные):**
*   `OLLAMA_NUM_PARALLEL=1` (Никаких параллельных запросов!)

*   `num_ctx=512` (Ограничение контекста — критически важно для 2ГБ VRAM)

### 4. Развертывание в Kubernetes

Мы используем `PersistentVolumeClaim` вместо `hostPath` для обеспечения переносимости и безопасности.

**deployment.yaml**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-mtp-service
  labels:
    app: llm-mtp
spec:
  replicas: 1
  selector:
    matchLabels:
      app: llm-mtp
  template:
    metadata:
      labels:
        app: llm-mtp
    spec:
      containers:
      - name: ollama
        image: ollama/ollama:latest
        resources:
          limits:
            nvidia.com/gpu: 1
            memory: "8Gi" # Увеличили лимит RAM для стабильного оффлоадинга
            cpu: "4"
          requests:
            nvidia.com/gpu: 1
            memory: "4Gi"
            cpu: "2"
        env:
        - name: OLLAMA_HOST
          value: "0.0.0.0"
        - name: OLLAMA_NUM_PARALLEL
          value: "1"
        - name: OLLAMA_MAX_LOADED_MODELS
          value: "1"
        ports:
        - containerPort: 11434
        volumeMounts:
        - name: ollama-data
          mountPath: /root/.ollama
      volumes:
      - name: ollama-data
        persistentVolumeClaim:
          claimName: ollama-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: llm-api
spec:
  selector:
    app: llm-mtp
  ports:
    - protocol: TCP
      port: 80
      targetPort: 11434
  type: LoadBalancer
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ollama-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

### Критический разбор (Ошибки и слабые места):

1.  **Главная техническая ошибка (MTP):** Ты предлагаешь использовать флаг `m_tp_layers` в Ollama/llama.cpp. **На текущий момент в стандартных сборках Ollama нет прямой поддержки Multi-Token Prediction через такой флаг.** MTP — это архитектурное изменение (как в моделях DeepSeek-V3), а не просто параметр конфига. Чтобы запустить MTP на такой карте, нужно использовать специфические веса моделей, обученных с MTP, и соответствующие библиотеки.
2.  **Проблема VRAM (2GB):** GTX 1050 с 2GB — это экстремально мало. Контекст `num_ctx 512` — это минимум, но при использовании `num_gpu_layers 15` для модели Qwen2-0.5B, память может мгновенно забиться KV-кэшем. Нужно предупредить о динамическом росте потребления памяти.
3.  **Пути в Kubernetes:** Использование `hostPath` для моделей — это "костыль" для тестов. В промышленном K8s лучше использовать `PersistentVolumeClaim` (PVC).
4.  **Версия Device Plugin:** Ссылка на `v0.14.0` может быть устаревшей. Лучше советовать установку через Helm или проверку актуальной версии.
5.  **Отсутствие стратегии "Shared Memory":** Для работы LLM в контейнерах часто требуется настройка `/dev/shm`, иначе `llama.cpp` может упасть при работе с тензорами.
