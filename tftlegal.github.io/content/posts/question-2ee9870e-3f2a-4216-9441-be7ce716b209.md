# Что таккое GOAWAY?

Слово Go away в общем английском языке означает «уходи», «покинь место» или «исчезни». В сфере IT и веб-технологий GOAWAY — это специальный управляющий кадр (frame) в протоколе HTTP/2, предназначенный для мягкого и корректного закрытия сетевого соединения.

Однажны в  одном из ботов Telegram, написанных на языке **Go**, вылезла ошибка:
```
time=2026-08-04T21:41:14.786Z level=INFO msg="[TGBOT] [ERROR] error get updates, error do request for method getUpdates, Post \"https://api.telegram.org/bot***/getUpdates\": http2: Transport: cannot retry err [http2: Transport received Server's graceful shutdown GOAWAY] after Request.Body was written; define Request.GetBody to avoid this error"
```
По ней видно, что клиент Go обрабатывает разрыв HTTP/2-соединения при использовании метода Long Polling (`getUpdates`) не совсем корректно.

---

### 🔍 Расшифровка ошибки по частям:

1. **`error get updates, error do request for method getUpdates`**  
   Ваш бот пытается получить новые сообщения от Telegram API, используя метод `getUpdates` (Long Polling).

2. **`http2: Transport received Server's graceful shutdown GOAWAY`**  
   Сервер Telegram использует протокол HTTP/2. Время от времени сервер инициирует graceful shutdown (корректное завершение) соединения и отправляет клиенту кадр `GOAWAY`. Это означает: *"Я закрываю это соединение, не отправляй сюда новые запросы, но я завершу обработку текущего"*. Для Long Polling, где соединение держится открытым до 50–60 секунд, это **абсолютно нормальное и ожидаемое поведение** серверов Telegram.

3. **`cannot retry err ... after Request.Body was written`**  
   Когда соединение закрывается, стандартный HTTP-клиент Go (`net/http`) пытается быть "умным" и автоматически повторить (retry) запрос на новом соединении. Однако он видит, что тело запроса (`Request.Body`) уже было отправлено в сеть. Из соображений безопасности Go **не может** автоматически повторить POST-запрос, так как он не знает, как заново прочитать или воссоздать тело запроса (оно уже "выпито" из потока).

4. **`define Request.GetBody to avoid this error`**  
   Это прямая подсказка от стандартной библиотеки Go. Чтобы клиент мог безопасно повторить запрос, у объекта `http.Request` должна быть определена функция `GetBody`, которая возвращает новую копию тела запроса для повторной отправки.

### 🛠️ Почему это происходит и как это исправить

Корень проблемы не в вашем коде напрямую, а в том, как библиотека для работы с Telegram Bot API, которую вы используете, формирует HTTP-запросы.

#### Решение 1: Обновите библиотеку Telegram-бота (Рекомендуемое)
Скорее всего, вы используете устаревшую версию популярной библиотеки (например, `go-telegram-bot-api` или подобную). Разработчики этих библиотек уже столкнулись с этой проблемой и исправили ее, добавив корректную обработку `GetBody` или изменив способ передачи параметров (например, через URL-параметры вместо JSON-body для `getUpdates`, или правильно клонируя тело запроса).
👉 **Действие:** Выполните `go get -u <путь_к_вашей_библиотеке>` и обновите зависимости.

#### Решение 2: Перейдите на Webhooks
Метод `getUpdates` (Long Polling) по своей природе держит соединение открытым, что делает его уязвимым для таких разрывов. Использование Webhook'ов (где Telegram сам присылает POST-запрос на ваш сервер) полностью исключает эту ошибку, так как ваш сервер не инициирует длинные исходящие соединения к API Telegram.
👉 **Действие:** Если ваш бот размещен на сервере с белым IP или за ngrok/cloudflare, настройте `SetWebhook`.

#### Решение 3: Если вы пишете HTTP-клиент самостоятельно
Если вы не используете готовую библиотеку, а делаете запросы через стандартный `net/http`, вам нужно явно указать `GetBody` при создании запроса. Пример:

```go
bodyBytes, err := json.Marshal(payload)
if err != nil {
    // обработка ошибки
}

req, err := http.NewRequest("POST", url, bytes.NewBuffer(bodyBytes))
if err != nil {
    // обработка ошибки
}

// ДОБАВИТЬ ЭТУ СТРОКУ:
req.GetBody = func() (io.ReadCloser, error) {
    return io.NopCloser(bytes.NewBuffer(bodyBytes)), nil
}
req.Body, _ = req.GetBody() // Устанавливаем тело для первого запроса

resp, err := http.DefaultClient.Do(req)
```

#### Решение 4: Игнорировать ошибку (если бот переподключается)
Обратите внимание на уровень логирования: `level=INFO`, хотя внутри сообщения есть `[ERROR]`. Если после этой ошибки ваш бот **успешно делает следующий запрос** и продолжает работать, то это просто "шум" в логах. Go-клиент не смог сделать *автоматический* retry, но ваш основной цикл бота (`for { getUpdates() }`) просто перейдет к следующей итерации и успешно установит новое соединение.  
👉 **Действие:** Убедитесь, что у вас есть механизм повторных попыток (retry loop) с небольшой задержкой (например, 1-2 секунды) при ошибке получения обновлений. Если он есть, эту ошибку можно просто отфильтровать или понизить уровень ее логирования до `DEBUG`.

### Резюме
Сервер Telegram корректно закрыл старое соединение. Ваш Go-клиент попытался его восстановить, но не смог из-за особенностей работы с телом POST-запроса. **Обновление библиотеки бота до последней версии** решает эту проблему в 99% случаев.

## Теперь имеет смылс разобрать, что такое retry loop и проанализировать риски от таких повторыных запросов.


### 1. Краткое определение  
**Ретрай** (от английского *retry* – «повторить») – это действие, когда вы снова выполняете тот же самый процесс, действие, запрос или эксперимент, чтобы получить более надёжный результат или убедиться в правильности полученных данных.

### 2. Почему это важно  
- **Ошибка в процессе**: иногда что‑то идёт не так (например, сеть падает, устройство не отвечает).  
- **Случайность**: в экспериментах измерения могут колебаться, и повторение помогает усреднить результат.  
- **Удостовериться**: проверяем, что результат воспроизводим, а не случайный.

### 3. Примеры из разных областей  


| Область | Что повторяют | Зачем |
|---------|---------------|-------|
| **Интернет‑запросы** | Отправка HTTP‑запроса к серверу | Сервер может временно недоступен, повторение повышает вероятность получения ответа |
| **База данных** | Запрос к таблице, если соединение потеряно | Повторный запрос восстанавливает связь и получает нужные данные |
| **Эксперименты** | Измерение температуры в лаборатории | Повторяем, чтобы исключить «шум» и получить более точную среднюю величину |
| **Приготовление пищи** | Тестируем рецепт, если результат не соответствует ожиданиям | Повторяем, чтобы понять, где произошла ошибка и как её исправить |


### 4. Как обычно реализуется ретрай  

1. **Попытка** – выполняем действие.  
2. **Проверка** – смотрим, успешна ли попытка (ответ 200 %? Ошибки?).
3. **Решение** – если неудача, определяем, стоит ли повторять.  
4. **Повтор** – снова выполняем действие, иногда с небольшим «паузы» (подождать 1–2 сек).  
5. **Ограничение** – задаём максимум повторов (например, 3–5 раз) и/или таймаут, чтобы не застрять в бесконечном цикле.

### 5. Итог  
Ретрай – это простая, но мощная стратегия, позволяющая сделать процессы более надёжными. Он помогает избежать ошибок, вызванных внешними условиями, и повышает точность результатов как в программировании, так и в научных исследованиях.


### Рецензия Критика


**Сильные стороны:**
1.  **Структура:** Логика разделения на состояния (Pre-send, In-flight, Completed) — это «золотой стандарт» для проектирования сетевых протоколов.
2.  **Идемпотентность:** Правильно выделен критический риск дублирования данных.
3.  **Backoff & Jitter:** Упомянуты обязательные механизмы защиты от Retry Storm.

**Слабые стороны и ошибки (требуют немедленной доработки):**
1.  **Отсутствие нюанса по Last Stream ID:** В спецификации HTTP/2 `GOAWAY` содержит `Last Stream ID`. Клиент **обязан** проверить, входит ли ID его текущего запроса в диапазон обработанных сервером запросов. Если ID запроса больше, чем `Last Stream ID`, значит, сервер *точно не получил* этот запрос. Это ключевой момент для автоматического ретрая.
2.  **Размытость ответственности Go Standard Library:** Вы пишете «в Go это проверяется через `context.Done()`». Это не совсем так. `context.Done()` сигнализирует о завершении контекста (таймаут или отмена), а не о получении кадра `GOAWAY` от сервера. Нужно уточнить, что стандартный `http.Transport` в Go уже умеет обрабатывать `GOAWAY` для большинства случаев, и ручная обработка нужна только при написании кастомных протоколов или специфических gRPC-интерцепторов.
3.  **Недостаточная детализация gRPC:** Если система на Go использует gRPC, логика `GOAWAY` сильно завязана на `Subchannels` и `Load Balancing`. Стоит упомянуть, что gRPC сам управляет пулом соединений и ретраями (через `ServiceConfig`).
4.  **Отсутствие упоминания "Circuit Breaker":** В высоконагруженных системах ретраи без прерывателя (Circuit Breaker) могут добить сервер, который уже находится в состоянии Graceful Shutdown из-за перегрузки.

# Стратегия обработки GOAWAY в высоконагруженных системах на Go

Протокол `GOAWAY` (HTTP/2, gRPC) — это механизм управляемого завершения сессии. Он сообщает клиенту: *«Я прекращаю принимать новые запросы на этом соединении, но завершу обработку тех, что уже получил»*.

Для разработчика на Go критически важно правильно интерпретировать этот сигнал, чтобы избежать потери данных или дублирования транзакций.

---

### 1. Анализ состояния запроса и Last Stream ID
При получении `GOAWAY` клиент должен сопоставить идентификатор текущего запроса (Stream ID) с полем `Last Stream ID` в кадре `GOAWAY`.

*   **Сценарий А (Stream ID <= Last Stream ID):** Сервер подтвердил получение запроса и начал его обработку.
*   **Сценарий Б (Stream ID > Last Stream ID):** Сервер не успел принять запрос в очередь. Запрос гарантированно не был обработан.

**Действие:**
- Если **Сценарий А**: Запрос находится в "серой зоне". Мы не знаем, завершил ли сервер обработку или упал в процессе.
- Если **Сценарий Б**: Запрос можно безопасно повторить немедленно.

### 2. Классификация запросов и стратегия ретрая
Решение о повторной отправке зависит от **идемпотентности** операции.

#### А. Неидемпотентные запросы (напр. `POST /payments`)
*   **Риск:** Двойное списание, создание дубликатов.
*   **Логика:** Если получен `GOAWAY` и запрос находится в "серой зоне" (Сценарий А), **ретрай запрещен**.
*   **Решение:** Клиент должен вернуть ошибку (например, `503 Service Unavailable` или кастомный статус), чтобы вызывающая сторона могла проверить статус транзакции через отдельный API (GET) или вручную.

#### Б. Идемпотентные запросы (напр. `GET`, `PUT` с ключом идемпотентности)
*   **Риск:** Минимальный (повтор операции не меняет результат).
*   **Логика:** Если получен `GOAWAY`, запрос можно повторить.
*   **Решение:** Автоматический ретрай через новое соединение.

### 3. Техническая реализация в Go

#### Использование стандартных библиотек
Если вы используете `net/http` с `http.Transport` или стандартный `grpc-go`:
- **Автоматизация:** Стандартные библиотеки Go уже умеют обрабатывать `GOAWAY`. Они помечают соединение как "draining" и начинают открывать новые соединения для новых запросов.
- **Ваша задача:** Настроить `MaxIdleConnsPerHost` и `IdleConnTimeout`, чтобы пул соединений оперативно обновлялся.

#### Кастомная реализация (Custom Transport / gRPC Interceptors)
Если вы пишете низкоуровневый клиент или сложную логику ретраев:
1.  **Connection Pooling:** При получении `GOAWAY` соединение должно быть немедленно исключено из активного пула.
2.  **Exponential Backoff + Jitter:**
    - Используйте формулу: $delay = min(cap, base \cdot 2^{attempt}) + jitter$
    - *Jitter* (случайное смещение) критически важен для предотвращения "эффекта стада" (Thundering Herd).
3.  **Circuit Breaker:** Внедрите паттерн "Прерыватель" (например, библиотеку `sony/gobreaker`). Если сервер массово шлет `GOAWAY`, прерыватель должен временно прекратить попытки отправки запросов, давая серверу время на завершение работы.

### 4. Алгоритм действий для клиента (Step-by-Step)

1.  **Получен GOAWAY:**
    - Извлечь `Last Stream ID`.
    - Проверить текущий запрос:
        - Если `ID > Last Stream ID` $\rightarrow$ **Ретрай** (выбрать новое соединение + Backoff).
        - Если `ID <= Last Stream ID` $\rightarrow$ **Проверка идемпотентности**:
            - Идемпотентный $\rightarrow$ **Ретрай**.
            - Неидемпотентный $\rightarrow$ **Ошибка** (прервать цикл, вернуть статус "Unknown").
2.  **Обновление пула:**
    - Пометить текущее соединение как `Closing`.
    - Инициировать `Pre-warming` (открытие нового соединения до того, как старое закроется).
3.  **Логирование:**
    - Зафиксировать событие `GOAWAY` для мониторинга (это сигнал о том, что сервер перегружен или перезагружается).
