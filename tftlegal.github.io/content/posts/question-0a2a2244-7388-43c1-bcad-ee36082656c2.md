To build a truly fault-tolerant Vault cluster you need to think in terms of independent failure domains, not a single "HA" checkbox. Vault's fault tolerance is a composition of several layers, each of which must survive its own class of failure: the storage backend, the network, the unseal mechanism, TLS, and the operational procedures around them. A cluster that still dies when your KMS key is rotated, or when your S3 bucket is unavailable, is not actually fault-tolerant. You need to enumerate every dependency and ask what happens when it goes away.

Start with the storage backend and quorum. The simplest and most self-contained option is Vault's integrated Raft storage. Run an odd number of nodes, three or five, so the cluster survives the loss of floor(N/2) members. Each node stores its own Raft log on local disk; no external storage is required. The critical constraint is that all Raft nodes must be in the same availability zone or have less than ten milliseconds of round-trip time between them, because Raft log replication is synchronous. Cross-AZ is fine; cross-region is not for the primary cluster. A hidden problem here is that if your local disk is a single SSD, a disk failure kills that node's data and its vote. Use RAID-1 or a replicated volume. If you run Vault in a container on Kubernetes, the local disk is ephemeral by default, so you must use a StatefulSet with a persistent volume or a local PV, or the pod will lose its Raft data on reschedule.

The alternative is an external storage backend such as S3, Postgres, Consul, or etcd. In that model the Vault nodes are stateless and any node can serve any request, but the storage backend becomes your single point of failure. If S3 is down, Vault is down; you have merely moved the problem. Postgres gives you strong consistency but introduces a database dependency. Consul or etcd give you Raft, but now you are operating two Raft groups. Prefer this approach only if you already have a highly available Postgres or Consul cluster, or if you need Vault nodes to be truly stateless for easy horizontal scaling.

For network and transport, every node must reach every other node on the Raft port, default 8201, and the API port, 8200. Put nodes in at least two availability zones or data centers. Place a load balancer, whether HAProxy, nginx, or a cloud ALB, in front of the API port so clients get a single endpoint. Use L7 load balancing with a health check hitting the sys/health endpoint with the standbyok parameter set to true, so standby nodes are considered healthy for reads but a fully sealed cluster returns a 503. The Raft port must be directly reachable between nodes and should not go through the load balancer. Enable TLS everywhere; mutual TLS is preferable if you want to prevent unauthorized nodes from joining the Raft group. Keep a consistent time source via NTP across all nodes.

The unseal strategy is the most overlooked failure domain. A Vault cluster that is sealed is a cluster that is down. Every node must be unsealed before it can serve traffic. With Shamir secret sharing, you need a threshold of key holders, say three out of five, and if those humans are unavailable you are sealed. With auto-unseal via a cloud KMS, you are fully automated but now depend on the cloud provider's KMS; if AWS KMS is degraded in your region, your Vault is sealed. A PKI-based auto-unseal removes the cloud dependency but requires you to manage the CA, and if the CA private key is lost you are sealed. The recommendation for true fault tolerance is a hybrid: use KMS as the primary auto-unseal mechanism for speed, and keep a Shamir fallback with shares held by three different teams in three different physical locations. Also note that auto-unseal keys are per-node; if you add a new node you must generate a new key or use a shared key, and if you rotate the KMS key you must re-unseal all nodes. Plan the rotation procedure before you need it.

For multi-site or geo-distribution, use performance replication. The primary site holds the Raft quorum and handles all writes. The secondary site runs a standby Raft cluster that is read-only until you promote it. Keep the replication lag low by co-locating the secondary close enough for sub-second sync, though in practice replication is asynchronous and you will lose the last few seconds of writes during a failover. If you need zero data loss you need synchronous replication, which means same-region and defeats the purpose of disaster recovery. The promotion is a manual, multi-step operation: unseal the secondary, set it as active, update DNS or the load balancer. Your RTO is minutes to hours, not seconds. If you need automatic failover you need a separate orchestration layer. Vault 1.11 and later also offer DR replication where the secondary can accept writes if the primary is unreachable, but with a split-brain risk if the primary comes back. Test the failover with a game-day where you kill the primary region and measure your actual RTO and RPO. Most teams discover they cannot unseal the secondary because the KMS key ARN is hardcoded.

On the operational side, set max_lease_ttl and unseal thresholds so a single node loss does not seal the cluster. Run each node on its own VM or instance; never co-locate two Raft peers on the same host. For Raft storage, use NVMe SSDs or equivalent, size the disk for total secrets times average size times two for log and snapshots plus headroom, and enable snapshot retention tuning. For external storage, use a managed HA Postgres with point-in-time recovery, or enable S3 versioning and place the bucket in a different AZ. Backups are critical: for Raft use the operator raft snapshot save command, which gives a point-in-time snapshot, but a snapshot without the unseal keys is useless, so back up the KMS key metadata or Shamir shares separately. For external storage, back up the backend itself.

Monitoring must distinguish between a sealed cluster and an unsealed cluster with no traffic. A naive health check will report a sealed Vault as healthy. Alert on sealed state, leader changes, follower lag, disk usage above 80 percent, and KMS API errors. Check the sys/health endpoint for sealed and standby status, the sys/raft/autopilot endpoint for leader and follower health, and the sys/raft/leader endpoint for who currently holds the leadership. A permanently unhealthy follower degrades your quorum margin, so do not ignore autopilot warnings.

For upgrades, Vault Raft upgrades are rolling: upgrade followers first, then the leader. If you upgrade the storage backend, such as a Postgres major version, while Vault is running, you can corrupt the data, so coordinate the two. For TLS certificate management, Vault's own certificates must be rotated. If you use a short-lived certificate and the rotation fails, the cluster goes down. Use Vault itself to issue its own certificates, bootstrapping with a long-lived cert and then switching to auto-issued certs, or use a dedicated CA with automated rotation.

On the client side, point applications at the load balancer VIP, enable retry with exponential backoff, and use AppRole or CIAR tokens rather than caching a root token, so a brief leader election does not break authentication.

A useful checklist of common pitfalls: three Raft nodes in the same AZ means one AZ outage kills the quorum. No fallback unseal mechanism means a KMS outage is a permanent seal. The Raft port behind a firewall that drops it means nodes cannot form quorum after a restart. No disk monitoring on Raft nodes means a full disk crashes the node and loses quorum. A single KMS key for all nodes means key rotation requires re-unsealing all nodes simultaneously. No DR failover test means you discover the procedure is broken during the actual outage. Vault in a container without persistent storage means a pod reschedule is data loss. Ignoring raft autopilot means a permanently unhealthy follower silently degrades your quorum margin.

A reference production architecture in multi-region would look like this. In the primary region, run five Vault nodes on Raft, each on a separate instance spread across three availability zones, with NVMe SSD storage, auto-unseal via the regional KMS, a Shamir fallback with shares held by three teams in three cities, and TLS from an internal CA with 90-day auto-rotated certs. Put an L7 load balancer in front with health checks on the sys/health endpoint. Keep the Raft port on direct VPC peering, not behind the load balancer. Monitor with Prometheus and Alertmanager for sealed state, leader changes, disk usage, and KMS errors. In the secondary region, run three Vault nodes as a performance replication target with its own regional KMS for auto-unseal and the same Shamir shares as the primary, behind its own load balancer for read-only traffic. The DR procedure is: verify the primary is unreachable for more than five minutes, unseal the secondary via KMS or Shamir, promote it with the raft autostandby command, update DNS or the load balancer to point to the secondary, verify writes, and later rebuild the primary and re-attach it as the new secondary.

The deeper question is that fault tolerance in Vault is ultimately about who holds the keys to the kingdom. The software can be perfectly replicated, but if the KMS key is in one region, the Shamir shares are in one person's email, the CA private key is on one laptop, and the backup is in the same S3 bucket as the primary, then you have a single point of failure in the operational layer, and no amount of Raft nodes will save you. Design the human and organizational redundancy as carefully as the technical one. In short: an odd number of Raft nodes across failure domains, TLS and a load balancer in front, a hybrid auto-unseal with a manual fallback, asynchronous replication for multi-site, and a tested, rehearsed DR procedure. That gives you a cluster that survives the loss of any single node, zone, or even an entire secondary site without data loss.
