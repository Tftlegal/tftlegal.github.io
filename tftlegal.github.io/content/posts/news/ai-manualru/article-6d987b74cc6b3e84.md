# Как проверить, видят ли ИИ-боты ChatGPT, Perplexity и Яндекса текст вашего сайта

## Краткое содержание

Текст представляет собой заголовок статьи, посвящённой проверке того, получает ли поисковый ИИ-бот доступ к тексту сайта. Описан процесс из четырёх шагов, позволяющий убедиться в успешном индексировании контента нейросетевыми поисковыми системами. Первый этап связан с анализом правил robots.txt, которые могут блокировать бот. Второй предполагает изучение запросов в серверных логах. Третий шаг — сверка IP-адресов бота с ожидаемыми. Четвёртый включает проверку HTTP-кодов ответов (403, 429, 5xx) и использование команды curl с контрольным слотом для финальной валидации. Таким образом, материал ориентирован на вебмастеров и SEO-специалистов, которым важно гарантировать видимость контента для ИИ-поиска.

## Полная статья

## Короткий ответ: три уровня проверки и что они доказывают

Проверка складывается из трёх уровней. Первый: правила robots.txt для конкретного агента. Второй: фактические запросы в серверных логах со сверкой IP. Третий: HTTP-ответ и HTML, который реально получил клиент. Ручной запрос через curl помогает увидеть тело ответа и найти в нём контрольное слово.

Успешная загрузка HTML подтверждает доступность страницы для конкретного запроса. Она не доказывает индексацию, попадание в ответ ChatGPT или цитирование в Perplexity. Это разные состояния, и между ними остаются решение поисковика, кэш, отбор источников и формулировка запроса.

Порядок такой. Сначала определите, какой агент важен: OAI-SearchBot для поиска ChatGPT, PerplexityBot для поиска Perplexity, роботы Яндекса для Алисы AI и YandexGPT. Затем проверьте robots.txt под этого агента. После этого ищите его запросы в access log и подтверждайте IP. В конце повторите запрос через curl и проверьте, есть ли в HTML контрольное слово. Если сайт за CDN, смотрите и журнал CDN: часть запросов до сервера не доходит.

## Какой именно бот вам нужен: OAI-SearchBot, GPTBot, ChatGPT-User, PerplexityBot, Perplexity-User

Имена агентов отличаются по задаче. Ошибка — проверять GPTBot, когда нужен поиск ChatGPT, или закрывать OAI-SearchBot, думая, что запрещаете обучение.

### Чем поисковый бот отличается от бота обучения и бота по запросу пользователя

Поисковый обход влияет на видимость в ответах. OAI-SearchBot обслуживает поиск ChatGPT. PerplexityBot ищет и цитирует сайты в Perplexity. Perplexity заявляет, что PerplexityBot не собирает контент для обучения базовых моделей. Бот обучения собирает контент для возможного обучения моделей. GPTBot относится к этой категории. Пользовательский fetch выполняется по запросу живого человека: ChatGPT-User и Perplexity-User загружают страницу разово, а не обходят сайт автоматически.

Практическое следствие: Disallow для GPTBot ограничивает сбор для обучения, но не убирает сайт из поиска ChatGPT. Disallow для OAI-SearchBot закрывает поисковому агенту доступ и может убрать страницу из поисковой выдачи ChatGPT. Для Perplexity запрет PerplexityBot ограничивает полнотекстовую индексацию, но домен, заголовок и краткое факт-резюме могут оставаться в ответах. Этот нюанс стоит учитывать при проверке.

ChatGPT-User выполняет действия по запросу пользователя, не обходит веб автоматически, и robots.txt может к нему не применяться. Perplexity-User, по документации Perplexity, обычно игнорирует robots.txt, потому что запрос инициировал человек.

| Агент | Назначение | robots.txt | Что проверять |
| --- | --- | --- | --- |
| OAI-SearchBot | Поиск ChatGPT | Да, проверять разрешение поискового обхода | Allow для нужных путей и доступ с опубликованных IP OpenAI |
| GPTBot | Сбор контента для возможного обучения моделей OpenAI | Да, запрет относится к обучению | Не путать с поиском ChatGPT |
| ChatGPT-User | Действия по запросу пользователя | Может не применяться | Разовые запросы, автоматический обход не выполняется |
| PerplexityBot | Поиск и цитирование в Perplexity | Да, по документации соблюдает | Сверка с диапазонами именно PerplexityBot |
| Perplexity-User | Загрузка страницы по запросу живого пользователя | Обычно игнорирует | Разовые запросы, отдельные диапазоны IP |
| Роботы Яндекса | Индексация и отдельные задачи, включая Алису AI и YandexGPT | Зависит от робота; у Алисы AI и YandexGPT общие правила не действуют | Обратный и прямой DNS, конкретное имя робота |

Если задача — попасть в ответы, начинайте с OAI-SearchBot и PerplexityBot. GPTBot проверяйте отдельно, если вам важен контроль обучения. Для Яндекса смотрите на конкретного робота и учитывайте, что у Алисы AI и YandexGPT отдельные имена, а общие правила robots.txt на них не действуют.

## Шаг 1. Проверяем robots.txt для конкретного агента

Откройте robots.txt и найдите блок User-agent для нужного агента. Сначала применяются правила для конкретного агента, затем общие. Проверьте, нет ли Disallow на путь, который хотите открыть. Уберите конфликтующие правила: если один блок закрывает раздел, а другой открывает, робот может выбрать более строгое правило.

Статусы по RFC 9309. Если robots.txt отвечает 404 или другим 4xx, который означает отсутствие файла, краулер вправе обходить сайт. Если файл недоступен из-за серверной или сетевой ошибки, робот должен считать обход полностью запрещённым. Поэтому 5xx на robots.txt опаснее, чем 404.

После правки откройте файл сразу и убедитесь, что отдаётся новая версия. Кэш или WAF могут держать старую. Учёт правил не мгновенный: Google кэширует содержимое robots.txt до 24 часов, OpenAI пишет примерно о 24 часах до подстройки систем, и это сказано про поиск ChatGPT. Запрет не отзывает уже собранные данные: robots.txt управляет будущими обходами, а не прошлыми.

robots.txt — это запрос, который боты должны соблюдать, но не обязаны. Файл не удаляет страницу из индекса и не гарантирует деиндексацию. Директиву noindex в robots.txt не поддерживают ни Google, ни Яндекс.

Готовый пример конфигурации с Allow для GPTBot, OAI-SearchBot, ClaudeBot и PerplexityBot и точечным Disallow для служебных путей разобран в[гайде по robots.txt для AI-краулеров](https://ai-manual.ru/article/aeo-i-geo-v-2026-kak-nastroit-robotstxt-dlya-ai-kraulerov-i-ne-poteryat-vidimost-v-otvetah-nejrosetej).

Чек-лист:

- файл отдаётся с кодом 200;
- в нём есть секция User-agent для нужного агента;
- на нужный путь нет Disallow;
- нет конфликтующих правил и синтаксических ошибок;
- после правки отдаётся новая версия файла, а не копия из кэша.

### Почему Allow: / не равен доступу

Allow: / означает только, что robots.txt не запрещает обход. Запрос проходит цепочку: CDN или reverse proxy, WAF или bot protection, затем HTML. Отказ на любом уровне делает страницу недоступной независимо от Allow.

Типичные причины: 403 из-за bot mitigation, JavaScript challenge, CAPTCHA, authentication, географические ограничения, rate limiting. Если сайт за CDN, запрос мог остановиться на защите и не дойти до сервера. Причина ищется в журнале CDN или WAF, а не в robots.txt.

OpenAI в справке по поиску ChatGPT рекомендует разрешить OAI-SearchBot и отдельно убедиться, что хостинг или CDN пропускает трафик с опубликованных IP поискового краулера.

## Шаг 2. Ищем запросы ботов в серверных логах и подтверждаем IP

Смотрите access log веб-сервера. Если перед сайтом стоит CDN или WAF, часть запросов до origin-лога не доходит: их видно только в журнале сервиса. Ищите строку User-Agent с именем агента, путь, код ответа и дату.

```
198.51.100.24 - - [26/Nov/2026:10:14:22 +0300] 'GET /blog/ai-agents/ HTTP/1.1' 200 48213 '-' 'Mozilla/5.0 (compatible; OAI-SearchBot)'
```

Поля: IP отправителя, дата и время с часовым поясом, метод и путь, код ответа, размер ответа, referrer, User-Agent. По этой строке видно, что запрос был, но не видно, настоящий ли это бот.

User-Agent можно подделать: HTTP-клиент ставит произвольную строку. Запись GPTBot или OAI-SearchBot в логе сама по себе не доказывает происхождение запроса. Сверяйте IP с официальными диапазонами конкретного сервиса. У Perplexity каждому агенту соответствует свой список IP, поэтому User-Agent нужно сопоставлять с диапазонами именно этого агента. OpenAI публикует отдельные файлы для OAI-SearchBot, GPTBot и ChatGPT-User; диапазоны меняются, их нельзя один раз прописать и считать неизменными.

У Perplexity есть задокументированный случай, когда запрос к странице, закрытой в robots.txt, пришёл под видом обычного Chrome. Официальная документация при этом утверждает, что PerplexityBot соблюдает robots.txt. Вывод для проверки один: одного User-Agent недостаточно, нужна сверка IP и анализ поведения.

Пустой результат поиска по логам не диагноз. Бот мог не приходить, запрос мог обслужить CDN, лог мог ротироваться. Блокировку подтверждает отказ в логе WAF или CDN.

### Проверка робота Яндекса через обратный и прямой DNS

Для Яндекса методика отличается от проверки по опубликованным диапазонам. Возьмите IP из лога и сделайте обратный DNS-запрос. Имя хоста должно принадлежать домену Яндекса, указанному в[справке Вебмастера](https://yandex.ru/support/webmaster/ru/robot-workings/check-yandex-robots). Затем сделайте прямой DNS-запрос по этому имени: полученный IP должен совпасть с исходным.

Обратный DNS без прямого не защищает от подделки: злоумышленник может настроить PTR-запись. Прямой запрос подтверждает, что имя действительно ведёт на тот же IP. Некоторые роботы Яндекса скачивают документы не для индексации и могут не учитывать ограничивающие директивы robots.txt, предназначенные для произвольных роботов. Поэтому проверяйте именно того робота, который важен для Алисы AI или YandexGPT. Для обычного YandexBot и для роботов Алисы AI и YandexGPT проверка строится вокруг DNS, но правила robots.txt у них различаются.

## Шаг 3. Читаем HTTP-ответы: 403, 429, 5xx и цепочки редиректов

Код ответа показывает, где искать причину. 403 значит доступ запрещён, часто это bot mitigation. 429 значит превышен лимит запросов. 5xx значит ошибка сервера, прокси или CDN. При таких кодах смотрите журнал CDN, WAF или антибот-защиты, а не только лог сервера.

| Код или симптом | Где искать | Что просить исправить |
| --- | --- | --- |
| 403 | CDN, WAF, bot protection, origin | Разрешить IP-диапазоны агента, снять JS challenge для поискового бота, проверить правила блокировки |
| 429 | CDN, WAF, origin | Поднять лимит для поисковых IP, проверить burst-правила |
| 5xx | Origin, reverse proxy, CDN | Смотреть логи ошибок, таймауты, коды 502 и 504 |
| 301 или 302 в цепочке | CDN, приложение, балансировщик | Убрать редирект на challenge-страницу или другой домен, проверить циклы |
| 200 с проверкой посетителя | WAF, bot protection | Отключить challenge для конкретного агента |

Редиректы 301 и 302 могут уводить на страницу проверки, на другой домен или зацикливаться. Бот может не пройти цепочку так, как браузер. Проверяйте конечный код и каждый шаг цепочки:`curl -I -L`покажет заголовки.

Типичные инфраструктурные причины сбоев: 403 Forbidden из-за bot mitigation, JavaScript challenges, CAPTCHA, authentication, географические ограничения, rate limiting. Если сайт за Cloudflare, включённый Bot Fight Mode не обходится правилами WAF: он может проверять ботов Perplexity даже при разрешающем правиле. Это отдельный пункт для разработчика.

## Шаг 4. Ручная проверка через curl: заголовки, HTML и контрольное слово

curl повторяет HTTP-запрос, но не исполняет JavaScript. Этого достаточно, чтобы увидеть заголовки, код ответа и исходный HTML. Запрос выполняйте с User-Agent нужного агента, сохраняйте заголовки и тело в разные файлы.

```
curl -L -A 'Mozilla/5.0 (compatible; OAI-SearchBot)' -D headers.txt -o page.html 'АДРЕС_СТРАНИЦЫ'
```

Флаг -L следует редиректам, -A задаёт User-Agent, -D сохраняет заголовки, -o сохраняет тело. После запроса посмотрите`head -n 40 headers.txt`, размер`wc -c page.html`и поищите контрольное слово:`grep -i 'контрольное-слово' page.html`.

Контрольное слово берите из середины статьи. Оно должно быть уникальным и не встречаться в меню, заголовке или мета-описании. Если слова нет, код 200 сам по себе ничего не доказывает.

Ловушки. Первая: ответ 200, но в теле страница проверки посетителя или пустой каркас приложения. Вторая: текст подгружается через JavaScript и в исходном HTML отсутствует. Третья: редирект на challenge-страницу. Сравните размер и содержимое HTML с тем, что видит браузер, поищите в заголовках и теле признаки challenge, CAPTCHA, проверки.

### Почему 200 OK со страницей проверки — худший вариант

Сервер отвечает 200, контента нет. Формально запрос успешен, фактически бот получил заглушку антибот-защиты или пустой каркас. Признаки: контрольное слово не найдено, HTML подозрительно короткий, в нём есть скрипты challenge. Всегда проверяйте тело, а не только статус.

Если текст есть в браузере, но отсутствует в HTML, проверка через curl не подтвердит доступ. Для страниц с клиентским рендерингом нужен другой инструмент или проверка у разработчика. Часть ИИ-краулеров не исполняет JavaScript, поэтому текст, который появляется только в браузере, может быть для них невидим. Подробнее о том, как ИИ-сервисы читают фрагменты страницы и почему JS-контент до них не доходит, написано в[разборе GEO-проверки сайта](https://ai-manual.ru/article/pochemu-nejroseti-putayut-vash-produkt-s-konkurentom-i-kak-eto-ispravit-geo-proverka-sajta).

## Что делать, если бот заблокирован: бриф для разработчика

Соберите пакет, чтобы разработчик не гадал. В него входят: дата и время запроса с часовым поясом, IP, User-Agent, путь, код ответа, размер ответа и фрагмент access log. Добавьте результат curl: headers.txt, page.html и строку с поиском контрольного слова.

Укажите, где искать событие: origin-лог, журнал CDN, WAF, антибот-защита. Пришлите код ответа и цепочку редиректов. Если есть 403, 429 или 5xx, приложите запись из журнала соответствующего уровня.

Что просить: разрешить IP-диапазоны конкретного агента в WAF или bot protection; снять JS challenge для поисковых ботов; проверить правила редиректов; убедиться, что robots.txt отдаётся с 200. Для Perplexity в[документации](https://docs.perplexity.ai/docs/resources/perplexity-crawlers)отдельно сказано, что при использовании WAF может понадобиться явно разрешить ботов. Для AWS WAF рекомендуют IP-наборы и правила, которые сопоставляют IP с User-Agent, с более низким приоритетом, чем блокирующие правила.

Не просите «разрешить всех ботов». Это ослабляет защиту. Правки делайте точечно под агента: OAI-SearchBot, PerplexityBot или конкретного робота Яндекса. IP-диапазоны меняются, поэтому правило нужно поддерживать, а не записывать один раз.

Как устроена современная детекция ботов и почему WAF и капча ошибаются, описано в[материале о детекции ботов](https://ai-manual.ru/article/investitsii-v-detektsiyu-botov-kak-spur-intelligence-boretsya-s-nechelovecheskim-trafikom-kotoryij-k-2026-godu-obgonit-lyudej).

## Почему успешная загрузка HTML ещё не доказывает индексацию

Разведите три состояния. Первое: страница доступна боту. Второе: страница проиндексирована. Третье: страница цитируется в ответах ИИ. Доступность — необходимое условие, но не достаточное. Между ними остаются решение поисковика, кэш, отбор источников и формулировка запроса.

Запись OAI-SearchBot, GET /article, 200 подтверждает успешную отдачу страницы этому запросу. Она не доказывает, что страница получила ранжирование, вошла в конкретный сгенерированный ответ или была процитирована. Запись GPTBot, GET /article, 200 показывает доступ краулера к URL, но не доказывает включение документа в обучающий датасет.

Успешная проверка через curl означает, что сервер отдал HTML с контрольным словом. Это гигиенический минимум. Дальше смотрите на индексацию в панелях вебмастера, на фактические упоминания страницы в ответах ИИ и на то, какие фрагменты сервисы цитируют. Сроки не обещайте: механика отбора источников у разных сервисов различается.
