# Smartsheet MCP на AWS: как подключить AI-агентов к рабочим данным через Amazon Quick и Kiro

## Краткое содержание

Smartsheet открыла публичный доступ к своему MCP-серверу, содержащему более 40 инструментов. Эти инструменты охватывают работу с листами, строками, столбцами и автоматизациями платформы. В тексте разбирается архитектура данного сервера. Отдельно рассматриваются два различных пути подключения к нему. Таким образом, Smartsheet делает свою инфраструктуру доступной для интеграции через протокол MCP, расширяя возможности автоматизации и взаимодействия с внешними системами.

## Полная статья

Smartsheet выпустила MCP-сервер в статусе общедоступного (generally available). Через него AI-ассистенты читают, записывают и управляют рабочими данными платформы по стандартизированному протоколу. Протокол покрывает более 40 инструментов: исследование, создание и управление листами, строками, колонками и автоматизациями ([публикация AWS](https://aws.amazon.com/blogs/machine-learning/work-management-context-for-ai-agents-with-smartsheet-mcp-on-aws)).

На практике это означает смену статуса, создание строк и правку структуры проекта естественным языком. Раньше такой сценарий требовал либо ручной работы в интерфейсе, либо отдельной интеграции под каждый ассистент.

На AWS есть два готовых пути к одному и тому же серверу. Amazon Quick подходит бизнес-пользователям, проект-менеджерам и операционным командам: готовый коннектор с OAuth, без кода. Kiro нужен разработчикам: конфигурация MCP через JSON и Personal Access Token. Ниже архитектура, требования, безопасность, сценарии и ограничения. Технические детали, которые подтверждает публикация AWS, идут со ссылкой на неё; то, что в открытой части материала не раскрыто, помечено отдельно.

## Что даёт Smartsheet MCP Server и кому он нужен

Сервер стоит между AI-клиентом и данными Smartsheet и превращает вызовы инструментов в запросы к API. Клиенту не нужно знать структуру API: он видит список из 40 с лишним инструментов и вызывает подходящий. Отсюда два типа пользователей. Первый - тот, кто ведёт работу в Smartsheet и устал обходить листы руками: ему нужен Quick. Второй - разработчик, которому спецификации, задачи и зависимости нужны рядом с кодом: ему нужен Kiro.

Интеграция не заменяет Smartsheet и не создаёт вторую копию портфеля. Она даёт ещё один способ дотянуться до тех же строк, поэтому команда может вести спринт в одной таблице, а обращаться к ней и из чата, и из IDE.

### MCP в одном абзаце: зачем стандартный протокол вместо кастомной интеграции

Model Context Protocol описывает, как AI-клиент узнаёт список доступных инструментов и вызывает их с аргументами. Один MCP-сервер обслуживает любое число клиентов, которые говорят на этом протоколе: сегодня это Amazon Quick и Kiro, завтра появился новый ассистент, и писать коннектор заново не нужно. Без протокола каждая пара «ассистент + система» требует своей интеграции, и число таких пар растёт быстрее, чем команда успевает их поддерживать. Устройство протокола и его экосистему разбирали в материале[MCP в 2026](https://ai-manual.ru/article/mcp-v-2026-kak-universalnyij-protokol-podklyuchaet-ii-agentov-k-lyubyim-instrumentam).

## Архитектура: MCP-сервер как центральный слой между клиентами и Smartsheet API

Схема в публикации AWS простая, и по ней сразу видно, где проходит граница ответственности. Слева MCP-клиенты, в центре Smartsheet MCP Server, справа Smartsheet API и слой данных. Amazon Quick и Kiro подключаются к серверу напрямую как MCP-клиенты, а к API Smartsheet обращается уже сам сервер.

| Слой | Что делает | Граница ответственности |
| --- | --- | --- |
| MCP-клиенты: Amazon Quick, Kiro | Формируют запрос на естественном языке, показывают результат пользователю | Не обращаются к Smartsheet API напрямую |
| Smartsheet MCP Server | Принимает вызовы инструментов, работает в контексте прав конкретного пользователя, обращается к API | Не служит копией портфеля: данные остаются в Smartsheet |
| Smartsheet API и слой данных | Отдают листы, строки, колонки, автоматизации | Источник истины по данным и правам доступа |

Из такой схемы следует практическая вещь: клиенту достаточно один раз пройти вход (OAuth в Quick, токен в Kiro), а дальше все запросы уходят от имени этого пользователя. Именно поэтому один и тот же вопрос даст разный результат двум сотрудникам с разными правами на лист.

### Streamable HTTP MCP и региональные эндпоинты

Транспорт Streamable HTTP MCP означает, что клиент общается с сервером по HTTP-эндпоинту и получает ответ потоком. Практический вывод сугубо инфраструктурный: нужен сетевой доступ к этому эндпоинту. Корпоративный прокси, инспекция TLS или firewall с белым списком доменов умеют ломать такое подключение, причём симптом будет выглядеть как проблема с токеном. Проверять сеть стоит до того, как начнёте отлаживать права.

В описании интеграции упоминаются три региональных эндпоинта: организация выбирает адрес по географии или по требованиям к размещению данных. Конкретные URL и список регионов в опубликованной части материала AWS не приводятся. Их нужно брать в документации Smartsheet, а не восстанавливать по аналогии с другими сервисами. Тот же принцип действует для точных имён полей конфигурации в Kiro.

## Что нужно до подключения: тарифы, доступы и токены

Интеграция не заработает на любом аккаунте. Проверять условия стоит до настройки, иначе половина времени уйдёт на выяснение, почему коннектор не появляется.

- Аккаунт Smartsheet на плане Business, Enterprise или AWM. На младших планах MCP-сервер недоступен, и это ограничение тарифа, а не ошибка конфигурации.
- Способ аутентификации под выбранный клиент: OAuth для Amazon Quick, Personal Access Token для Kiro.
- Для Amazon Quick: соответствующие права внутри самого Quick. Без них коннектор не подключится или не увидит нужные листы.
- Для Kiro: установленная IDE и Node.js в системе.
- Пользователь Smartsheet с доступом к тем листам, которые агент будет читать и менять.

Оговорка по источнику: раздел с предварительными требованиями в опубликованном фрагменте материала AWS обрывается, поэтому чек-лист собран по описанию интеграции. Перед настройкой сверьте формулировки с документацией Smartsheet, особенно состав планов и требования к Node.js. Если ваш план не подходит, дальше читать смысла мало: сначала разговор с аккаунт-менеджером.

### OAuth или Personal Access Token: что выбрать

| Критерий | OAuth в Amazon Quick | Personal Access Token в Kiro |
| --- | --- | --- |
| Кто настраивает | Бизнес-пользователь через коннектор | Разработчик вручную |
| Привязка доступа | К учётной записи Smartsheet конкретного человека | К токену, который создан и хранится у вас |
| Ротация | Управляется платформой | Полностью на вашей стороне |
| Главный риск | Доступ наследует права пользователя | Токен можно случайно закоммитить |
| Как отозвать | Отключить коннектор | Отозвать токен в Smartsheet |

Выбор диктует клиент, а не личные предпочтения: Quick работает через OAuth, Kiro через токен. Если нужны оба сценария, оба способа сосуществуют и обращаются к одним и тем же строкам, так что расхождений в данных не появится.

## Подключение через Amazon Quick: без кода, через готовый коннектор

Amazon Quick - агентное AI-пространство для бизнес-пользователей, проект-менеджеров и операционных команд. В нём задают вопросы, обновляют листы и строят дашборды на естественном языке, без кода. Smartsheet подключается готовым коннектором с OAuth: поднимать собственный сервер не нужно, а вход привязывает сессию к вашей учётной записи Smartsheet.

Что происходит после подключения: чат-агент Quick обращается к Smartsheet MCP Server, вытаскивает нужные строки и отдаёт результат в ответе. Отчёт или дашборд для этого строить не нужно, ответ собирается из живых данных Smartsheet.

Ограничение по правам проявляется быстро. Коннектор работает в контексте пользователя, поэтому лист, закрытый от вас в Smartsheet, Quick не покажет, сколько бы раз вы ни переформулировали запрос. Права внутри Quick проверяются отдельно: без них коннектор может просто не появиться в интерфейсе. Как устроен сам ассистент и что даёт корпоративное развёртывание на AWS, разбирали в[обзоре Amazon Quick](https://ai-manual.ru/article/amazon-quick-vyishel-na-desktop-obzor-korporativnogo-ai-assistenta-s-privatnostyu-i-auditom-na-aws).

### Проверка, что подключение работает

Тестируйте на одном листе, а не на всём портфеле. Попросите агента показать строки конкретного листа или собрать сводку по открытым задачам с владельцами и сроками. Ответ должен содержать реальные имена и даты из вашей таблицы, а не общие рассуждения о том, как обычно выглядит спринт.

Если ответ пустой или неполный, проверяйте по порядку: доступ пользователя к листу в Smartsheet, права в Amazon Quick, затем сетевой доступ к эндпоинту MCP-сервера. Токены и OAuth обычно уже ни при чём, если подключение один раз прошло успешно.

## Подключение через Kiro: JSON-конфигурация MCP и Personal Access Token

Kiro - агентная IDE. С подключённым Smartsheet разработчик ссылается на спецификации проекта, обновляет статусы задач и отслеживает зависимости, не выходя из рабочего процесса разработки. Это тот же MCP-сервер, что и в Quick, просто клиент другой, поэтому данные и правила доступа остаются общими.

Подготовка: установленный Kiro, Node.js и Personal Access Token Smartsheet. Логическая структура конфигурации MCP выглядит так:

- имя сервера, произвольное, чтобы отличать его от других MCP-серверов;
- транспорт: Streamable HTTP MCP;
- URL: адрес регионального эндпоинта Smartsheet;
- заголовок авторизации с Personal Access Token.

Как именно эти четыре элемента раскладываются по полям JSON и где лежит файл конфигурации, зависит от версии Kiro. В опубликованной части материала AWS готовый конфиг не приводится, поэтому сверяйтесь с документацией клиента, а не с примерами из чужих репозиториев: там часто попадаются устаревшие ключи.

Рабочий пример из публикации AWS: разработчик просит Kiro вытащить текущий лист спринта и показать открытые backend-задачи, назначенные ему. Kiro запрашивает Smartsheet через MCP и выводит список прямо в IDE ([AWS](https://aws.amazon.com/blogs/machine-learning/work-management-context-for-ai-agents-with-smartsheet-mcp-on-aws)). Переключение в браузер ради смены статуса исчезает из процесса.

### Безопасное хранение токена и ротация

PAT даёт доступ к рабочим данным и действует до отзыва. Держите конфиг с токеном вне репозитория, подставляйте значение из переменной окружения или локального хранилища секретов, а при подозрении на утечку отзывайте токен и выпускайте новый. Встроенных механизмов защиты токена публикация AWS не описывает, значит ответственность на вашей стороне.

Отдельно про область прав: не выдавайте агенту личный токен администратора аккаунта. Агент получит ровно те права, которые есть у токена, и это самый короткий путь к инциденту в рабочих листах.

## Модель безопасности: права пользователя, контроль организации и промпты

Заявленная модель опирается на три опоры.

- **Проверка прав на уровне пользователя.**MCP-сервер работает в контексте конкретного пользователя Smartsheet, а не от имени некоего суперпользователя интеграции. Что закрыто в интерфейсе, того агент не прочитает и не изменит.
- **Управление AI-функциями на уровне организации.**Администратор аккаунта решает, какие AI-возможности разрешены. Включение ограничивается политикой компании, а не надеждой на сознательность сотрудников.
- **Отсутствие хранения промптов на стороне сервера.**Текст запросов не оседает на MCP-сервере.

Границы этой модели важнее её достоинств. Права пользователя - главный контур: широкий доступ в Smartsheet означает широкие возможности агента, и никакая настройка MCP этого не компенсирует. Отсутствие хранения промптов на сервере не отменяет политик самих клиентов Quick и Kiro и внутренних требований к обработке данных. Детали модели безопасности в опубликованной части материала AWS свёрнуты, поэтому перед корпоративным развёртыванием запросите у вендора актуальную документацию по AI-контролям. Как в экосистеме Quick устроен доступ от имени конкретного зрителя и что это даёт для строк, разбирали в материале про[Live Data in Apps](https://ai-manual.ru/article/amazon-quick-zapuskaet-live-data-in-apps-zhivyie-dannyie-s-razgranicheniem-dostupa-v-prilozheniyah-sobrannyih-ii).

### Что остаётся на стороне команды

- Минимальные права в Smartsheet у всех, кто подключает агента. Рабочие листы под конкретные команды вместо одного «главного» листа на всю компанию.
- Понятный владелец у каждого токена и отдельный токен там, где сценарий не требует личного доступа сотрудника.
- Проверка org-level настроек AI до пилота и после него. Разрешения меняются, и поверхность доступа меняется вместе с ними.
- Дисциплина комментариев к строкам: обсуждение изменения остаётся рядом с данными, а не в чате, который через месяц никто не найдёт.

## Практические сценарии: от сводок по спринту до аудита изменений

Сценарии ниже опираются на примеры из публикации AWS и на логику работы сервера. Для каждого указано, кто пользователь, какой клиент задействован, что на входе и что на выходе.

### Сценарий 1: сводка по заблокированным задачам спринта в Amazon Quick

Пользователь: проект-менеджер или операционная команда. Клиент: Amazon Quick. Вход: вопрос вида «какие задачи спринта заблокированы на этой неделе, кто владельцы и какие сроки». Выход: сводка с именами владельцев и датами, собранная из живых строк листа, без построения отчёта или дашборда.

Ограничение: качество ответа зависит от разметки. Если блокеры отмечаются свободным текстом в комментариях, а не отдельной колонкой статуса, часть задач агент может пропустить. Привести структуру листа в порядок дешевле, чем убеждать модель угадать по формулировке.

### Сценарий 2: обновление статусов из Kiro и Kiro hook

Пользователь: разработчик. Клиент: Kiro. Вход: просьба показать открытые backend-задачи, назначенные этому разработчику, из текущего листа спринта. Выход: список прямо в IDE, без переключения в браузер.

Дальше срабатывает Kiro hook: после коммита исправления он автоматически переводит статус соответствующей строки в Complete. Проверьте до включения одну вещь: hook должен цепляться к нужной строке, а не к похожей с совпадающим названием. Пять минут отладки здесь дешевле месяца неверных статусов в отчётности.

### Сценарий 3: сверка статусов с трекером задач и аудит через комментарии

Сверка: запросить через MCP актуальные статусы задач в Smartsheet и сравнить с тем, что показывает трекер или система тикетов. Расхождения на стыке двух систем - норма, и агент закрывает ручную часть работы: собирает обе стороны в одном ответе. Какой источник считать истинным, решает команда, а не модель.

Аудит: изменения фиксируются через комментарии к строкам. Видно, кто и что поменял, причём рядом с самими данными, а не в отдельной таблице. Встроенного журнала аудита сверх возможностей Smartsheet MCP-сервер не добавляет, рассчитывать на него не стоит.

## Ограничения и когда интеграция не нужна

- Тариф. Аккаунт ниже Business, Enterprise или AWM: MCP-сервер недоступен, обойти это настройкой нельзя.
- Клиенты. Нужны права в Amazon Quick либо установленный Kiro с Node.js. Без этого сервер есть, а подключиться к нему нечем.
- Сеть. Транспорт Streamable HTTP MCP требует сетевого доступа к эндпоинту, а прокси и firewall умеют его ломать.
- Права. AI наследует права пользователя: широкий доступ означает широкие возможности агента.
- Качество данных. Ответы зависят от структуры листов: единые статусы, явные владельцы, отдельная колонка под блокеры.

Интеграция не нужна, если Smartsheet в компании остался хранилищем документов, а задачи ведутся в другом инструменте. Вы получите второй канал изменений и лишнюю точку расхождения. Не нужна она и там, где нет ресурса на управление токенами и правами: агент с токеном администратора это не автоматизация, а риск.

С чего начать: проверьте тариф и наличие подходящего клиента, выберите точку входа по роли (Quick для бизнеса и проектных команд, Kiro для разработки), возьмите один лист с чистой структурой и прогоните на нём тестовый запрос про открытые задачи с владельцами и сроками. Когда ответ совпадёт с тем, что вы видите в Smartsheet глазами, подключайте остальные листы.
