# Java4Shell - RCE-уязвимость в декодировщике Base64 из OpenJDK, затрагивающая многие Java-приложения

## Краткое содержание

В OpenJDK обнаружена критическая уязвимость (CVE-2026-114938), позволяющая злоумышленнику выполнить удалённый код или выкрасть содержимое памяти процесса. Эксплуатация возможна через штатный декодер Base64, который широко применяется в Java-проектах для передачи бинарных данных в текстовом виде — от аутентификации и загрузки файлов до электронной почты. Суть дефекта заключается в записи данных, контролируемых атакующим, за пределы выделенного буфера. Корнем проблемы является ошибка в ассемблерных оптимизациях, использующих инструкции AVX-512 VBMI (Vector Byte Manipulation Instructions). Таким образом, любой Java-приложение, обрабатывающее Base64-данные на процессорах с поддержкой AVX-512 VBMI, потенциально подвергается атаке.

## Полная статья

[Раскрыта](https://calif.io/java4shell)информация о критической уязвимости ([CVE-2026-114938](https://security-tracker.debian.org/tracker/CVE-2026-114938)) в[OpenJDK](https://github.com/openjdk/jdk), позволяющей добиться удалённого выполнения кода или утечки содержимого памяти процесса при атаке на написанные на языке Java проекты, использующие штатный декодировщик данных в формате[Base64](https://ru.wikipedia.org/wiki/Base64). Base64 применяется в протоколах аутентификации, при загрузке файлов на web-сервер, в электронной почте и во многих других ситуациях, требующих передачи бинарных данных в текстовом виде. Уязвимость приводит к записи контролируемых атакующим данных в память вне выделенного буфера и вызвана ошибкой в ассемблерных оптимизациях, использующих инструкции[AVX-512 VBMI](https://en.wikipedia.org/wiki/AVX-512#BW,_DQ_and_VBMI)(Vector Byte Manipulation Instructions).

Для вызова аварийного завершения приложения достаточно передать Base64-последовательность, состоящую из 64-символов "A", завершающуюся символом "=". Успешные атаки для удалённого выполнения кода, работающие на стадии до аутентификации, продемонстрированы для проектов Keycloak, Atlassian Jira, Atlassian Confluence, JFrog Artifactory, Jenkins и PingFederate. На стадии после аутентификации удалось эксплуатировать Apache Kafka Broker, Apache Solr, Elasticsearch, Gerrit и Spinnaker.

Но это лишь охваченные при начальном тестировании проекты и с учётом широты применения формата Base64 проблема может затрагивать многие другие системы. Среди прочего, созданы прототипы эксплоитов, способные атаковать приложения на базе фреймворков Apache Struts и Spring Boot. Также показана возможность совершения атаки на клиентские Java-приложения, устанавливающие TLS-соединение с сервером, который контролируют атакующие. Техника эксплуатации не является универсальной и для каждого применения Base64 требуется создание специального эксплоита, но исследователям удалось автоматизировать генерацию подобных эксплоитов при помощи AI.

Уязвимость проявляется начиная с OpenJDK 17.0.6 и затрагивает производные дистрибутивы Java, включая[Oracle Java SE](https://www.oracle.com/java/technologies/downloads/),[Oracle GraalVM](https://github.com/oracle/graal),[Amazon Corretto](https://github.com/corretto/corretto-17),[Eclipse Temurin](https://github.com/adoptium/temurin-build),[Microsoft OpenJDK](https://github.com/microsoft/openjdk),[Azul Zulu](https://github.com/zulu-openjdk/zulu-openjdk),[BellSoft Liberica](https://github.com/bell-sw/Liberica),[SAP SapMachine](https://github.com/SAP/SapMachine)и[Red Hat OpenJDK](https://github.com/rh-openjdk/jdk). Компания Oracle устранила уязвимость во вчерашнем корректирующем обновлении своих продуктов, в которых помимо рассматриваемой проблемы исправлено ещё[10 уязвимостей](https://www.oracle.com/security-alerts/cspunov2026.html#AppendixJAVA). Уязвимости[устранены](https://www.oracle.com/java/technologies/downloads/)в выпусках Java SE 27.0.1.1, 25.0.5.1, 21.0.13.1 и 17.0.21.1, 11.0.33.1 и 8u513. Статус устранения уязвимостей в дистрибутивах можно оценить на данных страницах:[Debian](https://security-tracker.debian.org/tracker/CVE-2026-114938),[Ubuntu](https://people.canonical.com/~ubuntu-security/cve/CVE-2026-114938),[SUSE/openSUSE](https://bugzilla.suse.com/show_bug.cgi?id=CVE-2026-114938),[RHEL](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2026-114938),[Gentoo](https://bugs.gentoo.org/show_bug.cgi?id=CVE-2026-114938),[Arch](https://security.archlinux.org/package/jdk-openjdk),[Fedora](https://koji.fedoraproject.org/koji/packageinfo?packageID=41934),[FreeBSD](https://www.vuxml.org/freebsd/).

Атака возможна только на системы, поддерживающие инструкции AVX-512 VBMI. Для систем Intel отмечено проявление уязвимости на CPU Intel Xeon Ice Lake, Sapphire Rapids, Emerald Rapids и Granite Rapids, а для систем AMD в CPU EPYC и Ryzen, начиная с микроархитектуры Zen 4. Системы на базе архитектуры ARM64 проблеме не подвержены. В качестве обходного пути блокирования уязвимости можно запустить OpenJDK с флагом "-XX:-UseBASE64Intrinsics" для отключения ассемблерных оптимизаций или "-XX:UseAVX=2" для отключения AVX-512.

Для проверки поддержки инструкций AVX-512 VBMI в Linux можно использовать команду (в выводе должны присутствовать 4 флага avx512f, avx512bw, avx512vbmi и bmi2):

```

   grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
```

Уязвимость присутствует в ассемблерной реализации декодировщика Base64, ускоренного при помощи векторных инструкций AVX-512 VBMI, позволяющих обрабатывать большие блоки данных за один такт с помощью битовых масок. Проблема возникает из-за некорректного расчёта размера строк, заканчивающихся символом "=", применяемым в качестве заполнителя (padding) неполных блоков, если длина исходных данных не кратна 3 байтам.

В процессе обработки символов "=" декодировщик уменьшает размер итоговой строки, так как финальный блок содержит 1 или 2 байта вместо 3, но из-за ошибки при расчёте в возникало целочисленное переполнение (underflow) при вычитании и наличие символа "=" в конце строки определённого размера приводило к вычислению отрицательного значения -1 или -2. Далее данные значения обрабатывались как беззнаковые 64-разрядные числа, что приводило к созданию битовой маски, в которой все биты равны 1 (-1u64).

Для сохранения результата раскодирования упакованной строки размером 64 байта выделялся буфер размером 50 байт (в Base64 каждые исходные 3 байта кодируются в 4 символа), но при указании битовой маски -1u64 в инструкции evmovdqub при обработке финальных символов, в позицию со смещением 48 выполнялась запись 64 байт вместо 2, т.е. 62 байта записывались за границу буфера. Для эксплуатации уязвимости осуществляется перезапись поля с размером следом идущего массива, благодаря чему атакующий получает примитивы для произвольного чтения и записи в память.
