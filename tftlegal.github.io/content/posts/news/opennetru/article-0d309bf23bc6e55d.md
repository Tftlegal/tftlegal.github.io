# NoisyTCP - уязвимость в TCP-стеке ядра Linux

## Краткое содержание

В стеке TCP ядра Linux раскрыта уязвимость CVE-2026-99288 с кодовым именем NoisyTCP. Она возникает из-за гонки состояний при многопоточной обработке серии входящих SYN-запросов, перемешанных с фрагментированными IPv4-пакетами, что заставляет ядро распределять обработку одного соединения по разным очередям приёма (RX). В результате происходит разыменование нулевого указателя или обращение к памяти после её освобождения. Уязвимость позволяет атаковать серверные процессы (например, HTTP- и SSH-серверы) специально сформированным потоком TCP-пакетов, вызывая отказ в обслуживании в виде ядра panic. Теоретически она допускает удалённое code execution, однако создание прототипа универсального RCE-эксплойта пока не увенчалось успехом. На данный момент подтверждённая эксплуатация ограничена DoS-атаками, а RCE в real-world conditions не продемонстрирована.

## Полная статья

[Раскрыта](https://github.com/V4bel/NoisyTCP)информация об уязвимости ([CVE-2026-99288](https://security-tracker.debian.org/tracker/CVE-2026-99288)) в TCP-стеке ядра Linux, получившей кодовое имя NoisyTCP и приводящей к разыменованию нулевого указателя или обращению к памяти после её освобождения из-за состояния гонки при многопоточной обработке серии входящих SYN-запросов вперемешку с фрагментированными IPv4-пакетами, что вынуждает ядро распределять обработку одного соединения по разным очередям приёма (RX). Уязвимость может быть эксплуатирована для вызова отказа в обслуживании (перевод ядра в состояние panic) через отправку специально сформированного потока TCP-пакетов к серверным процессам, принимающим TCP-соединения, например, к http- и ssh-серверам. Теоретически не исключается эксплуатация для удалённого выполнения кода, но попытки создания прототипа универсального эксплоита пока не увенчались успехом и совершение RCE-атаки не в лабораторных условиях пока не достигнуто.

Рабочие примеры совершения атаки для вызова отказа в обслуживании продемонстрированы для Nginx, Apache httpd и SSH в конфигурации по умолчанию. Уязвимость может использоваться для совершения атак на платформы контейнерной изоляции, так как эксплуатация уязвимости в любом контейнере приводит к остановке работы всего сервера. При тестировании в виртуальной машине на базе QEMU/KVM для эксплуатации потребовалось от 5 секунд до 2 минут, но при этом атака на сервер Nginx, выполняемый в основной системе, при использовании 8 RX-очередей заняла 14 часов.

Уязвимость присутствует[начиная](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=079096f103faca2dd87342cca6f23d4b34da8871)с ядра Linux 4.3 (2015 год) и[устранена](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=4e2b3ef19e0e04adca38442f07dd6bc93c712bf1)в выпусках[6.12.117, 6.18.63 и 7.3.4](https://kernel.org). Статус устранения уязвимостей в дистрибутивах можно оценить на данных страницах:[Debian](https://security-tracker.debian.org/tracker/CVE-2026-99288),[Ubuntu](https://people.canonical.com/~ubuntu-security/cve/CVE-2026-99288),[SUSE/openSUSE](https://bugzilla.suse.com/show_bug.cgi?id=CVE-2026-99288),[RHEL](https://bugzilla.redhat.com/show_bug.cgi?id=CVE-2026-99288),[Gentoo](https://bugs.gentoo.org/show_bug.cgi?id=CVE-2026-99288),[Arch](https://security.archlinux.org/package/linux),[Fedora](https://koji.fedoraproject.org/koji/packageinfo?packageID=8).

Проблема проявляется при использовании нескольких RX-очередей (по умолчанию, посмотреть можно через "ls /sys/class/net/имя_cетевого_интерфейса/queues") или при включении режима[RPS](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/6/html/performance_tuning_guide/network-rps)(Receive Packet Steering, проверить можно через "cat /sys/class/net/имя_cетевого_интерфейса/queues/rx-*/rps_cpus"). В качестве обходных путей блокирования уязвимости упоминается использование только одной очереди приёма пакетов (RX) или отключение SYN Cookie ("sysctl -w net.ipv4.tcp_syncookies=0"), что приведёт к снижению производительности из-за обработки всех входящих пакетов только одним ядром CPU и отключению защиты от SYN-флуда соответственно. Изменение настроек SYN Cookie требуется для всех пространств имён (для каждого контейнера).

В общем универсально и правильно так без обновления (закрываем TCP MF фрагментацию): table inet filter { chain predefrag { type filter hook prerouting priority -450; policy accept; ip protocol tcp ip frag-off & 0x3fff != 0 counter drop } Тогда у атакующего не будет возможности послать 1 и тот же пакет на 2 CPU ядра чтобы он разбежался и попал в kernel panic (пока еще нет эксплойта RCE через эту гонку) и при этом отключать очереди на сетевых картах не требуется, и syn_cookie тоже отключать не требуется. Применение заплатки проверяется так на примере любого TCP порта: nmap -f -p 22 1.2.3.4 22/tcp filtered ssh Без применения: nmap -f -p 22 1.2.3.4 22/tcp open ssh Другой способ более жесткий: sysctl -w net.ipv4.ipfrag_high_thresh=0 net.ipv4.ipfrag_low_thresh=0 Но он заглушит всё вообще и подходит далеко не везде.
