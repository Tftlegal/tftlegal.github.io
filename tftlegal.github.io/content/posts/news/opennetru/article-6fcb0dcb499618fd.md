# Уязвимость в PHP, потенциально позволяющая скомпрометировать любой PHP-сайт

## Краткое содержание

Разработчики PHP объявили о выпуске экстренных патчей (8.5.12, 8.4.27, 8.3.36, 8.2.35), запланированных на сегодня в 17:00 по Москве. Пatches устраняют две критические уязвимости — CVE-2026-109618 и CVE-2026-109619, детали которых официально раскроются только после публикации исправлений. По имеющимся данным, эти уязвимости позволяют злоумышленникам удалённо execute arbitrary code на any web-сервер running PHP-скриpts с default configuration. The vulnerability affects all PHP versions starting from 5.4. Admins of affected servers are strongly urged to install the patches immediately upon release.

## Полная статья

Разработчики PHP[анонсировали](https://www.php.net/archive/2026.php#2026-10-20-1)публикацию сегодня в 17:00 (MSK) экстренных корректирующих выпусков (8.5.12, 8.4.27, 8.3.36 и 8.2.35), в которых будут устранены две критические уязвимости. Всем администраторам серверов с PHP рекомендовано незамедлительно установить исправления на своих системах, сразу после их выпуска. Официально детали будут раскрыты только после появления исправлений, но судя по[появившейся](https://cert.europa.eu/publications/security-advisories/2026-018/)в открытом доступе[информации](https://x.com/watchtowrcyber/status/2112611507749982605), речь про уязвимости[CVE-2026-109618](https://security-tracker.debian.org/tracker/CVE-2026-109618)и[CVE-2026-109619](https://security-tracker.debian.org/tracker/CVE-2026-109619), потенциально позволяющие удалённо выполнить свой код на любом web-сервере, выполняющем PHP-скрипты в конфигурации по умолчанию. Проблемы проявляются во всех версиях, начиная с PHP 5.4.

В сети уже появились прототипы эксплоитов ([1](https://pastebin.com/kggc4q1T),[2](https://jackalsyn.com/posts/php-up-2026.html)) для проверки подверженности систем уязвимости. В[примечании](https://jackalsyn.com/posts/php-up-2026.html)к эксплоиту утверждается, что уязвимости вызваны обращением к уже освобождённой памяти в обработчике отслеживания прогресса загрузки файлов на сервер (session.upload_progress). Наличия на сайте функциональности для загрузки файлов для совершения атаки не требуется, достаточно автоматического срабатывания в PHP-интерпретаторе обработчика контента "multipart/form-data". Для успешной эксплуатации требуется определение раскладки структур в памяти процесса, которая специфична в каждой сборке (проблема решается перебором в эксплоите смещений, заранее вычисленных для пакетов из разных дистрибутивов).

В качестве обходного пути защиты[встречаются](https://phpc.social/@Girgias/117476477429221001)[рекомендации](https://x.com/J4ck3LSyN/status/2112703096443097263)выставить в php.ini параметр "session.upload_progress.enabled = off" (или "php_admin_flag[session.upload_progress.enabled] = off" в PHP-FPM), но[представитель проекта PHP](https://phpc.social/@Girgias/117476477429221001), а также[автор первого прототипа эксплоита](https://x.com/rina4_tot/status/2112723421641531772)утверждают, что для блокирования обеих уязвимостей этого недостаточно. В[примечании](https://jackalsyn.com/posts/php-up-2026.html)ко второму прототипу эксплоита упоминается, что помимо вышеупомянутой настройки в php.ini для предотвращения атаки без применения патча требуется полная блокировка запросов с типом контента "multipart/form-data", которая приведёт к невозможности загрузки файлов через web-формы.

В Apache httpd для блокировки multipart-запросов можно использовать следующее правило в mod_rewrite:

```

   RewriteCond %{HTTP:Content-Type} multipart [NC]
   RewriteRule ^ - [F,L]
```

Для блокировки в nginx:

```

    if ($http_content_type ~* "multipart") {
        return 403;
    }
```

Для блокировки в Caddy:

```

   @multipart header_regexp Content-Type (?i)multipart
   respond @multipart 403
```
