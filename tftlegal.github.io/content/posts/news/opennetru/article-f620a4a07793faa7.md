# Эксплуатируемая через SMS уязвимость в Android, приводящая к зацикленной перезагрузке

## Краткое содержание

В Android (CVE-2026-58882) раскрыта уязвимость, получившая название «SMS of Death», которая позволяет вызвать бесконечный перезагрузочный цикл отправки специально сформированного SMS-сообщения. Атака не требует никаких действий со стороны пользователя: сообщение обрабатывается в фоне и не отображается на экране. Уязвимость затрагивает все устройства с Android 12–17, однако исправление выпущено только для Android 14–17. Производители получили патч ещё в июле, а в октябре он был включён в обновление репозитория AOSP. Для устройств, которые не получили обновление, единственный способ выйти из the reboot loop is a factory reset or manual intervention via the ADB utility.

## Полная статья

[Раскрыты](https://smsofdeath.com/)детали и[опубликован](https://github.com/MarkBlah/smsofdeath)эксплоит для уязвимости ([CVE-2026-58882](https://x.com/GrapheneOS/status/2115863487381704935)) в платформе Android, позволяющей добиться зацикленной перезагрузки через отправку специально оформленного SMS-сообщения. Для устранения зацикленной перезагрузки требуется сброс к заводским настройкам или ручные манипуляции при помощи утилиты ADB. Уязвимость получила кодовое имя "SMS of Death" и[устранена](https://android.googlesource.com/platform/frameworks/opt/telephony/+/735d9672603fa206c4b43cb668c1aa273db70b97)в[октябрьском обновлении](https://source.android.com/docs/security/bulletin/)репозитория AOSP. Производители устройств[получили](https://x.com/GrapheneOS/status/2115862510373126280)доступ к патчу в июле. Атака может быть совершена на любые телефоны, оснащённые Android 12-17. Обновление выпущено только для Android 14-17. Эксплуатирующее уязвимость SMS-сообщение обрабатывается как фоновое и не отображается на устройстве. Для проведения атаки не требуется выполнение пользователем каких-либо действий.

Проблема вызвана неконтролируемым приведением типа при обработке некорректного заголовка WAP Push-сообщения, отправленного через SMS. Переполнение возникает так как поле с размером заголовка приводится из беззнакового значения (uintvar) к 32-разрядному знаковому типу int без должной проверки границ. Из-за приведения 64-битного типа long в 32-битный int в Java корректное с точки зрения протокола значение 0x80000000 интерпретируется как отрицательное число -2147483648 в переменной headerLength. В дальнейшем эта переменная используется при выделении памяти через вызов "new byte[headerLength]", что в случае получения отрицательного числа приводит к генерации исключения и аварийному завершению процесса com.android.phone.

Через несколько секунд процесс перезапускается, но эффект не ограничивается кратковременным прерыванием связи. Проблемное WAP Push-сообщение из-за аварийного завершения продолжает находиться в очереди необработанных сообщений и новая попытка его обработки приводит к очередному аварийному завершению процесса com.android.phone.

После серии подобных падений срабатывает обработчик RescueParty, который перезагружает устройство в режим Recovery, в котором предлагается выполнить сброс к заводским настройкам. Простая перезагрузка не помогает - если проблемное сообщение не удалено из очереди, примерно через 90 секунд устройство опять будет перезагружено.

Для удаления сообщения из очереди без сброса к заводским настройкам[предлагается использовать](https://github.com/MarkBlah/smsofdeath/issues/2)утилиту adb:

```

   adb shell content query --uri content://sms/raw --projection _id:destination_port:date:deleted
   adb shell cmd appops set com.android.shell WRITE_SMS allow
   adb shell "content delete --uri content://sms/raw --where \"address='<SENDER>'\""
   adb shell cmd appops set com.android.shell WRITE_SMS default
   adb shell pm clear com.android.providers.telephony
```

Но это лишь даст возможность извлечь SIM-карту, загрузиться и установить обновление прошивки. Так как из-за аварийного завершения процесса "com.android.phone" оператору связи не отправляется подтверждение обработки WAP Push-сообщения, до истечения таймаута он будет предпринимать новые попытки отправки и ситуация будет повторяться. В проведённых тестах повторные отправки продолжались от суток до недели. Для устройств, производители которых прекратили публикацию обновлений прошивки, обходного пути блокирования проблемы пока нет, кроме обращения к оператору связи с просьбой блокировки передачи сообщений WAP Push на его стороне.
