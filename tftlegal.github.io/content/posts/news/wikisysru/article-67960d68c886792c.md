# 13. Kubernetes. NetworkPolicy

## Краткое содержание

1. NetworkPolicy Хорошая статья NetworkPolicy — это ресурс Kubernetes, который определяет, как поды могут взаимодействовать друг с другом и с внешними сервисами по сети. Это встроенный механизм сетевой безопасности на...

## Полная статья

**[Хорошая статья](https://temofeev.ru/info/articles/vvedenie-v-setevye-politiki-kubernetes-dlya-spetsialistov-po-bezopasnosti/)**

`NetworkPolicy`— это ресурс Kubernetes, который определяет, как поды могут взаимодействовать друг с другом и с внешними сервисами по сети. Это встроенный механизм сетевой безопасности на уровне L3/L4 (IP, порты, протоколы), работающий по модели «белого списка» — всё, что явно не разрешено, запрещено.

Сам по себе,`NetworkPolicy`ничего не делает. Для реализации данной сетевой политики нужен CNI-плагин с поддержкой этой функциональности, например, Calico, Cilium, Weave и т.п. Без такого плагина политики игнорируются.

Принцип действия.

Политика применяется к набору подов, выбранных через`spec.podSelector`. Правила строятся из трёх секций:

- `podSelector`— выбор подов-целей (те, к кому применяется политика)
- `ingress`— правила для входящего трафика
- `egress`— правила для исходящего трафика из целевых подов

**Важно:**

- Основной принцип — запрещено всё, что не разрешено. Всё работает только тогда, когда сетевых политик нет. Трафик начинает фильтроваться при появлении первой политики. Отдельной запрещающей политики не существует. Это дефолтное правило и оно вставляется в самом конце цепочки. Весь трафик, который не попадает под предыдущие разрешения, будет отброшен.
- Политики аддитивны. Если у пода несколько NetworkPolicy, применяется объединение всех разрешённых правил. Отдельной политики «запретить, несмотря на другие» нет, т.е. нет способа явно запретить то, что разрешила другая политика. Разрешено = сумма всех разрешений из всех политик. Порядок создания/применения политик не важен.
- Пустой`podSelector`означает «все поды в неймспейсе». Отсутствие секции`ingress`/`egress`— запрет всего трафика (deny all).
- NetworkPolicy работает внутри текущего неймспейса, если не указан****`namespaceSelector`. Чтобы разрешить доступ из другого неймспейса, обязательно нужно добавлять`namespaceSelector`, иначе`podSelector`ищет поды только в текущем неймспейсе.
- Правила соединяются логическим ИЛИ. В рамках одной секции (например,`ingress`) все from-блоки объединяются через ИЛИ.
- Не работает с`hostNetwork: true`. Трафик к подам в режиме hostNetwork обычно не контролируется NetworkPolicy.
- Проблема с DNS на исходящих политиках. Если вы запретили весь egress (`egress: []`), pod не сможет делать DNS-запросы (UDP 53). Нужно явно разрешить DNS по CIDR кластерного DNS (обычно 10.96.0.10/32 или`kube-dns.kube-system.svc.cluster.local`, но с DNS-именем`ipBlock`не работает). Решение — разрешить UDP 53 на весь мир или на IP сервиса kube-dns.

`NetworkPolicy`— базовый строительный блок сетевой безопасности в K8s. Начинать следует с deny-all-ingress + явных разрешений, затем уже можно добавлять egress-правила.

Проектировщики Kubernetes выбрали аддитивную модель по следующим соображениям:

- Простота реализации — CNI-плагинам не нужно проверять конфликты политик.
- Предсказуемость — добавление новой политики может только расширить доступ, но никогда его не сузит (безопасно для rolling update).
- Декомпозиция — разные команды могут применять свои политики, не боясь, что кто-то другой перебьёт их запреты.

**1. Запретить всё:**

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: base
spec:
  podSelector:
    matchLabels: {}
```

Пустая matchLabels означает «все поды». В данном случае запрещается весь трафик на все поды в неймспейсе`base`. Такая политика используется как основа для default‑deny‑подхода: она применяется ко всем подам в неймспейсе.

**2. Разрешить доступ к подам с меткой`run=base`с подов с меткой`run=access`. Все поды в одном неймспейсе:**

![](/news/wikisysru/article-67960d68c886792c/image-01.png)

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: access-db
  namespace: base
spec:
  podSelector:
    matchLabels:
      run: base
  ingress:
  - from:
    - podSelector:
        matchLabels:
          run: access
```

Можно усилить политику, добавив порт и протокол. В таком случае будет разрешен доступ только по указанному порту и конкретному протоколу:

```
  ingress:
  - ports:
      - port: 22
        protocol: TCP
    from:
      - podSelector:
          matchLabels:
            run: access
```

Если в правиле`ingress`не указана секция`ports`, то разрешаются все порты и все протоколы. Если указан порт, но не указан протокол, то, по дефолту, разрешается TCP. Однако, для наглядности, лучше указывать протокол явно.

**3. Разрешить доступ из конкретного неймспейса:**

![](/news/wikisysru/article-67960d68c886792c/image-02.png)

Нам нужно пустить трафик от пода с меткой`run: access`, который теперь находится в другом неймспейсе. Для этого в разделе`from`необходимо указать`podSelector`и`namespaceSelector`. При этом, такая политика может быть задана вместе с той, что была рассмотрена выше (доступ в рамках текущего неймпейса, т.к. неймспейс не был указан). Тогда будет разрешен доступ уже из двух неймспейсов: из текущего и из prod.

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: access-db-prod
  namespace: base
spec:
  podSelector:
    matchLabels:
      run: base
  ingress:
  - ports:
      - port: 22
        protocol: TCP
    from:
      - podSelector:
          matchLabels:
            run: access
      - namespaceSelector:
          matchLabels:
            type: prod
```

## 3.**Фильтрация исходящего трафика****(Egress)**

![](/news/wikisysru/article-67960d68c886792c/image-04.png)

Для фильтрации исходящего трафика необходимо описать сетевую политику в разделе`egress`, где вместо`from`будет указан`to`. Кроме подов и неймспейса, можно также указать конкретные адреса. Для этого необходимо прописать сеть адресов в разделе`ipBlock.cidr`. По адресам из указанной подсети будет разрешен доступ из нашего пода.

Однако здесь есть один очень неприятный подводный камень. Если в спецификации будет указана только секция`egress`, то, API сервер, проанализировав поля`ingress`и`egress`, увидит их отсутствие в`policyTypes`. Тогда API сервер автоматически вычислит и добавит значение`policyTypes`и сохранится в etcd уже с заполненным`policyTypes`. Например:

```
# Мы отправляем такой манифест
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-prod
  namespace: prod
spec:
  egress:
  - to:
    - namespaceSelector: {}
      podSelector: {}
    - ipBlock:
        cidr: 8.8.8.8/32
    - ipBlock:
        cidr: 1.1.1.1/32
  podSelector: {}
  # Запретить всё остальное (выход в интернет) - нет правила для 0.0.0.0/0
  # policyTypes не указан
```

API сервер видит секцию`egress`. Казалось бы, такая политика должна влиять только на`egress`. Однако, если не указать`Ingress`, правило будет работать не так, как хотелось бы: API сервер автоматически добавит`policyTypes: [Ingress, Egress]`:

```
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-prod
  namespace: prod
spec:
  egress:
  - to:
    - namespaceSelector: {}
      podSelector: {}
    - ipBlock:
        cidr: 8.8.8.8/32
    - ipBlock:
        cidr: 1.1.1.1/32
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

В результате теперь весь Ingress трафик запрещён, потому что у нас в спецификации есть разрешающие правила для исходящего трафика (egress), но нет разрешающих правил для входящего трафика (ingress). А`policyTypes`внизу запретит оба вида трафика, то есть всё, что не разрешено выше.

То есть мы получаем следующее.

**Ожидание**

- Запретить доступ в интернет (0.0.0.0/0) — не разрешен
- Разрешить доступ к внутренним сетям
- Ingress трафик не трогать (оставить как есть)

После того, как в`policyTypes`автоматически добавится ingress

**Реальность**

- Egress: разрешён только к внутренним сетям (как и задумано)
- Ingress: теперь запрещён для всех подов`**{}**`всех неймспейсов`**{}**`, потому что`ingress`секция с разрешениями отсутствует.

Таким образом, исходной целью было «запретить подам выходить в интернет, но оставить возможность принимать входящие соединения». Вместо этого, pod не только не сможет выйти в интернет, но и никто не сможет подключиться к поду! Мы случайно запретили весь входящий трафик.

Отсутствие ingress правил в такой политике означает «запретить весь ingress» для выбранных подов[](https://kubernetes-client.github.io/javascript/classes/V1NetworkPolicySpec.html#discriminator)[](https://www.bookstack.cn/read/kubernetes-1.35-en/7a17f7961ee07ed1.md). Это неочевидное поведение, поэтому лучше всегда указывать`policyTypes`явно. Важно понимать, что само наличие`Ingress`в`policyTypes`не запрещает и не разрешает трафик. Это просто «переключатель», который как бы говорит: «Обрати внимание на секцию`ingress`, если она есть, или примени default-deny, если её нет».

Ранние версии Kubernetes предполагали, что если мы фильтруем исходящий трафик, то, вероятно, хотим контролировать и входящий. Это было сделано для «безопасности по умолчанию», но часто приводит к неожиданностям. Схематично, логика API сервера при валидации манифеста выглядит так:

![](/news/wikisysru/article-67960d68c886792c/image-05.png)

**В связи с этим, никогда не стоит полагаться на автоматическое добавление`policyTypes`API сервером. Следует всегда указывать`policyTypes`явно.**

Чтобы исправить такую ситуацию, в целевой политике, которая описывает правила исходящего трафика, следует явно указать`policyTypes: [Egress]`.

В противном случае API сервер увидит, что есть секция`egress`, но нет`policyTypes`. Тогда API сервер автоматически добавит`policyTypes: [Ingress, Egress]`. И из-за наличия`Ingress`в`policyTypes`, а также отсутствия секции`ingress`, эта политика запретит весь входящий трафик к подам. Если же мы добавим`policyTypes: [Egress]`, API сервер не станет добавлять`policyTypes: [Ingress]`, т.к. нужную политику мы указали явно и другая нам не нужна.

```
# Корректная политика для входящего трафика (egress)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-prod
  namespace: prod
spec:
  policyTypes:
    - Egress    # Явно указываем только Egress
  podSelector: {}
    matchLabels: {}
  egress:
    - to:
      - podSelector:
          matchLabels: {}
        namespaceSelector:
          matchLabels: {}
      - ipBlock:
          cidr: 8.8.8.8/32
      - ipBlock:
          cidr: 1.1.1.1/32
```

**Таким образом, если нам нужна политика только на egress, всегда следует писать`policyTypes: [Egress]`явно. Это единственный способ избежать нежелательной блокировки входящего трафика.**

`ipBlock`работает по принципу:

- **`cidr`**— разрешает диапазон IP
- **`except`**— исключает указанные подсети/адреса из разрешенного диапазона

```
ingress:
- from:
  - ipBlock:
      cidr: 10.0.0.0/16    # Разрешить всю сеть 10.0.0.0/16
      except:
      - 10.0.1.0/24        # Но запретить подсеть 10.0.1.0/24
      - 10.0.2.5/32        # И запретить конкретный IP 10.0.2.5
```

- Сначала применяется правило`cidr`(разрешает доступ)
- Затем из этого разрешенного диапазона вычитаются адреса из`except`

- `except`работает в паре с`cidr`
- Без`cidr`поле`except`не имеет смысла
- `except`— это исключения из правил, а не самостоятельное правило запрета

Таким образом,`cidr`определяет диапазон,`except`исключает его части

## 4. Работа в терминале

**Создание NetworkPolicy**

```
kubectl apply -f network-policy.yaml
kubectl apply -f ./policies/           # вся директория
kubectl apply -f https://example.com/policy.yaml  # из URL
```

```
kubectl create -f network-policy.yaml
```

Отличие от`apply`:`create`вызовет ошибку, если ресурс уже существует, а`apply`— обновит.

```
kubectl replace -f network-policy.yaml
```

Заменяет существующий ресурс (требует, чтобы ресурс уже существовал).

**Просмотр NetworkPolicy**

```
kubectl get networkpolicy -n <namespace>

# Cокращенно
kubectl get netpol -n <namespace>

# Во всех namespace
kubectl get netpol --all-namespaces

# С дополнительными колонками
kubectl get netpol -o wide

# В YAML/JSON формате
kubectl get netpol <policy-name> -n <namespace> -o yaml
kubectl get netpol <policy-name> -n <namespace> -o json
```

С помощью колонки`POD-SELECTOR`можно понять, на какие поды действует политика:

![](/news/wikisysru/article-67960d68c886792c/image-06.png)

Если указано`none`, значит политика применяется ко всем подам выбранного неймспейса:

![](/news/wikisysru/article-67960d68c886792c/image-07.png)

**Подробная информация о конкретной политике**

```
kubectl describe netpol <policy-name> -n <namespace>
```

**Редактирование существующей политики**

```
kubectl edit netpol <policy-name> -n <namespace>
```

**Удалить конкретную политику**

```
# Удалить конкретную политику
kubectl delete netpol <policy-name> -n <namespace>

# Удалить во всех namespaces
kubectl delete netpol --all --all-namespaces

# или
kubectl delete netpol --all -A
```

**Проверка, какие политики применяются к поду**

```
# Посмотреть все политики, влияющие на pod nginx-xxx
kubectl get netpol --all-namespaces | grep -i nginx
```

**Экспорт политик для бэкапа**

```
kubectl get netpol -n <namespace> -o yaml > all-policies.yaml
```
