# 11. Kubernetes. Сетевое взаимодействие подов одной ноды

## Краткое содержание

В модели сети Kubernetes каждому поду присваивается уникальный IP-адрес внутри кластера.
Этот адрес виден самому поду и служит его сетевой идентификацией.
Поды могут напрямую обмениваться данными, используя адреса других подов.
Если поды работают на одном узле, они так же общаются в рамках этой единой модели.
Кластер образует плоскую виртуальную сеть, где каждый под является самостоятельным сетевым узлом.
Такой подход упрощает взаимодействие между контейнерами и сервисами без необходимости NAT.

## Полная статья

Модель сети Kubernetes подразумевает, что

- Контейнеры внутри пода имеют один общий уникальный IP-адрес и свободно общаться друг с другом
- Поды могут общаться с любыми другими подами, используя их IP-адреса без NAT
- IP, который видит контейнер, должен быть таким для всех. Это означает, что любой субъект в кластере, независимо от его расположения, должен видеть pod с одним и тем же IP-адресом. Схематично это можно объяснить так:

```
┌────────────────────────────────────────────────────────┐│                Кластер Kubernetes                      │├────────────────────────────────────────────────────────┤│                                                        ││ Pod A (IP: 10.244.1.5)                                 ││      ↓                                                 ││      ├── Сам pod видит себя как 10.244.1.5             ││      ├── Pod B на той же ноде видит его как 10.244.1.5 ││      ├── Pod C на другой ноде видит его как 10.244.1.5 ││      └── Сервис K8s видит его как 10.244.1.5           ││                                                        ││  Нет NAT, маскарадинга или подмены IP                  │└────────────────────────────────────────────────────────┘
```

Это нужно для прозрачной диагностики, чтобы любой IP-адрес пода был одинаковым везде — внутри самого пода, в логах, в соседних подах, упрощая поиск проблем без путаницы с NAT.

## 1. Сетевой неймспейс пода

Сетевой неймспейс — это изолированный стек сети (интерфейсы, IP, маршруты, порты). в Linux процессы всегда находится в каком-то неймспейсе. По умолчанию, Linux назначает каждому новому процессу —**root сетевой нейсмспейс**.

Для общего развития: каждый процесс имеет ссылку на свой сетевой неймспейс. Увидеть сетевой неймспейс нужного процесса в Linux можно так:

```
ls -l /proc/<PID>/ns/net
```

Вывод будет выглядеть так:

```
lrwxrwxrwx 1 root root 0 апр 29 06:04 /proc/15543/ns/net -> 'net:[4026531840]'
```

![](/news/wikisysru/article-ad77e5afa4de74b7/image-01.png)

Число в квадратных скобках`4026531840`— это айнода неймспейса. Если у разных процессов айнода одинаковая — они в одном неймспейсе.

Команда`lsns`по умолчанию покажет только «лидеров» неймспейсов — то есть процессы, которые являются владельцами или первыми процессами в этом неймспейсе. У процессов в неймспейсе`root`лидером будет`init`, т.е. PID 1:

```
Показать все уникальные неймспейсы в системе (в хосте Linux):
lsns -t net -o NS,COMMAND,PID,USER
```

![](/news/wikisysru/article-ad77e5afa4de74b7/image-02.png)

В случае с контейнерами в общем, и в Kubernetes в частности, для каждого пода создается свой отдельный неймспейс. Контейнеры, которые входят в этот под, разделяют этот сетевой неймспейс между собой. Перед созданием пода, Kubernetes, в первую очередь создает сетевое пространство имен для этого пода. Это реализуется с помощью специального служебного контейнера`Pause`, который является родительским для всех контейнеров пода и нужен только для одного: держать сетевой неймспейс пода. Сколько бы контейнеров ни было, как бы они не перезагружались, сетевое пространство со всеми IP-адресами, правилами iptables и т.п., останется неизменным до удаления пода целиком.

![](/news/wikisysru/article-ad77e5afa4de74b7/image-03.png)

Благодаря тому, что контейнеры одного пода используют общий сетевой неймспейс, эти контейнеры могут общаться между собой с помощью localhost, а также взаимодействовать друг с другом с помощью портов.

## 2. Сетевые пары veth

Теперь рассмотрим, как общаются поды одного хоста (одной worker node) в разных сетевых неймспейсах. С точки зрения самого пода, он функционирует в своем собственном сетевом неймспейсе. Но как поду достучаться до хоста (worker node)? Для этого нужно обеспечить связь между сетевым неймспейсом пода и сетевым неймспейсом воркер-ноды (хоста). Чтобы связывать сетевые неймспейсы друг с другом, в Linux создается пара сетевых интерфейсов**Virtual ethernet device**—`veth`. Интерфейс`veth`, в свою очередь состоит из двух концов: это как два конца одного патч-корда, которые можно подключить к разным неймспейсам. То есть`veth`можно назвать неким «сетевым кабелем», пара концов которого может соединять два неймспейса — один конец интерфейса в поде (обычно,`eth0`), другой на воркер-ноде (имя типа`veth12345`). А уже пара таких интерфейсов обеспечивает связь между двумя подами:

![](/news/wikisysru/article-ad77e5afa4de74b7/image-04.png)

Таким образом, для того, чтобы связать сетевой неймспейс пода и root сетевой неймспейс хоста (воркер-ноды), одну часть такого «кабеля» подключают внутрь неймспейса пода, где он будет виден, наподобие`eth0`, а вторую часть — в root сетевой неймспейс с именем типа`vethxxx`.

Когда pod удаляется и освобождается пространство имен, все находдящиеся в нем`veth`-устройста уничтожаются.

Итак, поды подключаются к хосту с помощью виртуальных`veth`-интерфейсов. Под связывается с root сетевым namespace самой воркер-ноды. Это нужно, чтобы:

- Сервисы с`hostNetwork: true`работали
- Pod мог выйти в интернет через сетевой интерфейс ноды
- Другие поды (через мост или CNI) могли общаться с этим подом

Выводы:

- **`veth`(в контексте K8s) — это основной механизм связи пода с сетевым стеком ноды**.
В более широком контексте Linux — это сетевой интерфейс, предназначенный для****соединения разных сетевых неймспейсов.
- `veth`— это именно «пара виртуальных интерфейсов» (как два конца двух патч-кордов): один конец кабеля подключен к поду (обычно,`eth0`), другой — к воркер-ноде (имя типа`veth12345`).
- Фактически, оба конца`veth`находятся на одном хосте. Это означает, что`veth`не может соединять два разных физических компьютера — он работает только в пределах одной операционной системы Linux.

## 3. Сетевой мост (network bridge)

Итак, мы рассмотрели, что поды подключаются к хосту (вокер-ноде) с помощью`veth`. Но как поды взаимодействуют друг с другом? Ранее мы рассмотрели, что для этого, во-первых, нужна пара таких виртуальных сетевых интерфейсов. Но, помимо наличия связи сетевых неймспейсов двух подов и хоста с помощью пары виртуальных сетевых неймспейсов, необходим также сетевой мост (network bridge).

Для наглядности, рассмотрим прохождение трафика из пода 1 в под 2.

![](/news/wikisysru/article-ad77e5afa4de74b7/image-05.png)

Через один конец (`eth0`) первого виртуального интерфейса, трафик покидает сетевой неймспейс 1 и попадает в сетевой неймспейс`root`воркер-ноды с помощью второго конца (`vethxxx`) первого виртуального интерфейса.

Далее трафик попадает в сетевой мост`cbr0`, который узнает точку назначения с помощью ARP-запроса: мост отправляет ARP-запрос (кто владеет IP-адресом второго пода?). Сетевому мосту`cbr0`на это отвечает конец второго виртуального интерфейса второго пода —`vethyyy`, что у него есть нужный IP. То есть ARP-запрос проходит через`vethyyy`в сетевой неймспейс пода 2, под 2 отвечает, ответ идет обратно через`vethyyy`к мосту. Таким образом мост получает ответ и узнает, через какой свой интерфейс отправлять трафик во второй под.
