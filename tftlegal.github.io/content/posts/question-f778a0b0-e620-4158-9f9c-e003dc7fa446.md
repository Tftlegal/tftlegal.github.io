## 🚀 Шаг 1: Фундамент — Настройка окружения Ansible

Прежде чем писать код развертывания, мы должны обеспечить надежное и безопасное "рабочее место".

**Цель этого шага:** Установить Ansible, определить целевые узлы и создать стандартизированную, модульную структуру проекта.

### 1.1. Требования к окружению (Предположения)

Для выполнения этого шага предполагается, что у вас есть:
1. **Control Node:** Ваша рабочая станция, с которой запускается Ansible.
2. **Target Nodes:** Удаленные серверы (VMs/Bare Metal), на которых будут установлены ClickHouse и MongoDB.
3. **SSH Доступ (Ключевое требование):** Вы должны иметь **настроенный и протестированный SSH-ключевой доступ** от Control Node к Target Nodes с правами `sudo` (или `root`). **Использование паролей в конфигурации строго запрещено.**

### 1.2. Установка Ansible (На Control Node)

Убедитесь, что Ansible установлен.

**Для Debian/Ubuntu:**
```bash
sudo apt update
sudo apt install ansible -y
```

**Для CentOS/RHEL:**
```bash
sudo yum install epel-release -y
sudo yum install ansible -y
```

### 1.3. Создание Модульной Структуры Проекта

Мы используем структуру на основе **Ролей (Roles)**, что является лучшей практикой Ansible для изоляции функционала.

```bash
mkdir db_automation
cd db_automation
mkdir inventory
mkdir roles
```

**Идеальная структура проекта:**
```
db_automation/
├── inventory/        # Конфигурация целевых хостов
├── roles/
│   ├── clickhouse/   # Все задачи по развертыванию CH
│   └── mongodb/      # Все задачи по развертыванию Mongo
├── playbook.yml      # Главный оркестратор, вызывающий роли
└── ansible.cfg       # Конфигурационный файл Ansible (Рекомендуется!)
```

### 1.4. Определение Инвентаря (Inventory)

Файл инвентаря (`inventory/hosts.ini`) — это карта наших серверов.

**Создайте файл `inventory/hosts.ini`:**

```ini
[databases]
db_server_01 ansible_host=192.168.1.101 ansible_user=your_ssh_user
db_server_02 ansible_host=192.168.1.102 ansible_user=your_ssh_user

[all:vars]
# Автоматический запуск команд с привилегиями суперпользователя
ansible_become=true
# Указываем, что мы будем использовать SSH ключи, а не пароли
ansible_ssh_private_key_file=~/.ssh/id_rsa
```

**💡 Критический Момент:** Убедитесь, что `ansible_ssh_private_key_file` указывает на ваш приватный ключ, который имеет права на доступ к удаленным хостам.

## 2. 🐘 Развертывание и Конфигурация ClickHouse

ClickHouse требует настройки сервера и затем выполнения SQL-скриптов для определения структуры данных.

### 2.1. Развертывание Сервиса (Установка и Запуск)
*(Задача `main.yml` в роли `clickhouse`)*
Используем `apt` для установки, как в черновике.

### 2.2. Конфигурация Сервиса (Шаблонирование)
*(Задача в `main.yml`)*
Использование `template` для `/etc/clickhouse-server/config.xml`.

**✅ Ключевой момент:** Перезапуск сервиса при изменении конфигурации управляется через **Handler**.

### 2.3. Управление Схемой (🔥 **Критическое Дополнение**)
Вместо жесткой настройки пользователей в XML, мы используем Ansible для выполнения SQL-команд, что является стандартом индустрии.

**`roles/clickhouse/tasks/schema.yml`:**
```yaml
---
- name: Connect to ClickHouse and execute setup SQL
  ansible.builtin.shell: |
    clickhouse-client --query "
    CREATE DATABASE IF NOT EXISTS analytics_db;
    CREATE TABLE IF NOT EXISTS analytics_db.user_logs (
        event_time DateTime,
        user_id UInt64,
        event_name String
    ) ENGINE = MergeTree() ORDER BY event_time;
    "
  args:
    # Предполагаем, что клиент может подключиться без пароля на этапе развертывания
    executable: clickhouse-client
  become: yes
  become_user: clickhouse # Или пользователь с правами
```
**📌 Доработка:** Этот шаг должен выполняться *после* того, как сервис запущен и настроен.

## 3. 🗄️ Развертывание и Конфигурация MongoDB

MongoDB требует не только запуска, но и **жесткой настройки безопасности**.

### 3.1. Развертывание и Конфигурация Сервиса
*(Задачи в `main.yml`)*
Используем `template` для `/etc/mongod.conf`, динамически устанавливая `authorization: enabled`.

### 3.2. Управление Безопасностью (🔥 **Критическое Дополнение**)
Это самый важный шаг, который был упущен. Мы должны создать администратора, прежде чем кто-либо сможет подключиться.

**`roles/mongodb/tasks/security.yml`:**
```yaml
---
- name: Wait for MongoDB service to be fully ready
  ansible.builtin.pause:
    seconds: 10 # Даем время сервису инициализироваться

- name: Create initial admin user (MUST BE DONE FIRST)
  ansible.builtin.shell: |
    mongo --host 127.0.0.1 --port {{ mongo_port }} --eval "
    use admin;
    db.createUser({
      user: 'adminUser',
      pwd: 'StrongPassword123!',
      roles: [ { role: 'userAdminAnyDatabase', db: 'admin' }, 'readWriteAnyDatabase' ]
    });
    "
  args:
    # Важно: Здесь нужно обеспечить, что MongoDB работает без аутентификации
    # только на время этого первоначального скрипта!
    warn: no
  become: yes
  become_user: mongodb
```
**⚠️ Предупреждение о безопасности:** Выполнение первого подключения без аутентификации — это временная уязвимость, которую нужно минимизировать. В идеале, Ansible должен использовать временный, низкопривилегированный аккаунт для первого подключения.

### 3.3. Управление Схемой (Структура Данных)
Для MongoDB управление схемой — это обычно вставка документов или использование `db.collection.insertMany()`.

**`roles/mongodb/tasks/schema.yml`:**
```yaml
---
- name: Insert initial configuration document into a collection
  community.mongodb.mongodb_info:
    host: 127.0.0.1
    port: "{{ mongo_port }}"
    database: app_config
    collection: settings
    actions:
      - insert: "{{ item }}"
  loop:
    - { name: "feature_flag_x", value: true }
  delegate_to: localhost # Часто лучше выполнять операции с данными с контрольного узла
```
**✅ Ключевой момент:** Для MongoDB мы используем **модуль `community.mongodb.mongodb_info`**, а не `shell`, так как это более чисто, идемпотентно и безопасно.

## 4. 🧪 Тестирование и Валидация (Health Check)

Тесты должны быть не просто проверкой, что процесс запущен, а проверкой, что **сервис готов принимать запросы**.

### 4.1. Тест ClickHouse (Проверка запроса)
Использование `command` с проверкой `rc=0` — приемлемо, но для большей надежности можно использовать `uri` модуль, если настроен HTTP-интерфейс.

### 4.2. Тест MongoDB (Проверка команды)
Использование модуля `community.mongodb.mongodb_info` для проверки работоспособности подключения и выполнения команды `ping`.

```yaml
- name: Verify MongoDB health check (Ping)
  community.mongodb.mongodb_info:
    host: 127.0.0.1
    port: "{{ mongo_port }}"
    database: admin
    actions:
      - command: "db.adminCommand({ ping: 1 })"
  register: mongo_health
  # Если модуль успешно выполнился, значит, сервис доступен
```

## 📜 Финальный Плейбук Оркестрации (`playbook_master.yml`)

Этот файл связывает все роли вместе в правильном порядке.

```yaml
---
- name: 🟢 Deploy and Configure ClickHouse Cluster
  hosts: clickhouse_servers
  become: yes
  vars:
    clickhouse_port: 9001
  roles:
    - clickhouse
  tasks:
    # Выполняем проверку работоспособности после развертывания
    - name: Final ClickHouse Health Check
      ansible.builtin.command: clickhouse-client --query "SELECT 1"
      register: ch_final_check
      changed_when: false

    - name: Report ClickHouse status
      ansible.builtin.debug:
        msg: "✅ ClickHouse successfully deployed and responsive."
      when: ch_final_check.rc == 0

- name: 🔵 Deploy and Secure MongoDB Instance
  hosts: mongodb_servers
  become: yes
  vars:
    mongo_port: 27017
  roles:
    - mongodb
  tasks:
    # Выполняем проверку работоспособности после развертывания
    - name: Final MongoDB Health Check
      community.mongodb.mongodb_info:
        host: 127.0.0.1
        port: "{{ mongo_port }}"
        database: admin
        actions:
          - command: "db.adminCommand({ ping: 1 })"
      register: mongo_final_check

    - name: Report MongoDB status
      ansible.builtin.debug:
        msg: "✅ MongoDB successfully deployed, secured, and responsive."
      when: mongo_final_check is success
```
