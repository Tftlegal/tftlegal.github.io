### Логические и Архитектурные Ошибки

1.  **Question 2 (Read vs Write):**
    *   *Ошибка:* "Использование NoSQL баз данных для read-heavy систем."
    *   *Критика:* Это ложная дихотомия. SQL databases (PostgreSQL, MySQL) are excellent for read-heavy workloads when properly indexed and cached. NoSQL is often chosen for *schema flexibility* or *massive horizontal scale*, not solely for read performance. Read performance is usually achieved via caching (Redis) or replication in any DB type.
2.  **Question 3 (Durability/Consistency):**
    *   *Ошибка:* "Использование базов ACID-консистенции для read-heavy systems."
    *   *Критика:* ACID is a property of *transactions*, not specifically "read-heavy" systems. Read-heavy systems often prefer **Eventual Consistency** to allow for higher availability and lower latency (CAP theorem). Strong consistency (ACID) is expensive and usually associated with *write-critical* or *financial* systems, not just read-heavy ones.
    *   *Ошибка:* "Использование strong consistency for write-heavy systems."
    *   *Кritik:* Write-heavy systems often struggle with strong consistency due to the cost of consensus (Raft/Paxos). They often use **Eventual Consistency** with high throughput (e.g., Cassandra, DynamoDB) unless strict ordering is required.
3.  **Question 4 (Latency):**
    *   *Ошибка:* "Использование in-memory store... for высокомодульных (high-module?) applications."
    *   *Критика:* "High-module" is a translation artifact. It should be "high-performance" or "low-latency".
    *   *Ошибка:* "Внедрение batch processing for low-latency systems."
    *   *Критика:* **Contradiction.** Batch processing is inherently *high-latency*. It is used for *high-throughput* or *analytics* systems where immediate response is not needed. Low-latency requires synchronous, direct paths.
4.  **Question 5 (Cost):**
    *   *Ошибка:* "Использование auto-scaling... for reduce operational complexity."
    *   *Критика:* Auto-scaling *increases* operational complexity (managing scaling policies, cold starts, stateful scaling issues). It reduces *infrastructure management* burden but adds *architectural* complexity.
5.  **Anti-patterns Section:**
    *   *Error:* "Случайный распределение (unbounded replay) for распределенных systems." -> Translation garbage.
    *   *Error:* "Бесвязное чтение (unbounded replay) for read-heavy systems." -> "Unbounded replay" is not a standard term for read issues. It likely refers to **Unbounded Growth** of logs or **Cache Stampedes**.
    *   *Error:* "Связные RPC (sync RPC) through Kafka." -> Kafka is an async broker. Sending sync RPC *through* Kafka implies waiting for a consumer to respond, which defeats the purpose of Kafka and is a major anti-pattern (blocking on async infra).

### OWASP & Security Considerations (Missing in Draft)
The draft completely ignores security. In a professional design, you must consider:
*   **OWASP Top 10:** Input validation, SQL Injection (even in NoSQL, via operator injection), Broken Access Control.
*   **Data at Rest/In Transit:** Encryption standards (AES-256, TLS 1.3).
*   **Event-Driven Security:** Poison Pill messages, message tampering, replay attacks in event streams.
*   **Index Security:** Index bloat can lead to DoS via resource exhaustion.

# Designing Backend Systems: SQL vs NoSQL, Event-Driven Architecture, and Performance

Designing a scalable backend requires balancing five mutually constraining factors. Below is a comprehensive guide to making the right architectural choices, avoiding common anti-patterns, and ensuring security.

## 1. The Five Core Constraints

### 1.1. Scale and Growth Rate
**Question:** *What is the current user base, and what is the projected growth curve?*

*   **Analysis:**
    *   **< 100K Users:** A single-node RDBMS (PostgreSQL/MySQL) is sufficient. Keep it simple.
    *   **1M - 100M Users:** Horizontal scaling becomes necessary. Consider read replicas for SQL or sharding.
    *   **> 100M Users / High Velocity:** Distributed systems are mandatory. You must decide on sharding strategy (by user ID, geographic region, or tenant).
*   **Solution:**
    *   Start with **Vertical Scaling** (bigger server) until proven insufficient.
    *   Implement **Read Replicas** early to offload read traffic.
    *   Use **Sharding** only when a single node hits I/O or CPU limits.
    *   **Security Note:** Ensure sharding keys are not predictable if they expose business logic (prevents enumeration attacks).

### 1.2. Read vs. Write Workload
**Question:** *Is the system read-heavy, write-heavy, or balanced?*

*   **Analysis:**
    *   **Read-Heavy (e.g., Catalogs, Social Feeds):** Prioritize cache hit rates and index optimization. NoSQL is not automatically better here; PostgreSQL with GIN/GiST indexes can handle massive reads.
    *   **Write-Heavy (e.g., Logs, IoT, Clickstream):** Prioritize throughput and durability. LSM-Tree databases (Cassandra, RocksDB, DynamoDB) excel here because they append writes to disk sequentially.
*   **Solution:**
    *   **Read-Heavy:** Use **Caching Layers** (Redis/Memcached) + **Database Replication**.
    *   **Write-Heavy:** Use **LSM-Tree Storage** or **Event Sourcing**.
    *   **Hybrid:** Use a **CQRS (Command Query Responsibility Segregation)** pattern. Writes go to a transactional DB (SQL), reads go to an optimized read model (NoSQL/Search Engine).
    *   **Security Note:** Caching layers must be properly authenticated. Prevent **Cache Poisoning** by validating content integrity.

### 1.3. Durability and Consistency (CAP Theorem)
**Question:** *What data can you afford to lose, and how stale can the data be?*

*   **Analysis:**
    *   **Strong Consistency (Linearizable):** Required for banking, inventory counts. Uses Paxos/Raft. High latency cost.
    *   **Eventual Consistency:** Acceptable for social media, analytics. Lower latency, higher availability.
    *   **Durability (RPO/RTO):** How much data loss is acceptable? (RPO = Recovery Point Objective).
*   **Solution:**
    *   **Financial/Critical:** Use **ACID-compliant SQL** with synchronous replication (Quorum writes).
    *   **High Availability/Analytics:** Use **Eventual Consistency** (NoSQL).
    *   **Hybrid:** Use **Read Repair** or **Anti-Entropy** protocols to converge data in eventual consistency models.
    *   **Security Note:** Ensure **WAL (Write-Ahead Logs)** are encrypted. Protect against **Replay Attacks** by including timestamps and nonces in event messages.

### 1.4. Latency Budget
**Question:** *What is the maximum acceptable response time (P50/P99)?*

*   **Analysis:**
    *   **< 10ms:** In-memory stores (Redis, Memcached), Edge Computing, Colocation.
    *   **10ms - 100ms:** Standard SSD-backed RDBMS/NoSQL.
    *   **> 100ms:** Batch processing, Data Lakes, Async pipelines.
*   **Solution:**
    *   **Low Latency:** Use **In-Memory Caching** and **Connection Pooling**. Avoid synchronous calls to slow services.
    *   **High Throughput/Low Urgency:** Use **Async Messaging** (Kafka, RabbitMQ) and **Batch Processing**.
    *   **Security Note:** Monitor **Timing Attacks**. Ensure error responses do not leak system state or timing differences that reveal authentication status.

### 1.5. Total Cost of Ownership (TCO)
**Question:** *What is the cost of infrastructure, licensing, and human expertise?*

*   **Analysis:**
    *   **Cloud vs. On-Prem:** Cloud offers elasticity but higher per-unit cost at scale. On-prem offers control but high CapEx.
    *   **Complexity Cost:** Kubernetes and Microservices require senior DevOps expertise. A monolith on Postgres is cheaper to maintain.
*   **Solution:**
    *   **Start Simple:** Use **Open Source** (PostgreSQL, Redis, Kafka) to avoid licensing fees.
    *   **Right-Size:** Use **Auto-Scaling** for variable loads, but set strict **Budget Alerts** to prevent "Bill Shock."
    *   **Security Note:** Open Source requires rigorous **Dependency Scanning** (Snyk, Dependabot) to avoid supply chain attacks.

## 2. Event-Driven Architecture (EDA) Best Practices

When moving from synchronous RPC to Event-Driven Architecture:

1.  **Idempotency:** Consumers must handle duplicate messages. Use unique `message_id` or `correlation_id` to deduplicate.
2.  **Ordering:** Kafka guarantees order *within a partition*. If global order is needed, ensure all related events go to the same partition (e.g., partition by `user_id`).
3.  **Dead Letter Queues (DLQ):** Implement DLQs for failed messages to prevent pipeline blockage and allow manual inspection.
4.  **Schema Registry:** Use Avro/Protobuf/JSON Schema with a registry to ensure backward compatibility.

## 3. Critical Anti-Patterns to Avoid

| Anti-Pattern | Description | Consequence | Fix |
| :--- | :--- | :--- | :--- |
| **The Dual Write** | Updating a DB and a Cache/NoSQL store in two separate steps without a transaction. | Data inconsistency if one fails. | Use **Outbox Pattern**: Write event to DB table in same transaction, then publish via CDC (Change Data Capture). |
| **Chatty Microservices** | N+1 queries or synchronous RPC chains across services. | High latency, cascading failures. | Use **CQRS** and **Batching**. Implement **Circuit Breakers** (Hystrix/Resilience4j). |
| **God Topic** | A single Kafka topic handling all events for the system. | Consumer lag, difficulty in scaling specific consumers, security boundary blur. | Partition topics by **Domain** and **Event Type**. |
| **Unbounded Replay** | Allowing consumers to replay millions of messages without throttling. | DoS on downstream services, network saturation. | Implement **Rate Limiting** on producers/consumers. Use **Checkpointing** to track progress. |
| **Implicit Coupling** | Changing a message schema breaks consumers silently. | Production outages. | Enforce **Schema Evolution** rules (backward/forward compatibility). |

## 4. Security & OWASP Compliance in DB Design

When designing the database and event flow, explicitly address:

1.  **Injection Attacks:**
    *   **SQL:** Always use **Prepared Statements**. Never concatenate user input.
    *   **NoSQL:** Sanitize input to prevent **NoSQL Injection** (e.g., injecting `{"$gt": ""}`). Use ORM layers that escape operators.
2.  **Broken Access Control:**
    *   Ensure **Row-Level Security (RLS)** is enabled in SQL if multi-tenant.
    *   In NoSQL, ensure permissions are checked *after* data retrieval (don't rely solely on client-side filtering).
3.  **Insecure Direct Object References (IDOR):**
    *   In Event-Driven systems, ensure that an event consumer verifies the *identity* of the requester before processing sensitive actions.
4.  **Data Exposure:**
    *   **Encryption at Rest:** Enable TDE (Transparent Data Encryption) for SQL/NoSQL.
    *   **Encryption in Transit:** Enforce TLS 1.2+ for all database connections and Kafka brokers.
    *   **PII Masking:** Do not store PII in event logs unless absolutely necessary. If stored, mask it.
5.  **DoS via Index Bloat:**
    *   Limit the number of indexes. Unnecessary indexes slow down writes and consume memory.
    *   Monitor **Index Usage** to drop unused indexes.

## 5. Final Recommendation Checklist

1.  **Default to SQL (PostgreSQL):** It supports JSONB, ACID, and excellent indexing. Only move to NoSQL if you have specific scale or schema-flexibility needs.
2.  **Cache Aggressively:** Use Redis for hot data. Implement **Cache-Aside** pattern with proper invalidation strategies (TTL + explicit invalidation).
3.  **Decouple with Events:** Use Kafka/Event Sourcing for non-critical, high-throughput paths. Keep critical financial paths synchronous and transactional.
4.  **Monitor Everything:** Track **P99 Latency**, **Queue Depth**, **Error Rates**, and **Database Connection Pool Usage**.
5.  **Secure by Design:** Apply OWASP Top 10 controls at the database access layer and message broker layer.
