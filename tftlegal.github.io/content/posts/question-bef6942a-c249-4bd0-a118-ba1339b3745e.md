3. **Добавить безопасность**: Twelve-Factor напрямую пересекается с OWASP Top 10 (2021/2025). Без этого объяснение неполное для любого production-контекста.
4. **Разделить Disposition (ф. 6) от Processes (ф. 7)** — это принципиально разные концепции.
5. **Уточнить «stateless»**: ключевая идея ф. 7 и ф. 9 — процесс **не хранит состояние в памяти**, а не «работает параллельно».

## 3. OWASP Top 10 (2021) — где Twelve-Factor пересекается с безопасностью

| OWASP ID | Название | Связь с Twelve-Factor |
|----------|----------|----------------------|
| **A01** Broken Access Control | Ф. 5 (Port binding): приложение слушает только один порт → уменьшает поверхность атаки. Ф. 10 (Dev/prod parity): security-тесты в среде, приближённой к prod. |
| **A02** Cryptographic Failures | Ф. 3 (Config in env): секреты (API keys, DB passwords) **не** хранятся в VCS. Требует secret manager (Vault, AWS SSM, etc.), а не просто `.env` файлы. |
| **A03** Injection | Ф. 4 (Backing services): параметры подключения к БД/кэш приходят из env → не hardcode'ятся → сложнее подменить на malicious endpoint без detection. |
| **A04** Insecure Design | Ф. 6 (Disposition: build→release→run): immutable releases prevent «hot-patching» that bypasses security review. |
| **A05** Security Misconfiguration | Ф. 3 + Ф. 10: config externalized AND dev ≈ prod → fewer «it works in staging but not in prod» misconfigs. |
| **A07** Identification & Auth Failures | Ф. 4: each backing service (auth provider, token store) is a swappable attached resource → no single point of auth failure baked into code. |
| **A08** Software & Data Integrity Failures | Ф. 6: signed, versioned release artefacts. F. 9 (Disposability): crash → restart from known-good image, not from corrupted mutable state. |
| **A09** Logging & Monitoring Failures | **Ф. 11 (Logs as event streams)**: logs go to stdout → collected by centralized SIEM. No local log files to tamper with or lose. Directly addresses A09. |
| **A10** Server-Side Request Forgery | Ф. 4: backing service URLs come from env → can be validated/whitelisted at the platform layer (K8s NetworkPolicy) rather than buried in code. |

> **Пропуск в черновике:** ни один из этих пунктов не упомянут. Для «production-ready» объяснения это критический пробел.

## 4. Безопасная финальная версия

```markdown
# Twelve-Factor App — простыми словами

## Суть в одном предложении

> Приложение строится так, чтобы **код** был неизменным артефактом, а всё, что
> может отличаться между окружениями (настройки, сервисы, масштаб), выносилось
> **на外的** уровень и менялось без пересборки.

---

## 12 факторов (канонический список)

| # | Фактор | Простое объяснение |
|---|--------|--------------------|
| 1 | **Codebase** | Один код → много деплоев. Версионирование (Git), не «код на сервере». |
| 2 | **Dependencies** | Зависимости объявлены явно (package.json / Gemfile / go.mod + lock-файл). Нет «magical» импортов. |
| 3 | **Config** | Всё, что меняется между env (URLs, ключи, лимиты) — в **переменных окружения**, а не в коде. |
| 4 | **Backing services** | БД, Redis, SMTP, S3 — «прикреплённые ресурсы». Приложение подключается по URL из env; сервис можно заменить, не трогая код. |
| 5 | **Port binding** | Приложение слушает **один** порт (обычно 8080/3000). Снаружи — reverse proxy (Nginx, ALB). Нет «магических» портов. |
| 6 | **Disposition** | Строго раздельные этапы: **Build → Release → Run**. Release = код + версия конфигурации. Запуск — только из релиза. |
| 7 | **Processes** | Каждый процесс **stateless**: не хранит сессию в памяти. Любое состояние — во внешнем store (Redis, DB). |
| 8 | **Concurrency** | Масштабирование = запуск N идентичных процессов. Нет «special» master-процесс. |
| 9 | **Disposability** | Процесс стартует < 1 с, умирает gracefully (SIGTERM → flush → exit). Crash → оркестратор поднимает новый. |
| 10 | **Dev/prod parity** | Dev ≈ Staging ≈ Prod: те же процессы, те же backing services (можно локальные, но того же типа). Минимизация «works on my machine». |
| 11 | **Logs** | Приложение пишет в **stdout**. Сборка, агрегация, хранение — дело инфраструктуры (ELK, Datadog, CloudWatch). Нет файлов `/var/log/app.log` в контейнере. |
| 12 | **Admin processes** | Миграции, реиндексы, seed-скрипты — **one-off** процессы (не фоновые демона). Запускаются, делают работу, exit. |

## Аналогии (для запоминания)

- **Код = рецепт** в поваренной книге.
- **Config = список покупок** в холодильнике. Не вписывайте список в рецепт.
- **Backing service = магазин**: можно перейти от «Пятёрочки» к «ВкусВилл», рецепт не меняется.
- **Process = сотрудник на конвейере**: каждый делает одну и ту же работу, не хранит «свой» заказ в голове.
- **Log = лента в журнале смен**: пишется на общий стенд, а не в блокнот сотрудника.

|---|---|---|

| Logs | `grep /var/log/app.log` on 3 different servers | `kubectl logs` / centralized SIEM, one query |

## Безопасность: где 12-Factor пересекается с OWASP Top 10 (2021)

| OWASP | Как 12-Factor помогает |
|-------|------------------------|
| **A02 Cryptographic Failures** | Ф. 3: секреты в env / secret manager → не в Git history. *Условие:* env vars ≠ hardcoded; используйте Vault/SSM, не `.env` committed to repo. |
| **A05 Security Misconfiguration** | Ф. 3 + Ф. 10: config externalized AND dev ≈ prod → меньше «it works in staging» surprises. |
| **A09 Logging & Monitoring Failures** | Ф. 11: structured logs → stdout → SIEM. No local log files to tamper with or lose. |
| **A08 Software & Data Integrity** | Ф. 6: signed, versioned images. Ф. 9: crash → restart from known-good image, not corrupted mutable state. |
| **A01 Broken Access Control** | Ф. 5: single port → single ingress point → easier to apply WAF / NetworkPolicy. |
| **A10 SSRF** | Ф. 4: backing-service URLs from env → can be validated / whitelisted at platform layer. |

### Практические правила безопасности при внедрении

1. **Никогда не коммитьте** `DATABASE_URL`, API keys, JWT secrets в VCS. Use:
   - `git-secrets` / `gitleaks` в CI.
   - Secret manager with rotation.
2. **Logs = stdout only.** Ensure no PII / tokens in log lines (OWASP A03).
3. **Immutable releases.** No `scp` + `vim` on prod. No `docker exec` to change config at runtime.
4. **Network segmentation.** In K8s: `NetworkPolicy` restricts which pods can reach the DB (reinforces ф. 4).
5. **Graceful shutdown (ф. 9) must flush** connection pools and finish in-flight requests → no data loss, no half-written state (A08).

## Чего подход НЕ делает

- ❌ Не является фреймворком или SDK.
- ❌ Не предписывает язык, DB, или cloud provider.
- ❌ Не заменяates security policy — it *enables* it by making config external and state external.
- ❌ Не mandatory for every project. A 3-line cron script doesn't need 12 factors.
```
