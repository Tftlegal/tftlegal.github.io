Задача: Установка PostgreSQL

Для установки PostgreSQL необходимо знать, под какую операционную систему вы планируете её устанавливать. Возможные варианты:

1. Ubuntu / Debian
2. CentOS / Rocky Linux / AlmaLinux
3. Windows Server / Windows 10‑11 (Не рекомендуется)

# Установка PostgreSQL: пошаговое руководство с лучшими практиками

PostgreSQL — одна из самых мощных и надёжных реляционных СУБД с открытым исходным кодом. Однако «правильная» установка — это не просто `apt install postgresql`. Чтобы ваша база данных работала стабильно, безопасно и эффективно, нужно с самого начала заложить фундамент, который позволит масштабироваться и обслуживать систему без боли. В этой статье мы подробно разберём установку PostgreSQL на операционных системах семейства Debian/Ubuntu, а также дадим проверенные практические рекомендации, которые помогут избежать типичных ошибок.

---

## 1. Выбор версии и источника установки

### 1.1. Почему не стоит использовать системные репозитории

В стандартных репозиториях вашего дистрибутива (например, Ubuntu) обычно доступна версия PostgreSQL, которая была актуальной на момент выхода релиза ОС. Она может быть устаревшей и не содержать важных исправлений производительности и безопасности. Кроме того, вы можете не получить новые возможности, такие как улучшенный параллелизм или новые типы индексов.

**Лучшая практика:** устанавливайте PostgreSQL из **официального репозитория PostgreSQL** (PGDG — PostgreSQL Global Development Group). Это даст вам:

- Самую свежую стабильную мажорную версию.
- Возможность установить несколько версий бок о бок.
- Доступ к широкому набору расширений (например, `postgis`, `pg_stat_statements`, `pg_partman`).

### 1.2. Подключение официального репозитория

На сайте [postgresql.org/download](https://www.postgresql.org/download) выберите вашу ОС и версию. Для Debian/Ubuntu предлагается два способа: быстрый (две команды) и поэтапный. Рассмотрим быстрый.

Установите мета-пакет `postgresql-common`, который подготавливает систему для управления несколькими версиями и кластерами:

```bash
sudo apt install -y postgresql-common
```

Затем запустите скрипт, который подключит официальный репозиторий и обновит список пакетов:

```bash
sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh
```

После этого вы сможете установить PostgreSQL любой доступной версии, например:

```bash
sudo apt install postgresql-17
```

Если не указывать версию, будет установлена последняя стабильная.

## 2. Настройка конфигурации кластера по умолчанию

В Debian/Ubuntu создание кластеров PostgreSQL управляется утилитой `pg_createcluster`. Параметры, с которыми будут создаваться новые кластеры, задаются в файле `/etc/postgresql-common/createcluster.conf`. **Крайне рекомендуется** отредактировать этот файл **до** установки пакета, чтобы сразу применить правильные настройки.

### 2.1. Выделение каталога данных и WAL

По умолчанию каталог данных находится в `/var/lib/postgresql/%v/%c` (где `%v` — версия, `%c` — имя кластера). Однако в продакшене **никогда не храните данные на системном диске**. Выделите отдельный быстрый диск (SSD/NVMe) и примонтируйте его, например, в `/mnt/postgresql/data`.

Аналогично, **журнал транзакций (WAL)** рекомендуется вынести на отдельный физический диск (желательно ещё более быстрый, чем диск данных), чтобы избежать конфликта случайных и последовательных операций ввода-вывода.

В файле `createcluster.conf` раскомментируйте и измените следующие строки:

```
data_directory = '/mnt/postgresql/data/%v/%c'
waldir = '/mnt/postgresql/wal/%v/%c/pg_wal'
```

Убедитесь, что каталоги существуют и имеют правильные права (владелец `postgres:postgres`).

### 2.2. Включение контрольных сумм

Параметр `initdb_options` позволяет передать флаги `initdb`. Самый важный из них — `--data-checksums`. Он включает проверку контрольных сумм для каждой страницы данных. Это позволяет обнаружить повреждения, вызванные сбоями оборудования, и стоит всего лишь около 3–5% производительности, что приемлемо для подавляющего большинства сценариев.

```
initdb_options = '--data-checksums'
```

**Важно:** этот параметр **нельзя изменить после создания кластера**. Если вы его не включите, для активации придётся делать дамп, пересоздавать кластер и восстанавливать данные — долгая и рискованная процедура.

### 2.3. Настройка формата логов и других опций

Также в этом файле можно задать:

- `log_line_prefix` — формат строки лога. Добавьте `%h` (хост клиента) для отслеживания источников запросов.
- `add_include_dir = 'conf.d'` — создаст подкаталог `conf.d` внутри каталога конфигурации кластера, куда можно складывать отдельные файлы с настройками (лучшая практика для организации конфигурации).
- `cluster_name = '%v/%c'` — осмысленное имя, которое будет отображаться в заголовках процессов, упрощая администрирование.
- `stats_temp_directory = '/var/run/postgresql/%v-%c.pg_stat_tmp'` — хранит временные файлы статистики в оперативной памяти (tmpfs), снижая нагрузку на диск.

Ниже представлен пример оптимального `createcluster.conf`:

```
# Автосоздание кластера main при установке
create_main_cluster = true
# Автозапуск при загрузке
start_conf = 'auto'
# Каталог данных
data_directory = '/mnt/postgresql/data/%v/%c'
# Каталог WAL (отдельный диск)
waldir = '/mnt/postgresql/wal/%v/%c/pg_wal'
# Параметры initdb
initdb_options = '--data-checksums'
# Включаем SSL
ssl = on
# Имя кластера в процессах
cluster_name = '%v/%c'
# Временная статистика в tmpfs
stats_temp_directory = '/var/run/postgresql/%v-%c.pg_stat_tmp'
# Детальный формат логов
log_line_prefix = '%%m [%%p] %%h %%q%%u@%%d '
# Подключаем conf.d
add_include_dir = 'conf.d'
```

## 3. Установка PostgreSQL

Теперь можно установить пакет:

```bash
sudo apt install postgresql-17
```

Если вы хотите установить конкретную версию, укажите её явно. Если просто `postgresql`, будет установлена последняя.

После установки автоматически создастся кластер `main` (если `create_main_cluster = true`). Проверьте его статус:

```bash
sudo systemctl status postgresql@17-main
```

Посмотреть, где находятся данные и конфиги, можно с помощью:

```bash
ps aux | grep postgres
```

Или через `pg_lsclusters`:

```bash
sudo -u postgres pg_lsclusters
```

## 4. Первоначальная настройка безопасности

### 4.1. Установка пароля суперпользователя

Переключитесь на пользователя `postgres` и войдите в psql:

```bash
sudo -u postgres psql
```

Установите пароль для суперпользователя:

```sql
\password
```

Введите пароль дважды. **Не оставляйте пароль пустым** даже на тестовых системах.

### 4.2. Создание пользователя и базы данных для приложения

В целях безопасности **никогда не используйте суперпользователя `postgres` для повседневных задач приложения**. Создайте отдельного пользователя с минимальными необходимыми правами.

```sql
CREATE USER app_user WITH PASSWORD 'strong_password';
CREATE DATABASE app_db OWNER app_user;
GRANT ALL PRIVILEGES ON DATABASE app_db TO app_user;
```

Выходите из psql командой `\q`.

### 4.3. Проверка подключения от нового пользователя

```bash
psql -h localhost -U app_user -d app_db
```

Если подключение прошло успешно, значит, базовая настройка выполнена.

## 5. Настройка удалённого доступа (с осторожностью)

По умолчанию PostgreSQL слушает только `localhost` и не принимает внешние подключения. Чтобы разрешить доступ по сети, нужно изменить два файла.

### 5.1. postgresql.conf — разрешить сетевые интерфейсы

Откройте `postgresql.conf`:

```bash
sudo nano /etc/postgresql/17/main/postgresql.conf
```

Найдите параметр `listen_addresses` и измените его:

```
listen_addresses = '*'   # слушать все интерфейсы
```

Для продакшена лучше указать конкретные IP-адреса (например, `'localhost,192.168.1.100'`), чтобы не открывать доступ со всех сетей.

**Важно:** изменение `listen_addresses` требует **перезагрузки** кластера:

```bash
sudo systemctl restart postgresql@17-main
```

### 5.2. pg_hba.conf — правила аутентификации

Этот файл определяет, кто и откуда может подключаться. Откройте его:

```bash
sudo nano /etc/postgresql/17/main/pg_hba.conf
```

Добавьте правило для вашей сети (например, для подсети 192.168.1.0/24):

```
host    all             all             192.168.1.0/24          scram-sha-256
```

**Рекомендации по безопасности:**
- Используйте `scram-sha-256` вместо `md5` — это более современный и надёжный метод хеширования паролей.
- Ограничьте доступ только теми IP-адресами, которые действительно нуждаются в подключении.
- Никогда не используйте `trust` для удалённых подключений.
- Для репликации создайте отдельную запись с `replication` в столбце DATABASE.

После изменения `pg_hba.conf` перечитывать конфигурацию **не обязательно** — достаточно выполнить `SELECT pg_reload_conf();` или `sudo systemctl reload postgresql@17-main`.

### 5.3. Проверка доступности порта

Убедитесь, что порт 5432 открыт и слушается:

```bash
ss -tunlp | grep 5432
```

С клиентской машины проверьте доступность:

```bash
nc -zv <ip-сервера> 5432
```

Если порт недоступен, проверьте настройки брандмауэра (например, `ufw` или `iptables`).

## 6. Лучшие практики для продакшена

### 6.1. Использование SSH-туннеля вместо прямого доступа

Вместо того чтобы открывать порт PostgreSQL в интернет, используйте SSH-туннель. Это добавляет уровень шифрования и аутентификации, а также позволяет избежать необходимости настраивать SSL для PostgreSQL.

На клиенте:

```bash
ssh -L 5433:localhost:5432 user@server_ip
```

Теперь подключайтесь к локальному порту 5433:

```bash
psql -h localhost -p 5433 -U app_user -d app_db
```

### 6.2. Настройка SSL-соединений

Если прямое подключение необходимо, обязательно включите SSL. В `postgresql.conf` убедитесь, что:

```
ssl = on
```

Сгенерируйте сертификаты (или используйте Let's Encrypt). В `pg_hba.conf` для внешних подключений используйте `hostssl` вместо `host`.

### 6.3. Выделение ресурсов и настройка памяти

Сразу после установки настройте параметры памяти в `postgresql.conf` в соответствии с вашим сервером:

- `shared_buffers` — 25% от ОЗУ (но не более 8–10 ГБ для очень больших серверов).
- `effective_cache_size` — 50–75% от ОЗУ.
- `work_mem` — осторожно, особенно при большом количестве подключений (обычно 4–16 МБ для OLTP).
- `maintenance_work_mem` — 5–10% от ОЗУ (но не менее 1 ГБ для серьёзных операций).

Эти параметры лучше задавать через `ALTER SYSTEM` или в отдельном файле в `conf.d`, чтобы не трогать основной `postgresql.conf`.

### 6.4. Организация конфигурации через conf.d

Воспользуйтесь опцией `add_include_dir = 'conf.d'` в `createcluster.conf`. Создайте файлы, например:

- `conf.d/memory.conf`
- `conf.d/security.conf`
- `conf.d/replication.conf`

Это облегчит отслеживание изменений и перенос настроек между окружениями.

### 6.5. Мониторинг и логирование

Настройте логирование медленных запросов. В `postgresql.conf`:

```
log_min_duration_statement = 5000   # логировать запросы дольше 5 секунд
log_checkpoints = on
log_connections = on
log_disconnections = on
log_lock_waits = on
deadlock_timeout = '1s'
```

Используйте расширение `pg_stat_statements` для анализа производительности запросов:

```sql
CREATE EXTENSION pg_stat_statements;
```

Добавьте его в `shared_preload_libraries`.

### 6.6. Автоматическое резервное копирование

Настройте регулярные дампы (например, через `pg_dumpall` или `pg_basebackup`) и архивирование WAL. Для этого используйте cron или специальные инструменты (например, `barman`, `wal-g`).

### 6.7. Обновления и патчи

Подписывайтесь на рассылки безопасности PostgreSQL. При выходе новых минорных версий обновляйте пакеты через `apt update && apt upgrade`. Перед обновлением всегда создавайте полный бэкап.

### 6.8. Использование pg_hba.conf с принципом минимальных привилегий

Настраивайте правила максимально узко: указывайте конкретные базы данных, пользователей и IP-адреса. Не используйте `all` для удалённых подключений без крайней необходимости.

### 6.9. Автоматизация с помощью Ansible/Puppet

Для управления конфигурацией на нескольких серверах используйте системы управления конфигурациями. Это позволит централизованно поддерживать одинаковые настройки и быстро разворачивать новые инстансы.

## 7. Проверка установки и базовые команды

После всех настроек выполните проверку:

- Подключитесь к базе от имени приложения.
- Выполните простой запрос: `SELECT version();`
- Проверьте, что параметры применены: `SHOW all;` или через `pg_settings`.

Посмотрите логи на предмет ошибок:

```bash
sudo tail -f /var/log/postgresql/postgresql-17-main.log
```

Убедитесь, что автовакуум запущен (проверьте через `pg_stat_all_tables`).

- Как безопасно создать пользователей и базы данных.
- Как разрешить удалённый доступ, не нарушая безопасность.
- Дополнительные лучшие практики для продакшена: SSH-туннели, SSL, мониторинг, резервное копирование и автоматизация.
