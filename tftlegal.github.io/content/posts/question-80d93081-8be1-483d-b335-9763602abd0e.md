## Главная идея

**«Усложняй по боли, не заранее»**

Это фундаментальный принцип всего документа. Архитектура не должна быть спроектирована «на вырост». Каждый этап усложнения появляется только тогда, когда вы сталкиваетесь с реальной проблемой (болью), и конкретное решение устраняет именно эту боль. Не раньше.

Это противостоит распространённой ошибке новичков — сразу строить микросервисы, внедрять DDD, CQRS и другие паттерны в проект из 200 строк кода.

## Этап 1: Handler / Service / Repository

### Почему именно три слоя?

Документ утверждает, что существует **три типа изменяемых требований**, и каждый тип изолируется своим собственным слоем:

*   **Handler** — только транспорт.
*   **Repository** — только работа с БД.
*   **Service** — мозг. Не знает про HTTP и БД.

### Ключевой принцип

> **Три причины — три слоя. Это не набор вычур, а логика.**

## Этап 2: Interfaces and Validation (Интерфейсы и Валидация)

### Разделение валидации

Критическое архитектурное решение:

*   **Структурная валидация:** Проверяет, корректен ли формат данных (например, `quantity > 0`). Это забота Транспорта.
*   **Бизнес-валидация:** Проверяет правила, установленные в бизнес-логике (например, `stock >= quantity`). Это забота Сервиса.

### Где должно жить интерфейс? (Идиома Go)

В Go интерфейсы определяются **потребителем**, а не производителем.

**✅ Правильный Go-подход:** Определить интерфейс в пакете, где он будет использоваться (например, в `service`), а не в пакете, где он реализуется (`repository`).

### Идиомы Go: три правила

1.  **Принимать интерфейсы, возвращать конкретные типы:** Когда функция принимает реализацию, она должна принимать интерфейс. Когда она возвращает результат, она должна возвращать конкретный тип.
2.  **Частная структура, публичный конструктор:** Структура должна быть "скрыта" (`service`), и доступ к ней должен быть через конструктор (`NewService`), чтобы гарантировать корректную инициализацию.
3.  **Мелкие интерфейсы (1–3 метода):** Интерфейс должен делать одну, четко определенную вещь.

## Этап 3: Multiple Services + Atomicity (Мультисервисы и Атомарность)

### Проблема: Состояние гонки (Race Condition)

При работе с множеством сервисов и общим состоянием возникают проблемы конкурентности.

**Решение:** Использование мьютексов (`sync.Mutex`) или, что более важно для распределенных систем, использование **транзакций с блокировкой** (оптимистической или пессимистической).

### Чеклист: когда разбивать на сервисы

*   Разбивайте, когда разные домены имеют четко разделенные обязанности.
*   Один сервис может использовать несколько репозиториев.

## Этап 4: Rich Domain Model (DDD)

### Проблема: Анемичная модель

В анемичной модели вся логика уходит в Сервис, и структура данных (`struct`) становится просто "сумкой данных", без привязки к бизнес-правилам.

### Решение: Богатая модель (Rich Model)

*   **Value Object:** Валидируется при создании (например, `HullStrength`).
*   **Entity:** Логика помещается **рядом с данными** (например, `Hull.CanSupport()`).
*   **Сервис становится тонким:** Он оркестрирует, но логика находится в доменном объекте.

### Разделение моделей

Вы должны работать с **тремя моделями**:
1.  **Доменная модель:** Бизнес-логика и инварианты.
2.  **Модель персистентности:** Как это хранится в БД.
3.  **Модель Транспорта (DTO):** Как это передается через API.

## Этап 5: Anti-Corruption Layer (ACL)

### Проблема: Загрязнение домена

При работе с внешним API (поставщиком) его терминология (например, `vendor_sku`, `base_cost_credits`) проникает в ваш чистый домен.

### Решение: ACL

**Адаптер (ACL):** Служит переводчиком. Он знает о специфике внешнего источника (например, JSON) и переводит его в вашу собственную, чисто доменную терминологию (например, `Money` вместо `credits`).

**Результат:** Ваша система изолирована от изменений в сторонних системах.

## Этап 6: CQRS-lite (Модели для чтения)

### Проблема: Чрезмерная нагрузка при чтении

Загрузка всего агрегата для отображения всего 4-х полей.

### Решение: Читающий модель (Read Model)

*   **Что это:** Плоская, денормализованная структура, оптимизированная для **отображения** (UI), а не для бизнес-логики.
*   **Как это работает:** Вместо того чтобы выполнять сложные JOIN'ы, вы используете прямой, оптимизированный SQL-запрос для нужного вам среза данных.
*   **Разделение путей:**
    *   **Путь записи (Write Path):** Полный, агрегированный домен (для поддержания инвариантов).
    *   **Путь чтения (Read Path):** Прямой, плоский запрос (для скорости).

### Ключевой принцип

> **Агрегат $\rightarrow$ МЕНЯЕШЬСЯ (инварианты) $\cdot$ Модель чтения $\rightarrow$ ДЛЯ ДИСПЛЕЯ (оптимизировано)**

Этот документ демонстрирует **прогрессивный** подход к архитектуре. Большинство проектов будут довольствоваться стадией 1 или 2. Ключ — распознать **когда** каждый этап становится необходимым.

## Этап 0: Одна машина, один процесс

### Суть

Один сервер. Один процесс. Одна база данных. Никаких балансировщиков, кешей или очередей.

```
[Клиент] → [Сервер приложения (CPU + RAM + Disk)] → [PostgreSQL на том же диске]
```

### Когда это достаточно

| Условие | Пояснение |
|---|---|
| < 1000 одновременных пользователей | Современный сервер справляется с ~10k–50k req/s для простых API |
| < 100 ГБ данных | Помещается в RAM или на один SSD |
| < 100 МБ/с пропускной способности | Полностью в пределах одного NIC |
| Нет строгих SLA (99.9% вполне приемлемо) | Простой недоступности в несколько минут допустим |
| Небольшая команда (1–3 инженера) | Операционная сложность должна соответствовать размеру команды |

### Почему начинать с этого?

- **Простота — это функция.** Одна машина = одно место для поиска при сбое.
- **Нет сетевого разделения.** Все данные локальны. Транзакции ACID тривиальны.
- **Быстрая итерация.** Развернуть = перезапустить процесс. Нет миграций между узлами.
- **Стоимость.** Одна ВМ дешёва. Распределенная система требует 10+ машин, чтобы окупиться.

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| CPU/RAM постоянно > 70% | Вы достигаете аппаратного лимита |
| Запросы к БД > 100мс при нагрузке | Узким местом является I/O диска или сложность запроса |
| Вам нужна доступность 99.9%+ | Одиночная точка отказа недопустима |
| Данные не помещаются в RAM | Требуется шард или кеширование |
| Соотношение чтение/запись сильно смещено | Требуется разделение чтещих и пишущих путей |

## Этап 1: Добавление балансировщика и нескольких серверов приложений

### Проблема

Один сервер приложений = единая точка отказа. Если он падает, вся система останавливается. Кроме того, невозможно горизонтально масштабировать.

### Решение

```
[Клиент] → [Балансировщик] → [Сервер 1]
                                                  → [Сервер 2]
                                                  → [Сервер 3]
```

### Ключевые концепции

#### Балансировщик
- **Уровень 4 (TCP):** Перенаправляет чистые TCP-соединения. Быстро, просто. (например, HAProxy, AWS NLB)
- **Уровень 7 (HTTP):** Понимает HTTP. Может маршрутизировать по пути, заголовку, cookie. (например, Nginx, AWS ALB)

**Объяснение:** Балансировщик распределяет трафик между серверами. Он также обеспечивает:
- **Проверки работоспособности:** Удаление нездоровых серверов из ротации
- **Постоянство сессий (sticky sessions):** Удержание пользователя на том же сервере (если необходимо)
- **Терминация SSL:** Дешифровать TLS на LB, отправлять в бэкенды незашифрованный трафик.

#### Stateless-серверы приложений
**Критическое требование:** Серверы должны быть **без сохранения состояния (stateless)**. Все данные сессии должны храниться во внешнем хранилище (Redis, JWT токены).

```
❌ Stateful: Сессия хранится в памяти сервера → нельзя масштабировать, невозможно переключиться
✅ Stateless: Сессия в Redis / JWT → любой сервер может обработать запрос
```

**Почему?** Если сервер выйдет из строя, балансировщик направить трафик на другой сервер. Если сессия в памяти, пользователь выходит из системы. Если сессия в Redis, пользователь продолжает работать бесшовно.

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| БД — узкое место (CPU > 80%, медленные запросы) | Серверы приложений в порядке, но БД не успевает |
| Нужна кеширование горячих данных | Многократные запросы к БД для одной и той же информации |
| Соотношение чтение/запись > 10:1 | Чтение доминирует, требуются реплики |
| Нужно развязывать медленные операции | Почта, обработка видео и т.д. |

## Этап 2: Масштабирование БД (Репликация + Кеширование)

### Проблема

База данных становится узким местом. Одиночная инстанция PostgreSQL может справляться с ~10k–50k QPS. Для большего масштаба требуется масштабирование.

### Решение A: Репликаторы чтения (Read Replicas)

```
[Серверы приложений] → [Основная БД (запись)]
                   ↓ (асинхронная репликация)
              [Репликатор 1]
              [Репликатор 2]
```

**Как это работает:**
- Все **записи** идут в основную БД.
- **Чтения** распределяются по репликаторам.
- Репликация **асинхронная** (по умолчанию) $\rightarrow$ реплики могут быть немного отстающими

**Ключевые соображения:**

| Аспект | Объяснение |
|---|---|
| **Задержка репликации** | Пользователь записывает данные, затем немедленно читает $\rightarrow$ может увидеть устаревшие данные. Решение: чтение из основной БД для "чтения ваших записей" |
| **Переключение** | Если основная БД падает, её можно повысить до статуса репликатора. Время простоя = секунды до минут. Используйте инструменты типа Patroni, RDS Multi-AZ |
| **Масштабирование записи** | Репликаторы **не** помогают для записи. Остается один писатель |

**Когда использовать:** Сильно нагруженные на чтение рабочие нагрузки (фиды соцсетей, каталоги).

### Решение B: Кеширование (Redis / Memcached)

```
[Серверы приложений] → [Кеш (Redis)] → [Основная БД]
                   ↓ (пропуск)
              [Репликаторы чтения]
```

**Как это работает:**
- Горячие данные хранятся во в памяти.
- **Промах кеша** $\rightarrow$ запрос к БД, заполнение кеша.

**Ключевые паттерны:**

| Паттерн | Описание | Когда использовать |
|---|---|---|
| **Cache-aside** | Приложение проверяет кеш, если промах — запрашивает БД и заполняет кеш | Самый распространенный. Простой. |
| **Read-through** | Кеш прозрачно подгружает из БД | Когда вы хотите скрыть доступ к БД от приложения |
| **Write-through** | Запись в кеш и БД одновременно | Когда нужна немедленная согласованность |
| **Write-behind** | Запись в кеш, асинхронный сброс в БД | Когда допустима кратковременная несогласованность |

**Критические проблемы:**

| Проблема | Объяснение |
|---|---|
| **Инвалидация кеша** | "Две сложные проблемы в CS: инвалидация кеша и наименование" (т.е. как валидировать данные) |
| **Стампинг кеша** | Популярный ключ истек $\rightarrow$ 1000 запросов одновременно бьют в БД |
| **Горячие ключи** | Один ключ получает 90% трафика. Решение: локальный кеш, шардинг ключа |
| **Ограничение памяти** | Redis в памяти. Если данных не хватает, нужен механизм вытеснения (LRU, LFU) |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Одна БД не справляется с записью | Необходим шардинг базы данных |
| Объем данных > 1 ТБ | Одна дисковая система слишком медленна / дорога |
| Нужно развязывать медленные операции | Почта, видеообработка, уведомления |
| Нужно справляться с всплесками трафика | Всплески трафика перегружают систему |

## Этап 3: Шардинг базы данных (Горизонтальное разделение)

### Проблема

Единственная база данных имеет лимит по:
- **Хранилищу** (размер диска)
- **Пропускной способности** (CPU, I/O)
- **Параллельным подключениям**

Когда вы превышаете эти лимиты, вам нужно **шардировать** данные на несколько баз.

### Как работает шардинг

```
[Серверы приложений] → [Роутер Шарда]
                   ↓
              [Шард 1: user_id % 4 == 0]
              [Шард 2: user_id % 4 == 1]
              [Шард 3: user_id % 4 == 2]
              [Шард 4: user_id % 4 == 3]
```

**Ключ шардинга (shard key):** Поле, используемое для определения, в какой базе хранится запись. Распространенные варианты: `user_id`, `order_id`, `tenant_id`.

### Стратегии шардинга

| Стратегия | Описание | Плюсы | Минусы |
|---|---|---|---|
| **По диапазону** | Шард 1: user\_id 1–1М, Шард 2: 1М–2М | Легко делать запросы по диапазону | "Горячие точки" (самый новый шард получает весь трафик) |
| **По хешу** | shard = hash(user\_id) % N | Равномерное распределение | Сложно выполнять запросы по диапазону |
| **Таблица поиска** | Сопоставить user\_id $\rightarrow$ ID шарда | Гибкий | Требуется дополнительный поиск |
| **База данных** | Каждому шарду своя база | Простое управление | Ручное управление |

### Ключевые проблемы

| Проблема | Объяснение |
|---|---|
| **Кросс-шардовые запросы** | "Получить все заказы для пользователя X" легко (тот же шард). "Получить все заказы в 2024" требует запросить ВСЕ шарды |
| **Кросс-шардовые транзакции** | ACID между шардами сложен. Решение: паттерн сага (постепенная согласованность) |
| **Перебалансировка** | Добавление шарда требует перемещения данных. Решение: консистентное хеширование, виртуальные узлы |
| **Выбор ключа** | Если вы шардируете по `user_id`, вы не можете эффективно искать по `email`. Решение: денормализация, вторичные индексы |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Нужен независимый откат | Разные части системы требуют разного масштабирования |
| Размер команды > 10 | Нужен независимый деплоймент, независимое масштабирование |
| Разные жизненные циклы данных | Логи (однократная запись) против данных пользователя (тяжелое чтение) |
| Разные технологические стеки | ML-сервис требует GPU, API-сервис — низкая задержка |

## Этап 4: Микросервисы / Декомпозиция

### Проблема

Монолит становится сложным, потому что его трудно:
- **Масштабировать** (одна часть требует 10х больше CPU, другая — 10х больше RAM)
- **Развёртывать** (одно изменение требует перезапуска всей системы)
- **Обслуживать** (огромная кодовая база, команды мешают друг другу)
- **Инновации** (разные части требуют разных стеков технологий)

### Решение: Декомпозиция в сервисы

```
[Клиент] → [API Gateway]
              ↓
         [Сервис Пользователя]    [Сервис Заказов]    [Сервис Платежей]
              ↓                       ↓                     ↓
         [База Данных Пользователя] [База Данных Заказов] [База Данных Платежей]
```

### Ключевые принципы

#### 1. Каждый сервис владеет своими данными
**База данных на сервис.** Никаких общих баз данных. Никаких кросс-сервисных JOIN'ов.

```
❌ Монолит: SELECT u.name, o.total FROM users u JOIN orders o ON u.id = o.user_id
✅ Микросервисы: Сервис Пользователя возвращает пользователя, Сервис Заказов — заказ, API Gateway объединяет ответ
```

**Почему?** Общие базы данных создают жёсткую связанность (coupling). Если два сервиса имеют общую БД, они не могут эволюционировать независимо.

#### 2. Коммуникация через API

| Метод | Описание | Когда использовать |
|---|---|---|
| **Синхронный (REST/gRPC)** | Запрос-ответ. Вызывающий ждет ответа. | Когда вам нужен немедленный результат |
| **Асинхронный (Message Queue)** | Публикация-подписка. Вызывающий не ждет. | Когда допустима задержка, требуется декуплинговать |

**Синхронный vs. Асинхронный:**
*Синхронный:* [Сервис Заказов] $\rightarrow$ [Сервис Платежей] $\rightarrow$ Ответ
*(Если платеж недоступен, заказ проваливается)*

*Асинхронный:* [Сервис Заказов] $\rightarrow$ [Kafka] $\rightarrow$ [Сервис Платежей]
*(Если платеж недоступен, сообщение ставится в очередь, переотрабатывается позже)*

#### 3. API Gateway

Единая точка входа для всех запросов клиентов. Он управляет:
- **Маршрутизацией:** `/users/*` $\rightarrow$ Сервис Пользователя, `/orders/*` $\rightarrow$ Сервис Заказов
- **Аутентификация:** Валидация токена, передача контекста пользователя дальше
- **Ограничение частоты:** Защита сервисов от злоупотреблений
- **Агрегация:** Комбинирование ответов из нескольких сервисов
- **Терминация SSL**

#### 4. Сервисное обнаружение (Service Discovery)

Как Сервис А находит Сервис Б?
*DNS* или *Реестр сервисов* (Consul, Eureka, Kubernetes Service).

### Ключевые проблемы

| Проблема | Объяснение |
|---|---|
| **Транзакции** | ACID между сервисами невозможны. Используйте паттерн сага (последовательность локальных транзакций + компенсирующие действия) |
| **Сетевые сбои** | Любой сетевой вызов может завершиться неудачей. Нужно использовать ретраи, таймауты, обрывание контура (circuit breakers) |
| **Согласованность данных** | Неизбежна *постепенная согласованность* (Eventual Consistency). Стройте на этом. |
| **Операционная сложность** | 10 сервисов = 10 развертываний, 10 панелей мониторинга, 10 источников логов |
| **Задержка** | 5 синхронных вызовов = 5x сетевая задержка. Используйте асинхронность, где это возможно |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Нужна доступность 99.99%+ | Одна область может выйти из строя (отказ ЦОД) |
| Глобальные пользователи (задержка > 200мс) | Пользователи в Азии требуют обслуживания из США |
| Соблюдение требований к данным (GDPR) | Данные должны оставаться в определенных регионах |
| Необходимость справиться с массовым масштабом | 100М+ пользователей, 1 млрд+ запросов в день |

## Этап 5: Многорегиональный / Глобальный развертывание

### Проблема

В одной области есть:
- **Задержка:** Пользователи в Азии, обращающиеся к серверу в США, имеют задержку 200 мс+
- **Доступность:** Отказ ЦОДа останавливает всю систему
- **Соответствие требованиям:** Данные должны оставаться в определенных юрисдикциях

### Решение: Многорегиональное развертывание

```
[Пользователи США] → [Регион США] → [База данных США]
[Пользователи ЕС] → [Регион ЕС] → [База данных ЕС]
[Пользователи Азии] → [Регион Азии] → [База данных Азии]

         [Глобальный DNS / Anycast]
```

### Ключевые концепции

#### Активно-Активно vs. Активно-Пассивно

| Режим | Описание | Плюсы | Минусы |
|---|---|---|---|
| **Активно-Активно** | Все регионы обрабатывают чтение И запись | Лучшая задержка, лучшая доступность | Сложная синхронизация данных, разрешение конфликтов |
| **Активно-Пассивно** | Один регион — первичный, остальные — бэкапы | Проще, консистентен | Переключение занимает время, бэкапы простаивают |

#### Репликация данных между регионами

*   **Асинхронная репликация:** Основной писатель, реплики синхронизируют асинхронно. Задержка = секунды.
*   **Синхронная репликация:** Основной писатель ждет подтверждение от реплики. Консистентно, но медленно.
*   **CRDTs:** Типы данных, устойчивые к конфликтам (Conflict-free replicated data types). Созданы для конечной согласованности.
*   **Event Sourcing:** Репликация событий, а не состояния. Каждый регион применяет события независимо.

#### Разрешение конфликтов

Когда два региона записывают одни и те же данные одновременно:

*   **"Последняя запись побеждает"** (Last-write-wins): Самый простой. Использовать временные метки.
*   **Векторные часы:** Отслеживание причинности. Выявление конфликтов.
*   **Логика на уровне приложения:** Бизнес-логика разрешает конфликты (например, "более высокий баланс побеждает").
*   **CRDTs:** Математически гарантированная конвергенция.

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Теорема CAP** | Вы не можете иметь Согласованность, Доступность и Разделение одновременно. Выбирайте компромисс. |
| **Сеть** | Регионы могут стать недоступными. Нужно решать: возвращать устарелые данные или ошибки |
| **Суверенитет данных** | Данные должны оставаться в конкретных юрисдикциях. Тщательно проектировать границы данных |
| **Стоимость** | Многорегиональность = 3x стоимость инфраструктуры |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обслуживать 100М+ пользователей | Единая архитектура не может масштабироваться |
| Необходимость обрабатывать неограниченные потоки данных | Логи, клики, сенсоры |
| Необходимость построить платформу | Внутренние команды строят на вашей инфраструктуре |
| Необходимость оптимизировать стоимость при масштабе | Каждая миллисекунда и каждый доллар имеют значение |

## Этап 6: Архитектура, управляемая событиями / Потоковая обработка

### Проблема

Синхронный запрос-ответ не справляется для:
- **Высокопоточных событий** (1М+ событий/сек)
- **Неограниченных данных** (логи, клики, сенсоры)
- **Декуплированной обработки** (несколько потребителей, разные скорости)
- **Реального времени** (нужно обрабатывать данные по мере их поступления)

### Решение: Брокер сообщений / Потоковый процессор

```
[Продуценты] → [Kafka / Pulsar / Kinesis] → [Потребитель 1: Аналитика]
                                        → [Потребитель 2: Уведомление]
                                        → [Потребитель 3: ML-пайплайн]
```

### Ключевые концепции

#### Брокер сообщений vs. Потоковый процессор

| Признак | Брокер сообщений (RabbitMQ) | Потоковый процессор (Kafka) |
|---|---|---|
| **Удержание данных** | Удаляется после потребления | Сохраняется на дни/недели |
| **Потребители** | Один потребитель на сообщение | Несколько потребителей, каждый читает независимо |
| **Повтор** | Нет | Да (чтение с любого смещения) |
| **Пропускная способность** | ~100k msg/s | ~1М+ msg/s |
| **Применение** | Очереди задач, RPC | Потоки событий, аналитика |

#### Ключевые концепции Kafka

*   **Topic:** Категория сообщений (например, `orders`, `clicks`).
*   **Partition:** Тема разделяется на партиции. Каждая партиция упорядочена.
*   **Offset:** Позиция в партиции. Потребители отслеживают свой смещение.
*   **Группа потребителей:** Множество потребителей, использующих одну тему. Каждая партиция обрабатывается одним потребителем в группе.
*   **Репликация:** Каждая партиция реплицируется между брокерами для отказоустойчивости.

#### Паттерны, управляемые событиями

*   **Уведомление о событии:** "Что-то произошло" (без данных). Потребитель запрашивает детали.
*   **Передача состояния через событие:** Событие содержит все необходимые данные. Потребитель не запрашивает данные.
*   **Source of Truth (Event Sourcing):** Хранить события, а не состояние. Состояние = суммирование всех событий.
*   **CQRS:** Отделение читающей и пишущей моделей. События их связывают.

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Порядок** | В пределах партиции порядок гарантирован. Между партициями — нет. Используйте ключ партиции (например, `user_id`) для обеспечения порядка по пользователю. |
| **Обратная нагрузка** | Если потребители медленны, сообщения накапливаются. Нужно управлять задержкой. |
| **Точно один раз** | Сложно достичь. Используйте идемпотентные потребители + транзакционные продюсеры. |
| **Эволюция схемы** | Продуценты и потребители могут иметь разные версии. Используйте реестр схем (Avro, Protobuf) |
| **Отладка** | Распределенные, асинхронные, сложно отследить. Используйте распределенный трейсинг (Jaeger, Zipkin) |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Требуется обработка 1 млрд+ пользователей | Нужно оптимизировать стоимость, задержку и масштаб одновременно |
| Необходимость обслуживать несколько продуктовых линий | Разные SLA, разные модели данных |
| Необходимость построить платформу | Внутренние команды строят на вашей инфраструктуре |
| Необходимость оптимизировать стоимость при масштабе | Каждая миллисекунда и каждый доллар имеет значение |

## Этап 7: Платформа / Мультипользовательский / Пограничный (Edge)

### Проблема

При таком масштабе вы не просто создаете продукт — вы создаете **платформу**. Вызовы:
- **Мультипользовательский режим:** Многие клиенты на одной инфраструктуре
- **Пограничные вычисления (Edge computing):** Обработать данные близко к пользователю (IoT, AR/VR)
- **Оптимизация стоимости:** Каждая ошибка в расчете затрат важна при масштабе
- **Опыт разработчика:** Внутренние команды должны иметь возможность самообслуживания инфраструктурой

### Ключевые концепции

#### Мультипользовательский режим

| Модель | Описание | Плюсы | Минусы |
|---|---|---|---|
| **Общая все** | Все клиенты делят БД, приложение, инфраструктуру | Самый дешёвый | Нет изоляции, "шумный сосед" |
| **Общая БД, отдельные схемы** | Каждый клиент имеет собственную схему | Умеренная изоляция | Ограничения БД (например, 1000 схем) |
| **Отдельная БД на клиента** | Каждый клиент имеет собственную БД | Полная изоляция | Дорого, сложная настройка |
| **Отдельная инфраструктура** | Каждый клиент имеет свой кластер | Максимальная изоляция | Очень дорого |

#### Пограничные вычисления (Edge Computing)

```
[Устройство] → [Пограничный узел (Edge Node)] → [Облако (Центр)]
              ↓
         [Локальная обработка]
         [Низкая задержка]
         [Возможность работы офлайн]
```

**Когда использовать:**
- IoT устройства (сенсоры, камеры)
- AR/VR (задержка < 20мс)
- Приложения, работающие офлайн
- Защита данных (обработка локально)

#### Оптимизация стоимости при масштабе

| Техника | Описание |
|---|---|
| **Spot Instances** | Использование дешёвых, прерываемых ВМ для отказоустойчивых рабочих нагрузок |
| **Автомасштабирование** | Масштабирование вверх/вниз на основе нагрузки |
| **Кеширование** | Снижение затрат на сеть и хранение |
| **Сжатие** | Снижение сетевых и дисковых затрат |
| **Serverless** | Плата за вызов, а не за час |
| **Многоуровневое хранение** | Горячие данные на SSD, холодные — на S3 |
| **Serverless** | Плата за вызов, а не за час |

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **"Шумный сосед"** | Одна рабочая нагрузка влияет на других. Решение: квоты на ресурсы, изоляция |
| **Притяжение данных** | Данные стоят дорого для перемещения. Обрабатывайте данные там, где они живут |
| **Сложность** | Платформа = в 100 раз больше движущихся частей. Требуется сильная команда SRE |
| **Безопасность** | Мультипользовательский режим = поверхность атаки. Требуется сильная изоляция и аудит |

## 5 Главных принципов Системного Дизайна

1. **Масштабируй по узкому месту, не по амбициям** — Измеряйте сначала. Найдите реальный узкий момент. Решите его. Не добавляйте Kafka к системе с 100 пользователями.
2. **Начинай просто, добавляй сложность, когда это нужно** — Одна база данных может справиться с большинством стартапов. Добавьте репликаторы, затем шард, затем микросервисы — только когда боль того требует.
3. **Проектируй для сбоев** — Каждый сетевой вызов может завершиться неудачей. Каждая дисковая система может выйти из строя. Каждая область может упасть. Стройте ретраи, таймауты, обрывание контура, и отказ от самого начала.
4. **Оптимизируйте для 95-го процентиля, а не для 100-го** — Не переоптимизируйте для самого редкого случая. Справиться со средним случаем хорошо, а для редкого — иметь запасной план.
5. **Операционная сложность — это стоимость** — Каждый новый компонент (Kafka, Redis, Kubernetes) добавляет операционный балласт. Убедитесь, что команда может управлять им. Если нет — не добавляйте его.

## Финальные мысли

Дизайн системы — это не знание "правильной" архитектуры. Это **построение компромиссов** и **обоснование их** на основе ваших конкретных ограничений:

- **Масштаб:** Сколько пользователей? Какой объем данных? Какая пропускная способность?
- **Задержка:** Насколько быстрыми должны быть ответы?
- **Доступность:** Насколько допустим простой?
- **Согласованность:** Насколько свежими должны быть данные?
- **Стоимость:** Какой бюджет?
- **Команда:** Сколько инженеров? Каков их профиль?

Лучший дизайн системы — это **самый простой, который соответствует вашим требованиям**. Всё остальное — переоптимизация.

> **"Лучшая архитектура — та, которую вы можете эксплуатировать."**

# Микросервисная архитектура: от Monolith к Distributed System — 7 этапов эволюции

## Главная идея

**«Разделяй по границам, а не по размеру»**

Микросервисы — это не «маленькие сервисы». Это **автономные, независимо развёртываемые единицы**, которые владеют своими данными и общаются через явно определённые API.

Цель не в том, чтобы «иметь микросервисы». Цель — **развязать изменения** так, чтобы разные части системы могли развиваться, масштабироваться и выходить из строя независимо.

Многие ошибки в микросервисах возникают из-за разделения монолита по **техническим слоям** (UI, Сервис, База данных), а не по **бизнес-способностям**.

---

## Этап 0: Монолит

### Суть

Одна кодовая база. Одна единица развёртывания. Одна база данных. Один процесс (или несколько реплик).

```
[Клиент] → [Монолитное приложение] → [Одна База Данных]
```

### Когда это достаточно

| Условие | Пояснение |
|---|---|
| < 50 тыс. строк кода | Одна команда может понять всю систему |
| < 10 разработчиков | Нет конфликтов слияния, нет границ команд |
| Единые потребности в масштабировании | Все части масштабируются вместе |
| Простой домен | Нет сложных границ в бизнесе |
| Требуется быстрая итерация | Развёртывание = один артефакт |

### Почему начинать здесь?

- **Простота.** Одна кодовая база, одна развёртываемая единица, одна БД. Легко отладка.
- **Производительность.** Нет сетевых вызовов между компонентами. Внутрипроцессные вызовы быстры.
- **Транзакции.** ACID по всей системе тривиален.
- **Стоимость.** Одна кластерная система. Распределенная система требует много инфраструктуры.

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Код > 100 тыс. строк | Сложно навигация, сложно тестировать |
| Команда > 10 разработчиков | Конфликты слияния, конфликты развёртывания |
| Разные потребности в масштабировании | Одна часть требует 10х CPU, другая 10х RAM |
| Разные циклы выпуска | Одна часть меняется ежедневно, другая — ежемесячно |
| Разные технологические стеки | ML-сервис требует Python, API — Go |

## Этап 1: Модульный Монолит

### Проблема

Монолит превращается в «большой беспорядок» — запутанный код, нет чётких границ, изменения влияют на всё.

### Решение: Внедрение границ внутри монолита

```
[Клиент] → [Монолитное приложение]
              ├── [Модуль Пользователя]
              ├── [Модуль Заказов]
              ├── [Модуль Платежей]
              └── [Модуль Уведомлений]
                   ↓
              [Одна База Данных]
```

### Ключевые принципы

#### 1. Модули = будущие границы сервисов

Каждый модуль является **ограниченным контекстом** (понятие DDD). Он имеет:
- **Свою модель данных** (таблицы, сущности)
- **Свою бизнес-логику**
- **Свой API** (внутренний, внутрипроцессный)

```go
// ❌ Плохо: Модули вызывают внутренности друг друга
func (o *OrderService) CreateOrder(req OrderRequest) {
    user := o.userRepo.Get(req.UserID) // Прямой доступ к БД пользователя
    o.paymentRepo.Charge(req.Amount)   // Прямой доступ к БД платежей
}

// ✅ Хорошо: Модули вызывают API друг друга
func (o *OrderService) CreateOrder(req OrderRequest) {
    user := o.userAPI.Get(req.UserID)  // Внутренний вызов API
    o.paymentAPI.Charge(req.Amount)    // Внутренний вызов API
}
```

#### 2. База данных на модуль (логическое разделение)

Даже в монолите каждый модуль должен иметь свои таблицы. Нет кросс-модульных JOIN'ов.

```sql
-- ❌ Плохо: JOIN между модулями
SELECT o.id, u.name, p.status
FROM orders o
JOIN users u ON o.user_id = u.id
JOIN payments p ON o.id = p.order_id;

-- ✅ Хорошо: Модуль запрашивает свои данные, собирает их через API
-- Модуль Заказов: SELECT * FROM orders WHERE id = ?
-- Модуль Пользователя: SELECT * FROM users WHERE id = ?
-- Модуль Платежей: SELECT * FROM payments WHERE order_id = ?
```

#### 3. Нет общего кода (кроме утилит)

Модули не должны иметь общего бизнес-логического кода. Общий код = связанность.

```
❌ Общий: user_service.go, order_service.go оба импортируют "internal/models"
✅ Изолированный: user/models, order/models, payment/models (отдельные пакеты)
```

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Потребность в независимом развёртывании | Один модуль меняется ежедневно, другой — ежемесячно |
| Потребность в независимом масштабировании | Одна часть требует 10x больше ресурсов |
| Потребность в разных стеках | ML-модуль требует Python, API — Go |
| Границы команды совпадают с модулями | Каждая команда владеет одним модулем |

## Этап 2: Извлечение первого сервиса (Strangler Pattern)

### Проблема

Вы хотите извлечь один модуль в отдельный сервис, но вы ещё не готовы к полноценным микросервисам.

### Решение: Извлечение одного сервиса, остальное в монолите

```
[Клиент] → [API Gateway]
              ├── [Монолитное приложение]
              │     ├── [Модуль Пользователя]
              │     ├── [Модуль Заказов]
              │     └── [Модуль Уведомлений]
              │
              └── [Сервис Платежей] (отдельный процесс)
                    ↓
               [База Данных Платежей]
```

### Ключевые концепции

#### Паттерн Стражащего Фигового Дерева (Strangler Fig Pattern)

Постепенная замена частей монолита сервисами:

```
Фаза 1: [Монолит] обрабатывает всё
Фаза 2: [API Gateway] маршрутизирует /payments/* → [Сервис Платежей]
         [Монолит] обрабатывает всё остальное
Фаза 3: [API Gateway] маршрутизирует /orders/* → [Сервис Заказов]
         [Монолит] обрабатывает всё остальное
Фаза 4: [Монолит] пуст → удаляй его
```

**Почему это работает:**
- Не нужно делать "большой взрыв" (big-bang)
- Каждое извлечение мало и тестируемо
- Вы можете остановиться в любой точке
- Монолит уменьшается со временем

#### API Gateway

Единая точка входа для всех запросов клиентов. Он управляет:
- **Маршрутизацией:** `/payments/*` $\rightarrow$ Сервис Платежей, `/users/*` $\rightarrow$ Монолит
- **Аутентификация:** Валидация JWT, передача контекста пользователю
- **Ограничение частоты:** Защита сервисов от злоупотреблений
- **Агрегация:** Комбинирование ответов из нескольких сервисов

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Согласованность данных** | Монолит и сервис имеют разные БД. Как поддерживать их синхронизацию? |
| **Распределенные транзакции** | ACID между монолитом и сервисом сложен. Используйте паттерн сага |
| **Сетевые сбои** | Каждый вызов к сервису может потерпеть неудачу. Нужно использовать ретраи, таймауты, обрывание контура |
| **Операционная сложность** | Теперь у вас 2 развертывания, 2 панели мониторинга, 2 источника логов |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость асинхронной связи | Синхронные вызовы создают жесткую связанность |
| Нужен брокер сообщений | Нужно обрабатывать всплески трафика |
| Нужен откат (replay) | Отладка, аудит, повторная обработка |
| Необходимость декуплинговать продюсеров и потребителей | Разные скорости обработки |

## Этап 3: Общение Сервис-Сервис (EDA)

### Проблема

При наличии нескольких сервисов вам нужен надежный способ их связи.

### Решение A: Синхронная связь (REST/gRPC)

```
[Сервис Заказов] → [Сервис Платежей] → ответ
```
**Когда использовать:**
- Вам нужен немедленный результат.
- Вызывающий должен знать, удался ли операционный вызов.
- Низкая задержка критична.

**Ключевые паттерны:**
*   **Запрос-ответ**
*   **Circuit Breaker** (если сервис постоянно падает, прекратите вызывать его)
*   **Повторные попытки с задержкой**
*   **Таймаут** (не ждать вечно)

### Решение B: Асинхронная связь (Брокер сообщений)

```
[Сервис Заказов] → [Kafka] → [Сервис Платежей]
[Сервис Заказов] → [Kafka] → [Сервис Уведомлений]
[Сервис Заказов] → [Kafka] → [Сервис Аналитики]
```

**Когда использовать:**
- Вы не ждете немедленного результата.
- Несколько потребителей нуждаются в одном событии.
- Вы хотите отвязать продюсеров и потребителей.
- Нужна буферизация для всплесков трафика.

### Синхронная vs. Асинхронная

| Критерий | Синхронный | Асинхронный |
|---|---|---|
| **Задержка** | Низкая (немедленная) | Высокая (отложенная) |
| **Связанность** | Жесткая (вызывающий ждет) | Слабая (вызывающий не ждет) |
| **Обработка сбоев** | Обработчик должен обработать ошибки | Сообщение переотрабатывается |
| **Масштабируемость** | Ограничена вызывающей стороной | Масштабируется независимо |
| **Сложность** | Простая | Сложная |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Потребность в обработке 1000+ событий/сек | Брокер сообщений является узким местом |
| Потребность в обработке событий в реальном времени | Пакетирование слишком медленно |
| Необходимость повторной обработки событий | Отладка, аудит |
| Необходимость отвязать продюсеров и потребителей | Разные скорости обработки |

## Этап 4: Архитектура, управляемая событиями (EDA)

### Проблема

Синхронная связь создает жесткую связанность. Если сервис платежей недоступен, сервис заказов не может работать. Требуется **декуплинг**.

### Решение: Архитектура, управляемая событиями (EDA)

```
[Сервис Заказов] → [Kafka: "order.created"]
                     ↓
                  [Сервис Платежей]
                  [Сервис Уведомлений]
                  [Сервис Аналитики]
                  [Сервис Инвентаря]
```

### Ключевые концепции

#### События домена (Domain Events)

События представляют **факты**, которые произошли:

```go
// ✅ Хорошо: Бизнес-факт
type OrderCreated struct {
    OrderID   string
    UserID    string
    Total     Money
    CreatedAt time.Time
}

// ❌ Плохо: Техническая деталь
type OrderSavedToDB struct {
    OrderID string
    DB      string
}
```

**Принцип:** Публикуйте **факт**, а не команду. "Заказ создан" (факт) против "Пожалуйста, обработайте заказ" (команда).

#### Источниковое Происхождение Событий (Event Sourcing)

Хранение **событий**, а не состояния. Состояние = сумма всех событий.

**Преимущества:**
- **Проводка аудита:** Каждое изменение записывается
- **Путешествие во времени:** Восстановить состояние в любой момент времени
- **Отладка:** Увидеть, что именно произошло
- **Новые функции:** Добавление новых проецирований без изменения потока событий

**Сложности:**
- **Сложность:** Сложно реализовать корректно
- **Запросы:** Состояние выводится, не хранится. Нужны проецирования для запросов
- **Неизменяемость событий:** События нельзя менять

#### CQRS (Разделение команд и запросов)

Разделение **команд** (записи) и **запросов** (чтения):

```
ПУТЬ ЗАПИСИ (Command):
  [Клиент] → [Обработчик команды] → [Агрегат] → [Хранилище Событий]

ПУТЬ ЧТЕНИЯ (Query):
  [Клиент] → [Обработчик запроса] → [Модель Чтения] → [Ответ]
```

**Почему разделять?**
- Записи должны соблюдать инварианты (правила бизнеса)
- Чтения должны быть быстры и оптимизированы для UI
- Они имеют разные потребности в масштабировании

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Потребность в обработке 1М+ событий/сек | Брокер сообщений является узким местом |
| Потребность в обработке в реальном времени | Пошаговая обработка слишком медленна |
| Потребность в возможности воспроизвести события | Отладка, аудит, повторная обработка |
| Потребность в декуплинговании продюсеров и потребителей | Разные скорости обработки |

## Этап 5: Многорегиональное / Глобальное развертывание

### Проблема

В одной области есть:
- **Задержка:** Пользователи в Азии обращающиеся к серверу в США = 200 мс+
- **Доступность:** Отказ ЦОДа останавливает всю систему
- **Соответствие требованиям:** Данные должны оставаться в конкретных юрисдикциях

### Решение: Многорегиональное развертывание

```
[Пользователи США] → [Регион США] → [База данных США]
[Пользователи ЕС] → [Регион ЕС] → [База данных ЕС]
[Пользователи Азии] → [Регион Азии] → [База данных Азии]

         [Глобальный DNS / Anycast]
```

### Ключевые концепции

#### Активно-Активно vs. Активно-Пассивно

| Режим | Описание | Плюсы | Минусы |
|---|---|---|---|
| **Активно-Активно** | Все регионы обрабатывают чтение И запись | Лучшая задержка, лучшая доступность | Сложная синхронизация данных, разрешение конфликтов |
| **Активно-Пассивно** | Один регион — первичный, остальные — бэкапы | Проще, консистентен | Переключение занимает время, бэкапы простаивают |

#### Репликация данных между регионами

*   **Асинхронная репликация:** Основной писатель, реплики синхронизируют асинхронно. Задержка = секунды.
*   **Синхронная репликация:** Основной писатель ждет подтверждения реплики. Консистентно, но медленно.
*   **CRDTs:** Типы данных, устойчивые к конфликтам. Созданы для конечной согласованности.
*   **Event Sourcing:** Репликация событий, а не состояния. Каждый регион применяет события независимо.

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Нужна обработка 1 млрд+ пользователей | Одна архитектура не может масштабироваться |
| Нужна работа с разными продуктовыми линиями | Разные SLA, разные модели данных |
| Нужно построить платформу | Внутренние команды строят на вашей инфраструктуре |
| Нужно оптимизировать стоимость при масштабе | Каждая миллисекунда и каждый доллар имеет значение |

---

## Этап 6: Платформа / Мультипользовательский / Пограничный (Edge)

### Проблема

При таком масштабе вы не просто создаете продукт — вы создаете **платформу**. Вызовы:
- **Мультипользовательский режим:** Многие клиенты на одной инфраструктуре
- **Пограничные вычисления (Edge computing):** Обработать данные близко к пользователю (IoT, AR/VR)
- **Оптимизация стоимости:** Каждая ошибка в расчете затрат важна при масштабе
- **Опыт разработчика:** Внутренние команды должны иметь возможность самообслуживания инфраструктурой

### Ключевые концепции

#### Мультипользовательский режим

| Модель | Описание | Плюсы | Минусы |
|---|---|---|---|
| **Общая все** | Все клиенты делят БД, приложение, инфраструктуру | Самый дешёвый | Нет изоляции, "шумный сосед" |
| **Общая БД, отдельные схемы** | Каждый клиент имеет свою схему | Умеренная изоляция | Ограничения БД |
| **Отдельная БД на клиента** | Каждый клиент имеет свою БД | Полная изоляция | Дорого, сложная настройка |
| **Отдельная инфраструктура** | Каждый клиент имеет свой кластер | Максимальная изоляция | Очень дорого |

#### Edge Computing

```
[Устройство] → [Пограничный узел (Edge Node)] → [Облако (Центр)]
              ↓
         [Локальная обработка]
         [Низкая задержка]
         [Возможность работы офлайн]
```

**Когда использовать:**
- IoT устройства (сенсоры, камеры)
- AR/VR (задержка < 20мс)
- Приложения с офлайн-первой логикой
- Защита данных (обработка локально)

#### Оптимизация стоимости при масштабе

| Техника | Описание |
|---|---|
| **Spot instances** | Использование дешёвых, прерываемых ВМ для отказоустойчивых рабочих нагрузок |
| **Автомасштабирование** | Масштабирование вверх/вниз на основе нагрузки |
| **Кеширование** | Снижение затрат на сеть и хранение |
| **Компрессия** | Снижение сетевых и дисковых затрат |
| **Tiered storage** | Горячие данные на SSD, холодные — на S3 |
| **Serverless** | Оплата по вызову, а не по часам |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обрабатывать 1 млрд+ пользователей | Одна архитектура не может масштабироваться |
| Необходимость обслуживать несколько продуктовых линий | Разные SLA, разные модели данных |
| Необходимость построить платформу | Внутренние команды строят на вашей инфраструктуре |

# Архитектура, управляемая событиями (EDA): От опроса к Реактивным Системам — 7 Стадий Эволюции

## Подробное объяснение всех положений

---

## Главная идея

**«Развязывай по времени, а не по пространству»**

В традиционных системах запроса-ответа компоненты связаны по **пространству** (они должны существовать одновременно и общаться напрямую). В Архитектуре, управляемой событиями, компоненты связаны по **времени** (продуцент не знает, когда или даже если потребитель обработает событие).

Цель не в том, чтобы «использовать Kafka». Цель — **развязать изменения**, чтобы производители и потребители могли развиваться, масштабироваться и выходить из строя независимо.

Большинство сбоев в EDA возникают, когда события обрабатываются как «асинхронный RPC» (просто медленный запрос-ответ), а не как **бизнес-факты**, движимые системой.

---

## Этап 0: Синхронный Запрос-Ответ (Базовый уровень)

### Суть

Один компонент напрямую вызывает другой. Вызывающий ждет ответа.

```
[Сервис Заказов] → [Сервис Платежей] → Ответ
                  (ждёт)
```

### Когда это достаточно

| Условие | Пояснение |
|---|---|
| < 1000 req/s | Сетевая задержка не является узким местом |
| Нужен немедленный результат | Вызывающий должен знать, успешно ли выполнена операция |
| Малое число потребителей | Только одному сервису нужен результат |
| Простой домен | Нет сложных бизнес-процессов |
| Малая команда | Легко отладить, легко отследить |

### Почему начинать здесь?

- **Простота.** Один вызов, один ответ. Легко понять.
- **Согласованность.** Транзакции ACID тривиальны.
- **Отладка.** Трассировка стека показывает полную цепочку вызовов.
- **Задержка.** Нет задержки из-за очереди.

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Вызывающий должен ждать медленные операции | Почта, видеообработка, внешние API |
| Многим потребителям нужен один и тот же результат | Аналитика, уведомления, инвентарь |
| Одно сбой каскадируется | Если платеж упал → заказ падает |
| Транфик может перегрузить систему | Требуется буферизация |
| Разные скорости обработки | Продуцент быстрый, потребитель медленный |

## Этап 1: Внедрение Очереди Сообщений (Task Queue)

### Проблема

Синхронные вызовы создают **жесткую связанность**. Если Сервис Платежей недоступен, Сервис Заказов терпит неудачу. К тому же, медленные операции (отправка почты) блокируют основной поток.

### Решение: Развязывание с помощью очереди

```
[Сервис Заказов] → [RabbitMQ / SQS] → [Рабочий по почте]
                   (в очередь)           (обрабатывает позже)
```

### Ключевые концепции

#### Паттерн Очереди Задач

- **Производитель** публикует задачу (например, «отправить почту»).
- **Потребитель** подхватывает задачу и обрабатывает её.
- **Брокер** хранит задачу до её потребления.

**Преимущества:**
- **Развязывание.** Производитель не ждёт ответа.
- **Буферизация.** Обработка всплесков трафика.
- **Повторные попытки.** Неудачные задачи можно повторить.
- **Выравнивание нагрузки.** Потребители обрабатывают в своем темпе.

### Ключевые проблемы

| Проблема | Объяснение |
|---|---|
| **Потеря сообщений** | Если брокер падает, сообщения теряются. Решение: персистентность, подтверждения |
| **Повторные сообщения** | Сетевые сбои вызывают повторную отправку. Решение: идемпотентные потребители |
| **Порядок** | Сообщения могут быть обработаны вне порядка. Решение: разделение по ключу |
| **Мертвые письма** | Сообщения, которые постоянно терпят неудачу. Решение: очередь мертвых писем (DLQ) |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Многим потребителям нужен одно и то же сообщение | Очередь доставляет только ОДНО сообщение |
| Необходимость воспроизводить сообщения | Отладка, аудит, повторная обработка |
| Необходимость хранить сообщения днями/неделями | Очередь от задач удаляет после потребления |
| Нужна высокая пропускная способность (1М+ msg/s) | Очередь задач не предназначена для этого |

## Этап 2: Внедрение Потокового Обработчика (Kafka / Pulsar)

### Проблема

Очереди задач предназначены для **одного потребителя на сообщение**. Но во многих случаях **множество потребителей** нуждаются в одном и том же событии:
- Заказ создан $\rightarrow$ Сервис Платежей
- Заказ создан $\rightarrow$ Сервис Уведомлений
- Заказ создан $\rightarrow$ Сервис Аналитики
- Заказ создан $\rightarrow$ Сервис Инвентаря

### Решение: Потоковая передача событий (Event Streaming)

```
[Сервис Заказов] → [Kafka: тема "orders"]
                     ↓
                  [Сервис Платежей]
                  [Сервис Уведомлений]
                  [Сервис Аналитики]
                  [Сервис Инвентаря]
```

### Ключевые концепции

#### Архитектура Kafka

| Концепция | Описание |
|---|---|
| **Тема (Topic)** | Категория сообщений (например, `orders`, `clicks`) |
| **Партиция** | Тема разделяется на партиции. Каждая партиция упорядочена. |
| **Смещение (Offset)** | Позиция в партиции. Потребители отслеживают свое смещение. |
| **Группа потребителей** | Набор потребителей, совместно использующих тему. Каждая партиция обрабатывается одним потребителем в группе. |
| **Репликация** | Каждая партиция реплицируется между брокерами для отказоустойчивости. |
| **Удержание** | Сообщения сохраняются днями/неделями (настраиваемо). |

#### Очередь Задач vs. Поток Событий

| Признак | Очередь Задач (RabbitMQ) | Поток Событий (Kafka) |
|---|---|---|
| **Удержание данных** | Удаляется после потребления | Сохраняется на дни/недели |
| **Потребители** | Один потребитель на сообщение | Несколько потребителей, каждый читает независимо |
| **Воспроизведение** | Нет | Да (читать с любого смещения) |
| **Пропускная способность** | ~100k msg/s | ~1М+ msg/s |
| **Применение** | Очереди задач, RPC | Потоки событий, логирование, аналитика |

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Порядок** | В пределах партиции порядок гарантирован. Между партициями — нет. Используйте ключ партиции (например, `user_id`) |
| **Обратная нагрузка** | Если потребители медленные, сообщения накапливаются. Нужно управлять задержкой |
| **Точно один раз** | Сложно достичь. Используйте идемпотентные операции + транзакционные продюсеры |
| **Эволюция схемы** | Производители и потребители могут иметь разные версии. Используйте реестр схем |
| **Отладка** | Распределенная, асинхронная, сложно отследить. Используйте распределенную трассировку |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость восстановить состояние из событий | Аудит, трассировка, повторная обработка |
| Необходимость добавить новых потребителей без изменения продюсеров | Декуплингование |
| Необходимость обрабатывать сложные бизнес-процессы | Паттерн Сага |
| Необходимость обеспечить согласованность данных | Согласованность событий |

## Этап 3: Доменные События и Event Sourcing

### Проблема

События часто рассматриваются как «технические уведомления» (например, «запись в БД»). Но в истинной EDA события представляют собой **бизнес-факты**, движущие систему.

### Решение: Доменные события

#### Что такое Доменный Событие?

**Бизнес-факт**, который произошел и интересен другим частям системы.

```go
// ✅ Хорошо: Бизнес-факт
type OrderCreated struct {
    OrderID   string
    UserID    string
    Total     Money
    CreatedAt time.Time
}

// ❌ Плохо: Техническая деталь
type OrderSavedToDB struct {
    OrderID string
    DB      string
}
```

**Принцип:** Публикуйте **факт**, а не команду. «Заказ создан» (факт) против «Пожалуйста, обработайте заказ» (команда).

#### Источниковый Происхождение Событий (Event Sourcing)

Сохранение **событий**, а не состояния. Состояние = сумма всех событий.

```
События:
  OrderCreated(order_id=1, total=100)
  PaymentReceived(order_id=1, amount=100)
  OrderShipped(order_id=1, tracking=ABC123)

Состояние (выведенное):
  Order { id: 1, total: 100, status: "shipped", tracking: "ABC123" }
```

**Преимущества:**
- **Проводка аудита:** Каждое изменение записано
- **Путешествие во времени:** Реконструировать состояние в любой момент времени
- **Отладка:** Увидеть, что именно произошло
- **Новые функции:** Добавление новых проекций без изменения потока событий

**Сложности:**
- **Сложность:** Сложно реализовать корректно
- **Запросы:** Состояние выводится, а не хранится. Требуются проецирования для запросов
- **Неизменяемость событий:** События нельзя менять. Корректировки = новые события

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Постепенная согласованность** | Чтения могут быть немного отстающими. Стройте для этого. |
| **Эволюция схем** | Производители и потребители могут иметь разные версии. Используйте реестр схем |
| **Порядок** | В рамках партиции порядок гарантирован. Между партициями — нет. |
| **Идемпотентность** | Потребители должны обрабатывать дубликаты. Используйте идемпотентные операции |
| **Отладка** | Распределенная, асинхронная, сложно отследить. Используйте распределенную трассировку |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обработать 1М+ событий/сек | Потоковый процессор является узким местом |
| Необходимость обработать в реальном времени | Пакетная обработка слишком медленна |
| Необходимость восстановить события | Отладка, аудит, повторная обработка |
| Необходимость декуплинговать продюсеров и потребителей | Разные скорости обработки |

## Этап 4: Паттерн Сага (Распределенные Транзакции)

### Проблема

В монолите транзакция охватывает несколько таблиц. В микросервисах транзакция охватывает несколько сервисов. ACID между сервисами невозможен.

### Решение: Паттерн Сага

**Сага** — это последовательность локальных транзакций, каждая из которых изменяет локальные данные и публикует событие. Если шаг завершается неудачно, Сага выполняет **компенсирующие действия** для отмены предыдущих шагов.

#### Два подхода

| Подход | Описание | Плюсы | Минусы |
|---|---|---|---|
| **Хореография** | Сервисы реагируют на события. Нет центрального координатора. | Декуплингованные, масштабируемые | Сложно отслеживать, сложные рабочие потоки |
| **Оркестрация** | Центральный координатор посылает команды сервисам. | Легко отслеживать, сложные рабочие потоки | Центральная точка отказа |

**Пример Хореографии** (как в описании выше)

**Если Платеж не удался:**
```
[Сервис Платежей] → "ПлатежНеУдался" → [Сервис Заказов]
[Сервис Заказов] → "ОтмененЗаказ" → [Сервис Инвентаря]
[Сервис Инвентаря] → "ВыданЗапас" → [Сервис Отгрузки]
```

#### Оркестрация

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Компенсирующие действия** | Не все операции можно отменить. Нужно спроектировать это |
| **Частичный отказ** | Некоторые шаги успеют, другие — нет. Нужно это обработать |
| **Таймауты** | Шаг может зависнуть. Нужно обнаружить и обработать его |
| **Идемпотентность** | Компенсирующие действия могут быть повторены. Должны быть идемпотентными |
| **Отладка** | Распределенные, асинхронные, сложно отследить. Используйте распределенный трейсинг |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обрабатывать 1М+ событий/сек | Потоковый процессор является узким местом |
| Необходимость обрабатывать в реальном времени | Пакетная обработка слишком медленна |
| Необходимость воспроизвести события | Отладка, аудит, повторная обработка |
| Необходимость декуплинговать продюсеров и потребителей | Разные скорости обработки |

## Этап 5: Потоковый Процессор и Реальное Время Аналитика

### Проблема

События — это не только для декуплинга. Они являются **источником данных** для реального времени, мониторинга и ML.

### Решение: Потоковый процессор

```
[Производители] → [Kafka] → [Flink / Spark Streaming] → [Панель / ML Модель]
```

### Ключевые концепции

#### Фреймворки Потоковой Обработки

| Фреймворк | Описание | Применение |
|---|---|---|
| **Apache Flink** | Низкая задержка, обработка с состоянием | Реальное время, обнаружение мошенничества |
| **Apache Spark Streaming** | Микро-пакетная обработка | Близкий к реальному времени (near real-time) |
| **Kafka Streams** | Встроен в Kafka, простой | Легковесная потоковая обработка |
| **KSQL** | SQL-подобные запросы к потокам | Простые агрегации |

#### Ключевые паттерны

| Паттерн | Описание |
|---|---|
| **Окно (Windowing)** | Обработка событий в заданных интервалах времени |
| **Агрегация** | Вычисление сумм, средних, подсчетов в течение времени |
| **Присоединение** | Объединение событий из разных потоков |
| **CEP (Сложный обработчик событий)** | Обнаружение паттернов в последовательностях событий |

### Ключевые вызовы

| Вызов | Объяснение |
|---|---|
| **Водяные знаки (Watermarks)** | Обработка событий, пришедших не по порядку. Определение "когда завершен интервал?" |
| **Управление состоянием** | Процессоры потоков поддерживают состояние. Нужно управлять сбоями |
| **Обратная нагрузка** | Если процессоры медленные, сообщения накапливаются. Нужно управлять задержкой |
| **Точно один раз** | Сложно достичь. Используйте идемпотентные операции |
| **Эволюция схемы** | Производители и потребители могут иметь разные версии. Используйте реестр схем |

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обрабатывать 1 млрд+ событий/день | Потоковый процессор является узким местом |
| Необходимость обслуживать несколько продуктовых линий | Разные SLA, разные модели данных |
| Необходимость построить платформу | Внутренние команды строят на вашей инфраструктуре |
| Необходимость оптимизировать стоимость при масштабе | Каждая миллисекунда и каждый доллар имеют значение |

## Этап 6: Реактивные Системы и CQRS

### Проблема

Традиционная EDA — это про **декуплингование**. Реактивные системы идут дальше: они **отзывчивы, устойчивы, эластичны и управляемы событиями**.

### Решение: Реактивная Архитектура

#### Четыре Принципа Реактивных Систем

| Принцип | Описание |
|---|---|
| **Отзывчивый** | Быстрый ответ на запросы |
| **Устойчивый** | Выходить из строя элегантно, быстро восстанавливаться |
| **Эластичный** | Масштабирование по запросу |
| **Управляемый событиями** | Асинхронная коммуникация |

#### CQRS (Разделение Команд и Запросов)

Разделение **команд** (записи) и **запросов** (чтения):

```
ПУТЬ ЗАПИСИ:
  [Клиент] → [Обработчик Команды] → [Агрегат] → [Хранилище Событий]

ПУТЬ ЧТЕНИЯ:
  [Клиент] → [Обработчик Запроса] → [Модель Чтения] → [Ответ]
```

**Почему разделять?**
- Записи должны соблюдать инварианты (бизнес-правила)
- Чтения должны быть быстры и оптимизированы для UI
- Они имеют разные потребности в масштабировании

### Когда переходить на следующий этап

| Триггер | Почему |
|---|---|
| Необходимость обрабатывать 1 млрд+ пользователей | Одна архитектура не может масштабироваться |
| Необходимость обслуживать несколько продуктовых линий | Разные SLA, разные модели данных |
| Необходимость построить платформу | Внутренние команды строят на вашей инфраструктуре |
| Необходимость оптимизировать стоимость при масштабе | Каждая миллисекунда и каждый доллар имеют значение |

## Этап 7: Event Mesh / Платформа / Пограничный (Edge)

### Проблема

При таком масштабе вы не просто создаете продукт — вы создаете **платформу**. Вызовы:
- **Event Mesh:** Межсетевой каркас для событий. Маршрутизация, безопасность, наблюдаемость.
- **Edge computing:** Обработать данные близко к пользователю.
- **Оптимизация стоимости:** Каждая ошибка в расчете затрат важна при масштабе
- **Опыт разработчика:** Внутренние команды должны иметь возможность самообслуживания инфраструктурой

### Ключевые концепции

#### Event Mesh

| Компонент | Описание |
|---|---|
| **Маршрутизатор событий** | Маршрутизирует события к нужным потребителям |
| **Безопасность событий** | mTLS, OAuth2, JWT для событийной связи |
| **Наблюдаемость событий** | Логирование, метрики, трассировка событий |
| **Управление событиями** | Реестр схем, версионирование, отмена |

#### Пограничные вычисления (Edge Computing)

```
[Устройство] → [Пограничный узел (Edge Node)] → [Облако (Центр)]
              ↓
         [Локальная обработка]
         [Низкая задержка]
         [Возможность работы офлайн]
```

**Когда использовать:**
- IoT устройства (сенсоры, камеры)
- AR/VR (задержка < 20мс)
- Приложения с офлайн-первой логикой
- Защита данных (обработка локально)

### Ключевые вызовы

| Вызов | Объяснение |

### Разъяснение этапов (Краткая справка)

**Главная идея:** Не проектировать сразу идеальную схему (3NF). Начать с самой простой формы, а затем усложнять, когда наступит конкретная "боль" (медленный чтение, высокая нагрузка, изменение схемы).


## Проектирование БД (SQL)


### Этап 0: Простая Таблица (Flat Structure)
**Суть:** Простая, плоская структура. Никаких JOIN'ов.
**Когда это достаточно:** Если у вас мало данных $(< 100k$ строк) и все запросы просты.
**Когда двигаться дальше:** Если данные слишком велики, отношения слишком сложны, или вам нужно оптимизировать чтение.

### Этап 1: Нормализованная Реляционная Модель (3NF)
**Суть:** Разделение данных на отдельные, логически связанные таблицы (по нормам 1NF, 2NF, 3NF).
**Что дает:** Устранение избыточности данных (например, если вы меняете имя пользователя, вы меняете его только в одной таблице).
**Торги:** Это приводит к большим JOIN'ам и сложным запросам, что замедляет чтение.
**Когда двигаться дальше:** Если чтение становится медленным, или если вам нужно оптимизировать чтение (а не запись).

### Этап 2: Денормализация и Индексирование
**Суть:** Сознательный отказ от идеальной нормализации. Вы добавляете **дублирующиеся столбцы** (например, имя пользователя в таблицу заказов) и **индексируете** то, что часто запрашивается.
**Что дает:** Максимально ускоряет запросы (Чтение $\rightarrow$ оптимизируется).
**Торги:** Усложняется управление данными, так как данные дублируются.
**Когда двигаться дальше:** Если данные растут до очень больших объемов или если ваша система становится слишком сложной для управления.

### Этап 3: Шардинг и Партиционирование
**Суть:** Если данные слишком велики, они разбиваются на множество мелких баз данных (шардинг) или разбиваются по времени/ключу в рамках одной БД (партиционирование).
**Что дает:** Масштабируемость до гигантских объемов данных.
**Торги:** Появляются очень сложные задачи по запросам, требующие запроса ко всем шардам.
**Когда двигаться дальше:** Если вы превышаете лимит памяти/диска или если ваша система стала слишком сложной для управления.

### Этап 4: Неструктурированные/Полиглоты (NoSQL)
**Суть:** Не использовать только SQL. Используйте разные типы БД для разных задач: Redis для кеша, MongoDB для гибких данных, Elasticsearch для поиска.
**Что дает:** Гибкость, скорость, возможность хранить данные разного формата.
**Торги:** Появляется сложность, так как нужно управлять многими типами баз данных.
**Когда двигаться дальше:** Если ваша система требует обработки очень разных типов данных (графики, документы, поиск).

### Этап 5: Хранилище данных (Data Lake/Warehouse)
**Суть:** Когда данные приходят из многих источников (логи, API, файлы), их нужно собрать и упорядочить для анализа.
**Что дает:** Возможность анализировать данные, не просто хранить их.
**Торги:** Это сложная инфраструктура, требующая конвейеров данных (Pipeline).
**Когда двигаться дальше:** Если вам нужно анализировать огромные объемы разнородных данных.

### Этап 6: Event Sourcing и CQRS
**Суть:** Вместо хранения текущего состояния, вы храните **историю** (все события). Это позволяет вам "откатить" систему или "проиграть" ее с нуля.
**Что дает:** Полная возможность аудита (Time Travel) и разделение чтения/записи.
**Торги:** Очень высокая сложность, так как нужно управлять состоянием, выведенным из событий.
**Когда двигаться дальше:** Если вам нужна максимальная прозрачность аудита и вы готовы к сложности.

### Этап 7: Платформа / Data Mesh
**Суть:** На этом этапе вы перестаете думать об "оптимизации", а начинаете думать о "бизнес-продукте". Данные становятся **продуктом**, который продается внутри компании.
**Что дает:** Установка стандартов, самообслуживание, управление данными как сервисом.
**Торги:** Чрезвычайно высокий уровень операционной сложности.
**Когда двигаться дальше:** Если ваша система достигла уровня, когда она сама становится бизнесом (платформой).
