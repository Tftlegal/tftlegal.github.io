# Руководство по настройке и защите Egress-трафика в Kubernetes (Calico)

Данное руководство описывает методологию построения безопасного контура исходящего трафика, предотвращения сетевых штормов и минимизации поверхности атаки.

## 1. Аудит и инвентаризация сетевой топологии
Прежде чем внедрять ограничения, необходимо полностью картировать текущие потоки данных.

*   **Цель:** Определение путей трафика (NAT, Gateway, Proxy) и выявление критических внешних зависимостей.
*   **Ключевые действия:**
    *   **Анализ NAT-моделей:** Определите, как узлы выходят в интернет (SNAT на уровне Node, использование NAT Gateway или фиксированные IP).
    *   **Инвентаризация портов и протоколов:** Составьте реестр внешних API, БД и сервисов. Выделите обязательные порты (например, 443 для API, 53 для DNS, 123 для NTP).
    *   **Аудит текущих политик:** Используйте `calicoctl get networkpolicy -A` для анализа существующих правил. Выявите "разрешающие дыры" (например, `0.0.0.0/0` на всех портах).
    *   **Сбор данных через Flow Logs:** Включите логирование потоков (Flow Logs) в Calico, чтобы увидеть реальный трафик перед тем, как применять блокировки.

## 2. Внедрение модели Zero Trust (Default Deny)
Переход от модели «разрешено всё, кроме...» к модели «запрещено всё, кроме...».

*   **Цель:** Изоляция подов и ограничение их возможности связываться с неавторизованными внешними ресурсами.
*   **Этапы реализации:**
    *   **Создание GlobalNetworkPolicy (Default Deny):** Внедрите политику, блокирующую весь исходящий трафик для всех Namespaces.
    *   **Исключения для инфраструктуры:** Разрешите трафик к внутренним сервисам кластера, DNS-серверам (CoreDNS) и метаданным облачного провайдера (если требуется).
    *   **Потоковое разрешение (Whitelist):** Создавайте специфические `NetworkPolicy` для каждого приложения, разрешая доступ только к конкретным CIDR-блокам и портам.
    *   **Использование Calico Enterprise:** Если доступен Enterprise, используйте расширенные возможности для более гранулярного управления политиками на основе меток (labels).

## 3. Интеграция DNS-резолвинга и FQDN-фильтрации
Стандартные сетевые политики Calico работают на уровне IP/CIDR, что неудобно для динамических облачных сервисов.

*   **Проблема:** IP-адреса внешних сервисов (например, Google API) постоянно меняются.
*   **Решения:**
    *   **Вариант А (Calico Enterprise):** Использование встроенных механизмов фильтрации по FQDN (если поддерживается версией).
    *   **Вариант Б (Egress Gateway / Proxy):** Настройка централизованного прокси-сервера (например, Squid или Envoy). Весь трафик направляется на прокси, который выполняет проверку по доменным именам.
    *   **Вариант В (Service Mesh):** Использование Istio или Linkerd для управления Egress через `ServiceEntry` и `Gateway`, что обеспечивает фильтрацию на уровне L7.

## 4. Защита от сетевых штормов и аномалий
Для предотвращения ситуации, когда сбой приложения или атака вызывают лавинообразный рост трафика (Retry Storms).

*   **Механизмы защиты:**
    *   **Rate Limiting:** Настройте ограничения скорости (Bandwidth Policing) на уровне Calico для каждого пода или группы подов. Это предотвратит «засорение» канала при бесконечных ретраях.
    *   **Circuit Breaker (на уровне приложения/Service Mesh):** Внедрите паттерн «Предохранитель». Если внешний сервис недоступен, приложение должно перестать слать запросы сразу, а не пытаться переподключиться каждую миллисекунду.
    *   **Timeout Policy:** Установите жесткие таймауты на уровне сетевых соединений. Недопустимо оставлять соединения в состоянии `ESTABLISHED` бесконечно долго.
    *   **Контроль DNS-запросов:** Ограничьте частоту DNS-запросов от одного пода, чтобы предотвратить DNS-шторм при сбое логики приложения.

## 5. Мониторинг и реагирование
Настройка системы должна сопровождаться инструментами визуализации.

*   **Обязательные метрики:**
    *   Количество отброшенных пакетов (Dropped Packets) по политикам Calico.
    *   Задержки (Latency) на уровне Egress-шлюзов.
    *   Объем трафика по конкретным приложениям.
*   **Инструменты:** Prometheus + Grafana (экспорт данных из Calico), использование `calicoctl` для оперативной проверки статуса политик.

Настройка исходящего (egress) трафика в кластере Kubernetes с CNI Calico — задача, которая на первый взгляд кажется простой, но таит множество подводных камней. Ошибки в egress-политиках часто проявляются как **интермиттирующие сбои connectivity** — приложения работают нестабильно, часть внешних эндпоинтов доступна, а часть — нет, причём без явных признаков сетевой проблемы.

Ниже — систематический разбор типичных ошибок и подходов к защите от каскадных сбоев.

## 6. Типичные ошибки настройки egress-трафика

### 6.1 Забытый DNS-egress в deny-all политиках

**Самая частая ошибка.** При применении deny-all egress-политики блокируется UDP/TCP-порт 53 до CoreDNS, и приложения перестают резолвить имена.

**Симптом:** ошибки вида `Could not resolve host: my-service.default.svc.cluster.local`.

**Решение:** всегда включать DNS-разрешение в любую deny-all политику:

```yaml
egress:
  - action: Allow
    protocol: UDP
    destination:
      ports: [53]
  - action: Allow
    protocol: TCP
      ports: [53]
```

**Важный нюанс:** в некоторых системах (например, OpenShift) DNS-под слушает на порту 5353, но сервис DNAT-ит трафик с 53 на 5353. Calico видит трафик **после** DNAT, поэтому политика должна быть нацелена на **сервис**, а не на порт пода.

---

### 6.2 IP-адресные политики для динамических внешних API

Использование CIDR-блоков для внешних SaaS-сервисов приводит к **тихим сбоям** — API может сменить IP (особенно если использует CDN), и политика перестанет работать без каких-либо изменений в коде.

**Решение:** использовать FQDN-политики (доступно в Calico Cloud/Enterprise):

```yaml
apiVersion: projectcalico.org/v3
kind: NetworkSet
metadata:
  name: trusted-api
  namespace: app-ns
spec:
  allowedEgressDomains:
    - 'api.trusted-service.com'
```

Затем ссылаться на этот NetworkSet по селектору в NetworkPolicy.

---

### 6.3 Пропущенный ICMP в egress-правилах

Deny-all политики без явного разрешения ICMP ломают диагностические утилиты (`ping`, `traceroute`) и могут нарушить **MTU path discovery** для TCP-соединений.

**Решение:** добавить ICMP-разрешение, если требуется диагностика или MTU discovery:

```yaml
egress:
  - action: Allow
    protocol: ICMP
    destination:
      nets: [0.0.0.0/0]
```

---

### 6.4 Неполное покрытие namespace-ов при использовании Egress Gateway

При развертывании Egress Gateway часто настраивают только для отдельных namespace-ов, забывая про остальные. В результате часть трафика уходит через gateway-IP, часть — через node SNAT. Внешние firewall-ы получают запросы с **нескольких разных source IP**, часть из которых не входит в разрешённый список.

**Решение:** явно сконфигурировать, какие namespace-ы используют Egress Gateway, а какие — SNAT, и задокументировать ожидаемые source IP для каждого namespace.

---

### 6.5 Блокировка доступа к Kubernetes API

При применении default-deny egress-политик часто забывают разрешить трафик к Kubernetes API. Это ломает валидацию service account token-ов и работу контроллеров.

**Решение:** создать **базовую GlobalNetworkPolicy** с низким order (высоким приоритетом), которая всегда разрешает API и DNS до того, как будут применены остальные политики:

```yaml
apiVersion: projectcalico.org/v3
kind: GlobalNetworkPolicy
metadata:
  name: baseline-allow-k8s-internals
spec:
  order: 10
  selector: all()
  types: [Egress]
  egress:
    - action: Allow
      protocol: UDP
      destination:
        ports: [53]
    - action: Allow
      protocol: TCP
      destination:
        ports: [443, 6443]
        nets: [10.96.0.0/12]  # Service CIDR — подставить свой
```

---

### 6.6 Применение deny-all без предварительного аудита

Самая опасная операционная ошибка — применение deny-all egress-политики без понимания того, с какими внешними эндпоинтами реально общаются рабочие нагрузки. Это гарантированно ломает легитимную connectivity и требует экстренного отката.

**Процесс предотвращения:**
- Включить Calico flow logs (Cloud/Enterprise) или сетевой логинг на нодах
- Запустить рабочие нагрузки минимум на одну неделю для сбора данных о реальных egress-потоках
- На основе логов сформировать белый список разрешённых эндпоинтов

## 7. Защита от «шторма» при сбоях (High Availability & Failover)

Под «штормом» здесь понимается каскадный сбой connectivity, когда отказ одного компонента (ноды, gateway-пода, сетевого интерфейса) вызывает массовые ошибки во всех зависящих от него приложениях.

### 171 High Availability для Egress Gateway

Calico Enterprise/Cloud поддерживает **отказоустойчивую конфигурацию Egress Gateway**:

- **Балансировка нагрузки** между несколькими egress gateway: если один gateway становится недоступным, трафик автоматически перенаправляется на другой.
- **Health checks** непрерывно мониторят состояние каждого gateway и автоматически исключают отказавшие из пула балансировки.
- **Обнаружение отказа и failover** на основе исходящих проб (outgoing probes), проверяющих upstream connectivity.

При использовании **нескольких узлов** как Egress Gateway с плавающим Egress IP, при отказе одного узла Egress IP переключается на другой узел.

### 7.2 Graceful maintenance и long-lived соединения

При плановом обновлении или завершении работы Egress Gateway Calico добавляет **аннотации maintenance window** к зависимым рабочим нагрузкам. Это даёт приложениям время на переподключение (например, 60-секундное окно) до полного завершения gateway.

### 7.3 NAT-настройки как защита от нехватки IP

Если не использовать Egress Gateway, можно включить `natOutgoing` на IP Pool — тогда трафик будет выходить с IP узла, а не пода:

```bash
calicoctl patch ippool default-ipv4-ippool \
  --patch '{"spec":{"natOutgoing": true}}'
```

Это **защищает от истощения публичных IPv4-адресов** и упрощает firewall-правила (нужно разрешать только IP узлов, а не всей CIDR-сети подов).

### 7.4 Стратегия Tiered Policies для защиты от ошибок

Calico поддерживает **иерархические политики (tiers)** с разным приоритетом:

- В **верхнем tier** — базовые разрешения (Kubernetes API, DNS, ICMP) с наивысшим приоритетом
- В **нижних tier-ах** — специфичные для приложений deny/allow правила

Это гарантирует, что даже при ошибках в application-политиках **системный трафик не будет заблокирован**.

### 7.5 Преддеплойная валидация

Скрипт валидации перед применением любой новой NetworkPolicy:

```bash
#!/bin/bash
NAMESPACE=${1:-default}
kubectl run egress-test --image=curlimages/curl -n $NAMESPACE \
  --restart=Never --rm -i -- sh -c "curl -k https://kubernetes.default.svc"
```

Это позволяет обнаружить проблемы с API-доступом **до** того, как они затронут реальные рабочие нагрузки.

## Рекомендации по корректной настройке

## 8. Диагностика исходящего трафика в Kubernetes

Для диагностики исходящего (egress) трафика в кластере Kubernetes обычно используют комбинацию метрик, логов и перехвата пакетов. Ниже — практические подходы и инструменты.

## 8.1 Базовые проверки на уровне нод и подов

- **Проверка исходящего соединения из пода**:

```bash
kubectl run test-egress --rm -it --image=curlimages/curl --restart=Never -n <namespace> \
  -- curl -s -o /dev/null -w "%{http_code}" https://example.com
```

Это позволяет быстро проверить, работает ли DNS, NAT и egress в целом.[^1_1]
- **Проверка DNS**:

```bash
kubectl run dns-test --rm -it --image=busybox --restart=Never -n <namespace> -- nslookup example.com
```

- **Проверка маршрутизации и NAT** на нодах:

```bash
ip route
iptables -t nat -L POSTROUTING -n -v
```


## 8.2 Метрики и мониторинг

- **Prometheus + Grafana**:

Собирайте метрики:
    - `container_network_transmit_bytes_total` (cAdvisor / kubelet);
    - `node_network_transmit_bytes_total` (node-exporter);
    - метрики HAProxy / Ingress / egress-шлюзов.

Это позволяет увидеть, какие ноды / поды генерируют больше всего исходящего трафика.
- **HAProxy stats**:

Если используется HAProxy, включите страницу статистики и смотрите:
    - `bout` (байты на выходе);
    - число соединений;
    - `retries`, `redispatch`, `err`.


## 8.3 eBPF-инструменты для глубокой наблюдаемости

Для детального анализа трафика между подами и наружу хорошо подходят eBPF-решения:

- **Cilium Hubble** (если используется Cilium CNI):

```bash
hubble observe --follow
hubble observe --namespace production --to-port 443 --protocol tcp
hubble observe --verdict DROPPED
hubble observe --output json > flows.json
```

Hubble показывает потоки в реальном времени, включая source/destination pod, порт, протокол, verdict.[^1_2][^1_3]
- **Pixie**:

Автоматически собирает трассировки HTTP/gRPC, DNS, TCP и визуализирует их в UI. Полезен для анализа, какие сервисы генерируют много запросов наружу.[^1_3]
- **Coroot, Caretta, Inspektor Gadget**:

Более лёгкие eBPF-инструменты для анализа сетевых потоков и диагностики проблем.[^1_3]


## 8.4 Перехват пакетов (packet capture)

Если нужен посерверный анализ:

- **Kubeshark** (ранее KubeSniff):

```bash
kubeshark tap -A
kubeshark tap -n kube-system
```

Позволяет захватывать трафик в кластере и анализировать его в UI, похожем на Wireshark.[^1_4]
- **tcpdump / Wireshark** на нодах:

```bash
tcpdump -i any -w egress.pcap host <external_ip>
```

Затем открыть в Wireshark и проанализировать соединения, ретраи, объём данных.
- **eBPF-NetFlow**:

Можно собирать статистику в формате NetFlow через eBPF (например, через Cilium + сенсор на Go), затем отправлять в коллектор для анализа.[^1_5]


## 8.5 Анализ логов приложений и Kubernetes

- **Логи приложений**:

Искать паттерны:
    - `connection refused`;
    - `i/o timeout`;
    - `retry`;
    - `watch closed`;
    - `TLS handshake`;
    - всплеск `GET`, `LIST`, `WATCH`.
- **События Kubernetes**:

```bash
kubectl get events -A --sort-by=.lastTimestamp
kubectl describe node <node-name>
```

Это помогает найти рестарты подов, нод, проблемы с `kube-apiserver`, `kube-proxy`, CNI.


## 8.6 Сопоставление с инцидентом

Для вашего случая (кратковременные `Connection refused` на API-узлах):

    - `container_network_transmit_bytes_total` по API-нодам;

    - метрики HAProxy (`bout`, RPS, retries).
2. Проверьте, не было ли в это время:

3. Если рост трафика был значительным, ищите:
    - агрессивные retry-политики в клиентах;
    - массовые reconnect после восстановления API;
    - дополнительные фоновые задачи (синхронизация, бэкапы, сканирование).

- [ ] Посмотреть метрики `*_transmit_bytes_total` в Prometheus/Grafana.
- [ ] Включить/проверить HAProxy stats.
- [ ] Использовать Hubble / Pixie / Kubeshark для анализа потоков.
- [ ] Собрать pcap на нодах при необходимости.
- [ ] Проанализировать логи приложений и события Kubernetes.
- [ ] Сопоставить таймлайны сбоев и всплесков трафика.

Эти шаги помогут точно определить, какие компоненты генерируют исходящий трафик и связана ли деградация API-узлов с его ростом.
