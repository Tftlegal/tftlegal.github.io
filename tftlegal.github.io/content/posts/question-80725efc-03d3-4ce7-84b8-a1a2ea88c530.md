# Управление базами данных с Ansible: Полноценное руководство по развертыванию ClickHouse и MongoDB

## Введение

В современном мире автоматизация управления инфраструктурой стала не просто удобством, а необходимостью. Ручное администрирование баз данных приводит к ошибкам, несоответствиям сред и замедлению выпуска продуктов. **Ansible** предоставляет декларативный, идемпотентный и безопасный способ управления конфигурациями, позволяя инженерам описывать желаемое состояние системы в коде.

Данное руководство демонстрирует, как использовать Ansible для развертывания и настройки двух принципиально разных систем управления базами данных:

- **ClickHouse** — колоночная аналитическая СУБД (OLAP), оптимизированная для обработки больших объёмов данных в реальном времени.
- **MongoDB** — документоориентированная NoSQL база данных, гибкая и масштабируемая для работы с полуструктурированными данными.

Мы пройдём путь от подготовки управляющей машины до полного развертывания, конфигурации безопасности, управления схемой и проверки работоспособности. Все артефакты (плейбуки, роли, шаблоны, инвентарные файлы) будут представлены в готовом к использованию виде.

**Ключевые принципы, заложенные в решение:**
- **Идемпотентность** — повторное применение плейбуков не меняет систему, если она уже находится в желаемом состоянии.
- **Безопасность** — конфиденциальные данные (пароли, ключи) хранятся в зашифрованном виде с помощью Ansible Vault.
- **Модульность** — вся логика разбита на переиспользуемые роли, что упрощает поддержку и масштабирование.

## 1. Предварительные требования и подготовка среды

Прежде чем приступить к написанию плейбуков, необходимо обеспечить корректную работу Ansible и доступ к целевым хостам.

### 1.1. Контрольная машина (Ansible Control Node)

Установите Ansible на вашу локальную машину или выделенный сервер управления. Для Ubuntu/Debian:

```bash
sudo apt update
sudo apt install ansible -y
```

Для RHEL/CentOS/Fedora:

```bash
sudo dnf install epel-release -y
sudo dnf install ansible -y
```

Проверьте версию:

```bash
ansible --version
```

### 1.2. Настройка SSH-доступа к целевым хостам

Ansible взаимодействует с управляемыми узлами по SSH. Для автоматизации рекомендуется настроить бесключевой доступ:

```bash
# Генерация SSH-ключа (если ещё нет)
ssh-keygen -t rsa -b 4096 -C "ansible-key"

# Копирование публичного ключа на каждый целевой сервер
ssh-copy-id user@clickhouse_server_ip
ssh-copy-id user@mongodb_server_ip
```

Убедитесь, что можете подключиться без пароля:

```bash
ssh user@clickhouse_server_ip
```

### 1.3. Инвентарный файл

Инвентарь определяет, какие хосты существуют и как они группируются. Создайте файл `inventory/hosts.ini` со следующим содержанием:

```ini
# Группа серверов баз данных
[db_servers]
clickhouse_server ansible_host=192.168.1.10
mongodb_server   ansible_host=192.168.1.20

# Подгруппы для конкретных СУБД
[clickhouse_cluster]
clickhouse_server

[mongodb_cluster]
mongodb_server

# Глобальные переменные для всех хостов
[all:vars]
ansible_user=your_ssh_username       # замените на реального пользователя
ansible_ssh_private_key_file=~/.ssh/id_rsa
ansible_python_interpreter=/usr/bin/python3
```

> **Важно:** Убедитесь, что IP-адреса и имена пользователей указаны корректно. Для продакшена рекомендуется использовать динамический инвентарь (например, из AWS, GCP).

### 1.4. Проверка связи

Выполните ping-тест, чтобы убедиться, что Ansible видит все хосты:

```bash
ansible all -i inventory/hosts.ini -m ping
```

Ожидаемый ответ для каждого хоста:

```json
{
    "changed": false,
    "ping": "pong"
}
```

### 1.5. Ansible Vault: безопасное хранение секретов

**Никогда не храните пароли в открытом виде в плейбуках или переменных.** Используйте Ansible Vault для шифрования конфиденциальных данных.

Создайте файл с переменными, который будет зашифрован:

```bash
ansible-vault create group_vars/all/vault.yml
```

Внутри укажите пароли и другие секреты:

```yaml
# group_vars/all/vault.yml
db_mongo_admin_user: "admin"
db_mongo_admin_password: "Sup3rS3cr3tP@ssw0rd!"
db_mongo_app_user: "appuser"
db_mongo_app_password: "AppP@ssw0rd!"
db_clickhouse_user: "analytics_user"
db_clickhouse_password: "ChP@ssw0rd!"
```

При выполнении плейбуков передавайте пароль Vault через `--ask-vault-pass` или используйте файл с паролем (`--vault-password-file`).

## 3. Базовая настройка всех узлов (Role: `base_setup`)

Эта роль гарантирует, что на всех целевых хостах установлены необходимые системные пакеты, Docker (если используется), и созданы нужные группы пользователей.

**`roles/base_setup/tasks/main.yml`:**

```yaml
---
- name: Update apt cache (Debian/Ubuntu)
  ansible.builtin.apt:
    update_cache: yes
    cache_valid_time: 3600
  when: ansible_os_family == "Debian"

- name: Install essential packages
  ansible.builtin.package:
    name:
      - curl
      - wget
      - git
      - python3-pip
      - docker.io          # Для контейнерных развёртываний
      - docker-compose     # (или docker-compose-plugin)
    state: present
  become: yes

- name: Start and enable Docker service
  ansible.builtin.service:
    name: docker
    state: started
    enabled: yes
  become: yes

- name: Add ansible user to docker group (optional)
  ansible.builtin.user:
    name: "{{ ansible_user }}"
    groups: docker
    append: yes
  become: yes
  notify: restart docker  # если требуется перезапуск для применения группы

- name: Install Python Docker module (for Ansible docker_* modules)
  ansible.builtin.pip:
    name: docker
    state: present
  become: yes
```

**Handlers (`roles/base_setup/handlers/main.yml`):**

```yaml
---
- name: restart docker
  ansible.builtin.service:
    name: docker
    state: restarted
  become: yes
```

## 4. Развертывание MongoDB

MongoDB требует не только установки, но и тщательной настройки безопасности, создания администратора и, при необходимости, инициализации схемы.

### 4.1. Установка и конфигурация сервиса

**`roles/mongodb/tasks/main.yml`** (основные задачи):

```yaml
---
- name: Import MongoDB public GPG key
  ansible.builtin.apt_key:
    url: https://www.mongodb.org/static/pgp/server-7.0.asc
    state: present
  when: ansible_os_family == "Debian"

- name: Add MongoDB repository
  ansible.builtin.apt_repository:
    repo: "deb [ arch=amd64,arm64 ] https://repo.mongodb.org/apt/ubuntu {{ ansible_distribution_release }}/mongodb-org/7.0 multiverse"
    state: present
  when: ansible_os_family == "Debian"

- name: Install MongoDB packages
  ansible.builtin.apt:
    name:
      - mongodb-org
      - mongodb-org-server
      - mongodb-org-shell
      - mongodb-org-mongos
      - mongodb-org-tools
    state: present
  become: yes
  notify: restart mongod

- name: Ensure MongoDB data directory exists
  ansible.builtin.file:
    path: /var/lib/mongodb
    state: directory
    owner: mongodb
    group: mongodb
    mode: '0755'
  become: yes

- name: Deploy MongoDB configuration from template
  ansible.builtin.template:
    src: mongod.conf.j2
    dest: /etc/mongod.conf
    owner: root
    group: root
    mode: '0644'
  become: yes
  notify: restart mongod

- name: Enable and start MongoDB service
  ansible.builtin.service:
    name: mongod
    state: started
    enabled: yes
  become: yes
```

**Шаблон конфигурации `roles/mongodb/templates/mongod.conf.j2`:**

```jinja
# mongod.conf

# Where and how to store data.
storage:
  dbPath: /var/lib/mongodb
  journal:
    enabled: true

# Where to write logging data.
systemLog:
  destination: file
  logAppend: true
  path: /var/log/mongodb/mongod.log

# Network interfaces
net:
  port: {{ mongo_port | default(27017) }}
  bindIp: 127.0.0.1,{{ ansible_default_ipv4.address }}

# Security
security:
  authorization: enabled   # Включаем аутентификацию после создания пользователя

# Process management
processManagement:
  timeZoneInfo: /usr/share/zoneinfo
```

**Handlers (`roles/mongodb/handlers/main.yml`):**

```yaml
---
- name: restart mongod
  ansible.builtin.service:
    name: mongod
    state: restarted
  become: yes
```

### 4.2. Настройка безопасности (создание администратора)

Этот шаг критически важен: мы создаём администратора с правами `userAdminAnyDatabase` и `readWriteAnyDatabase`. Выполнять его нужно **после** запуска сервиса, но **до** включения аутентификации. В нашем шаблоне `authorization: enabled` уже стоит, поэтому мы должны создать пользователя на этапе, когда аутентификация ещё отключена, либо временно отключить её. Однако более безопасный подход — использовать файл с начальными настройками или выполнить создание пользователя через `localhost` исключение, если MongoDB позволяет.

В данном руководстве мы используем более надёжный метод: мы запускаем MongoDB без аутентификации, создаём пользователя, а затем перезапускаем с аутентификацией. Для этого в конфигурации временно устанавливаем `authorization: disabled`, выполняем создание, затем включаем. Но поскольку мы стремимся к идемпотентности и минимизации шагов, лучше создать пользователя сразу после установки, пока сервис ещё не перезапущен с новой конфигурацией.

**Упрощённый подход:** В `main.yml` мы создаём пользователя до включения `authorization` в конфиге. Чтобы не перезапускать сервис дважды, мы можем сначала запустить сервис с отключенной аутентификацией, создать пользователя, затем включить аутентификацию и перезапустить. В нашем примере мы вынесем создание пользователя в отдельную задачу, которая выполняется после первого запуска, но до применения конфигурации с `authorization: enabled`.

**`roles/mongodb/tasks/security.yml`**:

```yaml
---
- name: Wait for MongoDB to start
  ansible.builtin.wait_for:
    port: "{{ mongo_port | default(27017) }}"
    host: 127.0.0.1
    timeout: 30

- name: Create admin user (only if not exists)
  ansible.builtin.shell: |
    mongo --host 127.0.0.1 --port {{ mongo_port | default(27017) }} --eval "
    use admin;
    if (!db.getUser('{{ db_mongo_admin_user }}')) {
        db.createUser({
            user: '{{ db_mongo_admin_user }}',
            pwd: '{{ db_mongo_admin_password }}',
            roles: [
                { role: 'userAdminAnyDatabase', db: 'admin' },
                { role: 'readWriteAnyDatabase', db: 'admin' }
            ]
        });
    }
    "
  args:
    warn: no
  become: yes
  become_user: mongodb
  when: mongo_auth_enabled | default(true) | bool

- name: Create application user and database (if needed)
  ansible.builtin.shell: |
    mongo --host 127.0.0.1 --port {{ mongo_port | default(27017) }} --eval "
    use my_app_db;
    if (!db.getUser('{{ db_mongo_app_user }}')) {
        db.createUser({
            user: '{{ db_mongo_app_user }}',
            pwd: '{{ db_mongo_app_password }}',
            roles: [ 'readWrite' ]
        });
    }
    "
  args:
    warn: no
  become: yes
  become_user: mongodb
  when: mongo_auth_enabled | default(true) | bool
```

**Важно:** В идеале следует использовать модуль `community.mongodb.mongodb_user`, но он требует установки дополнительных зависимостей (`pymongo`). Для чистоты примера мы используем `shell`, но обеспечиваем идемпотентность через проверку существования пользователя.

### 4.3. Управление схемой (создание коллекций, индексов)

В продакшене часто требуется инициализировать структуру данных. Для MongoDB это создание коллекций, индексов и, возможно, вставка начальных документов. Мы создадим отдельную задачу.

**`roles/mongodb/tasks/schema.yml`**:

```yaml
---
- name: Create initial collections and indexes
  ansible.builtin.shell: |
    mongo --host 127.0.0.1 --port {{ mongo_port | default(27017) }} -u {{ db_mongo_app_user }} -p {{ db_mongo_app_password }} --authenticationDatabase my_app_db --eval "
    use my_app_db;
    // Создаём коллекцию, если её нет
    db.createCollection('logs', { capped: false });
    // Создаём индекс
    db.logs.createIndex({ timestamp: -1 });
    // Вставляем документ-заглушку (опционально)
    db.logs.updateOne(
        { _id: 'init' },
        { $setOnInsert: { created_at: new Date(), message: 'System initialized' } },
        { upsert: true }
    );
    "
  args:
    warn: no
  become: yes
  become_user: mongodb
  when: mongo_auth_enabled | default(true) | bool
```

Все эти задачи мы включаем в основной `main.yml` через `import_tasks` в нужном порядке.

## 5. Развертывание ClickHouse

ClickHouse может быть установлен как системный пакет или через Docker. В нашем руководстве мы используем Docker Compose для простоты и изоляции, но пакетная установка также возможна. Мы выберем компромисс: установка через официальный репозиторий (для демонстрации традиционного подхода). Однако для сложных конфигураций (кластеризация) Docker может быть удобнее.

Мы реализуем установку через `apt` (Debian/Ubuntu) с последующей настройкой.

### 5.1. Установка и конфигурация сервиса

**`roles/clickhouse/tasks/main.yml`**:

```yaml
---
- name: Add ClickHouse repository
  ansible.builtin.apt_repository:
    repo: "deb https://packages.clickhouse.com/deb stable main"
    state: present
  when: ansible_os_family == "Debian"

- name: Import ClickHouse GPG key
  ansible.builtin.apt_key:
    url: https://packages.clickhouse.com/deb/clickhouse-keyring.gpg
    state: present
  when: ansible_os_family == "Debian"

- name: Install ClickHouse server and client
  ansible.builtin.apt:
    name:
      - clickhouse-server
      - clickhouse-client
    state: present
  become: yes
  notify: restart clickhouse

- name: Deploy ClickHouse configuration
  ansible.builtin.template:
    src: clickhouse.xml.j2
    dest: /etc/clickhouse-server/config.xml
    owner: clickhouse
    group: clickhouse
    mode: '0644'
  become: yes
  notify: restart clickhouse

- name: Ensure ClickHouse data directory permissions
  ansible.builtin.file:
    path: /var/lib/clickhouse
    state: directory
    owner: clickhouse
    group: clickhouse
    mode: '0755'
  become: yes

- name: Start and enable ClickHouse service
  ansible.builtin.service:
    name: clickhouse-server
    state: started
    enabled: yes
  become: yes
```

**Шаблон `clickhouse.xml.j2`** (упрощённый, но можно расширить):

```jinja
<?xml version="1.0"?>
<clickhouse>
    <listen_host>0.0.0.0</listen_host>
    <listen_host>127.0.0.1</listen_host>
    <http_port>8123</http_port>
    <tcp_port>9000</tcp_port>
    <interserver_http_port>9009</interserver_http_port>
    <max_connections>4096</max_connections>
    <keep_alive_timeout>3</keep_alive_timeout>
    <max_concurrent_queries>100</max_concurrent_queries>
    <uncompressed_cache_size>8589934592</uncompressed_cache_size>
    <mark_cache_size>5368709120</mark_cache_size>
    <path>/var/lib/clickhouse/</path>
    <tmp_path>/var/lib/clickhouse/tmp/</tmp_path>
    <user_files_path>/var/lib/clickhouse/user_files/</user_files_path>
    <users_config>users.xml</users_config>
    <default_profile>default</default_profile>
    <!-- настройки логирования и т.д. -->
</clickhouse>
```

**Handlers (`roles/clickhouse/handlers/main.yml`):**

```yaml
---
- name: restart clickhouse
  ansible.builtin.service:
    name: clickhouse-server
    state: restarted
  become: yes
```

### 5.2. Создание пользователей и баз данных

В ClickHouse управление пользователями осуществляется либо через XML-файлы (`users.xml`), либо через SQL-команды (начиная с версии 20.3). Мы используем SQL-команды, что более гибко и позволяет избежать перезапуска сервера.

**`roles/clickhouse/tasks/security.yml`**:

```yaml
---
- name: Wait for ClickHouse to be ready
  ansible.builtin.wait_for:
    port: 9000
    host: 127.0.0.1
    timeout: 30

- name: Create ClickHouse user and database
  ansible.builtin.shell: |
    clickhouse-client --query "
    CREATE USER IF NOT EXISTS '{{ db_clickhouse_user }}'@'%' IDENTIFIED BY '{{ db_clickhouse_password }}';
    CREATE DATABASE IF NOT EXISTS analytics_db;
    GRANT ALL ON analytics_db.* TO '{{ db_clickhouse_user }}'@'%';
    "
  become: yes
  become_user: clickhouse
```

### 5.3. Управление схемой (создание таблиц)

**`roles/clickhouse/tasks/schema.yml`**:

```yaml
---
- name: Create tables for analytics
  ansible.builtin.shell: |
    clickhouse-client --query "
    CREATE TABLE IF NOT EXISTS analytics_db.user_events (
        event_time DateTime,
        user_id UInt64,
        event_type String,
        event_data String
    ) ENGINE = MergeTree()
    ORDER BY (event_time, user_id)
    PARTITION BY toYYYYMM(event_time);
    "
  become: yes
  become_user: clickhouse
```

## 6. Тестирование и валидация

После развертывания необходимо убедиться, что сервисы работают и готовы принимать запросы. Лучше использовать специализированные модули Ansible, но если их нет, можно обойтись `command` или `shell` с проверкой возвращаемого кода.

Создадим отдельный плейбук для проверки.

**`playbooks/verify_db.yml`**:

```yaml
---
- name: Verify MongoDB installation
  hosts: mongodb_servers
  become: yes
  tasks:
    - name: Wait for MongoDB port
      ansible.builtin.wait_for:
        port: "{{ mongo_port | default(27017) }}"
        host: 127.0.0.1
        timeout: 10

    - name: Test MongoDB connection with admin user
      ansible.builtin.shell: |
        mongo --host 127.0.0.1 --port {{ mongo_port | default(27017) }} -u {{ db_mongo_admin_user }} -p {{ db_mongo_admin_password }} --authenticationDatabase admin --eval "db.adminCommand({ ping: 1 })"
      register: mongo_test
      changed_when: false
      failed_when: "'ok' not in mongo_test.stdout"

    - name: Debug MongoDB test result
      ansible.builtin.debug:
        msg: "✅ MongoDB is responsive and authenticated."

- name: Verify ClickHouse installation
  hosts: clickhouse_servers
  become: yes
  tasks:
    - name: Wait for ClickHouse port
      ansible.builtin.wait_for:
        port: 9000
        host: 127.0.0.1
        timeout: 10

    - name: Test ClickHouse query with user
      ansible.builtin.shell: |
        clickhouse-client --user {{ db_clickhouse_user }} --password {{ db_clickhouse_password }} --query "SELECT 1"
      register: ch_test
      changed_when: false
      failed_when: ch_test.rc != 0

    - name: Debug ClickHouse test result
      ansible.builtin.debug:
        msg: "✅ ClickHouse is responsive and authenticated."
```

## 7. Управление жизненным циклом (Cleanup)

Для отката или полного удаления развёрнутого стека создадим плейбук очистки.

**`playbooks/cleanup.yml`**:

```yaml
---
- name: Completely remove MongoDB
  hosts: mongodb_servers
  become: yes
  tasks:
    - name: Stop MongoDB service
      ansible.builtin.service:
        name: mongod
        state: stopped
        enabled: no
      ignore_errors: yes

    - name: Remove MongoDB packages
      ansible.builtin.apt:
        name: mongodb-org*
        state: absent
        purge: yes

    - name: Remove MongoDB data and logs
      ansible.builtin.file:
        path: "{{ item }}"
        state: absent
      loop:
        - /var/lib/mongodb
        - /var/log/mongodb
        - /etc/mongod.conf

- name: Completely remove ClickHouse
  hosts: clickhouse_servers
  become: yes
  tasks:
    - name: Stop ClickHouse service
      ansible.builtin.service:
        name: clickhouse-server
        state: stopped
        enabled: no
      ignore_errors: yes

    - name: Remove ClickHouse packages
      ansible.builtin.apt:
        name: clickhouse-*
        state: absent
        purge: yes

    - name: Remove ClickHouse data and configs
      ansible.builtin.file:
        path: "{{ item }}"
        state: absent
      loop:
        - /var/lib/clickhouse
        - /etc/clickhouse-server
        - /var/log/clickhouse-server
```

## 8. Главный плейбук оркестрации

Теперь соберём все роли в единый плейбук, который будет развёртывать всю инфраструктуру в правильном порядке.

**`playbooks/deploy_all.yml`**:

```yaml
---
- name: 🟢 Base setup for all database servers
  hosts: db_servers
  become: yes
  roles:
    - base_setup

- name: 🔵 Deploy and configure MongoDB
  hosts: mongodb_servers
  become: yes
  vars:
    mongo_port: 27017
    mongo_auth_enabled: true
  roles:
    - mongodb
  tasks:
    - name: Ensure MongoDB security tasks run after service start
      ansible.builtin.import_tasks: roles/mongodb/tasks/security.yml
      tags: security
    - name: Ensure MongoDB schema tasks run after security
      ansible.builtin.import_tasks: roles/mongodb/tasks/schema.yml
      tags: schema

- name: 🟣 Deploy and configure ClickHouse
  hosts: clickhouse_servers
  become: yes
  roles:
    - clickhouse
  tasks:
    - name: Ensure ClickHouse security tasks run after service start
      ansible.builtin.import_tasks: roles/clickhouse/tasks/security.yml
      tags: security
    - name: Ensure ClickHouse schema tasks run after security
      ansible.builtin.import_tasks: roles/clickhouse/tasks/schema.yml
      tags: schema
```

Обратите внимание, что мы вызываем задачи безопасности и схемы явно, чтобы гарантировать порядок выполнения.

## 9. Практические примеры запуска плейбуков

Ниже приведены команды для выполнения различных операций с пояснениями и вариантами использования.

### 9.1. Полное развертывание с использованием Vault

```bash
# Переходим в корень проекта
cd database_automation/

# Запускаем главный плейбук, вводя пароль Vault при запросе
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --ask-vault-pass
```

Если вы предварительно создали файл с паролем Vault (например, `.vault_pass`), можно использовать:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --vault-password-file .vault_pass
```

### 9.2. Запуск только определённой роли (теги)

В плейбуке мы добавили теги `security` и `schema`. Можно выполнить только эти этапы для уже существующей инфраструктуры:

```bash
# Только настройка безопасности (создание пользователей)
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --tags security --ask-vault-pass

# Только создание схемы (таблиц, коллекций)
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --tags schema --ask-vault-pass
```

### 9.3. Выполнение с дополнительными переменными (--extra-vars)

Иногда нужно переопределить порт или пароль без изменения файлов переменных. Например, развернуть на другом порту:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --extra-vars "mongo_port=27018 clickhouse_port=9001" --ask-vault-pass
```

Можно также передать JSON-файл:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --extra-vars "@vars_override.json" --ask-vault-pass
```

### 9.4. Режим "проверки" (--check) для идемпотентности

Перед реальным применением можно выполнить сухой запуск, чтобы увидеть, какие изменения будут внесены:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --check --diff
```

Это особенно полезно для проверки корректности шаблонов и переменных.

### 9.5. Ограничение хостов (--limit)

Если нужно развернуть только на одном из серверов (например, только MongoDB):

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --limit mongodb_servers --ask-vault-pass
```

### 9.6. Подробный вывод (уровни verbose)

Для отладки используйте `-v`, `-vv`, `-vvv`:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml -vv --ask-vault-pass
```

### 9.7. Запуск плейбука проверки работоспособности

После развертывания выполните проверку:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/verify_db.yml --ask-vault-pass
```

### 9.8. Полная очистка (удаление всего)

Если необходимо полностью удалить базы данных и конфигурации:

```bash
ansible-playbook -i inventory/hosts.ini playbooks/cleanup.yml --ask-vault-pass
```

### 9.9. Использование отдельных ролей напрямую (для быстрого тестирования)

Иногда удобно запустить только одну роль, минуя главный плейбук. Для этого можно создать временный плейбук или использовать `ansible-playbook` с указанием роли как задачи:

```bash
ansible-playbook -i inventory/hosts.ini -e "role_name=mongodb" -e "mongo_port=27017" --ask-vault-pass -c local -vv
```

Либо просто вызвать задачу из роли (если она написана как include). Однако рекомендуется использовать основной плейбук с тегами.

### 9.10. Автоматизация с помощью CI/CD (Jenkins, GitLab CI)

В пайплайнах часто используют файлы паролей Vault, которые хранятся в защищённых переменных. Пример команды в GitLab CI:

```yaml
deploy:
  script:
    - echo "$VAULT_PASSWORD" > .vault_pass
    - ansible-playbook -i inventory/hosts.ini playbooks/deploy_all.yml --vault-password-file .vault_pass
```

## 10. Заключение

Мы создали полноценное, готовое к использованию решение для автоматизации развертывания двух популярных баз данных с помощью Ansible. Ключевые особенности нашего подхода:

- **Модульность** — каждая СУБД и общие задачи вынесены в отдельные роли.
- **Безопасность** — все секреты зашифрованы Ansible Vault, а доступ к сервисам защищён аутентификацией.
- **Идемпотентность** — плейбуки можно перезапускать без опасения нарушить состояние системы.
- **Гибкость** — использование переменных и тегов позволяет адаптировать развертывание под разные сценарии.
- **Проверяемость** — встроенные health-checks дают уверенность в работоспособности.

Данная архитектура легко масштабируется на кластерные конфигурации (Replica Set для MongoDB, кластер ClickHouse) путём расширения инвентаря и добавления соответствующих настроек. Также возможно использование динамического инвентаря для облачных провайдеров.

Мы надеемся, что это руководство станет прочным фундаментом для вашей практики Infrastructure as Code и поможет вам строить надёжные, управляемые системы хранения данных.
