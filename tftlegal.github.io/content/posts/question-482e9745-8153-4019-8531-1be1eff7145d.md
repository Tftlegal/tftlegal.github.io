Сравнение Redis и Hazelcast

1. Цели сравнения

Критерии оценки
- Типы поддерживаемых данных
- Возможности персистентности и восстановления
- Масштабируемость (шардирование, репликация, высокая доступность)
- Режимы работы (один узел, кластер, активный‑активный)
- Интеграция (клиентские библиотеки, экосистема, совместимость)
- Затраты (лицензирование, общая стоимость владения)
- Безопасность (аутентификация, шифрование, контроль доступа)
- Производительность (латентность, пропускная способность, поведение под нагрузкой)

Целевые рабочие нагрузки
- Кеширование (read‑through, write‑through, write‑behind)
- Очереди сообщений и потоковая обработка
- Распределённые карты (distributed maps)
- Обработка событий и сложная событийная обработка (CEP)
- Глобальное распределённое состояние / shared‑nothing вычисления
- Leaderboards, сессии, rate limiting, поиск

2. Архитектура и основные функции

2.1 Redis
Общее описание: Redis – in‑memory хранилище структур данных, работающее преимущественно в одном потоке обработки команд (с версии 6.0 – многопоточный I/O, но исполнение команд остаётся single‑threaded). Реализован на ANSI C, выступает как standalone‑сервис.

Поддерживаемые модели данных:
- Строки (до 512 МБ)
- Списки (двусвязные)
- Наборы (уникальные элементы)
- Отсортированные наборы (з‑sets) с score
- Хеши (поле‑значение)
- Битовые массивы, HyperLogLog, геопространственные индексы
- Streams (append‑only log)
- Модули: RedisJSON (документы JSON), RediSearch (полнотекстовый поиск), RedisGraph (граф), RedisTimeSeries, RedisBloom (фильтры Блума)

Режимы работы:
- Single‑node (без отказоустойчивости)
- Sentinel (мониторинг, автоматический failover)
- Cluster (хеш‑шардирование 16384 слотов, автоматический ребалансинг, репликация)
- Redis Enterprise (Active‑Active geo‑replication, CRDT, Redis on Flash)

Персистентность:
- RDB – периодические снапшоты на диск
- AOF – журнал всех записей, настраиваемая частота fsync (everysec, always, no)
- Гибридный режим (RDB + AOF)
- Raft‑based репликация (Redis Enterprise)

Отказоустойчивость:
- Sentinel – автоматический failover мастера, но требует ручного вмешательства при перезапуске клиентов
- Cluster – автоматический failover, перемаркировка слотов, минимум 3 мастера
- Redis Enterprise – активный‑активный репликация через CRDT, возможность zero‑RPO в некоторых сценариях

2.2 Hazelcast
Общее описание: Hazelcast – распределённая платформа in‑memory данных (IMDG), написанная на Java, может работать внутри JVM‑приложения или как отдельный процесс. Архитектура основана на распределённой хеш‑таблице (partitioned map).

Поддерживаемые структуры и модели данных:
- IMap – распределённая карта (ключ → значение), аналог ConcurrentHashMap на кластерном уровне
- IQueue, ITopic, ISet, IList – распределённые коллекции
- IPromise / ICompletableFuture – распределённые future
- Ringbuffer – кольцевой буфер для событий
- MultiMap – карта с несколькими значениями на один ключ
- CardinalityEstimator – HyperLogLog
- PN‑Counter – распределённый счётчик (CRDT)
- SQL‑движок – возможность выполнять SQL‑запросы к распределённым данным (встроенный H2‑селектор)
- Jet – движок для stream/batch‑обработки (аналог Spark Streaming, но лёгкий)
- CP Subsystem – реализация консенсуса на базе Raft (начиная с версии 5.x)

Архитектура:
- Все узлы равноправны (peer‑to‑peer), нет единого мастера
- Данные автоматически шардируются по партициям (по умолчанию 270)
- Возможна глобальная репликация (backup‑count настраивается)
- Обнаружение членов кластера через multicast, TCP/IP, Kubernetes API или облачные discovery‑модули

Персистентность:
- Hot Restart Persistence (HRP) – периодические дампы данных на диск, быстрый restart
- Persistent Memory – поддержка Intel Optane
- Сохранение в внешних хранилищах (S3, GCS, HDFS)
- Нет прямого аналога AOF/RDB; вместо этого используется WAL (write‑ahead log) в Enterprise‑версии

Отказоустойчивость:
- Backup‑репликация (синхронная/асинхронная) на N backup‑членов
- Защита от split‑brain через CP Subsystem (Raft‑based)
- Автоматическая рехарт‑шардинг при изменении состава узлов
- Entry listeners для отслеживания изменений

3. Производительность, масштабируемость и операционные аспекты

3.1 Производительность

Параметр | Redis | Hazelcast

### --- | --- | ---

Модель исполнения | Single‑threaded (команды), многопоточный I/O | Многопоточная JVM, конкурентная обработка
Типичная латентность | 0.1–1 мс (локально), 1–3 мс (по сети) | 1–5 мс (зависит от нагрузки и бэкапов)
Пропускная способность | 100 K–1 M+ ops/sec на одном узле | 50 K–500 K ops/sec на одном узле
CPU‑bound операции | Блокируют event loop (за исключением Lua) | Распределяются по потокам JVM
Память | Эффективное сжатие (intset, ziplist), низкий оверхед | Java‑object overhead + сериализация (≈50–100 байт на запись)

Ключевые наблюдения:
- Redis быстрее в простых get/set‑операциях благодаря single‑threaded модели без блокировок.
- Hazelcast лучше масштабируется для CPU‑bound задач (map‑reduce, агрегации, Jet‑pipeline), так как использует все ядра JVM.
- При большом числе backup‑реплик Hazelcast замедляется из‑за синхронной репликации; Redis с репликами работает асинхронно по умолчанию.

3.2 Масштабируемость

Redis Cluster:
- До 1000+ мастер‑узлов (ограничение 16384 слотов, на практике ≈ 1000)
- Ребалансировка требует перемещения слотов между узлами (MOV/ASK redirections)
- Клиент должен знать топологию кластера (smart‑client или прокси, например Redis Cluster Proxy)

Hazelcast:
- Горизонтальное масштабирование «из коробки» – добавление нового члена автоматически перераспределяет партиции
- Нет фиксированного числа слотов; партиций по умолчанию 270 (настраиваемо)
- Член discovery и реконфигурация автоматические (мгновенные или почти мгновенные)

3.3 Операционные аспекты

Развёртывание: Docker, Kubernetes (Helm‑charts) – Redis; embedded в Spring Boot, standalone JAR, Kubernetes‑operator – Hazelcast
Мониторинг: INFO, MONITOR, RedisInsight, Prometheus‑exporter – Redis; JMX, Management Center, Prometheus‑metrics – Hazelcast
Резервное копирование: RDB/AOF, BGSAVE – Redis; Hot Restart Persistence, WAL, S3‑backup – Hazelcast
Восстановление: restore из RDB/AOF – Redis; быстрый restart из HRP‑snapshot – Hazelcast
Обновление: rolling update (Cluster) – Redis; rolling update с migration партиций – Hazelcast
Сложность эксплуатации: низкая (Redis), средняя–высокая (Hazelcast – требует JVM‑tuning, настройки партиций, CP Subsystem)

4. Затраты, среда выполнения и безопасность

4.1 Лицензионные модели

- Redis: BSD 3‑Clause (Redis Server) – open source; Redis Enterprise (коммерческий) – Active‑Active, Redis on Flash, Redis Stack, Redis Cloud.
- Hazelcast: Apache 2.0 (Hazelcast IMDG) – open source; Hazelcast Enterprise (коммерческий) – Hot Restart, WAL, CP Subsystem, Security, Management Center, Jet.
- Облачные сервисы: Redis Cloud (Redis Ltd.), Amazon ElastiCache, Azure Cache for Redis, GCP Memorystore; Hazelcast Cloud (Managed Hazelcast).
- Примерные стоимости: Redis Enterprise ≈ 5 000 USD/узел/год; Hazelcast Enterprise ≈ 3 000 USD/узел/год.

4.2 Требования к среде выполнения

- Redis: реализован на C, standalone‑binary, не требует внешней среды, небольшие Docker‑образы (≈ 50 МБ).
- Hazelcast: требует JVM (Java 11+), более тяжёлые Docker‑образы (≈ 300 МБ), необходима настройка GC, heap‑sizing, возможно off‑heap‑режим.

4.3 Безопасность

Функция | Redis | Hazelcast

### --- | --- | ---

Аутентификация | ACL (Redis 6.0), AUTH (legacy) | Username/password, JAAS, Kerberos, LDAP, mutual TLS
Шифрование в пути | TLS (in‑flight) | TLS (in‑flight и at‑rest)
ACL/Authorization | Ролевая модель (user, channel, command, key‑pattern) | RBAC, интеграция с LDAP/AD
Аудит | Ограничен | Audit logging (Enterprise)
Изоляция сети | Bind, firewall, VPC | VPC, TLS, member‑level security
Шифрование at‑rest | Только через Redis Enterprise или ОС‑уровень | HRP с шифрованием (Enterprise)

5. Рекомендации и выводы

5.1 Сводная таблица сравнения

- Лучший для простого кеширования: Redis
- Лучший для очередей: Redis (Streams, LIST) и Hazelcast (IQueue, Ringbuffer) – оба подходят
- Распределённые вычисления: Hazelcast (Jet, map‑reduce)
- SQL‑запросы к данным: Hazelcast (встроенный SQL‑движок)
- Сложная событийная обработка: Hazelcast Jet
- Простота развёртывания: Redis
- Простота использования: Redis
- Масштабируемость CPU‑bound нагрузки: Hazelcast
- Персистентность: Redis (RDB/AOF) более зрелый; Hazelcast (HRP, WAL) – Enterprise‑функции
- Глобальная распределённость: Redis Enterprise Active‑Active, Hazelcast Enterprise WAN‑replication
- Экосистема интеграции: Redis – более широкая (50+ языков); Hazelcast – сильнее в Java‑окружении

5.2 Рекомендации по сценариям

- Простое кеширование, сессии, rate‑limiting, leaderboards → Redis
- Очереди задач, pub/sub → Redis Streams и IQueue (оба подходят)
- Распределённое состояние в Java‑микросервисах → Hazelcast (встроенная карта без сетевых вызовов)
- Распределённые вычисления, агрегация, CEP → Hazelcast Jet
- Необходима CP‑субсистема (сильная консистентность) → Hazelcast CP Subsystem
- Минимальный footprint контейнера → Redis
- Не требуется JVM → Redis
- Широкий набор клиентских библиотек → Redis

5.3 Итоговые выводы

- Redis – прежде всего хранилище данных и кеш. Превосходит в простоте, скорости, экосистеме и лёгкости развёртывания. Оптимален, когда задача ограничивается кешированием, простыми структурами данных и сообщениями.
- Hazelcast – распределённая вычислительная платформа (IMDG). Превосходит в сценариях, требующих shared state между JVM‑приложениями, распределённых вычислений, SQL‑запросов к данным и сложной событийной обработки. Если приложение написано на Java/Kotlin и работает в кластере, Hazelcast может быть встроен напрямую, устраняя сетевые вызовы.
- Компромиссы: Redis жертвует вычислительной мощью ради простоты и скорости; Hazelcast жертвует простотой и лёгкостью ради богатого функционала распределённых операций.
- Оба продукта имеют коммерческие Enterprise‑версии с расширенными возможностями (Active‑Active, CP Subsystem,持久ность, безопасность). Для критичных production‑систем рекомендуется учитывать поддержку и лицензирование.

Итог: выбор между Redis и Hazelcast определяется конкретными требованиями к нагрузке, необходимости в распределённых вычислениях, требованиям к персистентности и инфраструктурным ограничениям. При простом кешировании и сообщениях предпочтительнее Redis; при необходимости глубокой интеграции с JVM‑микросервисами и сложных распределённых операций – Hazelcast.
