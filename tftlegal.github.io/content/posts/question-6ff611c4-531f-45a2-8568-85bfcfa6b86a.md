# Kafka Exactly-once глазами разработчика: как не сломать консистентность в ПРОДе

Обеспечение консистентности данных в распределенных системах — одна из самых сложных задач. В Kafka механизм **Exactly-once Semantics (EOS)** позволяет гарантировать, что результат обработки сообщения будет записан ровно один раз, даже если произойдут сбои сети или перезагрузки сервисов.

## 1. Теория базы: Семантика доставки
Прежде чем внедрять EOS, важно понимать три базовых режима доставки:

*   **At-most-once (Максимум один раз):** Сообщение может быть доставлено один раз или не доставлено вовсе (потеря данных). Используется, когда потеря данных допустима, но дубликаты недопустимы (например, метрики).
*   **At-least-once (Минимум один раз):** Сообщение гарантированно будет доставлено, но может прийти несколько раз (дубликаты). Это стандартный режим для большинства систем.
*   **Exactly-once (Ровно один раз):** Сообщение обрабатывается и фиксируется ровно один раз. Это достигается за счет идемпотентности и транзакций.

## 2. Механика Kafka: Транзакционный API
Для реализации EOS Kafka использует внутренний механизм транзакций, состоящий из трех компонентов:

1.  **Producer ID (PID):** Уникальный идентификатор продюсера, который позволяет брокеру отслеживать сессию.
2.  **Sequence Numbers:** Каждое сообщение получает порядковый номер. Если брокер видит номер, который он уже получал, он отбрасывает дубликат.
3.  **Transaction Coordinator:** Брокер-координатор, который управляет жизненным циклом транзакции, хранит состояние (Ongoing, Prepare_Commit, Committed) и пишет данные в специальный внутренний топик `__transaction_state`.

## 3. Настройка Producer: Три кита идемпотентности
Чтобы включить EOS, необходимо правильно настроить продюсера. Недостаточно просто поставить флаг.

*   **`enable.idempotence=true`**: Включает идемпотентность. Брокер начинает проверять Sequence Numbers.
*   **`transactional.id`**: **Обязательный параметр.** Это уникальный ID для конкретного приложения. Он позволяет Kafka реализовать **Zombie Fencing** — если старый экземпляр приложения «ожил» и пытается отправить данные, брокер отклонит его, так как увидит новый сеанс с тем же `transactional.id`.
*   **`acks=all`**: Гарантирует, что сообщение записано на все синхронные реплики (ISR). Без этого транзакция не может считаться надежной.
*   *Важно:* Параметр `max.in.flight.requests.per.connection` должен быть $\le 5$ (в современных версиях Kafka это значение по умолчанию при включенной идемпотентности).

## 4. Настройка Consumer: Изоляция данных
Если продюсер пишет транзакционно, консьюмер должен знать, как эти данные читать.

*   **`isolation.level=read_committed`**: По умолчанию консьюмеры видят все сообщения (даже те, что были откачены в транзакции). Режим `read_committed` гарантирует, что консьюмер получит только те записи, которые были успешно зафиксированы (committed).
*   **Почему нельзя читать "undcommitted"?** Если консьюмер прочитает данные из незавершенной транзакции, а та позже будет откачена (rollback), консьюмер обработает данные, которых «не существует» в финальном состоянии системы. Это нарушает атомарность.

## 5. Паттерн Read-Process-Write (RPW)
Это классический сценарий использования EOS в Kafka (например, Stream Processing):
1.  **Read:** Консьюмер читает сообщение из топика А.
2.  **Process:** Приложение выполняет бизнес-логику.
3.  **Write:** Продюсер записывает результат в топик Б **и одновременно фиксирует смещение (offset)** в системном топике `__consumer_offsets` внутри одной транзакции.

**Результат:** Либо и результат обработки, и смещение будут сохранены, либо ничего не будет сохранено. Это исключает дублирование при перезагрузке приложения.

## 6. Внешние системы: Когда Kafka EOS не спасает
Kafka гарантирует EOS только **внутри своей экосистемы**. Если ваше приложение пишет в БД или внешний API, транзакция Kafka не распространяется на них.

**Решения:**
*   **Outbox Pattern:** Вместо прямой записи в БД и отправки в Kafka, приложение пишет данные в специальную таблицу `Outbox` в той же транзакции БД. Отдельный сервис (или CDC-инструмент типа Debezium) читает эту таблицу и отправляет данные в Kafka. Это гарантирует атомарность «БД + Kafka».
*   **Idempotent Consumer:** Если вы вызываете внешний API, сделайте его идемпотентным (передавайте уникальный `request_id`). Если Kafka переотправит сообщение из-за сбоя, внешний сервис поймет, что он его уже обрабатывал.
*   *Примечание по 2PC:* Классический Two-Phase Commit между Kafka и сторонней БД крайне сложен в реализации и часто является антипаттерном из-за проблем с производительностью и блокировками.

## 7. Мониторинг и отладка
Работа с транзакциями вносит свои нюансы в эксплуатацию:

*   **Stranded Transactions:** Транзакции, которые были начаты, но не были завершены (например, из-за падения приложения). Они могут занимать ресурсы координатора. Kafka автоматически очищает их по таймауту (`transactional.id.expiration.ms`).
*   **OutOfOrderSequenceException:** Возникает, если продюсер пытается отправить сообщение с порядковым номером, который не соответствует ожидаемому. Обычно это признак того, что два процесса пытаются писать под одним `transactional.id` или произошел серьезный сбой сетевой связности.
*   **Задержки (Latency):** Помните, что `read_committed` может увеличивать задержку, так как консьюмер ждет завершения транзакции перед чтением.
