По вашему `lsblk` таблица разделов и LVM, скорее всего, **не уничтожены**: видны `sda1`, `sda2`, `sda5`, LVM physical volume на `sda5` и все логические тома (`root`, `var`, `swap_1`, `tmp`). Это хороший признак: проблема вероятнее в файловой системе, загрузчике/initramfs или самом диске, а не в исчезнувших разделах.

Главное сейчас: **не запускайте `fsck` на смонтированном томе** и не выполняйте `pvcreate`, `vgcreate`, `mkfs`, `fdisk write`, `parted mklabel` и тому подобное. Эти команды могут превратить ремонт в восстановление из бэкапа.

## Сначала защитите данные

Загрузитесь с Live USB Linux того же или более нового дистрибутива, откройте терминал и соберите диагностику:

```bash
sudo -i
lsblk -f
blkid
fdisk -l /dev/sda
pvs
vgs
lvs -a -o +devices
```

Судя по именам, ваша VG — `tftlegal-vg`, а root LV доступен как:

```bash
/dev/tftlegal-vg/root
```

или через device-mapper:

```bash
/dev/mapper/tftlegal--vg-root
```

Сохраните метаданные LVM на внешний носитель, прежде чем что-либо чинить:

```bash
mkdir -p /mnt/usb/lvm-backup
vgcfgbackup -f /mnt/usb/lvm-backup/tftlegal-vg.conf tftlegal-vg
pvs -v > /mnt/usb/lvm-backup/pvs.txt
vgs -v > /mnt/usb/lvm-backup/vgs.txt
lvs -a -v -o +devices > /mnt/usb/lvm-backup/lvs.txt
```

Если внешнего носителя нет, хотя бы посмотрите резервные копии метаданных, которые LVM обычно хранит локально:

```bash
ls -lah /etc/lvm/backup /etc/lvm/archive
```

LVM умеет сканировать PV (`pvscan`), а копии метаданных VG обычно можно использовать только если именно LVM-метаданные повреждены; пока по вашему выводу оснований восстанавливать их нет. [manpages.debian](https://manpages.debian.org/buster/lvm2/lvm.8.en.html)

## Проверьте здоровье диска

Kernel panic плюс отказ загрузки может быть следствием проблем SATA-диска, кабеля, контроллера или RAM. Прежде чем агрессивно чинить файловую систему, проверьте SMART:

```bash
smartctl -x /dev/sda
```

Если `smartctl` не найден:

```bash
apt update
apt install -y smartmontools
smartctl -x /dev/sda
```

Критичны строки и счётчики:

```bash
smartctl -A /dev/sda | egrep -i \
'Reallocated|Pending|Offline_Uncorrectable|UDMA_CRC|Read_Error|Reported_Uncorrect'
```

Интерпретация:

| Признак | Что означает | Действие |
|---|---|---|
| `Current_Pending_Sector > 0` | Нестабильные/нечитаемые сектора | Сразу копировать данные/делать образ диска |
| `Offline_Uncorrectable > 0` | Есть сектора, которые диск не может прочесть | Не ремонтировать «на месте», сначала образ |
| `Reallocated_Sector_Ct` растёт | Диск деградирует | Планировать замену диска |
| `UDMA_CRC_Error_Count > 0` и растёт | Часто SATA-кабель/контакт, не поверхность диска | Переподключить или заменить SATA-кабель |
| SMART PASSED, ошибок нет | Вероятнее ФС, initramfs, GRUB или память | Продолжать проверку ФС и загрузчика |

Если найдутся ошибки чтения или SMART плохой, сначала клонируйте диск на исправный накопитель с `ddrescue`, а восстановление делайте уже на копии:

```bash
apt update
apt install -y gddrescue
ddrescue -f -n /dev/sda /dev/sdX /mnt/usb/sda-rescue.map
ddrescue -d -r3 /dev/sda /dev/sdX /mnt/usb/sda-rescue.map
```

Здесь `/dev/sdX` — **другой диск**, не раздел. Перепутать назначения нельзя: команда полностью перезапишет целевой диск.

## Активируйте LVM и проверьте ФС

В Live-системе активируйте группу томов:

```bash
modprobe dm_mod
pvscan
vgscan --mknodes
vgchange -ay tftlegal-vg
lvscan
```

Все тома должны стать `ACTIVE`, включая root и var. Активация VG через `vgchange -ay` — штатный шаг при восстановлении LVM из rescue/live-среды. [boycottsystemd](https://boycottsystemd.org/how-to-recover-an-lvm-volume-that-wont-mount-at-boot/)

Теперь определите типы ФС:

```bash
lsblk -f
blkid /dev/mapper/tftlegal--vg-root
blkid /dev/mapper/tftlegal--vg-var
blkid /dev/sda1
```

### Если это ext4

Сначала безопасная диагностика без изменений:

```bash
fsck -fvn /dev/mapper/tftlegal--vg-root
fsck -fvn /dev/mapper/tftlegal--vg-var
fsck -fvn /dev/sda1
```

Если вывод показывает ошибки, и SMART не указывает на умирающий диск, запускайте исправление по одному тому:

```bash
fsck -fy /dev/mapper/tftlegal--vg-root
fsck -fy /dev/mapper/tftlegal--vg-var
fsck -fy /dev/sda1
```

Том `/tmp`, если это отдельный ext4 и в нём нет нужных вам данных, тоже можно проверить:

```bash
fsck -fy /dev/mapper/tftlegal--vg-tmp
```

Не нужно запускать `fsck` на swap:

```text
/dev/mapper/tftlegal--vg-swap_1
```

Для ext2/3/4 файловую систему нужно проверять, когда она не смонтирована; `e2fsck`/`fsck` проверяет и при необходимости восстанавливает структуру ФС и журнал. [linuxcommandlibrary](https://linuxcommandlibrary.com/basic/systemrecovery)

### Если это XFS

`fsck` для XFS не используйте. Диагностика:

```bash
xfs_repair -n /dev/mapper/tftlegal--vg-root
xfs_repair -n /dev/mapper/tftlegal--vg-var
```

Ремонт — только после оценки вывода:

```bash
xfs_repair /dev/mapper/tftlegal--vg-root
xfs_repair /dev/mapper/tftlegal--vg-var
```

Если XFS скажет про log/journal и предложит `-L`, **не используйте `-L` сразу**: это обнулит журнал, возможна потеря последних изменений. Сначала попробуйте смонтировать том read-only и скопировать важное.

### Если это Btrfs

Не запускайте обычный `fsck`. Начните с read-only монтирования и:

```bash
btrfs check --readonly /dev/mapper/tftlegal--vg-root
```

`btrfs check --repair` без подтверждённой резервной копии — плохая первая реакция.

## Скопируйте данные до ремонта загрузки

Если root монтируется, сначала скопируйте важные данные. Монтируйте read-only:

```bash
mkdir -p /mnt/root
mount -o ro /dev/mapper/tftlegal--vg-root /mnt/root

mkdir -p /mnt/var
mount -o ro /dev/mapper/tftlegal--vg-var /mnt/var
```

Проверьте, что это именно ваша система:

```bash
cat /mnt/root/etc/os-release
cat /mnt/root/etc/fstab
ls -lah /mnt/root/boot
```

Для копирования на внешний диск, предположим, что он смонтирован в `/media/ubuntu/BACKUP`:

```bash
rsync -aHAXx --numeric-ids --info=progress2 \
  /mnt/root/ /media/ubuntu/BACKUP/rootfs/
```

Отдельный `/var` сохраняйте отдельно:

```bash
rsync -aHAXx --numeric-ids --info=progress2 \
  /mnt/var/ /media/ubuntu/BACKUP/varfs/
```

## Восстановите загрузку

Если ФС читается и система не стартует, причина может быть в GRUB или initramfs. Сначала проверьте тип загрузки:

```bash
test -d /sys/firmware/efi && echo UEFI || echo BIOS-legacy
parted -l
```

У вас `sda1` размером 731 МБ. Это может быть `/boot`, EFI System Partition или просто отдельный загрузочный раздел. Определите точно:

```bash
blkid /dev/sda1
file -s /dev/sda1
```

### Смонтируйте установленную систему

После успешного `fsck`:

```bash
mount /dev/mapper/tftlegal--vg-root /mnt

mkdir -p /mnt/var
mount /dev/mapper/tftlegal--vg-var /mnt/var
```

Если `sda1` указан в `/mnt/etc/fstab` как `/boot`:

```bash
mount /dev/sda1 /mnt/boot
```

Если в `fstab` он указан как `/boot/efi`, то:

```bash
mkdir -p /mnt/boot/efi
mount /dev/sda1 /mnt/boot/efi
```

Проверьте:

```bash
cat /mnt/etc/fstab
findmnt -R /mnt
```

Подготовьте chroot:

```bash
for i in /dev /dev/pts /proc /sys /run; do
  mount --bind "$i" "/mnt$i"
done

chroot /mnt /bin/bash
```

Внутри chroot:

```bash
mount -a
update-initramfs -c -k all
update-grub
```

Если `update-initramfs -c` сообщает, что initramfs уже существует, используйте:

```bash
update-initramfs -u -k all
```

### Для BIOS/Legacy boot

Если система загружалась в Legacy BIOS:

```bash
grub-install /dev/sda
update-grub
exit
sync
reboot
```

Важно: устанавливать GRUB нужно на **диск** `/dev/sda`, не на `/dev/sda1` и не на LVM LV.

### Для UEFI boot

Если загрузка UEFI и `sda1` — FAT32 EFI System Partition, после монтирования её в `/mnt/boot/efi`:

```bash
grub-install --target=x86_64-efi \
  --efi-directory=/boot/efi \
  --bootloader-id=ubuntu \
  --recheck
update-grub
exit
sync
reboot
```

Имя `ubuntu` не обязательно означает Ubuntu: это только имя UEFI boot entry. Но если установлен другой дистрибутив, можно подставить его имя, например `debian`.

## Если загрузка падает снова

Если после ремонта ФС и GRUB снова получаете kernel panic:

- В GRUB выберите **Advanced options** и загрузите предыдущее ядро.
- Временно добавьте в строку ядра через `e` параметр:

```text
systemd.unit=multi-user.target
```

Так вы исключите графический стек и часть пользовательских сервисов.

- Если panic связан с GPU, загрузитесь с:

```text
nomodeset
```

- Проверьте предыдущий boot после восстановления журналов:

```bash
journalctl -k -b -1 -p warning..alert
journalctl -k -b -1 | grep -Ei \
'panic|deadlock|oom|i/o error|ext4|xfs|btrfs|ata|reset|timeout|gpu|nvidia|amdgpu|nouveau'
```

- Прогоните Memtest86+ минимум несколько проходов. Сообщение на фото `System is deadlocked on memory` не доказывает поломку ОЗУ, но RAM, XMP/разгон и драйверы ядра — реальные кандидаты. До устранения причины желательно отключить XMP/разгон и проверить диск/кабель.

В вашей ситуации разумный порядок такой: **SMART → LVM backup → read-only mount и копия данных → fsck/xfs_repair по реальному типу ФС → chroot → rebuild initramfs и GRUB**. Это даёт максимальный шанс вернуть систему без потери данных.

В случае опасений повторения подобных проблем можно сделать **побайтовый клон всего диска** с HDD `/dev/sda` на SSD `/dev/sdc`. SSD должен бфьб больше (238.5G -->  232.9G), поэтому после копирования останется ~5.6G нераспределённого места; его можно отдать LVM.

**Важно:** команда полностью затрёт `/dev/sdc`. Не перепутайте `if=` и `of=`. Лучше выполнять с LiveCD/LiveUSB либо, как минимум, когда система не активна на `/dev/sda`; при работающей ОС клон может получиться несогласованным. `dd` копирует таблицу разделов, загрузчик, LVM и все данные целиком. [wiki.archlinux](https://wiki.archlinux.org/title/Dd_(%D0%A0%D1%83%D1%81%D1%81%D0%BA%D0%B8%D0%B9))

## 0. Проверка устройств

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL /dev/sda /dev/sdc
```

Убедитесь, что:

- `/dev/sda` — исходный HDD;
- `/dev/sdc` — целевой SSD;
- на `/dev/sdc` нет нужных данных;
- `/dev/sda` и `/dev/sdc` не смонтированы как источник/приёмник, если работаете из Live-среды.

Полезно использовать стабильные имена по ID:

```bash
ls -l /dev/disk/by-id/ | grep -E 'sd[ac]$'
```

## 1. Клонирование

```bash
sudo dd if=/dev/sda of=/dev/sdc bs=4M status=progress conv=fsync
```

- `bs=4M` — обычно быстрее мелких блоков;
- `status=progress` — прогресс;
- `conv=fsync` — дождаться физической записи на SSD перед завершением. [oneuptime](https://oneuptime.com/blog/post/2026-03-02-how-to-use-dd-for-disk-cloning-and-imaging-on-ubuntu/view)

Если на старом HDD могут быть читаемые ошибки, лучше использовать `ddrescue`:

```bash
sudo apt install gddrescue
sudo ddrescue -f -v /dev/sda /dev/sdc /root/sda-rescue.log
```

Но для заведомо исправного диска достаточно `dd`.

## 2. После копирования

```bash
sync
```

Проверьте структуру:

```bash
lsblk /dev/sdc
sudo blkid /dev/sdc*
```

Должны появиться те же разделы и LVM: `sdc1`, `sdc2`, `sdc5`, а также `tftlegal--vg-root`, `-var`, `-swap_1`, `-tmp`.

## 3. Расширить раздел LVM

На SSD осталось около 5.6G. Сначала расширьте расширенный раздел `sdc2` и логический `sdc5`.

Проверьте текущую разметку:

```bash
sudo parted /dev/sdc print
sudo fdisk -l /dev/sdc
```

Если установлен `growpart`:

```bash
sudo apt install cloud-guest-utils
sudo growpart /dev/sdc 2
sudo growpart /dev/sdc 5
```

Если `growpart` откажется из-за GPT backup header, сначала исправьте таблицу:

```bash
sudo sgdisk -e /dev/sdc
```

Для MBR/extended-раздела иногда проще сделать это в `fdisk`/`parted` вручную. Но обычно после `dd` и `growpart` схема такая:

```bash
sudo growpart /dev/sdc 2
sudo growpart /dev/sdc 5
```

## 4. Расширить PV, VG и LV

После расширения `sdc5`:

```bash
sudo pvresize /dev/sdc5
sudo vgs
sudo pvs
sudo lvs
```

Посмотрите свободное место:

```bash
sudo vgdisplay tftlegal-vg | grep -E 'VG Size|Free  PE'
```

Отдайте всё свободное место корневому LV и сразу увеличьте файловую систему:

```bash
sudo lvextend -r -l +100%FREE /dev/tftlegal-vg/root
```

`-r` вызывает изменение размера файловой системы; для ext4 это `resize2fs`, для XFS — `xfs_growfs`. [man7](https://man7.org/linux/man-pages/man8/lvextend.8.html)

Если хотите оставить запас и расширить, например, только на 4G:

```bash
sudo lvextend -r -L +4G /dev/tftlegal-vg/root
```

Проверка:

```bash
df -h /
sudo lvs
sudo vgs
```

## 5. Загрузка с SSD

Выключите сервер, физически отключите старый HDD `/dev/sda` (или измените порядок загрузки в BIOS/UEFI), затем загрузитесь с SSD.

После загрузки проверьте:

```bash
lsblk
df -h
sudo vgdisplay
cat /proc/cmdline
```

Если система загружается не с SSD или GRUB не видит диск, загрузитесь с LiveUSB и переустановите загрузчик:

```bash
sudo mount /dev/tftlegal-vg/root /mnt
sudo mount /dev/sdc1 /mnt/boot   # если /boot отдельный
sudo mount --bind /dev /mnt/dev
sudo mount --bind /proc /mnt/proc
sudo mount --bind /sys /mnt/sys
sudo chroot /mnt
grub-install /dev/sdc
update-grub
exit
```

Для старой MBR-схемы это обычно достаточно; для UEFI дополнительно проверьте наличие EFI-раздела и `grub-install --target=x86_64-efi`.

## Кратко: минимальный набор

```bash
# Проверить
lsblk -o NAME,SIZE,MODEL,SERIAL,MOUNTPOINTS /dev/sda /dev/sdc

# Клонировать HDD -> SSD
sudo dd if=/dev/sda of=/dev/sdc bs=4M status=progress conv=fsync
sync

# Расширить разделы, если нужно использовать остаток SSD
sudo growpart /dev/sdc 2
sudo growpart /dev/sdc 5
sudo pvresize /dev/sdc5
sudo lvextend -r -l +100%FREE /dev/tftlegal-vg/root

# Проверить
lsblk
df -h /
```

`dd` создаст точную копию, включая UUID файловых систем и LVM; поэтому **не подключайте старый и новый диск одновременно в загружаемой системе без изменения UUID/VG**, чтобы избежать путаницы при загрузке и сборке LVM. [wiki.archlinux](https://wiki.archlinux.org/title/Dd_(%D0%A0%D1%83%D1%81%D1%81%D0%BA%D0%B8%D0%B9))
