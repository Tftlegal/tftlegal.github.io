🧠 Мульти-Агентный ответ:

Conventional Commits — это набор правил, как оформлять сообщения к коммитам в системе контроля версий (например, Git). Их цель — сделать историю изменений понятной как людям, так и программам, чтобы можно было автоматически генерировать changelog, определять новые версии и настраивать CI/CD‑процессы.

Сообщение коммита состоит из трёх частей:
1. Тип изменений — короткое слово, которое показывает, что именно сделано (например, feat для новой функции, fix для исправления бага).
2. Область — необязательная часть в скобках, указывающая, в какой части проекта произошли изменения (например, auth для модуля авторизации).
3. Тема — краткое описание самого изменения в повелительном наклонении.

Пример сообщения: fix(auth): исправить ошибку входа.

Основные типы:
- feat — добавление новой функции.
- fix — исправление ошибки.
- docs — изменения только в документации.
- style — правки форматирования кода, не влияющие на логику.
- refactor — рефакторинг, улучшение структуры без новых функций.
- test — добавление или изменение тестов.
- chore — рутинные задачи, связанные с поддержкой проекта (обновление зависимостей, настройка инструментов и т.д.).
- Есть и другие типы для специфичных случаев: build, ci, revert и т.п.

Важно, что тип сообщения описывает *что* изменилось, а не *как* это сделано. Благодаря этому можно:
- Автоматически формировать changelog, анализируя типы коммитов.
- Определять версию релиза (major, minor, patch) в соответствии с семантическим версионированием.
- Настраивать пайплайны CI/CD, например, запускать публикацию только при коммитах типа feat или fix.

Преимущества использования Conventional Commits:
- История проекта становится прозрачной и легко читаемой.
- Инструменты вроде conventional-changelog или semantic-release могут работать без дополнительной настройки.
- Просто искать нужные изменения по типу (например, показать только коммиты с типом fix).
- Стандарт совместим с популярными сервисами и плагинами, что упрощает интеграцию в существующие workflows.

Короче говоря, Conventional Commits — это простой и единый формат написания сообщений к коммитам, который помогает автоматизировать выпуск версий, вести changelog и делает работу с кодом более предсказуемой и удобной.

# Полное руководство по Conventional Commits: Как сделать историю кода понятной для людей и машин

## Введение: Проблема "говорящих" коммитов

Представьте, что вы открываете историю Git-проекта и видите такие сообщения:

```
Fixed stuff
Update
tmp
final fix
real final fix
fix bug
```

Знакомо? Такая история кода не просто бесполезна — она вредна. Через месяц вы сами не вспомните, что именно было исправлено в том самом "final fix". А если в проекте работает команда из пяти или десяти человек, хаос становится неизбежным.

**Conventional Commits** (Стандартные коммиты) — это простое, но гениальное решение. Это **формат** для написания сообщений о коммитах, который делает историю кода структурированной, понятной и, что самое важное, **машиночитаемой**.

В этой статье мы разберём каждую деталь этого формата, рассмотрим множество практических примеров и покажем, как правильно применять его в реальных проектах.

---

## Анатомия правильного коммита

Стандартное сообщение коммита выглядит так:

```
<тип>(<область>): <краткое описание>

[необязательное тело коммита]

[необязательная нижняя колонтитул]
```

Разберём каждую часть подробно.

### 1. Тип коммита — самое важное

Тип — это сердце сообщения. Он говорит нам, *что именно* произошло с кодом.

Вот полный список типов с подробным объяснением и примерами.

---

#### `feat` — новая функциональность

Используйте `feat`, когда вы добавляете новую возможность для пользователя. Это может быть новая страница, новый API-эндпоинт, новая кнопка или любое другое изменение, которое расширяет функциональность продукта.

**Примеры:**

```bash
git commit -m "feat: добавить возможность сброса пароля"
git commit -m "feat(auth): реализовать вход через Google OAuth"
git commit -m "feat(api): добавить эндпоинт для получения списка заказов"
git commit -m "feat(ui): добавить темную тему оформления"
git commit -m "feat: добавить экспорт отчетов в PDF"
git commit -m "feat(profile): добавить загрузку аватара"
git commit -m "feat(notifications): настроить push-уведомления"
git commit -m "feat(search): реализовать фильтрацию по дате"
git commit -m "feat(payment): добавить поддержку криптовалют"
git commit -m "feat(dashboard): добавить виджет статистики продаж"
```

---

#### `fix` — исправление ошибки

Тип `fix` используется, когда вы чините баг, который влияет на работу продукта. Это может быть исправление логики, обработка исключительной ситуации или починка сломанного поведения.

**Примеры:**

```bash
git commit -m "fix: исправить ошибку валидации email"
git commit -m "fix(auth): исправить обновление токена после истечения срока"
git commit -m "fix(ui): исправить наложение элементов на мобильных устройствах"
git commit -m "fix(api): исправить обработку пустых запросов"
git commit -m "fix(parser): исправить краш при парсинге пустого файла"
git commit -m "fix(db): исправить утечку соединений с базой данных"
git commit -m "fix(router): исправить переход на несуществующий маршрут"
git commit -m "fix(forms): исправить сброс формы после отправки"
git commit -m "fix(cache): исправить инвалидацию кэша"
git commit -m "fix(websocket): исправить переподключение при обрыве связи"
```

---

#### `docs` — изменения в документации

Используйте `docs`, когда вы работаете исключительно с документацией: обновляете README, добавляете комментарии к коду, правите описание API или создаёте руководства для пользователей.

**Примеры:**

```bash
git commit -m "docs: обновить README с инструкцией по установке"
git commit -m "docs(api): дополнить описание эндпоинта /auth/login"
git commit -m "docs: добавить руководство по развертыванию проекта"
git commit -m "docs: обновить список используемых технологий"
git commit -m "docs(contributing): добавить правила для контрибьюторов"
git commit -m "docs: исправить опечатки в документации"
git commit -m "docs: добавить примеры использования основных функций"
git commit -m "docs: обновить лицензию на MIT"
git commit -m "docs(changelog): обновить лог изменений"
git commit -m "docs: добавить схему базы данных"
```

---

#### `style` — изменения, не влияющие на логику

Этот тип используется для изменений, которые не затрагивают работу кода, но делают его более читаемым или соответствующим стандартам оформления. Это правка отступов, добавление или удаление точек с запятой, переименование переменных.

**Важно:** `style` здесь относится к оформлению кода, а не к UI-стилям. Для изменения стилей интерфейса используйте `feat` или `fix`.

**Примеры:**

```bash
git commit -m "style: исправить форматирование отступов"
git commit -m "style: добавить точки с запятой во всех файлах"
git commit -m "style: переименовать переменную userData в user"
git commit -m "style: удалить неиспользуемые импорты"
git commit -m "style: привести код к единому стилю в соответствии с ESLint"
git commit -m "style: исправить длину строк до 80 символов"
git commit -m "style: упорядочить импорты по алфавиту"
git commit -m "style: добавить пробелы вокруг операторов"
git commit -m "style: переименовать файлы в kebab-case"
git commit -m "style: исправить именование констант на UPPER_SNAKE_CASE"
```

---

#### `refactor` — рефакторинг кода

Тип `refactor` используется, когда вы меняете код, не исправляя баг и не добавляя новую функциональность. Цель рефакторинга — улучшить читаемость, упростить архитектуру, уменьшить дублирование или подготовить код к будущим изменениям.

**Примеры:**

```bash
git commit -m "refactor: вынести логику валидации в отдельный сервис"
git commit -m "refactor: упростить цикл обработки данных"
git commit -m "refactor(auth): разделить контроллер на несколько модулей"
git commit -m "refactor: заменить циклы на функциональный подход map/filter/reduce"
git commit -m "refactor: улучшить обработку ошибок в API"
git commit -m "refactor(db): оптимизировать запросы к базе данных"
git commit -m "refactor: удалить дублирующийся код"
git commit -m "refactor: переписать класс на функциональный компонент"
git commit -m "refactor: улучшить типизацию с помощью TypeScript"
git commit -m "refactor: разбить большой компонент на маленькие переиспользуемые части"
```

---

#### `chore` — рутинные задачи

Тип `chore` (от англ. "рутина") используется для задач, которые не относятся к функциональности или документации напрямую. Это обычно настройка инструментов сборки, обновление зависимостей, конфигурация CI/CD, генерация файлов.

**Примеры:**

```bash
git commit -m "chore: обновить зависимости до последних версий"
git commit -m "chore: настроить webpack для production сборки"
git commit -m "chore: добавить Husky для pre-commit хуков"
git commit -m "chore(deps): установить библиотеку axios"
git commit -m "chore: обновить Node.js с 16 до 18"
git commit -m "chore: настроить GitHub Actions для автоматического деплоя"
git commit -m "chore: добавить .gitignore для файлов окружения"
git commit -m "chore: настроить Eslint с правилами Airbnb"
git commit -m "chore: обновить конфигурацию Docker"
git commit -m "chore: сгенерировать типы для GraphQL схемы"
```

---

#### Дополнительные типы (менее часто используемые)

```bash
# `perf` — улучшение производительности
git commit -m "perf: кэшировать результаты тяжелых вычислений"
git commit -m "perf: оптимизировать загрузку изображений"

# `test` — добавление или исправление тестов
git commit -m "test: добавить юнит-тесты для сервиса аутентификации"
git commit -m "test: исправить flaky тесты"

# `build` — изменения в системе сборки
git commit -m "build: обновить настройки Vite"
git commit -m "build: переключиться с npm на pnpm"

# `ci` — изменения в CI/CD конфигурации
git commit -m "ci: добавить проверку линтинга в GitHub Actions"
git commit -m "ci: настроить деплой на staging окружение"

# `revert` — откат предыдущего коммита
git commit -m "revert: откатить feat: добавить возможность сброса пароля"
```

### 2. Область (scope) — уточнение места изменений

Область указывает на конкретную часть проекта, в которой произошли изменения. Она пишется в круглых скобках после типа.

**Зачем это нужно?** Представьте, что у вас 100 коммитов с типом `feat`. Без области вы не поймете, что именно было добавлено. С областью история становится значительно более информативной.

**Примеры областей:**

```bash
git commit -m "feat(auth): добавить двухфакторную аутентификацию"
git commit -m "feat(payments): добавить поддержку Apple Pay"
git commit -m "feat(profile): добавить редактирование личных данных"
git commit -m "feat(notifications): добавить email-рассылку"
git commit -m "feat(dashboard): добавить виджет активности"
git commit -m "feat(api): обновить документацию Swagger"
git commit -m "feat(db): добавить индексы для ускорения запросов"
git commit -m "feat(ui): обновить дизайн кнопок"
git commit -m "feat(router): добавить защиту маршрутов"
git commit -m "feat(storage): настроить загрузку файлов в S3"
```

**Важно:** область не обязательна, но её использование считается хорошим тоном, особенно в больших проектах.

### 3. Breaking Changes — критически важные изменения

Если ваше изменение **ломает обратную совместимость**, это нужно обязательно отметить. В Conventional Commits для этого используется восклицательный знак `!` после типа или области.

**Примеры:**

```bash
# Ломаем API: изменяем структуру ответа
git commit -m "feat(api)!: изменить структуру ответа /user/profile"

# Меняем публичный метод
git commit -m "refactor!: изменить сигнатуру метода calculateTotal"

# Удаляем устаревший эндпоинт
git commit -m "feat!: удалить устаревший API /v1/orders"

# Меняем название переменной окружения
git commit -m "chore!: переименовать ENV переменную DB_HOST в DATABASE_HOST"
```

В теле коммита можно подробнее описать, что именно было сломано и как это исправить:

```bash
git commit -m "feat(api)!: изменить структуру ответа /user/profile

BREAKING CHANGE: поле 'name' разделено на 'firstName' и 'lastName'.
Миграция: используйте name.split(' ') для разделения."
```

## Как правильно писать описание коммита

### Золотое правило: повелительное наклонение

Описание должно звучать как команда, как будто вы говорите коду: «Сделай то-то».

**Правильно:**
- "Добавить валидацию полей"
- "Исправить обработку ошибок"
- "Обновить зависимости"

**Неправильно:**
- "Я добавил валидацию"
- "Исправлена ошибка"
- "Зависимости были обновлены"

### Длина описания

Краткое описание должно быть не длиннее 50-70 символов. Если нужно больше — используйте тело коммита.

## Полные примеры правильных коммитов

Вот как выглядят идеальные коммиты в реальных проектах:

```bash
# Простой коммит с функцией
git commit -m "feat: добавить возможность сортировки таблицы"

# Коммит с областью
git commit -m "feat(profile): добавить загрузку аватара пользователя"

# Исправление бага с указанием проблемы
git commit -m "fix(auth): исправить ошибку 'token expired'"

# Коммит с документацией
git commit -m "docs: добавить описание всех API эндпоинтов"

# Коммит с breaking change
git commit -m "feat(db)!: перейти с MongoDB на PostgreSQL"

# Коммит с телом
git commit -m "refactor: упростить логику обработки заказов

Ранее логика была распределена между тремя сервисами.
Теперь вся бизнес-логика сосредоточена в OrderService.
Удалены дублирующиеся методы."

# Коммит с несколькими изменениями (редко, лучше разбивать)
git commit -m "feat: добавить страницу профиля и исправить навигацию"
```

## Что НЕ надо делать ❌

Вот примеры плохих коммитов, которые не соответствуют стандарту:

```bash
# ❌ Непонятное сообщение
git commit -m "исправлено"

# ❌ Слишком общее
git commit -m "обновление"

# ❌ Нет типа
git commit -m "добавил валидацию пароля"

# ❌ Неправильный тип
git commit -m "fix: добавить новую страницу"  # должен быть feat

# ❌ Слишком длинное описание
git commit -m "feat: добавить возможность загружать файлы и проверять их размер и формат"

# ❌ Использование прошедшего времени
git commit -m "feat: добавил кнопку отправки"

# ❌ Описание в будущем времени
git commit -m "feat: будет добавлена валидация"
```

## Преимущества использования Conventional Commits

### 1. Автоматическая генерация CHANGELOG

Инструменты вроде `standard-version` или `semantic-release` могут автоматически создавать файл CHANGELOG.md на основе ваших коммитов.

### 2. Автоматическое управление версиями

Система может анализировать коммиты и определять, какую версию нужно выпустить:

- Коммиты `fix` → патч-релиз (1.0.0 → 1.0.1)
- Коммиты `feat` → минор-релиз (1.0.0 → 1.1.0)
- Коммиты с `BREAKING CHANGE` или `!` → мажор-релиз (1.0.0 → 2.0.0)

### 3. Упрощение Code Review

Когда разработчик видит `fix(auth): исправить утечку токена`, он сразу понимает суть изменений без погружения в код.

### 4. Лучшая навигация по истории

Фильтрация коммитов становится простой:

```bash
# Показать все новые функции
git log --grep="feat"

# Показать все исправления в модуле auth
git log --grep="fix(auth)"
```

## Инструменты для работы с Conventional Commits

### 1. Commitizen — интерактивный помощник

```bash
# Установка глобально
npm install -g commitizen

# Затем вместо git commit используйте:
git cz
```

Commitizen проведёт вас через все шаги: выберет тип, область, напишет описание.

### 2. Commitlint — валидация коммитов

```bash
npm install -g @commitlint/cli @commitlint/config-conventional
```

Этот инструмент проверяет, соответствуют ли ваши коммиты стандарту, и блокирует неправильные.

### 3. Husky + commitlint

Настройте Git хуки, чтобы каждый коммит проверялся автоматически:

```bash
npm install -D husky @commitlint/cli @commitlint/config-conventional
npx husky install
npx husky add .husky/commit-msg 'npx commitlint --edit "$1"'
```

Теперь каждый ваш коммит будет проходить проверку.

## Заключение: с чего начать?

Внедрять Conventional Commits в проект легко:

1. **Начните с себя.** Даже если вы работаете один, правильные коммиты помогут вам через полгода вспомнить, что вы делали.

2. **Договоритесь в команде.** Проведите митинг на 15 минут, объясните преимущества и выберите типы, которые будете использовать.

3. **Установите Commitizen.** Это сделает процесс простым и дружелюбным для всех разработчиков.

4. **Настройте автоматическую проверку.** Добавьте commitlint через Husky, чтобы никто случайно не создал "неправильный" коммит.

5. **Наслаждайтесь чистой историей.** Через месяц вы скажете себе спасибо за то, что все коммиты структурированы и понятны.

Помните: Conventional Commits — это не догма, а инструмент. Адаптируйте его под свои нужды, добавляйте свои типы, если это помогает вашей команде. Главное — делать историю кода полезной!
