# Статья 11. Запуск Ansible в Docker: тестирование, изоляция и CI/CD

Docker — это не только платформа для контейнеризации приложений, но и мощный инструмент для разработки и тестирования Ansible-плейбуков. Запуск Ansible внутри Docker-контейнера решает целый ряд практических задач: от проверки совместимости плейбуков с разными версиями Ansible до создания изолированных тестовых сред для отработки конфигураций. В этой статье мы подробно разберём, как использовать Docker для работы с Ansible, какие образы доступны и как это помогает в повседневной практике DevOps-инженера.

---

## 11.1 Зачем запускать Ansible в Docker?

Основные причины использовать Docker для запуска Ansible:

| Причина | Описание |
|---------|----------|
| **Изоляция версий** | На одной машине можно запускать разные версии Ansible без конфликтов зависимостей. |
| **Тестирование миграций** | Проверка устаревших плейбуков на новых версиях Ansible перед обновлением инфраструктуры. |
| **Воспроизводимость** | Одинаковое окружение для всех членов команды и CI/CD-пайплайнов. |
| **Безопасность** | Ограниченный контейнер не оставляет следов в основной системе. |
| **Интеграция с CI/CD** | Лёгкий запуск Ansible-задач в GitLab CI, Jenkins и других системах. |

## 11.2 Доступные Docker-образы для Ansible

### Официальные и популярные образы

| Образ | Описание | Особенности |
|-------|----------|-------------|
| `williamyeh/ansible` | Универсальные образы с разными версиями Ansible | Поддерживает теги `ubuntu12.04`, `ubuntu16.04`, `ubuntu18.04`, `centos7` и др. |
| `alpine/ansible` | Минималистичный образ на Alpine Linux | Только последняя версия Ansible (latest) |
| `quay.io/ansible/creator-ee` | Официальный образ от Red Hat для CI/CD | Включает Ansible, Molecule, линтеры; используется в GitLab CI |

**Примеры версий в образах williamyeh:**

```bash
# Версия 2.3.2.0 (Ubuntu 12.04)
williamyeh/ansible:ubuntu12.04

# Версия 2.7.2 (Ubuntu 16.04)
williamyeh/ansible:ubuntu16.04

# Версия 2.9.x (CentOS 7)
williamyeh/ansible:centos7
```

> **Важно:** Образ `alpine/ansible:latest` всегда содержит самую свежую версию Ansible и не подходит для тестирования старых релизов.

## 11.3 Тестирование плейбуков на разных версиях Ansible

При обновлении Ansible в инфраструктуре часто возникает проблема: старые плейбуки используют устаревший синтаксис (например, `sudo` вместо `become`, `with_items` вместо `loop`). Docker позволяет быстро проверить, как плейбук поведёт себя на новой версии, не затрагивая рабочую среду.

### Пример: проверка deprecated-параметров

Рассмотрим плейбук `deprecated.yaml`, содержащий устаревшие конструкции:

```yaml
---
- name: "Test deprecated syntax"
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: "Install package with sudo (deprecated)"
      sudo: true
      apt:
        name: htop
        state: present

    - name: "Loop with with_items (deprecated)"
      debug:
        msg: "{{ item }}"
      with_items:
        - one
        - two
```

**Запуск на версии 2.3.2.0 (будет работать с предупреждениями):**

```bash
docker run --rm -it -v $(pwd):/playbook williamyeh/ansible:ubuntu12.04 ansible-playbook /playbook/deprecated.yaml
```
*Вывод:* плейбук выполнится, но появятся предупреждения `DEPRECATION WARNING` о том, что `sudo` и `with_items` устарели.

**Запуск на версии 2.7.2 (вызовет ошибку):**

```bash
docker run --rm -it -v $(pwd):/playbook williamyeh/ansible:ubuntu16.04 ansible-playbook /playbook/deprecated.yaml
```
*Результат:* выполнение прервётся с ошибкой, потому что `sudo` больше не поддерживается. Это показывает, что перед обновлением нужно переписать плейбук.

**Запуск на последней версии (2.18.1):**

```bash
docker run --rm -it -v $(pwd):/playbook alpine/ansible:latest ansible-playbook /playbook/deprecated.yaml
```
Ошибка будет аналогичной. Таким образом, Docker помогает выявить проблемные места до того, как они сломают продакшн.

### Автоматизация миграции

Можно написать скрипт, который последовательно запускает плейбук на нескольких версиях и собирает отчёт о совместимости. Это особенно полезно в CI/CD, где каждый PR с изменением плейбука прогоняется через матрицу версий Ansible.

## 11.4 Запуск Ansible в Docker для управления удалёнными хостами

Docker-контейнер с Ansible может выступать в роли **control node** — управляющей машины, которая подключается к целевым хостам по SSH. Для этого нужно передать в контейнер SSH-ключи и файл инвентаря.

### Пример: запуск плейбука на удалённых серверах

```bash
# Запуск контейнера с пробросом SSH-ключа и инвентаря
docker run --rm -it \
  -v ~/.ssh:/root/.ssh \
  -v $(pwd)/inventory:/inventory \
  -v $(pwd)/playbook.yml:/playbook.yml \
  williamyeh/ansible:ubuntu20.04 \
  ansible-playbook -i /inventory /playbook.yml
```

**Объяснение:**
- `-v ~/.ssh:/root/.ssh` — монтирует SSH-ключи, чтобы Ansible мог подключаться к хостам.
- `-v $(pwd)/inventory:/inventory` — передаёт инвентарь.
- Команда запускает плейбук внутри контейнера.

Этот подход удобен, если вы не хотите устанавливать Ansible на свою локальную машину или если версия Ansible на хосте не подходит для конкретной задачи.

## 11.5 Использование Docker-контейнеров как тестовых хостов для Ansible

Docker-контейнеры могут выступать в роли **managed hosts** (управляемых узлов) для проверки плейбуков. Это быстрее и легче, чем поднимать полноценные виртуальные машины.

### Создание контейнера с SSH-сервером для тестирования

Ниже приведена команда, которая создаёт контейнер Ubuntu с настроенным SSH-сервером и пользователем `ansible` с правами sudo:

```bash
docker run -d --name ansible-test-ubuntu \
  -p 2222:22 \
  -e "SSH_PASSWORD=test123" \
  ubuntu:latest \
  /bin/bash -c "apt update && apt install -y openssh-server sudo && \
  useradd -m -s /bin/bash ansible && echo 'ansible:test123' | chpasswd && \
  echo 'ansible ALL=(ALL) NOPASSWD: ALL' >> /etc/sudoers && \
  service ssh start && tail -f /dev/null"
```

После запуска вы можете подключаться к контейнеру по SSH на порт 2222:

```bash
ssh -p 2222 ansible@localhost
```

### Инвентарь для тестового контейнера

Добавьте хост в инвентарь Ansible:

```ini
# test_hosts.ini
[test]
test_container ansible_host=localhost ansible_port=2222 ansible_user=ansible ansible_password=test123
```

Затем вы можете запускать плейбуки на этом контейнере так же, как на реальном сервере:

```bash
ansible-playbook -i test_hosts.ini test-playbook.yml
```

После завершения теста контейнер легко уничтожить:

```bash
docker stop ansible-test-ubuntu
docker rm ansible-test-ubuntu
```

### Преимущества такого подхода

- **Скорость:** контейнер запускается за секунды.
- **Чистота:** каждый тест начинается с чистого образа.
- **Экономия ресурсов:** контейнеры потребляют меньше памяти и CPU, чем ВМ.

## 11.6 Ansible в CI/CD: использование образа `quay.io/ansible/creator-ee`

Современные пайплайны CI/CD всё чаще используют готовые образы с предустановленными инструментами. Официальный образ `quay.io/ansible/creator-ee` включает:

- Ansible Core
- Molecule для тестирования
- Linters (ansible-lint, yamllint)
- Python-библиотеки для работы с облачными провайдерами

**Пример GitLab CI-задачи:**

```yaml
test-molecule:
  image: quay.io/ansible/creator-ee:v24.2.0
  stage: test
  script:
    - ansible-galaxy collection install community.mysql
    - cd roles/myapp
    - molecule test
  only:
    - merge_requests
```

Этот подход гарантирует, что все проверки выполняются в предсказуемом окружении, независимо от агента CI.

## 11.7 Лучшие практики работы с Ansible в Docker

1. **Используйте `--rm` флаг** для автоматического удаления контейнера после завершения.
2. **Монтируйте только необходимые файлы** (плейбуки, инвентарь, ключи), чтобы не загромождать контейнер.
3. **Для чувствительных данных используйте Docker secrets или переменные окружения**, а не передавайте их через командную строку.
4. **Версионируйте образы** — фиксируйте тег, чтобы избежать неожиданных изменений.
5. **Для тестовых контейнеров используйте `--privileged` только если нужен доступ к systemd** (например, для тестирования сервисов).
6. **Проверяйте версию Ansible перед запуском** с помощью `docker run --rm williamyeh/ansible:ubuntu16.04 ansible --version`.

## 11.8 Заключение

Docker расширяет возможности Ansible, делая его более гибким и безопасным инструментом. С помощью контейнеров вы можете:

- **Тестировать плейбуки** на разных версиях Ansible без установки дополнительных пакетов.
- **Изолировать окружение** для разработки и CI/CD.
- **Использовать контейнеры как временные хосты** для проверки конфигураций.

Сочетание Ansible и Docker — это мощный тандем, который позволяет автоматизировать не только управление инфраструктурой, но и сам процесс разработки и тестирования плейбуков. Внедрение этих практик сокращает время на отладку, повышает качество кода и делает вашу инфраструктуру более устойчивой к изменениям.

## Шаг 14. Настроить изоляцию среды через Docker Compose

### 14.1. Создать `docker-compose.yml`

```yaml
version: "3.8"

services:
  ansible:
    image: ansible-test:latest
    container_name: ansible_test
    volumes:
      - ./ansible:/workspace
    working_dir: /workspace
    command: >
      sh -c "
      ansible-playbook -i /workspace/inventory/hosts.ini /workspace/playbooks/site.yml &&
      echo '✅ Playbook executed successfully'
      "
    tty: true
    stdin_open: true

  # Опциональный тестовый хост
  testhost:
    image: alpine:latest
    container_name: testhost
    command: ["sh", "-c", "apk add --no-cache openssh-client && sleep infinity"]
    networks:
      - testnet
    cap_add:
      # - net_admin
      []

networks:
  testnet:
    driver: bridge
```

### 14.2. Запустить изоляцию

```bash
docker-compose up --build
```

### 14.3. После завершения работы контейнера `ansible_test` посмотреть логи

```bash
docker logs ansible_test
```

## Шаг 15. Автоматизировать тестирование в CI/CD

### 15.1. Пример GitHub Actions (`.github/workflows/ansible-ci.yml`)

```yaml
name: Ansible CI

on:
  push:
    branches: [ main ]
  pull_request:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build image for lint
        run: docker build -t ansible-test:lint .

      - name: Run ansible-lint
        run: |
          docker run --rm \
            -v ${{ github.workspace }}/ansible:/workspace \
            -w /workspace \
            ansible-test:lint ansible-lint roles/**/*.yml

  test:
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - uses: actions/checkout@v4

      - name: Build image for test
        run: docker build -t ansible-test:ci .

      - name: Run playbook with docker-compose
        run: |
          docker-compose -f docker-compose.yml up --abort-on-container-exit
```

### 15.2. Пример GitLab CI (`.gitlab-ci.yml`)

```yaml
stages:
  - build
  - test

build_image:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker build -t ansible-test:gitlab .

test_playbook:
  stage: test
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker-compose up --abort-on-container-exit
  only:
    - main
```

### 15.3. Сохранение логов при падении (GitHub Actions)

```yaml
- name: Save logs on failure
  if: failure()
  run: |
    mkdir -p artifacts
    docker logs ansible_test > artifacts/docker.log

- name: Upload logs
  uses: actions/upload-artifact@v4
  with:
    name: ansible-logs
    path: artifacts/
```
