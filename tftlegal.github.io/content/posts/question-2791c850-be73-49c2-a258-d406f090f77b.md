Designing a Fault-Tolerant Vault Cluster

1. Choose Your HA Topology

The first decision shapes everything else: where does the source of truth live?

Raft (built-in): 3 or 5 Vault nodes, no external dependency. Best for self-contained, on-prem, or single-DC deployments.
External storage (Postgres, etcd, Consul): quorum depends on the backend, introduces an external dependency. Best when you already run that infrastructure or need multi-DC without Vault-native replication.
Cloud-native (S3 + DynamoDB): managed, AWS-specific, elastic.

For most teams, Raft with 5 nodes is the sweet spot: no external dependency, tolerates 2 simultaneous failures, and keeps the cluster self-contained. With 3 nodes you survive 1 failure; with 5 you survive 2; with 7 you survive 3 (rarely needed, adds latency).

2. Node Topology and Sizing

Place a Layer-4 load balancer (HAProxy, ALB, nginx, Envoy) in front of all Vault nodes. Behind it, run 5 Vault nodes communicating over Raft on port 8201 and serving the API on port 8200. Spread nodes across at least 2 availability zones (3 for stronger guarantees). Each node should be on different hardware and in a different failure domain.

Node roles:
- Active node (leader): handles all writes, serves reads.
- Performance standby (optional): read-only replicas that offload read traffic. Add 1 or 2 if read QPS is high.
- Follower: participates in Raft consensus, can become leader on failover.

Hardware per node (minimum): 2 vCPU, 4 GB RAM (8 GB if caching many secrets), NVMe SSD with 100 GB or more for the Raft log and WAL, and network latency under 1 ms to other nodes on a dedicated VLAN or VPC. Disk I/O is the critical path; a spinning disk will bottleneck Raft commit latency.

3. Network and TLS

Ports:
- 8200: API (HTTP/HTTPS), exposed via the load balancer only.
- 8201: Raft replication, internal only.
- 8202: Performance standby replication, internal only.

TLS strategy (non-negotiable):
- Mutual TLS between all Raft peers. Each node presents a certificate signed by an internal CA that is separate from the public API CA.
- API TLS: terminate at the load balancer or at the node. If at the node, use a wildcard or SAN certificate covering all node hostnames.
- Certificate rotation: use Vault's own PKI or short-lived certificates (for example, 24 hours) with automatic renewal. A lapsed Raft certificate means a partitioned cluster.
- Enforce TLS 1.2 minimum.

Network isolation:
- Raft traffic (port 8201) must be on a dedicated, low-latency network segment (same rack or DC, ideally under 0.5 ms).
- Do not route Raft traffic over the public internet or a high-latency WAN without a DR design.
- Restrict port 8200 to the load balancer and port 8201 to Raft peers only via security groups or network policies.

4. Unseal and Key Management

A sealed cluster is a dead cluster. Design for automatic unseal so a node restart does not require human intervention.

Option A: Auto-unseal with KMS (recommended for cloud). Configure the auto_seal block with your cloud KMS key. The KMS key becomes the single point of failure, so protect it with IAM policies, multi-region KMS, and a backup key. If KMS is unavailable, the cluster stays sealed. Mitigate with a secondary unseal method such as Shamir as a fallback.

Option B: Shamir (on-prem, no cloud dependency). Use 5 shares with a threshold of 3. Distribute shares across physically separate locations (different racks, buildings, or HSMs). Automate unseal with a script that collects 3 shares and calls the unseal endpoint. Risk: if all 3 share-holders are unavailable simultaneously, the cluster is sealed.

Option C: HSM (highest security). Use a hardware HSM (YubiHSM, AWS CloudHSM, Thales) as the auto-unseal backend. Eliminates the "who holds the shares" problem.

Regardless of method, store unseal keys, root tokens, and CA certificates in a separate, independently protected system (HSM, offline backup, separate KMS). Never co-locate them with the cluster.

5. Storage and Data Durability

Raft storage layout on each node: a raft directory containing the append-only log (compacted periodically), periodic state snapshots, and metadata; a WAL directory; and a core directory for secret engine data.

Durability settings:
- Use fsync on every commit.
- Place the data volume on a dedicated NVMe volume, not shared with the OS.
- Use ext4 with data=ordered or XFS. Disable atime, enable noatime.

Backup strategy:
Raft snapshots are not a backup. You need:
- Periodic snapshots copied to off-cluster storage (S3, NFS, object store). Keep them under 5 GB for fast RTO.
- Configuration backup: store vault.hcl in version control.
- Test restore quarterly in a staging environment. A backup you have not restored is not a backup.
- Keep backups immutable and off-cluster to protect against ransomware or accidental deletion.

RPO and RTO targets:
- RPO under 1 second: Raft replication (leader commits to majority).
- RTO under 30 seconds: automatic leader election plus load balancer health checks.
- RPO under 5 minutes for DR: periodic snapshots plus async replication.

6. Load Balancing and Client Access

Clients connect to a DNS name (vault.example.com) that resolves to the load balancer. The load balancer routes TCP traffic on port 8200 to all healthy Vault nodes.

Load balancer configuration:
- Health check: GET /v1/sys/health?standbyok=true&sealedcode=200. Returns 200 if the node is healthy (active or standby), 503 if sealed or in maintenance.
- Connection draining: 30 seconds, so in-flight requests complete during failover.
- No sticky sessions: any node can serve any request because Raft ensures consistency.
- Timeouts: 30 seconds read, 10 seconds connect.
- Use 3 consecutive failures with a 5-second interval to avoid false failovers during brief GC pauses.

Client-side resilience:
- Configure clients with retry and exponential backoff (Vault SDKs do this by default).
- Use multiple DNS A records or a service mesh for load balancer redundancy.
- Set VAULT_ADDR to the load balancer, not a single node.
- Route writes to the active node and reads to any node.

7. Multi-Datacenter and Disaster Recovery

If you need to survive a full datacenter loss, a single Raft cluster in one DC is insufficient because Raft requires a majority in the same network partition.

Strategy: Active-Active Replication.
Run a primary cluster in DC-A (3 nodes) and a secondary cluster in DC-B (2 nodes). Enable performance replication (or DR replication) from the primary to the secondary. The secondary site holds a full copy and can take over if the primary site is lost.

Key considerations:
- Latency: Raft replication over WAN adds 50 to 200 ms per commit. Acceptable for most workloads, not for high-frequency trading.
- Failover: When DC-A is lost, promote DC-B's secondary cluster to primary using the replicate promote command.
- Split-brain: If the network partitions, the DC with the majority of Raft nodes retains leadership. The other DC becomes read-only or unavailable. Design the quorum so the primary DC holds the majority (3 in DC-A, 2 in DC-B).
- DNS failover: use a short TTL (30 seconds) or a service mesh (Consul, Istio) for fast failover.

Alternative: Active-Passive (simpler).
DC-B runs a standby cluster that receives snapshots periodically. On DC-A failure, unseal DC-B and restore the latest snapshot. RPO equals the snapshot interval (for example, 5 minutes). RTO equals unseal plus restore time.

8. Failure Modes and Mitigations

1 node down: no impact, quorum intact. Load balancer health check removes the node.
2 nodes down (5-node cluster): no impact, quorum still 3 of 5.
3 nodes down (5-node cluster): cluster unavailable. Accept as worst case; monitor and alert.
Leader disk failure: leader steps down, new leader elected. Mitigate with NVMe plus RAID-1 or cloud EBS.
Network partition (minority side): minority side becomes read-only. Design quorum in the primary DC.
All nodes sealed: no secrets accessible. Mitigate with auto-unseal and KMS redundancy.
Certificate expiry: Raft communication breaks. Mitigate with auto-rotation and monitoring alerts.
Configuration drift: inconsistent behavior. Mitigate with config in GitOps and periodic vault status checks.
Software bug or bad upgrade: corrupted state. Mitigate with rolling upgrades and a snapshot before each upgrade.
Ransomware or deletion: data loss. Mitigate with off-cluster immutable backups.

Brain-split prevention: Raft handles this natively. Only the partition with a majority can elect a leader. Ensure the load balancer does not route writes to a minority partition. Use standbyok=false in health checks if you want to route only to the active node.

9. Operational Runbook

Upgrades (rolling):
1. Take a snapshot.
2. Upgrade one node at a time, starting with a follower. Stop Vault, replace the binary, start Vault, verify with vault status and vault operator raft list-peers.
3. Last, upgrade the leader. It will step down and a new leader will be elected.
Vault supports rolling upgrades without data loss because Raft handles version skew. Never upgrade all nodes simultaneously.

Monitoring:
Expose metrics via Prometheus on port 8202 or through the telemetry block. Critical alerts:
- vault_core_unsealed equals 0 (cluster is sealed).
- vault_core_seal_time greater than 0 (was recently sealed).
- vault_raft_leader changes unexpectedly.
- vault_raft_follower_count less than 2 (quorum at risk).
- vault_raft_log_size greater than 100 MB (compaction issue).
- vault_request_duration_seconds p99 greater than 500 ms.
- TLS certificate expiry less than 7 days.
- Disk usage on the data volume greater than 80 percent.
- vault_raft_snapshot_size growing unbounded.

Log management:
- Raft logs grow until compacted. Monitor log size via vault operator raft list-peers.
- Set log_level to info in production, not debug.
- Ship logs to a central aggregator (ELK, Loki, CloudWatch).

Capacity and failure drills:
- Load-test to confirm the cluster handles peak traffic with N-1 nodes down.
- Run chaos experiments quarterly: kill the leader, kill 2 followers, partition the network. Verify failover behavior matches expectations and RTO stays under 30 seconds.

10. Security Hardening

- Least-privilege policies: each service gets a scoped policy, not root.
- Token TTLs: set default_lease_ttl and max_lease_ttl conservatively.
- Audit logging: enable a file or syslog audit device on all nodes.
- Disable unauthenticated endpoints: /v1/sys/health is public by design; everything else requires a token.
- Network policies: restrict 8200 to the load balancer, 8201 to Raft peers only.
- Secret engine isolation: use separate mounts per team or service.
- PII in secrets: Vault protects data at rest, but logs and audit trails may leak. Scrub audit logs.

11. Example Production Configuration (5-Node Raft, AWS)

The vault.hcl file should include:
- ui = true
- A tcp listener on 0.0.0.0:8200 with TLS certificate and key paths, tls_min_version set to tls12, and a telemetry block enabling Prometheus with 30-minute retention.
- A raft storage block with node_id set from an environment variable, path set to /var/lib/vault/data, five retry_join entries pointing to each node's internal address on port 8201 with the corresponding leader_api on port 8200, and an auto_seal block referencing the AWS KMS key name and region.
- api_addr set to the public HTTPS endpoint (https://vault.example.com:8200).
- cluster_addr set to the node's internal address on port 8201.
- log_level set to info, log_format set to json.
- An audit file device writing to /var/log/vault_audit.log.

12. Common Pitfalls

1. Single AZ or single rack: 5 nodes in one rack means one fire kills the cluster. Spread across at least 3 AZs.
2. Forgetting the Raft port in security groups: port 8201 must be open between all nodes.
3. No auto-unseal: manual unseal with Shamir means a human must be available at 3 AM.
4. Load balancer health check too aggressive: a brief GC pause triggers a false failover. Use 3 consecutive failures with a 5-second interval.
5. Not testing failover: run a chaos test (kill the leader, kill 2 followers) quarterly.
6. Ignoring snapshot size: a 50 GB snapshot takes minutes to restore. Keep it under 5 GB for fast RTO.
7. Certificate management: if the Raft CA certificate expires, the cluster partitions. Automate rotation.
8. Mixing Raft with external storage: do not. Pick one. Raft is self-contained; adding Postgres behind it defeats the purpose.

13. Summary Checklist

- 5 Vault nodes across at least 3 AZs (or 3 nodes across 3 AZs for minimum viable HA).
- Raft storage on NVMe, dedicated volume.
- Mutual TLS between all Raft peers with auto-rotating certificates.
- Layer-4 load balancer with health checks, no sticky sessions, 30-second connection draining.
- Auto-unseal via KMS or HSM with a fallback method.
- Periodic snapshots to immutable off-cluster storage, tested quarterly.
- Prometheus metrics and alerting on seal state, quorum, disk usage, certificate expiry, and replication lag.
- Audit logging enabled on all nodes.
- Rolling upgrade procedure documented and tested.
- Chaos test: kill leader plus 1 follower, verify under 30-second failover.
- DR plan: multi-DC replication or snapshot-restore, tested quarterly.
- Runbook covering unseal, failover, restore, upgrade, and certificate rotation.

Minimum viable HA setup: 3 Vault nodes in Raft mode across 2 AZs, auto-unseal via KMS, mutual TLS, a load balancer with health checks, and a DR replica in a second region. That gives you survival of a single node or AZ failure with automated recovery. The full 5-node, 3-AZ, multi-DC design above gives you survival of 2 simultaneous node failures or a full AZ loss with automated recovery and a tested DR path.
