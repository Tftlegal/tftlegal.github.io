# Designing Hybrid SQL/NoSQL Systems with Event-Driven Architecture

Designing a robust system that combines SQL, NoSQL, and Event-Driven Architecture (EDA) requires balancing **data consistency**, **latency**, **scalability**, and **security**. This guide provides a step-by-step approach to modeling such systems, focusing on best practices, anti-patterns, and security compliance.

## 1. Core Architectural Decisions

Before writing SQL or choosing a NoSQL store, define the following constraints:

### A. Data Consistency Model (CAP Theorem)
*   **Strong Consistency (ACID)**: Use SQL (PostgreSQL, MySQL) for financial transactions, inventory counts, or any data where incorrect state is unacceptable.
*   **Eventual Consistency (BASE)**: Use NoSQL (Cassandra, DynamoDB) or CQRS read models for high-throughput feeds, analytics, or catalog data where slight delays are acceptable.

### B. Access Patterns (Read vs. Write)
*   **Write-Heavy**: Prefer NoSQL (Cassandra/RocksDB) or partitioned SQL. Avoid complex joins. Use append-only logs (Event Sourcing).
*   **Read-Heavy**: Prefer SQL with aggressive caching (Redis/Memcached) or NoSQL with denormalized structures. Use covering indexes.
*   **Mixed**: Use **CQRS (Command Query Responsibility Segregation)**. Write to a command store (SQL/Event Log), project to read-optimized views (SQL/NoSQL/Elasticsearch).

### C. Data Types & Structure
*   **Structured**: Relational tables (SQL).
*   **Semi-Structured**: Documents (MongoDB/DynamoDB) or JSONB columns in SQL.
*   **Unstructured**: Object Storage (S3/GCS) with metadata in SQL/NoSQL.

## 2. Database Design & Indexing Strategies

### SQL Design (Relational)
1.  **Normalization vs. Denormalization**:
    *   Normalize (3NF) for write-heavy, integrity-critical data.
    *   Denormalize for read-heavy, report-oriented data.
2.  **Indexing Best Practices**:
    *   **Primary Key**: Always use a surrogate key (UUIDv7 or Snowflake ID) for performance and partitioning, not natural keys (like email).
    *   **Composite Indexes**: Order columns by selectivity (highest to lowest). Use **Covering Indexes** to avoid table lookups for frequent queries.
    *   **Avoid Redundant Indexes**: Each index increases write cost. Use `EXPLAIN ANALYZE` to validate usage.
    *   **Partial Indexes**: Use `WHERE` clauses in index definitions to index only relevant subsets (e.g., `CREATE INDEX ... WHERE status = 'active'`).
3.  **Partitioning**:
    *   Use **Range Partitioning** (by date) for time-series data to enable efficient archiving.
    *   Use **Hash Partitioning** for distributing load across shards.

### NoSQL Design (Non-Relational)
1.  **Key Design is King**:
    *   **Partition Key**: Determines data distribution. Must be high-cardinality to avoid hot spots.
    *   **Sort/Clustering Key**: Determines order within a partition.
    *   *Anti-Pattern*: Low-cardinality partition keys (e.g., `user_id` if one user has 1M records) cause hot spots.
2.  **Data Modeling**:
    *   **Denormalize by Design**: No joins. Store related data together if accessed together.
    *   **Embed vs. Link**: Embed small, frequently accessed collections (e.g., tags on a post). Link large, infrequently accessed ones (e.g., user profile).
3.  **TTL (Time-To-Live)**: Use built-in TTL for ephemeral data (sessions, logs) to automate cleanup.

## 3. Event-Driven Architecture (EDA) Integration

### A. Event Sourcing vs. Event Notification
*   **Event Sourcing**: The event log *is* the source of truth. Replay events to rebuild state. Best for audit trails and complex business logic.
*   **Event Notification**: Events signal changes to other services. The database remains the source of truth. Simpler, but requires careful consistency handling.

### B. The Outbox Pattern (Solving Dual Writes)
*   **Problem**: Writing to DB and publishing to Kafka in separate transactions leads to inconsistency if one fails.
*   **Solution**: Use the **Transactional Outbox Pattern**.
    1.  Write data to the primary table.
    2.  Write an "event" record to an `outbox` table in the **same SQL transaction**.
    3.  A separate poller service reads the `outbox` table and publishes to Kafka.
    4.  Mark the outbox record as sent.

### C. Event Schema & Versioning
*   Use **Avro** or **Protobuf** for binary compatibility and size efficiency.
*   Maintain a **Schema Registry** (e.g., Confluent Schema Registry) to enforce backward/forward compatibility.
*   **Rule**: Never change a field type. Add new optional fields; deprecate old ones slowly.

### D. Delivery Semantics & Idempotency
*   **At Least Once**: Kafka default. Consumers **must** be idempotent.
*   **Idempotency Key**: Include a unique ID (e.g., `order_id`) in the event. The consumer checks if this ID has already been processed before applying changes.
*   **Dead Letter Queue (DLQ)**: Route failed messages to a DLQ for manual inspection or retry logic. Do not block the main pipeline.

## 4. Security & Compliance (OWASP & Best Practices)

### A. Data Security
1.  **Encryption**:
    *   **In Transit**: Enforce TLS 1.2+ for all DB connections and Kafka topics.
    *   **At Rest**: Enable AES-256 encryption for all storage volumes.
    *   **Field-Level**: Encrypt sensitive PII (SSN, Credit Cards) in the application layer before storing, or use DB-native encryption (e.g., Oracle TDE, AWS RDS Encryption).
2.  **Access Control**:
    *   **Least Privilege**: DB users should have minimal permissions (e.g., `SELECT` only for read services).
    *   **Multi-Tenancy**: Use **Row-Level Security (RLS)** in SQL or distinct collections/partitions in NoSQL to isolate tenant data.
    *   **Kafka ACLs**: Restrict which services can produce/consume from specific topics.

### B. Injection Prevention
*   **SQL**: Always use **Parameterized Queries** or a safe ORM. Never concatenate user input into SQL strings.
*   **NoSQL**: Be aware of **NoSQL Injection**. Ensure user input is validated and types are enforced.
*   **Events**: Validate event payloads against the schema registry. Reject malformed events.

### C. Audit & Compliance
*   **Immutable Audit Log**: Store all changes to sensitive data in an append-only log (can be part of the Event Log).
*   **Data Retention**: Implement automated policies to delete or anonymize data after the retention period (GDPR/CCPA).
*   **PII Minimization**: Do not store PII in events unless necessary. If stored, mask it in logs.

## 5. Anti-Patterns to Avoid

| Anti-Pattern | Description | Consequence |
| :--- | :--- | :--- |
| **Dual Write** | Writing to DB and Kafka in separate operations. | Data inconsistency on partial failure. |
| **N+1 Queries** | Fetching a parent, then looping to fetch children individually. | Database overload, high latency. *Fix: Use JOINs or batch fetching.* |
| **Hot Spots** | All writes hitting one partition/node. | Single point of failure, throughput bottleneck. *Fix: Salt partition keys.* |
| **God Topic** | One Kafka topic containing events for all services. | Coupled consumers, difficult scaling, massive message size. *Fix: Split by domain.* |
| **Unbounded Replay** | Replaying years of events without pruning. | High storage cost, slow consumer recovery. *Fix: Use snapshots for state restoration.* |
| **Select \*** | Retrieving all columns when only a few are needed. | Network overhead, cache misses. *Fix: Select specific columns.* |
| **Sync RPC over Kafka** | Using Kafka as a request-response queue (waiting for reply). | High latency, complex error handling. *Fix: Use REST/gRPC for sync, Kafka for async.* |

## 6. Decision Framework (Answering the Key Questions)

When designing the system, answer these questions to finalize the architecture:

### 1. Scale & Growth
*   **Question**: What is the QPS (Queries Per Second) and data volume (GB/TB) now and in 3 years?
*   **Action**:
    *   < 10k QPS, < 1TB: **PostgreSQL** is likely sufficient.
    *   > 100k QPS, > 10TB: **Sharded SQL** or **NoSQL (Cassandra/DynamoDB)**.
    *   High Growth: Design for **horizontal scaling** (stateless services, sharded DBs).

### 2. Read vs. Write Dominance
*   **Question**: Is the system 90% reads or 90% writes?
*   **Action**:
    *   **Read-Heavy**: Optimize **indexes**, use **Caching** (Redis), consider **Read Replicas**.
    *   **Write-Heavy**: Optimize **partitioning**, use **Append-Only** structures, minimize **index count**, consider **Event Sourcing**.

### 3. Data Criticality (Durability)
*   **Question**: What data is "never lost"?
*   **Action**:
    *   **Critical (Money/Legal)**: Use **SQL with ACID transactions**. Ensure **WAL (Write-Ahead Logging)** is replicated to a different AZ/Region.
    *   **Non-Critical (Analytics/Logs)**: Use **NoSQL** or **Data Lake**. Accept potential data loss during outages if cost is a priority.

### 4. Latency Requirements
*   **Question**: What is the acceptable P99 latency?
*   **Action**:
    *   **< 10ms**: Local **In-Memory** cache (Redis) or **Co-located** storage.
    *   **< 100ms**: Optimized **SQL** (SSD, proper indexing) or **NoSQL**.
    *   **> 1s**: **Batch processing**, **Async** workflows, **Eventual Consistency**.

### 5. Total Cost of Ownership (TCO)
*   **Question**: What is the budget for infrastructure and engineering?
*   **Action**:
    *   **Low Budget/Simple**: Managed **PostgreSQL** + **Kafka** (Confluent Cloud or MSK).
    *   **High Scale/Low Ops**: Managed **DynamoDB/Cassandra** + **Kafka**.
    *   **Complex/Custom**: Self-hosted **Cassandra** + **Kafka** + **Custom Sharding Logic**. *Warning: High engineering cost.*
    *   *Note*: The cost of **operational complexity** (on-call engineers, debugging distributed systems) often exceeds the cloud bill.
