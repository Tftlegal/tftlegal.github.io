# Проектирование БД: Базовая структура с Event-Driven Architecture, индексами и антипаттернами

**Шаг 1: Зафиксировать 5 ограничений**

Масштаб/рост, R/W ratio, RPO (что не потерять), P99 latency, 3-годовая стоимость эксплуатации (TCO).

### Рассмотрим примеры:

*   100 пользователей с ростом 10x в год: простая база данных на одном сервере.
*   Миллионы пользователей с ростом 10x в год: распределенный кластер, шардирование и горизонтальное масштабирование.
*   Banковские транзакции с высоким RPO и RTO: ACID, репликация с quorum, WAL (write-ahead log).
*   Аналитика или логи с низким RPO:low latency.
*   Вопрос о TCO включает стоимость инфраструктуры, лицензий и операционной сложности.

### Понимание ограничений:

*   Масштаб/rost: может потребоваться горизонтальное масштабирование.
*   R/W ratio: соотношение чтения и записи, влияет на балансность систем.
*   RPO: вероятность того, что данные будут потеряны.
*   P99 latency: 99-ю-percentильная задержка для 99% от занимаемого трафика.
*   3-годовая TCO: общая стоимость эксплуатации за 3 года.

**Шаг 2: Выбрать хранилище по паттерну доступа**

*   Default: PostgreSQL с JSONB для гибких полей.
*   NoSQL/LSM-tree (Cassandra, RocksDB): только если write-throughput > 50k ops/s и eventual consistency допустим.
*   Гибрид: Postgres для транзакций, Redis/LSM для hot reads или append-only logs.

### Понимание выбора хранилища:

*   PostgreSQL: robust, scalable, и flexible, но может быть сложным в настройке.
*   NoSQL/LSM-tree: high write-throughput, but may not be suitable for all use cases.
*   Гибрид: комбинация преимуществ двух хранилищ, может быть optimalna для некоторых приложений.

**Шаг 3: Спроектировать схему и индексы**

### SQL:

*   Composite indexes по частым WHERE-сортировкам.
*   Covering indexes для read-heavy queries.
*   BRIN для time-series.

### NoSQL:

*   Partition key = high-cardinality (user_id, not status).
*   Clustering key = secondary sort.
*   Avoid: low-cardinality partition → hot spots; unbounded JSONB without GIN.

### Понимание индексов:

*   Composite indexes: improve query performance for common WHERE-clauses.
*   Covering indexes: improve query performance for read-heavy queries.
*   BRIN: optimize time-series data storage.

**Шаг 4: Построить event-driven слой (Outbox Pattern)**

### Transactional Outbox in Postgres → CDC (Debezium) → Kafka.

*   Guarantees: no dual-write, at-least-once delivery.
*   Consumers: idempotent (dedup by event_id), handle out-of-order, dead-letter queue for poison pills.

### Понимание Outbox Pattern:

*   Transactional Outbox: ensures atomicity and consistency of writes.
*   CDC (Debezium): captures changes to the database and sends them to Kafka.
*   Kafka: provides high-throughput and fault-tolerant messaging.

**Шаг 5: Разделить read/write (CQRS) + кэширование**

### Write path → Postgres (ACID).
### Read path → materialized view / Redis cache / denormalized read-model.
### Invalidate cache on Outbox event, not on direct write.
### Keep ACID on write; eventual consistency on read is fine.

### Понимание CQRS:

*   Write path: uses ACID compliance for write-heavy queries.
*   Read path: uses materialized view, Redis cache, and denormalized read-model for read-heavy queries.
*   Invalidate cache on Outbox event, not on direct write, ensures data consistency.

**Шаг 6: Пройти чек-лист антипаттерна**

*   Dual write без atomicity (fixed by Outbox).
*   N+1 / chatty ORM queries.
*   Index bloat (unused, redundant, low-selectivity).
*   Partition key = low cardinality.
*   Message broker as synchronous call.
*   Schema drift without migration (evolution rules: additive-only, no breaking in-place).
*   "We'll optimize later" on hot path.

### Понимание антипаттерна:

*   Dual write: avoids dual-write issues by using Outbox.
*   N+1 / chatty ORM queries: avoids chatty ORM queries by using caching.
*   Index bloat: avoids index bloat by using composite indexes and covering indexes.
*   Partition key = low cardinality: avoids hot spots by using high-cardinality partition key.
*   Message broker as synchronous call: avoids synchronous call by using asynchronous messaging.
*   Schema drift without migration: avoids schema drift by using evolution rules and migrations.

**Шаг 7: Security и операционные guardrails**

*   Prepared statements (no string concat).
*   Row-Level Security for multi-tenant.
*   TLS everywhere.
*   Schema evolution via migrations (Flyway/Liquibase).
*   Observability: slow-query log, consumer lag metrics, idempotency-key hit-rate.

### Понимание security и guardrails:

*   Prepared statements: improves security by avoiding string concatenation.
*   Row-Level Security: improves security by providing row-level access control for multi-tenants.
*   TLS: improves security by encrypting data in transit.
*   Schema evolution via migrations: improves security by ensuring schema drift is handled through migrations.
*   Observability: improves security by providing visibility into system performance and errors.
