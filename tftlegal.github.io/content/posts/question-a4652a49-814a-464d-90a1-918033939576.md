Выглядит как элементарная задача, но часть подводных камней заставила скопировать подсказки дабы избежать повторного попадаения них. 
ИИ написал что на хост Kali проще всего собрать llama.cpp из исходников. 
Для RTX 3090 есть три практичных варианта: CPU, Vulkan или CUDA. 
Надо сказать, что установка последней версии драйвера 615 к успеху не привела - получил проблемы с nvidia-smi. После отката на более стабильный 550 драйвер nvidia-smi заработала но стал недоступен  CUDA toolkit, по этому ИИ предложил  начать именно  с **Vulkan** — он даст GPU-ускорение без `nvcc` и CUDA toolkit. [docs.liquid](https://docs.liquid.ai/deployment/on-device/llama-cpp)

## Быстрый CPU-вариант

```bash
sudo apt update
sudo apt install -y build-essential cmake git ccache libcurl4-openssl-dev

git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j"$(nproc)"

./build/bin/llama-cli --version
```

Это официальный базовый способ сборки: `cmake -B build`, затем `cmake --build build --config Release`. [docs.liquid](https://docs.liquid.ai/deployment/on-device/llama-cpp)

## Vulkan для RTX 3090

```bash
sudo apt install -y build-essential cmake git ccache \
  libcurl4-openssl-dev \
  libvulkan-dev glslc mesa-vulkan-drivers vulkan-tools

cd llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_VULKAN=ON

cmake --build build --config Release -j"$(nproc)"
```

Проверь Vulkan:

```bash
vulkaninfo --summary | grep -A5 -i nvidia
```

Запуск:

```bash
./build/bin/llama-cli \
  -m /path/to/model.Q4_K_M.gguf \
  -ngl 99 \
  -c 8192 \
  -p "Привет! Расскажи коротко о себе."
```

`-ngl 99` выгружает почти все слои модели на GPU. Для RTX 3090 с 24 ГБ VRAM comfortably пойдут 7B–14B Q4/Q5 модели; для 30B+ нужно следить за VRAM.

## CUDA-вариант: позже, после починки NVIDIA

CUDA-сборка требует установленный CUDA toolkit и `nvcc`:

```bash
sudo apt install -y build-essential cmake git ccache libcurl4-openssl-dev nvidia-cuda-toolkit

cd llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=86

cmake --build build --config Release -j"$(nproc)"
```

`86` — архитектура CUDA для RTX 3090 (Ampere). Официальная документация llama.cpp использует `-DGGML_CUDA=ON`; также можно явно задать архитектуры, например `86;89`. [github](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)

Но у тебя сейчас `nvidia-cuda-toolkit` недоступен в Kali и NVIDIA-стек смешан с локальным 615. Поэтому CUDA-сборку лучше делать после того, как приведёшь драйвер к согласованному состоянию.


CMake `FindBLAS` ищет BLAS-реализацию; при `GGML_BLAS_VENDOR=OpenBLAS` требуется установленный OpenBLAS. [cmake](https://cmake.org/cmake/help/v3.19/module/FindBLAS.html)

# CUDA

В этой части для сборки пришлось разыскать две старые библиотеки libxml2.so.2 и libicuuc.so.72, установить GCC 12,  а также переопределить 
```
export PATH=/usr/local/cuda-12.4/bin:$PATH
export LD_LIBRARY_PATH=/usr/local/cuda-12.4/lib64:$LD_LIBRARY_PATH
```
И наконец сделать кастомную установку CUDA Toolkit с override

`--override` отключает проверку версии компилятора при установке; далее мы не дадим `nvcc` использовать GCC 16.

Не делай симлинк `libxml2.so.16 -> libxml2.so.2`: это разные ABI. Твой Kali поставил libxml2 2.15 с новым soname `.so.16`, а старый CUDA-installer слинкован против `.so.2`; нужна именно старая библиотека 2.9.x, но лучше не менять системную. [discussions.unity](https://discussions.unity.com/t/linux-editor-6000-6-0f1-fails-to-launch-exit-127-missing-libxml2-so-2-on-ubuntu-26-04/1736325)

## Положи старую libxml2 рядом, не трогая систему

```bash
sudo mkdir -p /opt/cuda-compat
cd /opt/cuda-compat

wget http://deb.debian.org/debian/pool/main/libx/libxml2/libxml2_2.9.14+dfsg-1.3~deb12u6_amd64.deb

dpkg-deb -x libxml2_2.9.14+dfsg-1.3~deb12u6_amd64.deb ./root

find ./root -name 'libxml2.so*'
```

Должен найтись:
```
./root/usr/lib/x86_64-linux-gnu/libxml2.so.2.9.14
```

Debian 12 bookworm содержит `libxml2 2.9.14`, чей файл — `libxml2.so.2.9.14`, то есть именно soname `libxml2.so.2`, который ожидает CUDA-installer. [packages.debian](https://packages.debian.org/bookworm/libxml2)

## Запусти установщик с этой библиотекой

```bash
sudo env \
  LD_LIBRARY_PATH=/opt/cuda-compat/root/usr/lib/x86_64-linux-gnu \
  CC=/usr/bin/gcc-12 \
  CXX=/usr/bin/g++-12 \
  sh /root/cuda_12.4.1_550.54.15_linux.run \

  --toolkit \
```

Если путь к библиотеке отличается, подставь его из вывода `find` выше.

## Почему так

Современный libxml2 перешёл на soname `libxml2.so.16` и больше не предоставляет `libxml2.so.2`; для старых бинарников стандартное решение — извлечь `.deb` со старой 2.9.x в отдельный каталог и подключить через `LD_LIBRARY_PATH`, не устанавливая её глобально. [discussions.unity](https://discussions.unity.com/t/linux-editor-6000-6-0f1-fails-to-launch-exit-127-missing-libxml2-so-2-on-ubuntu-26-04/1736325)

CUDA 12.4.1 runfile официально поддерживает silent-установку только toolkit через `--toolkit`, что и нужно, чтобы не трогать текущий драйвер 550.163.01.

Теперь не хватает `libicuuc.so.72` — тоже зависимости старой libxml2 2.9. Поставь Debian bookworm `libicu72` в тот же изолированный каталог.

```bash
cd /opt/cuda-compat

wget http://deb.debian.org/debian/pool/main/i/icu/libicu72_72.1-3+deb12u1_amd64.deb
dpkg-deb -x libicu72_72.1-3+deb12u1_amd64.deb ./root

find "$PWD/root/usr/lib/x86_64-linux-gnu" -maxdepth 1 -name 'libicu*' -printf '%f\n'
```

Должны появиться, как минимум:

```text
libicuuc.so.72
libicuuc.so.72.1
libicui18n.so.72
libicui18n.so.72.1
libicudata.so.72
libicudata.so.72.1
```

CUDA 12.4 не поддерживает GCC 16 как host-компилятор. `--override` позволит **установить toolkit**, но для сборки llama.cpp всё равно нужен совместимый `gcc/g++` — оптимально GCC 12. CUDA 12.4 официально ориентирован на GCC до 13.x, а GCC 16 слишком новый. [ia600708.us.archive](https://ia600708.us.archive.org/1/items/nvidiacuda/CUDA_12.4_Toolkit_Release_Notes.pdf)

## Собираем llama.cpp с GCC 12

Здесь важно указать `nvcc`, CUDA toolkit и host-компилятор:

```bash
cd /root/llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_C_COMPILER=/usr/bin/gcc-12 \
  -DCMAKE_CXX_COMPILER=/usr/bin/g++-12 \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.4/bin/nvcc \
  -DCMAKE_CUDA_HOST_COMPILER=/usr/bin/g++-12 \
  -DCUDAToolkit_ROOT=/usr/local/cuda-12.4 \
  -DCMAKE_CUDA_ARCHITECTURES=86

cmake --build build --config Release -j"$(nproc)"
```

`CMAKE_CUDA_HOST_COMPILER` транслируется в `nvcc -ccbin`, то есть именно заставляет `nvcc` компилировать host-код через `g++-12`, а не системный GCC 16. [cmake](https://cmake.org/cmake/help/v3.25/variable/CMAKE_CUDA_HOST_COMPILER.html)

## Примени патч

```bash
sudo patch /usr/local/cuda-12.8/targets/x86_64-linux/include/crt/math_functions.h <<'EOF'
--- a/crt/math_functions.h
+++ b/crt/math_functions.h
@@
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 cospi(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  cospif(float x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 sinpi(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  sinpif(float x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 rsqrt(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  rsqrtf(float x);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 cospi(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  cospif(float x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 sinpi(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  sinpif(float x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 rsqrt(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  rsqrtf(float x) noexcept (true);
EOF
```

Суть — добавить `noexcept (true)` к шести объявлениям: `cospi`, `cospif`, `sinpi`, `sinpif`, `rsqrt`, `rsqrtf`. Именно такой фикс рекомендован в llama.cpp и подтверждён в отчётах о проблеме. [raw.githubusercontent](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/build.md)

# MTP 

## HauhauCS FastMTP: как ускорить Qwen3.8-27B в 3 раза без потери качества ответов

**Вышла нецензурированная агрессивная версия Qwen3.8-27B с проприетарным механизмом спекулятивного декодирования FastMTP, который даёт до 3,02-кратного прироста скорости генерации документов и 1,93-кратного — для рассуждений по сравнению с обычным режимом без MTP.**

Релиз от HauhauCS представляет собой дообученную версию Qwen3.8-27B с профилем «Aggressive»: модель отвечает прямо, без характерного для многих алайнментов «предисловия» и попыток уйти от ответа на сложные запросы. Заявленный показатель — 0 отказов из 465 тестовых промптов . Важно понимать: это не новая базовая модель, а адаптация существующей Qwen3.8-27B с сохранением всех исходных возможностей — текста, изображений, видео и агентных сценариев.

Каждый текстовый GGUF-файл сохраняет нативную голову NextN (MTP), встроенную в архитектуру Qwen3.8. Поверх неё HauhauCS добавили FastMTP — компактный сайдкар-драфтер на 32K токенов и патч для рантайма llama.cpp .

## Почему FastMTP работает иначе, чем встроенный MTP?

Стандартный встроенный MTP уже даёт ускорение: по бенчмаркам HauhauCS, 2,23x для документов и 1,60x для рассуждений относительно полностью отключённого MTP. 
FastMTP идёт дальше: +35,2% к скорости генерации документов и +21,1% к скорости рассуждений по сравнению со стандартным встроенным MTP.
Ключевой момент — механика верификации. Драфтер FastMTP предлагает токены, но неизменённая полная целевая модель проверяет каждый из них. Это означает, что FastMTP не подменяет модель и не меняет её ответы — он только ускоряет генерацию . Именно поэтому прирост скорости не сопровождается деградацией качества: вы получаете те же ответы, что и без ускорения, но быстрее.

## Цифры бенчмарка

| Сравнение | Документы (TG) | Рассуждения (TG) |
|---|---|---|
| FastMTP против MTP отключён | **3,02x** (+202%) | **1,93x** (+93,3%) |
| FastMTP против стандартного встроенного MTP | +35,2% | +21,1% |
| Стандартный встроенный MTP против отключённого | 2,23x | 1,60x |

Замеры проводились на одной RTX PRO 6000 Blackwell 96 GB при контексте 204 800 токенов, полной выгрузке в CUDA и без mmap .

## Что нужно для запуска

FastMTP требует сборки llama.cpp с патчем от HauhauCS. Без патча при загрузке драфтера вы увидите ошибку несоответствия размеров (`expected 5120, 248320, got 5120, 32768`) — это признак того, что сайдкар корректен, но исполняемый файл не пропатчен .

Помимо FastMTP, релиз включает кастомные кванты K_P («Perfect»), которые сохраняют качество на уровне на один-два кванта выше при размере всего на 5–15% больше базового. Файлы остаются стандартными GGUF и работают в llama.cpp, LM Studio и других совместимых рантаймах без специальной сборки .

Для работы с изображениями и видео требуется отдельный BF16-проектор — он совместим с любым текстовым квантом .

## Кому это нужно

FastMTP имеет смысл в первую очередь тем, кто запускает Qwen3.8-27B локально и упирается в скорость генерации при длинных документах или сложных цепочках рассуждений. Прирост в 3 раза на документах — это разница между «подождать пару минут» и «подождать минуту» на объёмных задачах. Для коротких диалоговых сценариев выигрыш будет менее заметен, но в агентных пайплайнах с множеством последовательных вызовов накопленный эффект существенен.

Стоит также учитывать, что «агрессивный» профиль нецензурирования — это осознанный выбор. Для задач, где критична предсказуемость и следование строгим политикам, safer-вариантом остаётся стандартная Qwen3.8-27B или сбалансированные релизы, если они появятся .

## Как подобрать размер KV-кэша и тип квантизации? 

KV-кэш (кэш ключей и значений) модели Qwen3.8-27B — это область видеопамяти (VRAM), в которой сохраняются вычисленные векторы ключей и значений для уже обработанных токенов, чтобы не пересчитывать их заново при генерации каждого следующего токена.)

Зачем он нужен и как работает

• Ускорение генерации: при создании ответа модель опирается на весь предыдущий текст. Кэш хранит промежуточные состояния слоёв внимания и ускоряет вывод новых токенов
• Рост с длиной контекста: в отличие от весов модели, которые занимают фиксированный объём памяти, KV-кэш увеличивается по мере роста диалога или документа.
• Ограничение по VRAM: на длинных контекстах (например, в сотни тысяч токенов) кэш может требовать десятки гигабайт видеопамяти и становиться главным ограничением для локального запуска.

Особенности и способы экономии для Qwen3.8-27B

• Квантизация кэша: для снижения потребления памяти кэш переводят из формата F16 в более сжатые форматы вроде Q8 или Q4. Это экономит VRAM, но на больших контекстах может ухудшать точность или приводить к ошибкам генерации.
• Альтернативные режимы (например, CMF): в экспериментальных конфигурациях (см. разбор на Хабре) растущий KV-кэш в слоях полного внимания заменяется на состояние фиксированного размера. 
• Контекстный кэш (в бытовой речи при обсуждении локального запуска LLM).

Примеры использования

• Длинные диалоги и анализ документов: удержание в памяти больших объёмов текста или кода без повторного прогона всего промпта на каждом шаге.
• Локальный запуск на видеокартах с ограниченной VRAM: подбор формата кэша (F16, Q8, Q4) или сжатия под конкретный объём памяти GPU и целевую длину контекста.

### Q8_0 Мнимое качество


Для **q8_0 KV** расчёт такой: у Qwen3.8-27B KV-кэш создают только 16 full-attention слоёв; в q8_0 это примерно **34 KiB на токен** с учётом блочных scale-значений. Qwen3.8 имеет нативный контекст 262 144, поэтому потолок архитектуры — 256k, но на одной 3090 он достижим только на самых лёгких квантах. [huggingface](https://huggingface.co/TelperionAI/Qwen3.8-27B-GLA-g2)

## Бюджет VRAM

Для 3090 считаем доступными **22.5 GiB** из 24 GiB: reserve на драйвер, compute buffer, MTP/служебные буферы — около 2.5 GiB. Плюс фиксированное linear state Gated DeltaNet — около 0.15 GiB. 

Формула:

```text
макс. токенов ≈ (22.5 - вес модели - 0.15 - 2.5) GiB / 34 KiB
```

q8_0 KV требует включённого flash attention: `-fa 1`. [github](https://github.com/gravitee-io/gravitee-singularitee/blob/main/docs/reference/models/llama_cpp.md)


## Максимум контекста

| Модель | Размер | Теоретический максимум | Безопасный `-c` | Вердикт |
|---|---:|---:|---:|---|
| `IQ3_XS` | 11.34 GiB | **~262k** | **208–256k** | 256k возможно, впритык |
| `IQ3_M` | 11.91 GiB | **~245k** | **208k** | 256k рискованно |
| `IQ4_XS` | 14.62 GiB | **~161k** | **144–160k** | 128k комфортно, 160k на пределе |
| `Q4_K_P` | 16.69 GiB | **~98k** | **80–96k** | 96k максимум, лучше 80k |
| `Q5_K_P` | 18.83 GiB | **~31k** | **24–32k** | Длинный контекст практически недоступен |

То есть с q8_0 KV:

- **256k реально только на IQ3_XS**, и то без mmproj и внешнего draft.
- **208k — разумный максимум для IQ3_M.**
- **IQ4_XS — примерно 160k**, не 256k.
- **Q4_K_P — примерно 96k.**
- **Q5_K_P — примерно 32k.**

## Если используете FastMTP

Ваш внешний `FastMTP-32K.gguf` занимает 0.84 GiB. Он уменьшает бюджет примерно на **26k токенов**:

| Модель | С внешним FastMTP | Рекомендуемый `-c` |
|---|---:|---:|
| `IQ3_XS` | ~236k теоретически | **208k** |
| `IQ3_M` | ~219k теоретически | **192–208k** |
| `IQ4_XS` | ~135k теоретически | **128k** |
| `Q4_K_P` | ~72k теоретически | **64k** |
| `Q5_K_P` | ~5k теоретически | **не использовать с 256k/длинным контекстом** |

Если добавите ещё BF16 `mmproj` на 0.87 GiB, вычтите ещё около **27k токенов**. Для агентного кодинга без изображений mmproj лучше не загружать вообще.

```
let actx=null;
function ensureCtx(){
  if(state.muted)return null;
  if(!actx){try{actx=new (window.AudioContext||window.webkitAudioContext)();}catch(e){return null;}}
  if(actx.state==='suspended')actx.resume();
  return actx;
}
function ding(){
  const ctx=ensureCtx();if(!ctx)return;
  const t0=ctx.currentTime;
  [[0,1],[0.13,0.65]].forEach(([dt,amp])=>{
    [[1567.98,0.16],[2093,0.10],[3135.96,0.035]].forEach(([f,g])=>{
      const o=ctx.createOscillator(),ga=ctx.createGain();
      o.type='sine';o.frequency.value=f*(1+(Math.random()-.5)*0.004);
      ga.gain.setValueAtTime(0.0001,t0+dt);
      ga.gain.exponentialRampToValueAtTime(g*amp,t0+dt+0.008);
      ga.gain.exponentialRampToValueAtTime(0.0001,t0+dt+0.55);
      o.connect(ga).connect(ctx.destination);o.start(t0+dt);o.stop(t0+dt+0.6);
    });
  });
}
function tick(){
  const ctx=ensureCtx();if(!ctx)return;
  const t0=ctx.currentTime,o=ctx.createOscillator(),g=ctx.createGain();
  o.type='triangle';o.frequency.setValueAtTime(880,t0);o.frequency.exponentialRampToValueAtTime(440,t0+0.06);
  g.gain.setValueAtTime(0.05,t0);g.gain.exponentialRampToValueAtTime(0.0001,t0+0.07);
  o.connect(g).connect(ctx.destination);o.start(t0);o.stop(t0+0.08);
}
```
