Выглядит как элементарная задача, но часть подводных камней заставила скопировать подсказки дабы избежать повторного попадаения них. 
ИИ написал что на хост Kali проще всего собрать llama.cpp из исходников. 
Для RTX 3090 есть три практичных варианта: CPU, Vulkan или CUDA. 
Надо сказать, что установка последней версии драйвера 615 к успеху не привела - получил проблемы с nvidia-smi. После отката на более стабильный 550 драйвер nvidia-smi заработала но стал недоступен  CUDA toolkit, по этому ИИ предложил  начать именно  с **Vulkan** — он даст GPU-ускорение без `nvcc` и CUDA toolkit. [docs.liquid](https://docs.liquid.ai/deployment/on-device/llama-cpp)

## Быстрый CPU-вариант

```bash
sudo apt update
sudo apt install -y build-essential cmake git ccache libcurl4-openssl-dev

git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release -j"$(nproc)"

./build/bin/llama-cli --version
```

Это официальный базовый способ сборки: `cmake -B build`, затем `cmake --build build --config Release`. [docs.liquid](https://docs.liquid.ai/deployment/on-device/llama-cpp)

## Vulkan для RTX 3090

```bash
sudo apt install -y build-essential cmake git ccache \
  libcurl4-openssl-dev \
  libvulkan-dev glslc mesa-vulkan-drivers vulkan-tools

cd llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_VULKAN=ON

cmake --build build --config Release -j"$(nproc)"
```

Проверь Vulkan:

```bash
vulkaninfo --summary | grep -A5 -i nvidia
```

Запуск:

```bash
./build/bin/llama-cli \
  -m /path/to/model.Q4_K_M.gguf \
  -ngl 99 \
  -c 8192 \
  -p "Привет! Расскажи коротко о себе."
```

`-ngl 99` выгружает почти все слои модели на GPU. Для RTX 3090 с 24 ГБ VRAM comfortably пойдут 7B–14B Q4/Q5 модели; для 30B+ нужно следить за VRAM.

## CUDA-вариант: позже, после починки NVIDIA

CUDA-сборка требует установленный CUDA toolkit и `nvcc`:

```bash
sudo apt install -y build-essential cmake git ccache libcurl4-openssl-dev nvidia-cuda-toolkit

cd llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=86

cmake --build build --config Release -j"$(nproc)"
```

`86` — архитектура CUDA для RTX 3090 (Ampere). Официальная документация llama.cpp использует `-DGGML_CUDA=ON`; также можно явно задать архитектуры, например `86;89`. [github](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md)

Но у тебя сейчас `nvidia-cuda-toolkit` недоступен в Kali и NVIDIA-стек смешан с локальным 615. Поэтому CUDA-сборку лучше делать после того, как приведёшь драйвер к согласованному состоянию.

Vulkan-вариант — обойдёт отсутствие CUDA toolkit и, вероятно, заработает сразу после того, как заработает корректно `nvidia-smi`.

Ошибка потому, что не установлен dev-пакет OpenBLAS. Для твоей цели он вообще не нужен: `GGML_BLAS` ускоряет только CPU, а GPU будет через Vulkan. Официальная документация llama.cpp для OpenBLAS на Debian/Ubuntu требует `libopenblas-dev`. [ggml-org-llama-cpp.mintlify](https://ggml-org-llama-cpp.mintlify.app/concepts/backends)

## Лучший вариант: только Vulkan


Не указывай `GGML_BLAS`: он не заменяет Vulkan и для GPU-инференса не нужен.

## Если всё же нужен OpenBLAS

```bash
sudo apt install -y libopenblas-dev
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_BLAS=ON \
  -DGGML_BLAS_VENDOR=OpenBLAS \
  -DGGML_VULKAN=ON

cmake --build build --config Release -j"$(nproc)"
```

CMake `FindBLAS` ищет BLAS-реализацию; при `GGML_BLAS_VENDOR=OpenBLAS` требуется установленный OpenBLAS. [cmake](https://cmake.org/cmake/help/v3.19/module/FindBLAS.html)

# CUDA

В этой части для сборки пришлось разыскать две старые библиотеки libxml2.so.2 и libicuuc.so.72, установить GCC 12,  а также переопределить 
```
export PATH=/usr/local/cuda-12.4/bin:$PATH
export LD_LIBRARY_PATH=/usr/local/cuda-12.4/lib64:$LD_LIBRARY_PATH
```
И наконец сделать кастомную установку CUDA Toolkit с override

`--override` отключает проверку версии компилятора при установке; далее мы не дадим `nvcc` использовать GCC 16.

Не делай симлинк `libxml2.so.16 -> libxml2.so.2`: это разные ABI. Твой Kali поставил libxml2 2.15 с новым soname `.so.16`, а старый CUDA-installer слинкован против `.so.2`; нужна именно старая библиотека 2.9.x, но лучше не менять системную. [discussions.unity](https://discussions.unity.com/t/linux-editor-6000-6-0f1-fails-to-launch-exit-127-missing-libxml2-so-2-on-ubuntu-26-04/1736325)

## Положи старую libxml2 рядом, не трогая систему

```bash
sudo mkdir -p /opt/cuda-compat
cd /opt/cuda-compat

wget http://deb.debian.org/debian/pool/main/libx/libxml2/libxml2_2.9.14+dfsg-1.3~deb12u6_amd64.deb

dpkg-deb -x libxml2_2.9.14+dfsg-1.3~deb12u6_amd64.deb ./root

find ./root -name 'libxml2.so*'
```

Должен найтись:
```
./root/usr/lib/x86_64-linux-gnu/libxml2.so.2.9.14
```

Debian 12 bookworm содержит `libxml2 2.9.14`, чей файл — `libxml2.so.2.9.14`, то есть именно soname `libxml2.so.2`, который ожидает CUDA-installer. [packages.debian](https://packages.debian.org/bookworm/libxml2)

## Запусти установщик с этой библиотекой

```bash
sudo env \
  LD_LIBRARY_PATH=/opt/cuda-compat/root/usr/lib/x86_64-linux-gnu \
  CC=/usr/bin/gcc-12 \
  CXX=/usr/bin/g++-12 \
  sh /root/cuda_12.4.1_550.54.15_linux.run \
  --silent \
  --toolkit \
  --no-opengl-libs \
  --no-drm \
  --no-man-page \
  --tmpdir /root/cuda-tmp \
  --override
```

Если путь к библиотеке отличается, подставь его из вывода `find` выше.

## Почему так

Современный libxml2 перешёл на soname `libxml2.so.16` и больше не предоставляет `libxml2.so.2`; для старых бинарников стандартное решение — извлечь `.deb` со старой 2.9.x в отдельный каталог и подключить через `LD_LIBRARY_PATH`, не устанавливая её глобально. [discussions.unity](https://discussions.unity.com/t/linux-editor-6000-6-0f1-fails-to-launch-exit-127-missing-libxml2-so-2-on-ubuntu-26-04/1736325)

CUDA 12.4.1 runfile официально поддерживает silent-установку только toolkit через `--toolkit`, что и нужно, чтобы не трогать текущий драйвер 550.163.01.

Теперь не хватает `libicuuc.so.72` — тоже зависимости старой libxml2 2.9. Поставь Debian bookworm `libicu72` в тот же изолированный каталог.

```bash
cd /opt/cuda-compat

wget http://deb.debian.org/debian/pool/main/i/icu/libicu72_72.1-3+deb12u1_amd64.deb
dpkg-deb -x libicu72_72.1-3+deb12u1_amd64.deb ./root

find "$PWD/root/usr/lib/x86_64-linux-gnu" -maxdepth 1 -name 'libicu*' -printf '%f\n'
```

Должны появиться, как минимум:

```text
libicuuc.so.72
libicuuc.so.72.1
libicui18n.so.72
libicui18n.so.72.1
libicudata.so.72
libicudata.so.72.1
```

CUDA 12.4 не поддерживает GCC 16 как host-компилятор. `--override` позволит **установить toolkit**, но для сборки llama.cpp всё равно нужен совместимый `gcc/g++` — оптимально GCC 12. CUDA 12.4 официально ориентирован на GCC до 13.x, а GCC 16 слишком новый. [ia600708.us.archive](https://ia600708.us.archive.org/1/items/nvidiacuda/CUDA_12.4_Toolkit_Release_Notes.pdf)

## Собери llama.cpp на GCC 12

Здесь важно указать `nvcc`, CUDA toolkit и host-компилятор:

```bash
cd /root/llama.cpp
rm -rf build

cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_CUDA=ON \
  -DCMAKE_C_COMPILER=/usr/bin/gcc-12 \
  -DCMAKE_CXX_COMPILER=/usr/bin/g++-12 \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.4/bin/nvcc \
  -DCMAKE_CUDA_HOST_COMPILER=/usr/bin/g++-12 \
  -DCUDAToolkit_ROOT=/usr/local/cuda-12.4 \
  -DCMAKE_CUDA_ARCHITECTURES=86

cmake --build build --config Release -j"$(nproc)"
```

`CMAKE_CUDA_HOST_COMPILER` транслируется в `nvcc -ccbin`, то есть именно заставляет `nvcc` компилировать host-код через `g++-12`, а не системный GCC 16. [cmake](https://cmake.org/cmake/help/v3.25/variable/CMAKE_CUDA_HOST_COMPILER.html)

## Примени патч

```bash
sudo patch /usr/local/cuda-12.8/targets/x86_64-linux/include/crt/math_functions.h <<'EOF'
--- a/crt/math_functions.h
+++ b/crt/math_functions.h
@@
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 cospi(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  cospif(float x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 sinpi(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  sinpif(float x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 rsqrt(double x);
-extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  rsqrtf(float x);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 cospi(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  cospif(float x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 sinpi(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  sinpif(float x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ double                 rsqrt(double x) noexcept (true);
+extern __DEVICE_FUNCTIONS_DECL__ __device_builtin__ float                  rsqrtf(float x) noexcept (true);
EOF
```

Суть — добавить `noexcept (true)` к шести объявлениям: `cospi`, `cospif`, `sinpi`, `sinpif`, `rsqrt`, `rsqrtf`. Именно такой фикс рекомендован в llama.cpp и подтверждён в отчётах о проблеме. [raw.githubusercontent](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/docs/build.md)
