# Inteface

## 🧩 Что такое Интерфейсы(Простыми словами)?

Интерфейсы в Go (Golang) — это одна из ключевых концепций языка, и она заметно отличается от того, как интерфейсы устроены в Java или C#.
Суть: контракт поведения, а не данные
В Go интерфейс — это набор методов, которые должен реализовать тип. Интерфейс описывает поведение, а не структуру данных. 
Это как договор: «если ты умеешь делать вот эти действия, ты подходишь».

Пример объявления:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
```
Любой тип, у которого есть метод Read с такой сигнатурой, автоматически считается реализующим интерфейс Reader. Никаких ключевых слов вроде implements не нужно.

** Главная особенность: неявная реализация **

В отличие от многих других языков, в Go тип не обязан явно заявлять, что он реализует интерфейс. Достаточно иметь нужные методы с точными сигнатурами.


```go
type Speaker interface {
    Speak() string
}

type Human struct {
    Name string
}

// Human неявно реализует Speaker, потому что у него есть метод Speak
func (h Human) Speak() string {
    return "Привет, меня зовут " + h.Name
}

func main() {
    var s Speaker
    s = Human{Name: "Анна"} // можно присвоить, потому что Human реализует Speaker
    fmt.Println(s.Speak())
}
```
Компилятор сам проверяет: «есть ли у типа все методы из интерфейса?». Если да — всё ок.

Представьте, что вы хотите построить очень сложный механизм, где разные части должны взаимодействовать друг с другом. У вас есть:

1.  **Машинный блок (Бизнес-логика):** Это то, что знает, *что* делать.
2.  **Электрический блок (Подача данных/БД):** Это то, что знает, *как* получать данные.

**Интерфейс в Go — это контракт.** Это набор обещаний, который вы даете другой части кода.

Если вы объявляете `UserRepository` как интерфейс, вы по сути говорите: "Я обещаю, что эта сущность будет уметь делать `GetUser` и `CreateUser`".

**Важно:** Интерфейс — это **описание** поведения, а не **реализация** поведения.

### Почему это важно? (Преимущество)

Потому что если вы используете этот контракт (интерфейс), вы можете написать код, который **зависит только от этого контракта**, а не от конкретной реализации.

Это позволяет вам **разделить то, *что* вы делаете (бизнес-логика), от того, *как* это делается (реализация с БД)**.

## 🧪 Модульные тесты и Интерфейсы (Как это работает?)

Ваш вопрос очень проницательный: **Да, именно интерфейсы позволяют писать модульные тесты до написания финального кода!**

Поскольку ваш бизнес-сервис зависит от *контракта* (`interface`), а не от конкретной *реализации* (например, `PostgresRepo`), вы можете создать **заглушку (Mock)**, которая имитирует этот контракт, ещё до того, как вы напишете реализацию для PostgreSQL.

### Пошаговый процесс (Тестирование до реализации)

Предположим, у вас есть `UserService` (бизнес-сервис), который зависит от `UserRepository`.

#### 1. Определяем контракт (Интерфейс)
Вы объявляете, что `UserRepository` должен существовать (даже если вы ещё не написали, как он будет работать с Postgres).

#### 2. Создаем Заглушку (Mock)
Вы создаете класс, который реализует этот интерфейс, но **не использует базу данных**. Это и есть ваш `MockRepository`. В этом моке вы просто жестко прописываете ответ.

#### 3. Тестирование (Unit Test)
Вы передаете `MockRepository` в ваш `UserService` и вызываете его. Вы проверяете, работает ли логика *правильно*, даже если ваша БД пока не готова.

**Пример (в теории):**

```go
// Мы знаем, что UserService требует что-то, что реализует UserRepository.

// 1. Создаем Мок (имитацию)
mockRepo := &MockUserRepository{} 
// Мы заранее прописываем, что если UserService попросит пользователя ID=1, 
// Мок вернет User, а не вызовет БД.

// 2. Тестируем
service := NewUserService(mockRepo) // Передаем Мок в сервис

// Тест: Убедиться, что сервис правильно обработает ответ, 
// даже если мок вернул данные.
result := service.GetUser(1) 
// Тест успешно проходит, потому что мы "заставили" сервис работать, 
// не дожидаясь настроенной базы.
```

### 🎯 Почему это дает высокую изоляцию и покрытие?

1.  **Высокая Изоляция:** Вы **изолируете** бизнес-логику от технической реализации. Если вы меняете PostgreSQL на SQLite, код `UserService` остается тем же, потому что он зависит от **контракта**, а не от конкретной библиотеки.
2.  **Тестовое Покрытие (Test Coverage):** Вы получаете **100% покрытие для логики** вашего сервиса, потому что вы можете изолировать его от внешних зависимостей (БД, сеть, внешние API). Вы проверяете **бизнес-поведение**, а не **инфраструктурное поведение**.

**Вывод:** Интерфейсы в Go позволяют вам **тестировать логику, игнорируя инфраструктуру**. Вы тестируете *логику*, а не *соединение* с БД. Это золотой стандарт в современном программировании.
