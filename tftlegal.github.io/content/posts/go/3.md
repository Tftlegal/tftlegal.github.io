# CRUD

## Что такое CRUD?

**CRUD** — это аббревиатура, которая расшифровывается как **C**reate, **R**ead, **U**pdate, **D**elete.

По сути, это **набор базовых операций**, которые вы выполняете с данными в любой базе данных или системе, которая управляет данными.

*   **C (Create / Создание):** Добавление новой записи. (Пример: Добавить новый пользователь в базу.)
*   **R (Read / Чтение):** Получение данных. (Пример: Загрузить список всех пользователей.)
*   **U (Update / Обновление):** Изменение существующих данных. (Пример: Изменить email у существующего пользователя.)
*   **D (Delete / Удаление):** Удаление записи. (Пример: Удалить пользователя из системы.)

**В контексте Go (или любого другого бэкенда):** Вы используете эти операции, чтобы сделать так, чтобы ваше приложение могло **работать** с данными. Когда вы пишете сервис на Go, вы пишете логику, которая позволяет пользователю выполнять эти 4 базовые действия с данными, хранящимися, например, в PostgreSQL.

## Как микросервис на Go должен взаимодействовать с БД (PostgreSQL)

В архитектуре микросервиса взаимодействие с базой данных должно быть **структурированным, изолированным** и **управляемым**.

Ваш сервис на Go, вероятно, будет следовать архитектурному принципу **Repository Pattern** (или Data Mapper).

### 🧱 Структура взаимодействия

1.  **Слой Сервиса (Service Layer):** Это бизнес-логика. Здесь происходит вся магия, обрабатывается ввод данных (request) и вызывается хранилище.
2.  **Слой Хранилища/Репозитория (Repository Layer):** Этот слой *абстрагирует* детали базы данных. Он отвечает за все операции CRUD.
3.  **Контекст (Context):** Вы передаете всю необходимую информацию (например, токен, данные запроса) через контекст Go (`context.Context`).

### ⚙️ Пошаговый процесс (Пример с PostgreSQL)

1.  **Подключение (Connection):** Вы используете библиотеку для работы с PostgreSQL (например, `pgx` или `sqlc`). Вы создаете пул подключений (connection pool), чтобы не открывать и закрывать соединение для каждого запроса.
2.  **ORM/Query Builder:** Вы пишете код, который транслирует ваши бизнес-операции в SQL-запросы.
3.  **Транзакции:** Все операции (C, U, D) должны быть обернуты в **Транзакцию** (`BEGIN`/`COMMIT`). Это критически важно для целостности данных (ACID).
4.  **Пример CRUD:**
    *   **C (Create):** Вы вызываете метод репозитория: `repo.CreateUser(data)`. Этот метод выполняет `INSERT INTO users (...) VALUES (...)` и обрабатывает возможные ошибки.
    *   **R (Read):** Вы вызываете `repo.GetUserByID(id)`. Этот метод выполняет `SELECT * FROM users WHERE id = ?` и возвращает структурированные данные.
    *   **U (Update):** Вы вызываете `repo.UpdateUser(id, new_data)`. Этот метод выполняет `UPDATE users SET ... WHERE id = ?`.
    *   **D (Delete):** Вы вызываете `repo.DeleteUser(id)`. Этот метод выполняет `DELETE FROM users WHERE id = ?`.

## ✨ Лучшие практики (Best Practices)

1.  **Изоляция (Separation of Concerns):** Никогда не смешивайте логику бизнес-сервиса с SQL-запросами. Используйте четкие слои (Service $\leftrightarrow$ Repository).
2.  **Использование Транзакций (Transactions):** Всегда оборачивайте связанные операции (например, изменение данных и запись в лог) в одну транзакцию. Если что-то пошло не так, транзакция откатывается (`ROLLBACK`).
3.  **Обработка ошибок (Error Handling):** В Go ошибки обрабатываются явным возвратом `error`. Всегда проверяйте возвращаемые ошибки и передавайте их дальше, чтобы бизнес-логика не зависела от низкоуровневых деталей БД.
4.  **Использование ORM/SQLC:** Используйте современные инструменты (например, `sqlc` для генерации кода на основе схемы). Это минимизирует ошибки, связанные с синтаксисом SQL.
5.  **Контекст (Context Propagation):** Всегда передавайте `context.Context` через всю цепочку вызовов (Service $\rightarrow$ Repository) для отслеживания таймаутов, отметок времени и передачи токена.

## 🚫 Антипаттерны (Anti-Patterns)

Антипаттерн — это плохая, неоптимизированная или нелогичная практика.

1.  **Прямое встраивание SQL в бизнес-логику:** Если ваш код выглядит так: `conn.QueryRow("SELECT * FROM users WHERE id = $1", id)`, вы **встраиваете** логику SQL прямо в код. Если вам нужно будет менять таблицу или поля, вам придется искать это по всему коду. (См. Best Practice №1).
2.  **Полигональная (No Repository):** Попытка выполнять все операции (C, R, U, D) и управление подключением прямо в самом главном объекте. Это приводит к "смешиванию обязанностей".
3.  **Полингвистическая зависимость (Lack of Abstraction):** Если вы привязываете свой сервис жестко к PostgreSQL, а потом хотите переключиться на MySQL, вам придется переписывать почти всю бизнес-логику. **Хорошая практика** — использовать интерфейс репозитория, который вы затем реализуете для PostgreSQL.
4.  **Отсутствие Транзакций (The "Oops" Approach):** Выполнение операции, которая состоит из двух шагов (например, обновление пользователя и запись в историю), но если первый шаг успешен, а второй — нет, вы не откатываете транзакцию. Это приводит к **несогласованным данным**.
