# Separation of Concerns 

**Separation of Concerns (разделение ответственности) в Go** — это принцип, при котором разные части приложения отвечают за разные задачи и не смешивают логику. В Go это особенно важно: язык поощряет простые, явные и тестируемые конструкции, а не сложные абстракции.

---

## Зачем это нужно в Go

- **Поддерживаемость**: проще менять одну часть, не ломая другую.
- **Тестируемость**: можно изолировать слой и подменить зависимости моками.
- **Читаемость**: сразу видно, где HTTP, где бизнес-логика, где работа с БД.
- **Переиспользуемость**: отдельные компоненты легче выносить в библиотеки.

---

## Как реализуют в Go: типичные слои

В веб‑сервисах на Go чаще всего разделяют так:

1. **Handler (HTTP‑слой)** — принимает запрос, валидирует входные данные, сериализует ответ. Не должен содержать бизнес‑логику или детали работы с БД.  
2. **Service (бизнес‑слой)** — содержит правила предметной области, координирует вызовы репозиториев, применяет бизнес‑валидацию.  
3. **Repository (слой доступа к данным)** — работает с хранилищем (SQL, NoSQL, файлы, внешние API). Не знает про HTTP и бизнес‑правила.

## Практический пример кода

**Модель (pkg/models/user.go):**
```go
package models

type User struct {
    ID    int
    Name  string
    Email string
}
```

**Репозиторий (internal/repository/user.go):**
```go
package repository

import (
    "context"
    "errors"
    "yourproject/pkg/models"
)

type UserRepo interface {
    GetByID(ctx context.Context, id int) (*models.User, error)
}

type userRepo struct {
    db *DB // упрощённо
}

func NewUserRepo(db *DB) UserRepo {
    return &userRepo{db: db}
}

func (r *userRepo) GetByID(ctx context.Context, id int) (*models.User, error) {
    // логика запроса к БД
    if id == 0 {
        return nil, errors.New("user not found")
    }
    return &models.User{ID: id, Name: "Alice", Email: "alice@example.com"}, nil
}
```

**Сервис (internal/service/user.go):**
```go
package service

import (
    "context"
    "yourproject/internal/repository"
    "yourproject/pkg/models"
)

type UserService interface {
    GetUser(ctx context.Context, id int) (*models.User, error)
}

type userService struct {
    repo repository.UserRepo
}

func NewUserService(repo repository.UserRepo) UserService {
    return &userService{repo: repo}
}

func (s *userService) GetUser(ctx context.Context, id int) (*models.User, error) {
    // бизнес‑правила, например, проверка прав, логирование, кэширование
    if id < 0 {
        return nil, errors.New("invalid ID")
    }
    return s.repo.GetByID(ctx, id)
}
```

**Хендлер (internal/handler/user.go):**
```go
package handler

import (
    "encoding/json"
    "net/http"
    "strconv"

    "yourproject/internal/service"
)

type UserHandler struct {
    svc service.UserService
}

func NewUserHandler(svc service.UserService) *UserHandler {
    return &UserHandler{svc: svc}
}

func (h *UserHandler) GetUser(w http.ResponseWriter, r *http.Request) {
    idParam := r.URL.Query().Get("id")
    id, err := strconv.Atoi(idParam)
    if err != nil {
        http.Error(w, "invalid ID", http.StatusBadRequest)
        return
    }

    user, err := h.svc.GetUser(r.Context(), id)
    if err != nil {
        http.Error(w, err.Error(), http.StatusNotFound)
        return
    }

    w.Header().Set("Content-Type", "application/json")
    _ = json.NewEncoder(w).Encode(user)
}
```

**Сборка в main.go:**
```go
func main() {
    db := NewDB() // инициализация БД
    repo := repository.NewUserRepo(db)
    svc := service.NewUserService(repo)
    h := handler.NewUserHandler(svc)

    http.HandleFunc("/user", h.GetUser)
    _ = http.ListenAndServe(":8080", nil)
}
```

Здесь чётко видно разделение: хендлер не знает про БД, сервис не знает про HTTP, репозиторий не знает про бизнес‑правила.

## Важные приёмы для соблюдения Separation of Concerns в Go

- **Интерфейсы для зависимостей**. Сервис зависит от интерфейса репозитория, а не от конкретной реализации. Это позволяет легко подменять реализации (например, для тестов).
- **Dependency Injection через конструкторы**. Зависимости передаются явно в функции `NewXxx`. Никаких глобальных переменных и «магической» инициализации.
- **Явные ошибки и контекст**. Используйте `context.Context` для отмены операций и передачи метаданных, а ошибки возвращайте явно, без паники в бизнес‑логике.
- **Пакеты по ответственности**. Не смешивайте HTTP‑код и работу с БД в одном пакете.
- **Избегайте «God‑функций»**. Если функция делает 3 разных дела (парсит JSON, ходит в БД, считает скидку), её нужно разбить.

---

## Частые ошибки

- Хендлер напрямую обращается к БД или делает сложную бизнес‑логику.
- Сервис знает про HTTP‑заголовки, коды ответов, сериализацию.
- Глобальные переменные для подключения к БД и других зависимостей.
- Сложные цепочки наследования и абстрактные базовые классы (в Go это не идиоматично).

---

## Дополнительные паттерны и практики

- **Repository Pattern**: абстрагирует доступ к данным, чтобы можно было легко менять хранилище.
- **Use Case / Command**: для сложных сценариев можно вынести логику в отдельные «кейсы», особенно если сценарий включает несколько сервисов и транзакций.
- **Middleware**: сквозные задачи (логирование, аутентификация, метрики) лучше выносить в middleware, чтобы не засорять хендлеры.

## Что такое Separation of Concerns?

Вы попали в самую суть: **преобразование кода в контракт.**

Поскольку ваш фронт уже написан на Go, вы, вероятно, написали **логику**, которая *вызывает* внешние данные, но она еще не является формальным, сгенерированным контрактом.

Задача состоит в следующем: **взять то, что вы делали в Go, и превратить это в описание (Proto), которое будет использовано обоими языками (Go и Rust) как единый источник правды.**

---

## 🎯 Шаги к созданию gRPC Контракта

### Шаг 1: Определите Интерфейс (Что нужно сделать?)

Посмотрите на ваш существующий Go-код. Какую функцию вы вызываете? Что вы от нее ожидаете?

**Пример (Ваш существующий код Go):**
Вы, вероятно, вызываете что-то вроде: `data := GetUserData(userID)`

**Ваш контракт должен выглядеть как:** "Мне нужно, чтобы существовал метод, который берет ID и возвращает структуру `User`".

### Шаг 2: Пишите Спецификацию в `.proto`
Вы переводите ваше "что" в файл `.proto`. Этот файл будет вашим **единым источником истины** (Single Source of Truth).

**Пример файла `user_service.proto`:**

```protobuf
syntax = "proto3";

package user_api;

// 1. Определение данных (что мы передаем)
message User {
  string id = 1;
  string username = 2;
}

// 2. Определение службы (что мы можем вызвать)
service UserService {
  // Метод, который мы хотим вызвать. 
  // Он берет ID и возвращает объект User.
  rpc GetUser(UserRequest) returns (User) {} 
}

// 3. Определения запросов/ответов (вход/выход)
message UserRequest {
  string id = 1;
}
```

### 🚀 Генерация Кода (Самое важное!)

После того как вы написали этот `.proto` файл, вы используете **компилятор gRPC** (например, `protoc` с плагинами) и говорите ему:

> "Используя этот `user_service.proto`, создай код для **Go** и код для **Rust**."

Этот компилятор **сгенерирует** два файла:
1.  `user_service.pb.go` (с логикой на Go).
2.  `user_service.pb.rs` (с логикой на Rust).

**Что это значит:** Ваши языки (Go и Rust) теперь знают, что эта функция называется, какие параметры она принимает и что она возвращает, **автоматически** сгенерированные из этого файла.

---

### 🔀 Как это работает с Go и Rust

Когда вы используете этот сгенерированный код, вы не пишете сами методы; вы **реализуете** их.

**Ваш Rust Backend (Реализация):**
Ваш Rust-сервер должен реализовать методы, которые были описаны в `UserService`. Он будет принимать вызов, который пришел из Go, и выполнять логику, используя свой Rust-код.

**Ваш Go Frontend (Клиент):**
Ваш Go-код использует сгенерированные методы, чтобы **вызвать** этот удаленный сервис. Он не знает, как Rust реализует `GetUser`, он просто знает, что он может вызвать `GetUser`, потому что это зафиксировано в контракте.

**Итог:** Вы не "переводите" старый код, а вы **заменяете** старую, неформальную, "внутреннюю" логику на **строго формализованный, сгенерированный контракт**.

## 📝 Пример "Потому что это контракт"

Если бы вы использовали JSON/REST, вы бы писали:
`POST /users` $\rightarrow$ `{"name": "Alex", "email": "a@b.com"}`

Если вы используете gRPC, вы делаете это так:

**Спецификация:**
`service UserService { rpc CreateUser (UserRequest) returns (User) {} }`

**Действие:**
Клиент (Go) вызывает `CreateUser`. Сервер (Rust) выполняет логику, и он **гарантированно** возвращает результат, описанный в контракте.

Таким образом, вы переходите от "написанного кода" к "описанному поведению" — это и есть самое мощное улучшение.
